# 主题漫谈长跑实测（2026-10-05）

构建 `40e8cce0`（HTTP 层字节化 P0–P2 + 截断回复走断线重试）。用户实例（Debug，22:03 启动）上的真实群（下称「漫谈群」），
五名成员（成员 A 主持、成员 B–E）+ 化身，主题是整理某个虚构世界的世界观，产物进草稿目录。

要看的两件事：

1. HTTP 层字节化之后，长跑下的内存与分配是否与 10-05 基准一致；
2. 截断回复（流正常收尾，但只有思考、没有 finish_reason）会不会再出现，出现时重试是否接得住。

## 跑法

- 不退出用户实例，经开发控制通道（`UiharuMind.CLI app call`）每约 40 分钟 `group.dump` + `diag.memory` 看进度与内存。
- 外部每 5 秒采 RSS / CPU / 线程数；`dotnet-counters` 采 System.Runtime（csv）；`caffeinate -dis -w <pid>` 防息屏。
- 日志从 `~/.uiharu/Logs/Log.txt`（session `22:03` 起）里数截断、断线重试、429。

  - `Avalonia.Reactive.WeakObserverSubscription` 从 23:33 的 27,735 个涨到 01:38 的 **88,715** 个，每小时约 +3 万；而 `LocalizedString` 只有 209 个。
  - 最大的四张观察者表都在群产物面板：`GroupArtifactOpen` / `GroupArtifactReveal` / `GroupArtifactDraftBadge` / `GroupArtifactWorkspaceBadge`，**各 18,991 个订阅**，但活着的 `KindBadge` 只有 76 个。其次是 `Copy` 2,813、`ToolViewFullText` 2,070。
  - 成因有两层：
    1. `LocalizedString` 是静态缓存的 `IObservable` 源。Avalonia 用 `WeakObserverSubscription` 弱订阅，控件被回收而没退订时，这个小壳仍留在 `_observers` 里；只有源再推一次值（`OnNext` 发现目标已死）才会清掉，而我们只在切语言时推值，所以只增不减。
    2. `GroupArtifactsViewData.RefreshAfterDelayAsync` 每次刷新都 `Items.Clear()` 再整批 `Add`，触发源是任一成员的用量上报、运行状态变化和草稿目录的文件事件。群一忙就重建全部容器（31 份产物 × 约 600 次），每次每项泄漏 4 个订阅（其中两个在从不进可视树的 `ContextMenu` 里）。
  - 量级：目前每个泄漏约 70 字节（壳 + 弱引用 + 槽位），共约 6MB，不是活对象每 40 分钟 +45MB 的主因（那部分跟着会话历史与界面条目走）。但它只增不减，并且会把面板重建的成本放大。
  - 建议：
    1. `LocalizedString` 改为 `INotifyPropertyChanged`（`LocExtension` 返回 `Source=LocalizedString, Path=Value` 的绑定），走 Avalonia 的弱事件管理，它会自动压缩死订阅；
    2. 产物面板改为按路径比对增量更新，内容不变就不动 `Items`。
- **活对象**：强制回收后 362MB，主要是字符串 54MB（55.6 万个）、界面对象（13,179 个合成视觉、63,266 个 `StyleInstance`、60,020 个 `DynamicResourceExpression`，对应群里 304 条与驻留的会话），以及 TextMate 语法表约 20MB（一次性加载，不随视图增加）。
