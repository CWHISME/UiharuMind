## 两口径（用户钉死：可交互 = 恢复会话能发消息）

- **首帧净收益：-134ms**（普拉娜净数口径：vm-ctor 176+view 86+layout 347 = 609 → 187+96+192 = 475）。来自 B：右栏物化后置（Content 不绑定 → Background 物化 + 版本失效防串会话 + 命中同步物化），首帧只出壳、宽度固定无位移。
- **严格可交互：1060ms 不变**。B 是首帧收益（右栏非发消息必需）；switch 异步化尝试后撤（见下）。主题六对「能发消息」秒数贡献为 0——诚实定位：首帧感知 -134ms、UI 不冻结，这就是全部交付。

## 为什么 switch 异步化撤了（教训）

`SessionManager.Load` 挪 `Task.Run` 后台后：`conversation/switch` 177→12ms（UI 线程空闲化成功），但 load-session 51→463–527ms。分段打点证明 **Load 本身只有 ~50ms**（load-read 7–59ms / load-unload <5ms）——511ms 的墙钟是「后台 Load 完成后回 UI 线程排队等首帧布局/settle 结束」。UI 单线程结构性矛盾：要么 load 占 UI（51ms 卡顿但数据早可用），要么后台（UI 空闲但数据要等 UI 忙完）。严格可交互 51→~500ms 劣化，验收不达，还原同步。**结论：要再动 switch，得解决「回 UI 排队」而不是 Load 本身。**
