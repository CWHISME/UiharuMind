# 会话历史按上限驻留，本体实例永不换

决定：

1. `SessionManager` 的已加载本体缓存**继续只增不减**——本体实例一经加载就不换、不摘。
2. 按会话长度增长的那一份（`ChatSession.History`）改为**可卸载**：内存里同时保留历史的
   会话数设上限（`SessionResidencyPolicy.MaxResidentHistories`，暂定 6），
   超出的冷会话把历史卸掉，下次访问按需从盘上重载。
3. 卸载连带**放掉执行者**（`DisposeRunnerAsync`）：装配快照、框架会话状态与 MCP 租约都挂在它身上。
4. 冷却时间 1 分钟是**正确性**要求，不是调优（见下）。
5. 持有历史里那些 `ChatMessage` **实例**的人要 `SessionManager.Pin` 钉住它，
   目前只有界面壳（`ConversationViewModel.AttachSessionSignals`）。

## 为什么是历史，不是本体

实测：30 份最大的会话档落盘 48.7MB，解析成 `ChatMessage` 对象图后在堆上占 164.6MB
（约 3.4 倍——UTF-16 加上每条消息的对象头与 `Contents` 列表）。而本体除历史之外
全是标量与短字符串，一份不到 1KB。所以「内存随使用时长涨」这件事，问的只有历史。

本体实例**必须**长命：执行者、界面壳、后台派发认的都是那一个实例，
换实例就会出现两份历史各写各的，最后一个存盘的赢——那是静默的存档损坏。
原先那个 `Release(sessionId)`（把本体整个摘掉）正是这个形状，所以它从写下那天起
就没有任何调用点，等于一条没人敢走的路。

卸历史而不换实例，代价只剩一个：界面条目持有的 `ChatMessage` 实例在重载后认不回来，
编辑/删除/分叉/重试静默失效。而那正是**冷会话**的定义——没有界面壳挂着它。
有壳挂着的用 `Pin` 排除，剩下的不存在这个问题。

## 为什么要冷却一分钟

后台那几条路（交回报告、定时任务、子代理派发）的形状都是「`Load` 出来、跨几个 await
用完再存」。中途把历史卸掉，它们手上那份 `List<ChatMessage>` 就成了孤儿——
往里写的东西不会被任何人落盘，而且**没有任何报错**。

理论上正确的做法是让每一条这样的路都 `Pin`，但那是一份会漏的清单：
今天数得清，明天新写一条就漏一个，而漏掉的症状是「偶尔丢一条消息」。
冷却时间把这条竞态整体排除——那些操作都在秒级之内完成，一分钟的余量下它不可能发生。
代价只是冷会话晚一分钟让位，而让位这件事本来就不急。

## 卸载前要写一次盘

内存里那份才是权威，而「有没有人改过它还没保存」在卸载点判不出来。
多写一次几毫秒，换的是「卸载永远不会丢东西」。
唯一的例外是空历史一律不写——会话文件读坏时 `LoadHistory` 也会给出空列表，
这时候回写等于拿一次读取失败把盘上那份真历史抹掉。
