# 主子代理提示词共用一套段落编排

主代理与子代理的系统提示，从前各自手写一套 `StringBuilder` 编排。现在**工具纪律那一段由
同一张声明式清单产出**（`ToolDisciplineSections`），两档的差别只剩一份 `ToolDisciplineFacts`
里的几个开关。段与段的拼接交给 `PromptSectionList`。

顺带把语言口径写死：**系统提示中文，工具描述英文**。

## 为什么

### 两处各写一套编排，差异不是设计而是漂移

拆之前的实际状态（全部核过代码，不是推测）：

1. **子代理拿着 `Edit`/`Write`，却从没收到过文件修改纪律。** 通用档子代理在完全自动档下
   装配了写工具，但它的「# 做法」段只说「你可以用 `Glob`、`Grep` 和 `Read` 探查文件」。
   Edit 与 Write 的分工、oldString 的唯一匹配、「同一文件的改动合进一次调用」——一句都没有。
2. **同一个子代理却收到一段指名了 `Edit` 的 shell 纪律**（「单点改动用 `Edit`」）。
   它引用的是一段从没发给它的纪律。既有的「反引号指名的工具必须真实存在」那条不变量
   拦不住这个：`Edit` 确实在工具集里，缺的是**纪律**，不是工具。
3. **段序两边说的是相反的话。** 主代理侧注释写着「工作目录排在最前，后面每一段纪律都以
   路径怎么写为前提」；子代理侧把工作目录放在整段 shell 纪律**之后**。
4. **主代理挂了 `WebSearch`/`WebFetch` 却零指示**，而子代理侧反倒有一句。
5. **点名的子智能体，「# 工作循环」在同一份提示词里出现两次**：新建智能体时它被预填进
   角色卡（ADR 0004），子代理装配又在末尾无条件追加同一份常量。每轮都多付一遍钱。

这五条的共同点是：**没有任何测试拦得住**。两段散文谁也不知道对方说了什么，而漂移的表现
全是静默的——提示词照发、模型照跑、错误只在实机上偶尔冒出来一次。

### 清单化之后，段序成为一张可读的表

`ToolDisciplineSections.Build` 里是一串 `list.Section(条件, 标题, 正文)`，顺序就是发出去的
顺序。「Python 挂在命令行之下」「记忆要文件工具」这类约束在那一行上一眼可读，而不再是
两处 `StringBuilder` 调用顺序的巧合。新增不变量测试四条钉住其余的：同一段落不得出现两次、
子代理段序与主代理同构、探索档不得出现写工具、能改东西的子代理必须拿到写侧纪律
（最后一条防的是「反引号校验空转」——写侧整段缺席时那条校验当然通过）。

### 读、写拆成两段

`FileAccessDefault` 拆成 `FileReadDefault` + `FileWriteDefault`，理由是**只读装配也要读**。
探索档子代理有 `Glob`/`Grep`/`Read` 却没有 `Edit`/`Write`：两半并成一段时，它要么整段拿不到
（连上下文卫生、contextLines、`limit=-1` 都没有），要么整段拿到（被指名两个不存在的工具）。
拆开之后两档各拿该拿的那半。

「先 `Read` 再改」「也不要读太少」两句归**写**那一侧：它们的理由整条都是 oldString 要精确匹配，
没有写工具时说它们等于指一件做不了的事。

## 子代理的身份与协作口径

「# 做法」段拆掉，工具那部分归入 `# 工具` 之下的各分节，剩下的成为 `# 协作` 段。同时修掉三处
提示词与代码不一致的地方：

- **不再说「独立完成派给你的任务，然后交回结论」。** 基础设施早就按多轮讨论设计了——
  `BackgroundSubAgentDispatcher.MaxConsecutiveWakeTurns` 取 32 的注释原话就是
  「主、子代理多轮讨论时 12 轮不够一次讨论收敛」。提示词说「独立」、代码等着来回谈，
  冲突的是提示词。
- **告诉子代理用户可能直接插话。** 用户能在子会话窗口直接说话（`SubAgentTool` 里
  「本轮是否出现过用户插话」就是为此存在），而子代理从前完全不知道，会把用户的话
  当成派活方的追问。主代理侧倒是知道。
- **删掉 `SubAgentProfile.RoleHint`。** 它与 `BoundaryCanMutate`/`BoundaryReadOnly`
  近乎逐字同义，一个挂在「# 角色」、一个挂在「# 做法」，同一件事说了两遍。

「缺信息就停下来等追问」那条从硬规矩改成「不要猜着补」，去掉了写死的
「以『需要你补充：』开头」和「必须结束本轮」——前者钉死句式，后者把「先做能做的」这条路堵了。
「回复要聚焦：先结论再依据」降为交终版时的默认。

**「不要以工具调用收尾」一字未动**：它不是风格，它对着代码兜底（模型以工具调用结束时要
额外追加一轮 `SummaryPrompt`），松了就是每次白烧一轮。

### 身份只谈判断标准，不谈扮演

派活时给的 `role` 从光秃秃一句「你这次的身份：X。」改成「……按这个身份的视角和判断标准来
做这件事。」，并在主代理的 `## 委派` 段补一句教它用（从前**整段从没提过这个参数**，`role`
实际上是个死参数）。

落点是「视角与取舍口径」而不是「扮演」，理由有两条：persona 当能力暗示用的证据本就很弱；
而本地小模型对文体极敏感（`LanguageNeutrality` 那句护栏的存在就是证据），
一句「请始终以这个身份思考和回应」很可能换来角色腔的汇报而不是干活。

角色卡与 `role` 同时在场时明确表态「这一趟按这个侧重来，其余仍按你自己的方式」——
不表态的话，一张写得强势的角色卡（长度与具体度都碾压那一句）会直接压过它。

## 语言口径：系统提示中文，工具描述英文

这条一直事实成立却没记过，于是看起来像不一致（`SubAgentToolPrompts` 全英文，而 ADR 0017 说
「提示词只留中文一份」）。边界是：

- **系统提示段落**（`AgentToolPrompts` / `SubAgentPrompts` / `AgentPromptHeadings`）：中文，
  只有中文一份。
- **工具描述与参数说明**（各 `Tool` 类 + `SubAgentToolPrompts`）：英文，与框架侧
  function schema 的惯例一致。
- **工具结果**（回执、错误串）：英文，与描述同侧。

改成全中文要连带动所有 Tool 类，那是另一个工程；而问题从来不是不一致，是这条边界没写下来。

## 顺带修掉的

- `## 委派` 段写死的「只读，只有 5 个工具（`Grep`/`Glob`/`Read`/`WebSearch`/`WebFetch`）」。
  **两处都不成立**：工具集随能力配置变（关掉网络搜索就只剩三个，探索档还恒定没有识图），
  而 `WebSearch`/`WebFetch` 在 `EnableWebSearch` 关闭时根本没装配——那句话会指名两个
  不存在的工具。现在只说性质，不数数。
- `VisionToolDefault` 把 `[Attached file: <path>]` 也放进了反引号。违反「反引号专表工具名」
  这条约定，改用双引号。这条违规一直活着是因为主代理那份校验不到（要真工具集才能比对），
  子代理从前用的是另一句——两档共用同一段才把它撞出来。
- 子代理的草稿目录段不再给 markdown 图片语法。它的正文不进用户对话，交出去的是报告，
  展示归派活方；给它 `![](file://…)` 只会让它写出一段没人渲染的引用。改成
  「在结论里写出绝对路径」。
- `## 委派` 段第一条句尾的 `。，`。

## 已知代价

- **主代理多了一段 `## 联网`**（约 40 字，仅在 `EnableWebSearch` 开启时）。它填的是一个真实
  缺口——挂了两个工具零指示——但确实是每轮的固定开销。
- **子代理的提示词变长了**：多了写侧文件纪律与 `## 联网`。这是补齐，不是膨胀：
  从前短是因为它缺东西。
- **`PromptSectionList` 多了一层间接**。换来的是段序只有一处定义；两份平行散文那种
  「改一处、另一处静默走样」的缺陷，在这个仓库里已经真实发生过五次（见上）。
