# 子代理模型可配多个，派活依次取用

设置页那几档子代理模型（通用 / 整理 / 探索 / 评审）从**单选**改成**多选**（Ursa `MultiComboBox`）。
同一档配了多个时，**派活依次取用**——一个档一个游标，进程内共享，按配置顺序往下轮，
跳过钉不住的那些（`LlmModelPinProbe.Pin` 那条判据不变）。空列表仍是「回退到主代理模型」。

前端形状：`AgentSettingConfig.GeneralSubAgentModelNames` / `BrainSubAgentModelNames` /
`ExplorerSubAgentModelNames` / `ReviewerSubAgentModelNames`（`List<string>`）。

## 为什么要多选

起因是一次旁观：主代理一轮里连着派出几个子代理，它们**全落在设置页配的那一个模型上**。
远程供应商的并发额度就那么几条，几个子代理于是互相排队——用户看到的是「一委派就卡」，
而界面上只有一个模型名，翻会话元数据才看得出它们用的是同一个。

这不是模型弱，是**同一时刻所有请求打在一个账号的一个模型上**。让它摊开最省事的做法就是配几个：
第一个走 A、第二个走 B、第三个再回 A。

## 为什么是「依次」而不是「挑最闲的」

挑最闲要读运行中的会话表：一次派活就得翻一遍全量会话、比对 `SessionModelName` 与忙碌态。
而「一轮内连派几个」这个真实用法里，依次取已经把它们摊开了——第 N 个必然落在第 N 个模型上，
只要配置的模型数量 ≥ 并发数，就没有一个模型上撞两次。

依次还带来一个可解释的副作用：**用户勾选的先后就是轮到它们的先后**，界面上看得见、排得动。
换成「最闲」就变成玄学，用户没法通过配置表达意图。真要按负载挑，改 `SubAgentModelRotation` 一个类就够。

## 形状

- **游标按档各一份**且进程内共享：通用档推进不该把探索档带跑。
  同一档的两次派活无论来自哪个会话、哪条线程都接着上次往下取（`Interlocked`）。
- **跳过钉不住的**，而不是整档回落：配了三个只起来一个，就一直落在起来的那个上。
  全都不行才返回 null，交回调用方回落派活者/全局模型（并留一条带完整名单的日志）。
- **钉动作发生的那一刻定死**：模型名照旧钉进子会话的 `SessionModelName`，一个子会话整个生命里不换脑子。
  这一条 ADR 0031 已经定过，这里只是「取哪一个」的规则变了。
- **点名仍然压过设置**：`CreateAgent` 的 `model` 参数语义不变（这一趟用哪个 > 默认用哪个）。

## 落盘与界面

`SelectedItems` 是**单向**绑过去的：控件拿住 ViewModel 的那个集合实例，自己往里增删。
所以 `SubAgentModelSlot.Selected` 实例恒定，回填只能清空重填——换实例等于把绑定断开，
症状是「勾了模型、界面也变了，配置里却只有第一次的那几个」。无头测试钉住这条。

各档的差异只有「存配置里的哪一列」，回填、重建、恢复默认、落盘、反馈全收在 `SubAgentModelSlot`
里写一遍；界面上那几行的形状也一样，所以多选控件收成一个 `SubAgentModelPicker`
（`Slot` 是它唯一的输入，页面里每行只剩一句）。

**候选里暂时没有的模型名留在配置里**：模型被停用 / 被删时界面显示不出来，但那不代表用户要删掉它，
模型回来就该自动再生效。这条是改动前单值那套的既有行为，多选沿用。
代价是它们也看不见、无勾可选——所以「恢复默认」必须连这串名字一起清掉，且按钮的可见性
看的是**配置**而不是界面上勾了几个（否则这串名字就永远没有入口清）。

**配置里的列表是跨线程共享的，所以写方换实例、读方拷一份**：设置页增删一个模型原来会
`Clear` + 重填同一个 List，而派活常在后台线程上读那一列——读方能拿到空名单
（静默回落主代理）或直接越界，连 `List.ToArray()` 都不是原子的。现在写方一律赋新列表
（设置页、装配重建都是），发布出去的列表不再变；`SubAgentProfile.ResolveModelNames`
再拷一份只是兜底（防的正是“以后某人又改回原地增删”）。

## 不做旧档兼容

旧的单值键（`GeneralSubAgentModelName` 等三条）**直接作废**：升级后它们在配置里被忽略，
列表从空开始，用户在设置页重配一遍即可。没有 `Legacy*` 字段、没有读档迁移、也没有
「读到旧形状就转换」的钩子。

理由是这个功能刚落地、只有开发者在用，而兼容代码的代价是长期的：一个只读字段、一段迁移、
一个读完档才跑的钩子，之后每个读配置的人都得先弄明白「哪个才是真的」。
真要做兼容时，正确的位置也不是这些属性，而是 `SaveUtility.Load`（读失败先备一份 `.bad`
再回落默认，让用户的配置能捞回来）——那是全仓所有配置共有的问题，不该在这三个键上单点开口。

## 已知代价

- **只配一个模型时行为与从前一致**，但游标仍在推进——同一个模型被反复选中，无害。
- **配置里留着的死名字**（模型已被删）会每趟被判据跳过，并按 `Debug` 逐条记一条。这是有意的：
  静默跳过会让「我配了三个，为什么只用两个」无从查起。Debug 而不是 Warning，是因为那名字
  会每趟都被跳一次，配三个就刷屏。
- **不均衡**：依次取不看各模型的并发额度、价格或能力，撞上某个额度小的模型照样排队。
  要按额度分配得引入模型侧的并发上限元数据，现在没有。
- **可能一轮里预热多个远程模型**：钉一个模型会顺带把它拉起来（ADR 0031），多选后连派几个
  子代理就是连着拉起几个。这是「摊开并发」的另一面，不是意外。
- **手改成字符串会把整份配置打回默认**：这三个键是数组，写成一个字符串时 STJ 抛异常，
  而 `SaveUtility.Load` 的口径是“一抛就整份 `new T()`”。这是全仓所有配置共有的行为，
  本次没为它单开一个转换器（只针对三个键做容错会让“哪份配置能容忍类型错”变成随机的）。

## Ursa 那两处口径，补在壳里

`MultiComboBox`（Ursa 2.2.0）有两处与这里的用法不对付，都不等上游，自己收在一个壳里：

- **占位文案的空态伪类会残留**：它只在集合增删与套模板那一刻更新 `:selection-empty`，
  整体换 `SelectedItems`（回填好的集合在模板之后才绑上来）不同步，`OnUnloaded` 又把集合监听
  摘掉后再不挂回来——切一次页签，之后的增删就再不反映到伪类上。表现是框里已经有一枚标签、
  旁边还挂着一句「未设置」。所以 `Shared/Controls/MultiSelectComboBox` 自己拿监听，
  在赋值 / 套模板 / 挂回界面时各同步一次；模板与主题仍按 `u:MultiComboBox` 找。
- **滚轮会漏到下拉外面**：列表滚到底后 `ScrollContentPresenter` 会把事件标成未处理
  （`IsScrollChainingEnabled` 默认开），而 Windows 上浮层是独立窗口，未处理的滚轮被转发回主窗口，
  落到设置页的 `ScrollViewer` 上——整页跟着滚，浮层被顶走、看着就错了。
  `Assets/Themes/CustomPopupStyle.axaml` 里关掉多选下拉两处滚动容器的滚动链，滚到底就停在列表里
  （真窗口里量过：关之前列表停在 412 后每格页面 +50，关之后不再动）。
