# 角色档位从四档枚举改为一轴派生，用户卡退出角色体系

`ECharacterKind` 四档枚举退役。角色只剩**一条派生轴**：`IsAgent` —— 这个角色开不开 harness
（装配工具、工作目录、工作循环提示词）。`Roleplay` 与 `Tool` 合并为**普通角色**，
两者原先的差别（人格、开场白、挂了哪些提示词片段）降级为**数据**。
`UserCard` 不再是档位，暂留独立单例标记，后期迁出角色体系。

本 ADR 取代 [0003](0003-角色档位定版为四档真旗标.md) 的**档位部分**。
0003 的另一半——工具开关从全局下沉到角色（`AgentToolConfig`）、挂载退役、提示词片段、
子智能体名单——**全部继续有效**。

> **决策先行，实现未落地。** 落地节奏见文末「分阶段」。

## 背景

四档里只有**一条**真的机械分界线。0003 自己把它写明了：

> **`Tool` 与 `Agent` 的分岔点是「要不要 harness」，不是工具数量。**

而 `Roleplay` 与 `Tool` 之间**没有任何机械差异**——两档都「不开 harness」，走同一条
`BuildRoleplayOptions`。术语表里两行的区别是「有人格与开场白」对「一段纯提示词只干一件事」，
那描述的是**这张卡上填了什么**，不是装配管线走哪条。用一个身份轴去表达一个数据差异，
代价是徽章、筛选、编辑表单三处都要为一个不影响行为的区分分叉。

推动这次收拢的是群聊方案
（[`docs/proposals/代理人格化/群聊多角色代理设计方案_v5.md`](../proposals/代理人格化/群聊多角色代理设计方案_v5.md)）：
它要求「系统里只有角色」，群成员可以是普通角色也可以是 agent，同一个人格卡在群里和单聊里是同一个东西。
档位枚举在那个模型里会变成一张需要处处特判的表。

## 决策

1. **`ECharacterKind` 退役。** 身份由一条派生轴表达：**`IsAgent` = 这个角色开不开 harness**。
   判据是角色身上有没有装配 agent 那一套（工具集 + 工作目录 + 代码注入的 agent 提示词段），
   不是「工具数量大于零」。
2. **`Roleplay` 与 `Tool` 合并为「普通角色」。** 差异降为数据：有没有写开场白、
   挂了哪些提示词片段、Template 写得像人格还是像一句指令。
   **agent 不发开场白**（普通角色才发），这条写死，见 [0016](0016-开场白是旁白，仍入历史.md)。
3. **`UserCard` 不再是档位**，暂留一个独立的单例标记。它不在「开不开 harness」这条轴上
   （它不对话、不开会话），派生不出来。**方向是让它彻底退出角色体系**——
   走自己的数据形态，届时也能支持多张用户卡。本 ADR 不做这一步。
4. **`AgentToolConfig` 保留。** 群聊方案 §6.8 要求「工具定义全量静态、角色之间没有任何工具差异」，
   **这一条不采纳**，理由见下。
5. **`CharacterKindRouting` 仍是唯一定义处**：`IsAgent()` / `IsChat()` / `CanStartSession()`
   三个判据一个不删，只是输入从枚举换成派生。`CanStartSession()` 的唯一排除项变成用户卡。

## 取舍

- **为什么不是两轴（`IsAgent` + `HasTools`）。** 拟稿时提过这个方案，是为了安置「装了工具但不要
  harness」的角色。查证后作废：术语表写着**工具、MCP、技能、子智能体名单、记忆一律只对 `Agent`
  档有意义**——`Tool` 档从来没有工具。第二轴恒等于第一轴，是一个死维度。

- **为什么保留 `AgentToolConfig`，不跟群聊方案删。** 方案 §6.8 删它的唯一理由是 KV cache：
  「增删工具会让所有共享该前缀的会话失效」。**这个理由有事实错误——角色之间本来就不共享前缀。**
  不同角色 = 不同系统提示 = 不同会话，改一个角色的能力配置影响不到别的角色。
  真正成立的是同一条约束的另一半（同一会话内**中途**改前缀会失效），那一半保留，见
  [0044](0044-委派门面统一为SendMessage，子会话骨架不动.md)。
  删掉它还有个连带后果：普通角色会挂着 shell 和文件写工具，而一个陪聊角色
  **不该靠提示词说服自己别用 shell**。

- **为什么 `IsAgent` 按 harness 派生而不是按「有没有工具」。** 这是 0003 最值钱的那条洞见，
  原文已说透：工具全关的智能体仍然会吃下框架那一大段平台指令、技能目录 provider、
  上下文自动压缩与审批机制，还带着工作目录与权限档。**贵的是 harness，不是工具。**
  按工具数量派生，等于把一个零工具的 agent 误判成普通角色，它的工作目录和权限档就没地方挂了。

- **为什么用户卡现在不动。** 它有专属编辑窗、必须保持活引用（改了用户卡，所有开着开关的角色
  下一轮跟着变）。把它和档位改造捆在一起，会让这次改动横跨两个不相干的数据形态。
  留一个标记先跑通，迁出单独做。

## 代价（明说）

- **老存档里 `Roleplay` 与 `Tool` 的区分丢失。** 两档合并后，筛选和徽章从三类变两类
  （普通角色 / 智能体）。想继续区分「这是个陪聊」和「这是个翻译器」的，只能靠名字和分组。
  不写迁移代码——个人项目量级，且这个区分本来就不影响任何行为。
- **徽章与编辑表单要改。** 原先直读 `Kind` 的分类、筛选、徽章、落在哪一类会话，全部改读派生。
  0003 把「不要手写 `Kind == Roleplay` 当是不是 agent 用」定为规矩，这次是把那条规矩变成
  **语法上不可能违反**。
- **`DefaultCharacter` 那 14 张内置卡要重新定位。** 0003 刚给它们定过一次档，这是第二次。
- **派生轴意味着「改能力 = 改身份」。** 给一个普通角色装上 harness，它当场变成 agent，
  徽章和列表归属一起变。这是收益（一致性靠构造保证）也是意外来源——编辑页要把这件事说清楚，
  不能让用户在不知情的情况下把陪聊角色变成 agent。

## 已定（原「未决」两条，落地时拍板）

- **翻译动作下拉的候选判据** → **「不是 agent、不是用户卡、没有开场白、没开注入用户卡」**。
  把档位这个代理指标换成**它本来在代理的那个属性**——那正是「一段纯提示词只干一件事」的
  实质定义，不需要新字段。若图省事改成 `!IsAgent()`，所有陪聊角色都会挤进翻译下拉。
  落在 `TranslationWindow.axaml.cs`。
- **存量 `Tool` 内置卡的开场白** → **保持空白，不补**。它们是一次性技能卡，开场白对它们是噪音。
  （合并之后开场白与用户卡开关对它们全部开放，只是默认不填。）

## 未决

- ~~翻译动作下拉的候选判据~~（见上） 摸底找到全仓**唯一**一处真正靠
  `Roleplay` vs `Tool` 区分**运行时行为**的代码：`TranslationWindow.axaml.cs:174-180`
  把候选精确限定为 `Kind == Tool`，注释写明理由——「扮演角色带着开场白与用户卡，
  智能体带着一整套工具，都不该出现在翻译下拉里」。
  合并后若简单改成 `!IsAgent()`，**所有扮演角色都会被塞进翻译下拉**，与该注释的意图直接冲突。
  倾向的新判据：**把档位这个代理指标换成它本来在代理的那个属性**——
  「没有开场白 且 没开注入用户卡」。那正是「一段纯提示词只干一件事」的实质定义，
  不需要新字段。**动手前必须定，否则这处会被随手改错。**
- **10 张 `Tool` 内置卡合并后，开场白与用户卡开关对它们全部开放。**
  （`Assistant` / `Translator` / `VisionOcr` 等）倾向**保持空白、不补开场白**——
  它们是一次性技能卡，开场白对它们是噪音。但这是产品决定，需要确认。
- 用户卡迁出角色体系的具体形态（含多用户卡）。
- 群聊里一个群能否混装普通角色与 agent。方案 §6.4 说可以，
  [0042](0042-对话页合并为单页，类型由左栏切换器唯一决定.md) 把群的类型判定列为 P1 未决，本 ADR 不提前定。

## 分阶段

1. **一轴上线**（已落地）：`CharacterData` 的存储轴换成 `IsAgent` + `IsUserCard` 两个 bool；
   `Kind` 降级为 **`[JsonIgnore]` 的派生只读投影**（永不产出 `Tool`）。
   这个投影是本次改动churn 小的关键——**约 35 个读取点一行没动**，
   编译器只报出了写入点。扮演与工具人在徽章、筛选、排序、头像、编辑表单五处合并；
   16 张内置卡的 JSON 就地改写；翻译下拉换判据。
   - **迁移靠 `CharacterData.LegacyKind`**：一个 `[JsonPropertyName("Kind")]` 的**只写属性**，
     老存档的 `"Kind": "Agent"` 进来即映射到新轴，只有 setter 所以不参与序列化。
     没有它，升级前的角色卡会全部落到 `IsAgent=false`——**现存智能体静默降级**。
     仓库里的 16 张卡我直接改了，但 `SaveDefaultCharacterDataPath` 下**用户改过的内置角色副本**
     不在仓库里（见 [0003](0003-角色档位定版为四档真旗标.md) 同类代价），垫片是为它们留的。
     有测试钉住往返与迁移两头。
2. **枚举删除**：`ECharacterKind` 与派生投影一起移除，调用点改读 `IsAgent` / `IsUserCard`。
3. **用户卡迁出**：独立数据形态，届时另开决策。
