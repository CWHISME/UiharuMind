# 历史裁剪从自建改为框架在环压缩

喂给模型的历史不再由 `SessionChatHistoryProvider` 自己裁剪，改挂框架的在环压缩：

```
SessionChatHistoryProvider  全量供给（图片开窗除外）
        ↓
HistoryCompaction           两段式，阈值现读当前模型的上下文
        ├ 0.5 水位  ToolResultCompactionStrategy   折叠老的工具调用组
        └ 0.8 水位  TruncationCompactionStrategy   截断最老的消息组
```

删除 `TrimToTokenBudget`、`EstimateTokens`、`CountTokensCached`、`CreateTrimNotice`
与全局设置 `ChatSettingConfig.HistoryTokenBudget`。压缩对**三档全开**（智能体、扮演/工具人、子代理）。

上下文上限改由模型自己说了算：远程走「用户填的 → `ModelIdVariants` 预设表 → 200k 兜底」，
本地走运行期实际加载的 `ContextSize`（兜底 8192），见 `ModelContextResolver`。

## 为什么（1.16.0）

1. **当初不用框架那套的前提已经不成立。** `SessionChatHistoryProvider` 里原本写着
   「框架的在环压缩需要 `MaxContextWindowTokens`+`MaxOutputTokens` 才会构造，我们从未配置
   （等于不存在），模型侧也没有上下文长度元数据」。后半句已被 `ModelContextResolver` 解决——
   预设表里本来就有每个 ModelId 的上下文，只是原先只在「新建模型」对话框里预填一次，
   运行期从不推导，于是早先添加的模型把 `ContextLength = 0` 固化了下来。
   把查表挪到运行期之后，这个数字就有了。
2. **框架那套比自建的强一档。** 自建版只会截断；框架先做**工具结果折叠**——把老的
   `assistant tool call + tool results` 组换成一条 YAML 式摘要，保留「调了什么、返回了什么」，
   不动任何用户消息。对本项目最典型的负载（Grep→Grep→Read 的工具循环，工具结果就是大头）
   正中要害。
3. **孤儿工具结果从结构上消失。** 自建版有一句
   `while (IsToolResultMessage(history[start])) start++`，专防窗口起点落在工具调用组内部导致
   API 拒收。框架的 `CompactionMessageIndex` 把调用与结果组织成原子组，产生不了孤儿。
4. **token 估算不再是我们的责任。** 自建版把任何非文本内容一律按 256 token 计
   （`_ => 256`），十张截图记 2.5k、实际两万起——预算形同虚设。

## 取舍

- **不用现成的 `ContextWindowCompactionStrategy`，改用它的两个公开原语自己拼。**
  那个类的阈值在构造函数里就按上下文算死，而本项目的 agent 只在切换工作区/权限档时重建，
  模型却可以随时切：用现成的，从 Deepseek(1M) 切到 GLM(128k) 之后预算仍停在 1M，请求必然超长。
  `CompactionTrigger` 是个 `bool(CompactionMessageIndex)` 委托，因此阈值可以每次触发时现读，
  口径与 `LazyChatClient` 取模型完全一致。代价是我们复刻了框架的两段式编排，
  它若将来改进那套流程，我们不会自动跟上。
- **不设 `HarnessAgentOptions.MaxOutputTokens`，自建 `CompactionStrategy` 挂上去。**
  框架文档写明该属性同时会成为 `ChatOptions.MaxOutputTokens` 的默认值，而
  `ChatPromptExecutionSettings.ToChatOptions()` 从来不设它（请求体里只有 temperature/top_p），
  一旦设上就等于凭空给生成加了一道今天不存在的闸。改由 `ReserveFor` 出一个纯内部的预留量：
  它不再是「模型最多能生成多少」这种要查证的外部事实，而是我们自己说了算的余量，少一类会猜错的 bug。
- **预留量随上下文缩放**（`Clamp(ctx/8, 512, 8192)`）而不是取固定值。固定 8192 会让一个
  4096 上下文的本地模型算出负预算，构造阈值时当场抛。
- **远程与本地的兜底是两个独立常量**（200k / 8192）。共用一个的话，本地模型拿到远程那份
  会每一轮都必然溢出——两边差两个数量级，这不是能省的重复。
- **压缩成为「非智能体档零注入」不变量的唯一例外。** 扮演档与工具人档原先
  `DisableCompaction = true`，由 `AssemblyInvariantsTests` 钉着。现在放开，理由是压缩**只删不加**：
  排除消息组、折叠工具结果，不往上下文里写任何新内容；而扮演档没有工具调用，
  这条链退化成纯截断，正是原先自建版替它做的事，只是组边界更正确。
  不变量改成「压缩必须显式传入才生效」——没传策略时 `DisableCompaction` 仍为 true，
  免得框架哪天给它加了默认行为就悄悄生效。
- **那张 `ModelIdVariants` 预设表从「默认值」升格为「运行期依据」。** 写错一个数字的后果，
  从「用户看到默认值不对，改一下」变成「预算算错，请求被拒或历史被过度裁剪」。
  它此后要当代码维护，不是当默认值维护。
- **用户填的 `ContextLength` 永远优先于预设表。** 模型标称 1M 却实测拒收时，
  模型编辑窗里那个数是唯一的压制手段，运行期补齐只在它为 0 时介入。

## 代价（明说）

- **框架把非文本内容按 `字节数 / 4` 估 token，方向与自建版正好相反且偏得更远。**
  一张缩到 1568px 的截图 PNG 约 500KB，会被估成约 125,000 token，而真实视觉成本约 1,600——
  偏约 80 倍。在 GLM 的 128k 上下文（输入预算 119,808、折叠水位 59,904）下，
  **单独一张图就足以让压缩长期处于触发状态**；Deepseek 的 1M 则无碍。
  两条缓解已经落地：发送前把长边缩到 1568（`ConversationImageDownscaler`）、
  历史里只有最近 2 条带图消息真的带图（`HistoryImageWindow`）。是否还需要继续降分辨率
  或把保留数改成 1，待实机观察压缩触发频率后再定。
- **复刻了框架的两段式编排。** 见上「取舍」第一条：换来了模型热切换的正确性，
  失去的是自动跟随框架该流程的改进。
- **删掉了一个用户可调的全局项。** `HistoryTokenBudget` 没有迁移代码——配置文件里残留的那行
  会被 `System.Text.Json` 当未知属性忽略。逃生舱换成了每模型的 `ContextLength`，
  比全局值精确，但用户得知道去模型编辑窗里找。
- **界面新增的占用条依赖服务端返回的 usage。** 分子取最近一次响应的输入 token
  （`TurnUsageLedger.LastInput`），因此切换会话后要等第一次响应才有数，
  空窗期由既有的「≈输入估算」补上。不认 usage 的兼容服务将只看到估算值。
