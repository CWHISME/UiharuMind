# 前台也按消息边界裁，跟底闸收口

**修订 ADR 0037 第 4 条「前台不变，仍旧只在轮末裁」。** 决定：前台<br>同一消息边界裁一次，但**受跟底闸收口**，用户一上滚就停。

## 决定

1. 前台与后台一样，在「消息边界」这一轮内时机各裁一次；前台走
   `TrimIfNeeded()`（运行期上限 80），后台走 `TrimToBackgroundBudget()`（一屏量级）。
2. 前台裁剪**只在跟底时生效**：`canTrimSource` 那道闸在 `ConversationItemWindowTrimmer`
   里，用户上滚就自动关掉——正在读的内容不会被抽走。
3. ADR 0037 第 4 条那句「前台不变，仍旧只在轮末裁」废除。

## 为什么前台也要在轮内裁

只裁后台不够：长轮次里除了切走的那个会话，**还挂在界面上的这个**也在不停涨。

实测：agent 的一轮可以跑几十次服务调用、堆出几百个条目；会话流**没有虚拟化**，
一张工具卡就是上百个控件，一轮长下来光控件对象图就能涨 86MB——
而这个峰值正是 GC 提交量下不来的源头（见 `IdleMemoryReclaimer` 的注释，
它只还「死了的空地」，还不了「活对象为什么有 196MB」那一半）。

原来的顾虑是「流式中途裁会打乱跟底与 Offset」——它拦对了时机，拦错了结论：
消息边界恰恰是轮内最安稳的时刻，流段刚收尾、来源消息也刚落盘，
锚点与滚动位置都是确定的。见 `ConversationViewModel.OnMessageBoundaryReached`。

## 顺带定案的两处开发路径口子

1. `DevScriptRunner` 的 `quit` 用 `Process.GetCurrentProcess().Kill()`（先 `App.Dispose()`）：
   本应用窗口关闭是<b>隐藏</b>（常驻托盘），`lifetime.Shutdown()` 关完窗口进程照样活着——
   实机验证过，所以这条路是刻意的，不是偷懒。
2. `diag.memory` 的 `collect=true` 直接调 `GC.Collect`：
   这是诊断命令刻意开的观测口（量「活对象 vs 已提交 vs 碎片」时需要先压一次），
   只读、无业务副作用，不算「替用户说话」，与 DevAutomation 的读/导航口径不冲突。
