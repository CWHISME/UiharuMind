# 会话历史收成带锁的集合，跨多条操作的读一律取快照

> **状态**：accepted（2026-11-02）。修的是实机崩溃
> `Collection was modified; enumeration operation may not execute`
> （`ConversationItemActions.WireStreamed` ← `CatchUpTail` ← 用量上报）。

## 起因

`ChatSession.History` 一直是裸 `List<ChatMessage>`，没有任何锁。而它天生是跨线程的：

- **写方在执行线程**：`SessionChatHistoryProvider.StoreChatHistoryAsync` 每完成一次服务调用就追加；
  子代理交回报告（`SubAgentReportHandoff`）、群投递（`SessionDelivery` / `SessionMessenger`）、
  群成员发言回流（`GroupMemberReplyFeed`）都在后台线程写。
- **读方在 UI 线程**：对账（`ConversationHistoryReconciler`）、渲染（`ConversationHistoryRenderer`）、
  搜索（`SessionSearch`）、用量统计（`ConversationUsageViewData`）都在读。

一次整表枚举撞上一次 `Add` 就是 `InvalidOperationException`。按下标读的地方更隐蔽：
列表变短抛 `ArgumentOutOfRange`，变长则静默少画几条——**故障从崩溃退化成"界面偶发少几条"**。

`ConversationViewModel` 那道 `_driver.IsRunning` 守卫拦不住：它只判"本视图自己驱动的那一轮"。
崩溃现场恰恰是**别人在跑**（唤醒轮、群轮、子代理），本视图只是旁观，`IsRunning == false` 直接放行。
而 `CatchUpTail` 的设计目标就是"轮内每发一次请求补一次尾巴"——它与写方并发是**定义上必然**，
不是偶发。Docs 里此前没有任何一条覆盖"历史的跨线程读写"，这条约束从来没被写下来过。

## 决定

1. **`ChatSession.History` 的类型从 `List<ChatMessage>` 换成 `SessionHistory`**
   （`Core/AI/Chat/SessionHistory.cs`）：内部 `List<ChatMessage>` + 一把私有锁，
   实现 `IList<ChatMessage>` 与 `IReadOnlyList<ChatMessage>`。
   调用方原本写 `History.Add(...)` / `RemoveAt(...)` / `Count` / `[i]`，**一处都不用改**。
2. **锁只在单次集合操作期间持有**：临界区里只有一次 `List` 操作，不做 IO、不回调。
   唯一例外是 `RemoveAll` 的谓词（同步执行、无重入）。
3. **跨多条操作的读必须先 `Snapshot()`**：锁内 `ToArray()`，出锁之后随便枚举。
   对账、补尾巴、按下标切片、算 token、构造 `HashSet` 全部改成"整趟只用一份快照"。
   这些方法的形参本来就是 `IReadOnlyList<ChatMessage>`，传数组是零改动。
4. **枚举器也吐快照**（`GetEnumerator() => Snapshot()`）：`foreach` 活历史不会因为别处追加而抛。
   代价是每次 `foreach` 复制一次引用数组——热路径自己 `Snapshot()` 一次重复用。
5. **落盘起点改用 `AddReturningIndex`**：原来是"先读 `Count` 再 `Add`"，
   两句话之间别人插一条，记下的下标就指着别人的消息，`SaveAppended(from)` 会把别人的那条再写一遍。
6. **`ChatSession.History` 的字段自身也有锁**（`_historyLock`）：装/卸/懒重载都要原子，
   否则两个线程同时看到 `null`，各读一次盘，后发布的那份把先到的写全丢了。
   重载（磁盘 IO）在锁外做，发布在锁内——后到的发现已有人发布就丢掉自己那份（它还没交给任何人）。
7. **不加 `try/catch` 兜底**。吞掉之后对账会静默跳过，而按下标读的地方仍然会越界。

## 取舍

- **让 `History` 变成只读、写方改走 `AppendMessage()`**：语义更干净，但测试里 70 多处
  `session.History.Add(...)` 全得改，收益不值这个风险。
- **写方维护不可变快照、读者直接读数组字段**：任何绕过写入口的直接 `Add` 都会让读者看到陈旧数据，
  从"崩"退化成"静默不一致"，更难查。
- **加 `try/catch` 兜住对账**：掩盖问题。见决定 7。
- **`lock` vs `SemaphoreSlim`**：锁里没有 `await`，用 `lock`。集合操作都是 O(1)～O(n) 的纯内存操作，
  无争用时约 20ns，UI 线程上感觉不到。

## 已知代价

- **快照是 O(n) 拷贝**。UI 侧每个操作一次（不是每条消息一次），长会话（万条）一次 78 KB 引用数组。
- **按下标读仍假设"只追加"**：`AppendTail` / 删除下标 / 群投递游标都靠"追加不改已有下标"。
  压缩会让下标失效，但压缩只在会话空闲时由执行线程做，不与这些读并发。
- **`SessionHistory` 不保证跨多条操作的原子性**：`if (Count > 0) History[0]` 这类写法仍有 TOCTOU 缝，
  只是不再抛异常。要原子就读快照。注意 `IList<T>` 让 LINQ 的 `Skip/Take/ElementAt` 走快速路径、
  直接读活 `Count` 与索引器，绕过 `GetEnumerator` 那层快照——一串 LINQ 之间历史仍可能在变。
- **追加与落盘仍不是一个原子步**。`AddReturningIndex` 只保证「落盘起点不指到别人的消息」，
  关不掉下面这条：A 追加到 10、B 追加到 11 且先落盘、A 再 `SaveAppended(10)` 会把 11 一起写，
  文件里 11 出现两次（顺序成 `11,10,11`），重开会话工具调用与结果配对错位。
  根治要一条每会话的「已落盘水位线」（`Append` 用 `max(from, 水位)` 切片并回写水位），这次没做。
- **`IList<T>` 的 `RemoveAll` 谓词在锁内执行**，里面不许再碰会话（调 `Save` 之类会成环）。
  当前唯一调用点是 `HashSet.Contains`，安全。

## 分配量与 GC（实测 2026-11-02，Release，Windows）

万条消息的会话，一次快照 **78 KB / 7 µs**（`ToArray`）。看着像"每次读都 new 一个大数组"，
但它是纯 gen0 短命对象，没有任何引用留存：

- 连取 2000 次快照（累计分配 156 MB）：**GC0 触发 10 次**，GC1/GC2 零次，
  存活堆 **12 MB → 12 MB 纹丝不动**。
- 同样 2000 次"裸 List 整表遍历"：208 ms；2000 次快照：**14 ms**（数组枚举比 `List<T>`
  的枚举器快，它每次 `MoveNext` 都要查 `_version`，快照那点拷贝成本被抵掉了）。

所以它抬的是 GC **频率**（每 200 次快照一次 gen0），不是堆**大小**。真正的常驻内存大头在别处
（会话流的控件对象图，见 `ConversationViewModel.OnMessageBoundaryReached` 的注释）。

一次服务调用的读路径分配（万条会话）：改造前约 276 KB，改造后一度到 588 KB，收了两处后约 **510 KB**：

1. `SessionManager.Append` 落盘只取尾部 → `SnapshotFrom(fromIndex)`（48 B，不再是 78 KB）。
   这条是每次服务调用都走的，最该省。
2. 消息边界上 `WireStreamed` 与 `CatchUpTail` **共用一份快照**（`CatchUpTail` 加了可选入参）。

剩下的大头是 `WireStreamed` 里那个覆盖整份历史的 `HashSet`（198 KB，流式时一个边界建两次），
**是原有代码**，不属于这次改动。它只探测至多 `_items.Count` 个来源却哈希了整份历史，
真要再省应当改它，而不是回退快照。

**没有做**"版本号 + 快照缓存"：收掉上面两处之后它只能再省一次边界上的 78 KB，而代价是
读者可能拿到陈旧数组、冷会话的缓存数组会把消息钉在内存里（与驻留策略冲突）。不值。


## 验证

`UiharuMind.Core.Tests/Chat/SessionHistoryConcurrencyTests.cs`：写方 2 万次 `Add` 的同时，
读方循环"取快照 → 构造 `HashSet` → 整表 `foreach`"（就是崩溃现场那条路的原样复刻），断言不抛；
另有 `AddReturningIndex` 下标稳定性、快照与后续追加解耦、删与读并发三例。
换回裸 `List` 时这几个用例会当场炸。
