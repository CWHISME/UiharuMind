# 占用口径分报告与有效，压缩分母扣掉固定开销

「上下文占用」从一个量拆成两个，「历史能占多少」从输入预算收窄为**历史额度**：

| 词 | 是什么 | 谁用它 |
|---|---|---|
| **报告占用** | 服务端 usage 里的输入 token（`TurnUsageLedger.LastInput`） | 记账；进度条实色那段 |
| **有效占用** | `max(报告占用, 固定开销 + 历史估算)` | 交接文档水位(0.8)；进度条整条填充；配色档位 |
| **固定开销** | 系统提示 + 工具定义，每轮重发（`AgentCapabilitySnapshot.EstimatedTokens`） | 从输入预算里扣 |
| **历史额度** | 输入预算 − 固定开销（`HistoryCompaction.HistoryQuotaFor`） | 折叠(0.5) / 截断(0.9) 的分母 |

## 为什么

起因是一件查清了的疑案：我们估 Unity MCP 那套工具占 21k，GLM4-Flash 报的 `prompt_tokens`
只有 12.3k。结论是**我们的估算是对的**——请求体实测 128,599 字符，÷ 我们估的 25.6k ≈ 5.0 字符/token
（正常），÷ GLM 报的 12.3k ≈ 10.5 字符/token（任何分词器都做不到）。GLM 少算了工具定义。

当时的判断是「这只影响那条显示」。核代码之后发现有一半是错的，而且错在最贵的那条上。

### A：交接文档水位读的正是服务端 usage

`TurnDriver` → `HistoryHandoff.ShouldWrite(lastInput, ...)`。走框架估算（`CorrectedTokenCount`）的
只有折叠与截断两条，交接文档不走。

GLM 少报一半 ⇒ 交接文档要等真实占用约 1.6 倍输入预算才触发 ⇒ **永远不触发**，请求早爆了。
三条水位里唯一会调模型、也唯一能保住上下文的那条，在那类服务端上是死的。

### B：折叠与截断的分子只含消息，不含固定开销

`CorrectedTokenCount` 是对 `CompactionMessageIndex.Groups` 求和——消息组。
系统提示（`ChatOptions.Instructions`）与工具定义都不是消息，进不了那个索引，却实打实吃掉分母。

```
GLM 128k → 输入预算 119808
旧截断水位 0.9 × 119808 = 107827        ← 只数消息
实际请求 = 107827 + 25600 = 133427 > 128000   ← 已经爆了，截断才动手
```

**这一条与服务端报不报得准无关，任何模型配任何大工具集都中**，本地 8192 的模型更是必然。

两条指向同一个根：**「占用」在三处有三个不同的分子，分母却是同一个输入预算。**
[CONTEXT.md](../CONTEXT.md) 把分母的三层收缩定义得很清楚，分子一个字没定义过。

## 为什么 A 取 `max` 而不是直接换成我们的估算

两侧代价**不对称**：

- **晚压**：请求撞上下文上限直接失败，通常发生在 agent 跑了十几轮工具之后，那一轮全废。
- **早压**：多写一次交接文档（一次请求），丢一些细节。

所以取大的方向是对的。但它有个真实的失效模式：假如某个模型的分词器与 `o200k_base`
差 1.5 倍，我们就永远在真实 53% 处触发交接文档，用户白丢近一半上下文，而**屏幕上什么异常都没有**。

因此差异本身要**被观测，而不是被 `max` 悄悄吞掉**：`TurnDriver.LogUsageRatio` 每轮至多记一条
`报告 / 我们估的` 的比值，正常落在 0.8~1.2，越界打 Debug 并说明是哪个方向。
GLM 那次会落在 0.48。当初定位到 GLM 靠的正是这个比值。

## 为什么 B 扣分母而不是加分子

数学上等价（差一个 fraction 因子），但语义不同。扣分母之后**分子分母都是「历史消息」的口径**；
加分子会变成「分子是历史加开销、分母是全量预算」，两个混起来的量。

而且扣分母不碰服务端那个数，因此完全不受上面那个估算偏差的影响。

## 为什么进度条画两段而不是换成有效占用

第一反应是让进度条直接显示有效占用。但「进度条要能跟官方控制台对上」是真需求，
换掉服务端的数就对不上了。

反过来只画报告占用也不行 —— 那会引入 CONTEXT.md 自己禁掉的**第二把尺子**
（「同一个应用里讲什么时候开始丢上下文，不该有第二把尺子」）。GLM 上的症状会是
**进度条显示 30%，交接文档却开始写了**，而出问题的那一刻用户根本不会去读 tooltip。

所以把差额**画出来**：

```
├──── 报告占用 12.3k ────┼── 未计入 13.3k ──┤        ┆水位
   实色（服务端说的）        半透明（我们估的差额）
```

- 服务端的数原样显示，一个字没改，要对账随时能对。
- 差额被明确标为「未计入」——那正是这件疑案的结论，直接画在了它该出现的地方。
- 水位标记落在两段末端，与压缩实际动手的位置重合，不再有第二把尺子。
- 比值正常时第二段恒为 0，绝大多数模型上看不出区别。
- 首轮之前没有报告占用，第一段为 0、第二段就是固定开销。

**让误解不可能发生，比事后解释误解便宜。** 原先计划的两条收尾文案（CONTEXT.md 补一句
「固定开销 > 占用是可能的，不是 bug」、tooltip 补「也可能是不同口径」）因此**作废**——
有效占用 ≥ 固定开销 + 历史估算 ≥ 固定开销，那个怪象在数学上不再可能出现。

## 实现细节里承重的几处

- **固定开销缓在 `AgentHandle` 上，惰性算一次。** 它含系统提示的分词，从前只服务能力面板、
  因而每次刷新现算；接进压缩之后就落在发消息路径上了，每轮现算不能接受。
  不需要失效机制：handle 本身只在装配快照变化时重建，这份跟着重算。
- **固定开销与压缩策略经 `TurnInputEstimate` 这个盒子接上。** 压缩策略在
  `AgentAssemblyPlan.Resolve` 里就要构造好，而固定开销要等装配完成才算得出来（它含系统提示，
  而提示是装配现场拼的）。盒子在装配末尾绑定，读的时候才分词。
- **历史估算由 `ExceedsFraction` 顺手回写，不额外分词。** 那里本就要算一遍
  `CorrectedTokenCount`。截断靠「排除一组 → 重问一次条件」收敛，所以最后落下的是**压完之后**
  的值——那正是本轮真会发出去的历史大小，比压之前的数更该用。
- **额度为 0 时一律不压缩。** 两种成因：预算未知（没有模型在跑），或固定开销自己就吃光了预算。
  两种情况下请求本来就发不出去，压缩救不了，只会白毁历史。

## 代价（明说）

- **交接文档在少报的服务端上会比"真实占用"更早触发。** 取 `max` 意味着按两者中悲观的那个走。
  这是有意的（见上），但用户会感到那类模型上压缩来得勤一些。
- **纯提示词档（扮演 / 工具人）的固定开销仍记作 0。** 它们不登记工具与提示分段，
  能力快照恒为空，于是它们的分母没有扣除。它们的系统提示确实也占位，
  但相对预算小得多；按档位补齐这笔账是另一件事，没做。
- **`HistoryQuotaFor` 的分母会随工具开关跳变。** 用户在角色编辑页关掉一批工具，
  下一轮的历史额度就变大、水位跟着上移。这是对的，但意味着「还能聊多久」不是一个稳定的数。
- **比值观测只进日志。** 它对用户没有可行动性（分词器不是用户能改的），
  与 `ToolTokenBreakdown` 的三段归因同属**开发者诊断设施**，日志就是它们正确的落点。
  代价是用户遇到问题时捞不出来——要一个可导出的诊断面板，那是另一件事。
- **「框架每轮请求前都会问一次触发条件」这个前提没有被实证。** 历史估算的"零额外成本"
  依赖它。若不成立，症状是有效占用在某些轮次上偏旧（退化为只信服务端），不会算错方向。
