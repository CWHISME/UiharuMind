# 并行群聊调度（唤醒边界 + @ 路由 + 主持人点名 + 实时广播），与串行并存

群聊新增**并行**调度模式，与现状的**串行**（一圈即停 + 手动继续）并存，建群时选、运行中可调。
并行 = 方案 §3.2 的完整调度在投递架构（ADR 0046）下的翻译：被唤醒的成员并发开跑、
**任一成员发言即时广播给正在跑的成员**（走插话通道）、停止条件可选（保守自动挂起 / 激进手动停）。
解决串行一圈 = 三人之和的实测慢；保留串行给「审阅节奏」场景。

> **状态**：accepted（v2：由「滞后一轮」修订为「实时广播」），**已实现**（2026-09-26，实现期补定的细节见文末
> 「实现时定下的」）。成员审批进群视图（顺序 4）不随本 ADR 做；私聊已在 `1ad06216` 落地（`GroupMemberTurnGate`）。

## 决策

1. **调度模式是群的一个新属性**，与群类型（智能体/普通群，ADR 0042 建时定死）是两根轴：
   **串行群聊**（现状：成员按顺序一人一轮、一圈即停、手动继续）与**并行群聊**（本 ADR）。
   建群时选，运行中可切换——**当前圈跑完、下一轮起生效**，不打断进行中的轮次。
2. **并行语义（实时广播）**：被唤醒的成员并发开跑。任一成员完成发言**即时 append** 进群流水，
   并**即时广播给正在跑的成员**——他们反正开着，走注入队列在安全点插话（与用户插话同一条通道，
   ADR 0046 决策 3 的「跑时注入」）；**没在跑的成员不被叫醒**，下一轮自然看到（守住账单）。
   投递两种形态（合成一条 / 跑时单条插话）不变，**换并行只改调度、不改投递**。
3. **唤醒边界**（方案 §3.2 原文，按成员数分流）：
   - **大群（成员 ≥3）**：用户发言唤醒 **被 @ 者 + 主持人**；成员发言不自动唤醒别人
     （等主持人点名或用户 @，但**正在跑的成员**会经决策 2 实时收到）。
   - **小群（成员 ≤2）**：用户发言**全员**唤醒；成员发言 → 另一成员必答一次（§6.1）。
   - **无主持人**（见决策 4）：退回「用户发言全唤醒」，接受账单更高，换取简单语义。
4. **主持人**：群内成员中可选一位，建群弹窗指定；默认**无主持人**。
   有主持人且用户发言未 @ 任何人时，主持人的**默认动作是点名，不是自己回答**
   （方案 §3.2 v3 冷启动规则）。v8 §6.4 初春的主持职责是这个人设面，调度只认「群里有主持人」这个位。
5. **@ 路由**：文本语法——输入 `@名字`，字面保留在消息正文里（成员看得见自己被点）。
   不做预算注入（§3.4 已砍；动态状态不进系统提示，与 ADR 0048 同一口径）。
6. **停止条件（可选两档）**：
   - **保守**：广播后收到者都回应过、且没人再发新言 → 自动挂起；手动「继续」兜底（强制再跑一圈）。
   - **激进**：不做自动干预，让模型自己聊到自然停，用户手动点「停止」收场
     （§3.4「可见性优先、不做自动干预」的基调）。
7. **「这一轮」边界保持 ADR 0046 决策 4 原口径**：成员从被唤醒/收到投递到他自己产出一次群发言为止；
   实时插话只影响「看到什么」，不影响「这一轮怎么算」——被插话后他的回应就是他的群发言。

## 取舍

- **为什么实时广播而不是「滞后一轮」**：v1 写的是同圈快照、下一轮才见（批量回合），
  用户确认要的是「A 说完正在跑的 B 立刻看到」——这更接近真人群聊（谁先说完谁先发、
  正在说的人立刻能接）。事件驱动，不是批处理。
- **为什么广播只给正在跑的**：实时感的价值在「正在说的人能立刻接」，不是把睡着的人全部叫起来听；
  没在跑的人等下一轮，与真人群聊里「没看手机的人之后才回」是一回事。全员广播 = 账单爆炸 + 自激更凶。
- **为什么停止条件可选**：保守档防自激空转（两个模型互相 ping-pong 停不下来），
  激进档是纯放手 + 手动刹车。两档各自成立，不做默认自动干预（§3.4）。
- **为什么不底层拆多条 user 消息**：模板层事实——部分本地对话模板遇到连续 user 消息直接报错，
  合成一条正是为守 user/assistant 严格交替（ADR 0046 决策 3）。存储拆多条 + 供给再合成 =
  两处各写一套逻辑 + 存储与供给不一致的账。**视觉等价靠渲染层拆段**（`GroupDelivery` 标记 +
  按 `[名字]: ` 前缀拆成多个左侧气泡，头像/名字都在），存储与供给一字不动。
- **为什么并行与串行并存**：两种模式服务不同场景——串行 = 审阅节奏，并行 = 发散 + 快。
  不是替换关系，建群时选、可自由调整。
- **为什么直接做完整调度、不做中间态**：用户判定，一点点改只会越来越麻烦；投递从一开始就做好，
  换调度不动投递。
- **为什么唤醒边界依赖 @ 而不是全员**：账单——标准会审每轮 4 次最强模型不可接受
  （方案 §3.2 v2 修订）。
- **为什么不叫「异步群聊」**：系统里「异步」已被**异步委托**占用（ADR 0025）。叫**并行群聊** / **串行群聊**。

## 与现状的关系

- 串行路径保留为一种模式（`SerialGroupScheduler`），不是退役。
- §3.2 伪码的「预算注入：剩余轮次 / 预算 %」**不做**——§3.4 已砍自动干预，只留面板可见性。
- 黑板时代伪码（§3.1 统一 inbox、blackboard.append）不照搬：投递进成员会话（ADR 0046）已经是
  per-member 的天然 inbox，唤醒边界只决定「这一轮谁拿到投递」。

## 实现时定下的（2026-09-26 会审拍板）

原「未定」里前两条与几处含糊，落地前定死：

1. **成员的 @ 也叫醒人**，不只主持人。否则成员之间没法直接追问，主持人成了唯一引擎。
2. **保守档 = 一跳防护**：被**成员**发言叫醒的人（小群必答、成员 @），他的回复不再叫醒任何人；
   用户与主持人引起的唤醒不受限。小群因此是一问一答即停；激进档去掉这条，只靠手动停。
   没有这条时，决策 3 小群的「另一成员必答一次」会无限来回，决策 6 的两档在大群里也分不出差别。
3. **用户 @ 了人就只叫被 @ 的**，不再捎上主持人：主持人的活是冷启动点名（决策 4），用户已经点了名就用不着。
   决策 3「被 @ 者 + 主持人」按此收窄。小群不看 @，照旧全员。
4. **主持人点完名、被点的人说完，不再叫醒主持人**，等用户下一句（省一次调用；要追问主持人在点名时一并说）。
5. **主持人建群时选，右栏可改**（原定「不可改」，已由 ADR 0048「实现时的修订」第 2 条改掉）：身份写在各成员系统提示的场景段里，
   改了各自下一轮开跑时重建装配生效。冷启动规则（用户这句没 @ 任何人时先点名）另在给主持人的投递末尾附一句——
   只在那一刻成立，是动态状态，不进系统提示。
6. **一波**：并行没有「圈」。用户发言（或点「继续」）开一波，没人在跑、也没人待叫醒即结束——保守档的自动挂起就是这么来的。
   模式与停止条件在开波时定格，运行中切换下一波起生效（决策 1 的「当前圈」即当前这一波）。
   「继续」在并行里叫醒所有还有新话没听的成员（按用户叫醒算）。
7. **在跑的人又被点到**：广播已把那句插给他，他这一轮的回应就算数（决策 7）；只有那句**没被消费**
   （他已在最后一次调用里）时，这一轮结束后再叫他一次。
8. **插话收尾撤回**（串行也受益）：一轮结束时把注入队列里没被消费的插话撤回来，由游标下一轮随投递补上。
   不撤的话它留到下一轮第一次调用才被取走，紧跟新投递成连续两条 user——正是决策 3 合成一条要守的东西。
9. **串行不认 @、不看主持人**：本来就人人轮到。@ 语法与主持人说明照样写进场景段，切到并行时直接生效。
10. 文本 @ 解析：`@` / `＠` 后接成员名，名字从长到短比（「白井黑子」不被「白井」吃掉），不区分大小写；不做特殊渲染。
    输入框有 **@ 补全**：群里光标前是 `@半个名字` 就弹成员列表（前缀命中在前、名字中间命中在后），采纳只换那半个名字。
    与 `/` 技能补全共用一个列表——输入框补全抽成 `ICompletionSource`（`SkillCompletionSource` / `MentionCompletionSource`），
    `CommandPaletteViewData` 只管列表、键盘导航与写回。

11. **一轮里每次说完都是一条群发言**（2026-09-26 实测后补，修订 0046 决策 4「这一轮最后的回复正文」）：插话让一轮说好几次话——
    模型答完，框架发现注入队列里有新发言，接着再调一次模型。只取最后一条的话，前几段只留在成员自己的会话里
    （实测五人并行群里多数回复这么丢了）。判据是助手消息有正文且不带工具调用，每次服务调用落盘即进群、即广播
    （`GroupMemberReplyFeed`）；SendMessage 发的以工具发的为准，它所在那条消息带工具调用、按定义不算「说完」，
    之后每次说完照常进群（2026-09-28 修订，见 0046 同名修订：原口径跨消息去查，吞掉了本轮最后那条结论）；
    被停或失败时已说完的几段照常算。
    模型照着投递格式自加的 `[自己名字]:` 在**落盘前**就剥掉（`SessionChatHistoryProvider` → `GroupTranscript.StripOwnPrefix`），
    成员会话里存的是干净的一份，他下一轮不会在自己历史里看到再学；界面另有 markdown 防误吞兜底（`MarkdownDefinitionGuard`）。
    广播进来、模型还没消费的发言在成员会话输入框上方合成一行（「群里新话 N 条，等他接收… 最新：…」，全文进提示；
    逐条列会在插话多时把会话区挤没，用户自己的待发插话仍逐条列、高度封顶滚动）：
    执行者公开 `PendingInjections` 与变更事件，界面据此对账——群轮不经界面插话，界面自己记不到。
    带工具调用的正文（「先查一下」这类过程话）不进群。模型有时把对群说的话写成调工具前的开场白（2026-09-27 实测），
    于是场景段明说「调用工具时顺手写的话只留在你这里，群里看不到；要对大家说的，等工具用完再说」；
    进了群的那条盖 `_groupPosted` 标记（轮末有标记就整份重存一次），成员会话里在时间旁挂「已发到群」，
    过程话与私聊回复不挂，一眼分得清哪些大家看到了。

12. ~~**保守档的实时广播按唤醒边界收窄**~~（2026-09-26 加，**2026-09-27 撤回**，回到决策 2「正在跑的成员实时收到」）：
    当时为治五人保守群满屏「我也收住」，把成员的话只插给唤醒边界点到的人。实测代价比预想的大：
    在跑的人（尤其是一轮要改几分钟代码的）看不到同伴刚说的话，同伴明说支持他的方案他也不知道，界面上看着就像插话丢了。
    连环接话的根子是模型没有不说话的选项，这一点第 13 条已经单独补上，于是撤掉收窄：成员的话照旧插给所有在跑的人，
    两档在插话上一致；叫醒仍按唤醒边界，一跳防护照旧，「跑着时被成员点到，他接下来说的按第二跳算」保留。
    `IGroupScheduler.ShouldInject` 随之删掉（各实现恒为 true，留着是空抽象）。
    **若满屏接话复现**，备用刹车：因一条没点他名的插话而多说的那句，只进群、不再插给别人（最多一跳）。
    要细抠它对「他后面那句正式回复还能不能点名叫人」的影响，所以真复现了再上。
    （2026-09-28 复现，改用「说完即封口」治，见文末修订：不让那句多说的话产生，而不是产生了再拦。）
13. **可以不接话**：场景段告诉成员「没什么要补充时只回复 `[跳过]`，不会发到群里」（`GroupTranscript.PassReply` / `IsPass`）。
    模型本来就想收住，只是每句回复都会变成群发言，它没有不说话的选项。它靠模型配合；第 12 条撤回之后，它是收住连环接话的主要手段。
14. **被打断的成员，「继续」叫得醒**（2026-09-27 实测后补）。实测：嫌模型慢，停下一位成员、换了模型，群里点「继续」叫不回她——
    投递开跑前就交给了她、游标已推过去，「继续」只叫还有新话没听的人（串行同理，没新话即跳过）。
    现在群轮被停或失败（`RunTurnAsync` 返回未完成）的成员记进 `_interrupted`；「继续」时 `HasNewLines` 对她恒真，
    没有新话就交一句 `GroupTranscript.ResumeNote`（接着做完；已经做完的把结果跟大家说一句——她可能已在私聊里做完，那份结果群里没人看见）。
    有新话就照常投递，标记随这次叫醒一并清掉。只在内存里，重启即丢；那时在群里 @ 她一句即可。

**代码结构**：`GroupChatCoordinator` 只留两种模式共用的投递、广播、群流水写入，实现 `IGroupTurnHost`；
每波一个 `IGroupScheduler`（`SerialGroupScheduler` / `ParallelGroupScheduler`）决定「谁、什么时候」；
唤醒边界是纯函数 `GroupWakePolicy`，@ 解析是 `GroupMentions`；一波的状态在 `GroupRun`，
一位成员一轮的插话与收尾在 `GroupMemberTurnState`。测试见 `ParallelGroupChatTests`、`GroupWakePolicyTests`。

## 修订：跑着时被点到按最近一跳，开跑后抛出也要收尾（2026-09-27）

Hello World 首跑里成员审代码审出来的两处，已对照代码核实并修掉（测试见 `ParallelGroupChatTests`）：

- **跑着时再被点到，来由按最近这一跳算**。原先只往弱里变，于是「被成员点到降为第二跳」成立，
  「被主持人点名算主持人叫醒」（`GroupWakePolicy`）却在他正跑着时失效：以第二跳在跑的人被主持人点名，说完仍叫不醒人。
  说完后补叫仍取攒下来由里最强的那个，两处取法写在 `EGroupWakeCause` 注释里。
- **登记「在说」之后任何一处抛出都要收尾**：撤回已插进去的插话、摘掉「在说」。原先只有正常路径摘，
  抛出时这一波里他一直算在说，广播还往一个没人消费的轮次里插，他下一轮开跑时连同新投递一起冒出来。
  并行调度出错时连同待补叫一起清掉。
- 读群流水的两处（主持人冷启动判定、回复进群判定）与追加同一把锁。⚠️ 回复进群那处的「下一段从哪算起」
  必须在贴完这一段**之后**取——成员的修复把它挪到了贴之前，一轮说两次时第二次被当成已发过而吞掉。
- **死波窗口**（二跑里成员审出）：调度器收场到宿主把这一波摘掉之间，用户发言会撞进已收场的那一波——
  广播没人可插、唤醒被拒，只落盘没人接，要等下次「继续」才补投；「继续」也会被当成重复调用静默落空。
  现在调度器报 `IsFinished`，`OnPosted` 回答接没接住（并行在算唤醒期间先占一份，不让这一波中途被判空闲）；
  用户发言与「继续」撞上已收场的波，就等它摘掉（`Episode.Removed`）再开一波。成员发言照旧：没有在跑的波就只落盘。
  串行最后一位收尾时来的插话若没赶上被消费，仍等下次「继续」补投（注释在 `SerialGroupScheduler.OnPosted`）。
  协调器这层的重试没有确定性测试：窗口只有一次续跑那么长，调度器那层钉在 `GroupSchedulerClosingTests`。

## 修订：说完即封口，激进档静下来补位一轮（2026-09-28）

实测（六人并行激进群「下一图的方案」，无主持人）：一句用户发言引出 16 条群发言、历时 15 分钟，
一句问用户的话被轮着在发言末尾再催了七遍；`[跳过]` 一次没用过。投递次数 OP-01 / L / 茵蒂克丝各 14，
御坂 3、食蜂 1——**旱的旱死，涝的涝死**。根子不在停止条件（插话本来两档一样），在续轮：
框架（`MessageInjectingChatClient`）模型说完时见注入队列非空就再调一次，不分插话来源。
于是在跑工具的人一直被同伴的发言续着说，说得越多同伴越有话插给他；大群里没被 @ 的人一个都不叫。
第 13 条「靠模型回 `[跳过]`」这次全靠不住。

1. **说完即封口（只并行）**：成员每说完一段（回复不带要执行的工具调用）、交回注入层之前，
   `ServiceCallSignalingChatClient.Finishing` 报一声，群轮（`GroupMemberTurnState.SealAsync`）不再收插话，
   并把队列里还没被带走的群插话撤回。注入层看到空队列就不续轮。
   - 他调工具期间的插话照旧在下一次调用里带给他——第 12 条撤回时要保的「跑几分钟代码的人看得到同伴」不变。
   - 撤回的点了他名：走第 7 条「没被消费就补叫」；没点他名：游标下一轮随投递补上。
   - ~~用户在他会话里的私聊插话不经群轮登记，照旧续轮~~：与代码不符，私聊从不插进群轮。现口径见 ADR 0063：私聊抢占群轮，私聊完接回。
   - 串行不封：本来人人轮到，没有谁被续着一直说。
   - 执行者侧只开一个与群无关的口（`ICharacterRunner.ReplyFinishing`），群轮整轮持有轮次闸，不会串到私聊那一轮。
   - 承重的框架行为钉在 `ServiceCallSignalTests`：不撤就续一次、在说完那一声里撤就不续，流式与非流式都测。
2. **激进档静下来补位一轮**（`GroupWakePolicy.ForCatchUp`，来由 `EGroupWakeCause.CatchUp`）：
   这一波没人在跑、也没人待叫醒时，先给还有没看过的发言的成员各补一次再收场；这一波没跑成过的（失败、被私聊占着）不补，
   失败多半还会再失败，交给「继续」。每句用户发言补一次（用户再发言清掉）；补位里的 @ 照常按唤醒边界叫人。
   投递末尾带 `GroupTranscript.CatchUpHint`（没新角度、或只是想再催谁，就回 `[跳过]`），界面随每轮重锚一并不画。
   **补位不看他说没说过话**：没主持人时人人开头都说过，只补没说过的就谁也补不上。
   保守档不补——一问一答、用户来收。于是两档的差别从「@ 接力能传几跳」扩成：
   保守 = 被点名只回应一次，省；激进 = 可以一直互相点名，静下来时人人再看一遍全程。
3. **场景段按「一个意思只说一次」重排**：原先「没新东西别说」分四条说（各人角度、不复述、别催用户、`[跳过]` 与不必表态），
   「一轮怎么算」分三条说（过程话群里看不到、`PostToGroup` 用法、说了要查就查完），同一个意思说几遍，模型反而分不出哪条最要紧。
   合并成：格式 / 尺度 / 一轮怎么算（只 agent 形态有，普通形态没工具不提）/ 只说新的（含「已经有人问了用户、正等着回答的事别再催」）/
   不接话，外加草稿目录两条。新进的规矩与实测依据：别再催用户（首跑七遍）、别人正在查在核的不再查（首跑四个人核同一份事实）、
   说了要查就在这一轮查完（二跑里「让我去翻一下」成了她这一轮的全部发言）。`PostToGroup` 那句「其余正文不重复贴」工具说明与返回里已有，删掉。
   补位提示只留这一刻的事实（这一波说完了、有新角度就说、没有回 `[跳过]`），不再重复场景段的规矩。
4. **发言预算暂不做**：封口之后能一直聊下去的只剩成员明着互相 @，那正是激进档要放开的（决策 6「不做自动干预」）；
   补位本身有上限。两人小群激进档的互相必答仍会一直来回，这是现状、封口没让它变坏，用户可停。
   **若激进档实测停不下来**，备用刹车：每人每句用户发言一个宽松上限（如 8 轮），只防失控、不控节奏；
   用户与主持人点名不受它拦。
