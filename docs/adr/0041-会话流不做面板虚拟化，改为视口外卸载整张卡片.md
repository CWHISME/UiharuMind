# 会话流不做面板虚拟化，改为视口外卸载整张卡片

决定：**会话流继续用非虚拟化的 `ItemsControl`，容器一个不少**；但给容器补上
「滚远一屏以外就把这张卡整棵丢掉、只留一个**等高**空占位」的那一半。滚动区高度因此分毫不动，
跟底、滚到顶续窗、前插补偿三条路径一行都不用改。

> 第一版只卸「气泡正文」，留着卡片外壳。那一版的两个教训都写在下面：
> 装回不能指望气泡自己的视口通知（**用户消息会永久变空白**），
> 以及外壳才是剩下的大头。现在收整张卡，两个问题一起没了。

同时收紧两处常驻：TextMate 注册表全进程共用一份，窗口缓存补上全局上限与空闲淘汰。

## 现场

一个跑了约五小时、然后一直放着不动的 Debug 进程，`phys_footprint` **921MB**（峰值 1039MB）：

| | |
|---|---|
| 托管堆已提交 | 475 MB（gen2 存活 410MB、LOH 47MB，碎片只有 4MB） |
| MALLOC_SMALL / LARGE | 236 MB |
| graphics + IOSurface | 96 MB |

已提交 475MB 对存活 410MB——**GC 没浪费，是真的有 410MB 活对象**。

把 gcdump 的 485 万个对象按归属分桶：

```
200.8 MB (48.9%)  System.*      52万 string / 18万 字典桶数组 / 24万 int[] / 21.8万 byte[]
129.1 MB (31.4%)  Avalonia      UI 树、样式、渲染
 31.7 MB ( 7.7%)  TextMateSharp
 13.5 MB ( 3.3%)  Svg/Skia
 10.9 MB ( 2.6%)  ML.Tokenizers
  1.7 MB ( 0.4%)  UiharuMind    ← 自有数据几乎不占
```

**吃内存的不是数据，是渲染数据的控件树**，而那 200MB 的 `System.*` 绝大部分也是
Avalonia 的属性存储（`StyleInstance` 9.5 万、`StyleClassActivator` 9.9 万、
`DynamicResourceExpression` 9.6 万、`WeakReference<AvaloniaObject>` 16 万）。

关键计数：**3 个 `ConversationView` / 17 个 `ConversationViewModel`**（14 个是后台会话，
已被 `TrimToBackgroundBudget` 裁到 10 条），实化出的卡片 205 张，
对应 **16,018 个 `CompositionDrawListVisual`**——**每张卡约 78 个可视对象**。

空闲本身没问题：40 秒 idle 采样只有 1 次 `AllocationTick`、9 个 GC 事件。
**不是放着不动涨上去的，是用过之后没降下来。**

## 为什么仍然不用虚拟化面板

`ConversationView.axaml` 的注释早就写着「已实测不可用」，这里补上源码依据：
虚拟化面板的 `Extent` 是按**已实化项**估算的，不定高气泡下估值一直在变，
于是进度条跳变、滚动回跳、与跟底互搏。而本仓的滚动语义全部建立在
「Extent 是真实测量值」之上——`AnchorToBottom` 迭代贴底、`PrependKeepingViewport`
按前插高度补偿 Offset、`OnViewerScrollChanged` 判 `Offset.Y` 续窗，三条都要求 Extent 可信。

**换个说法：真正要省的从来不是「容器」，是容器里那棵树。**
205 张卡对应 16,018 个可视对象，容器本身只占 205 个。把容器虚拟化掉是为了省那 205 个，
却要赔上整套滚动语义——不划算。

## 等高占位：省了树，留住高度

原本只有「进视口才建」（`SimpleMarkdownViewer` 的 `RealizeNow` / 视口通知驱动的排队），
建出来之后就一直留着——一窗 80 条全滚过一遍，80 份完整视觉树就全挂在列表上。
现在补上反向的一半，做在**容器**（`ContentPresenter`）这一层：

- `Height` 钉成**刚刚量到的那个高度**；
- `Content = null`，`ContentPresenter` 在下一次布局里把整棵子树摘掉丢弃；
- 装回就是把 `Content` 放回去、清掉占位高度，模板重新实例化一份。

容器在竖排里横向本来就拉满，所以**只有高度需要钉**。这一点顺带避开了第一版的坑：
那时占位做在气泡上，两个子块一收控件宽度就塌成 0，而 `Rect.Intersects` 对零宽矩形恒为 false
（`rect.X < Right` → `x < 0`），连带气泡外层 `ScrollViewer` 的 presenter 也塌成零宽、
把视口矩形裁成空——**通知既不会再来，来了也判不出「看得见」**。那条「滚回来就装回」的分支
于是是死代码，装回全靠清扫；而清扫走的 `RealizeNow()` 只认 markdown 一档
（`Realize()` 对纯文本档直接 return false），**用户消息恒为纯文本档**
（`TextMessageCardView` 的 `IsPlaintext` 绑定里 `IsUser` 一项就够），
表现就是滚远过的每条用户消息都变成一段等高空白。

收整张卡之后这类状态机整个不存在了：卡片在不在，只看容器有没有 `Content`，
没有第二处状态可以不同步。回归测试 `ScrollingBack_ReloadsBubbles_PlaintextIncluded`
留着看门（**混排**才测得到，只用 markdown 条目全绿）。

**装回之后要当场补一次布局再转 markdown**：刚放回的 `Content` 此刻还只是个对象，
视觉树要等布局才长出来；不补这一下，用户会先看到一帧原文再变 markdown。

## 判距离为什么在宿主，不在气泡自己

查了 Avalonia 源码（`LayoutManager.CalculateEffectiveViewport`）：

```csharp
if (control != target && control.ClipToBounds)
    viewport = control.Bounds.Intersect(viewport);
```

视口矩形被**每一个 `ClipToBounds` 祖先**求交，而 `Rect.Intersect` 无交集时返回 `default`。
所以气泡一滚出去，它拿到的矩形就是空的——**只看得出「看不见了」，看不出「离多远」**。
更要命的是同一处的抛事件条件：

```csharp
if (viewport != l.Viewport) l.Listener.RaiseEffectiveViewportChanged(...);
```

矩形不变就不抛。远处那些一直是 `default`，再怎么滚也收不到通知。

因此：`SimpleMarkdownViewer` 只提供**动作**（`UnloadForViewport()` / `RealizeNow()`），
「离多远算远」由持有 `ScrollViewer` 的那一侧判，收在 `ConversationCardViewport` 里——
用 `TranslatePoint(default, Viewer)` 换算，实化与卸载共用同一套几何（原先各写一份，
已经是一份重复）。上下各留**一整屏**缓冲：贴着视口边缘卸载，轻微滚动就会来回拆建，
而重建是要钱的。

## 清扫本身不能贵

清扫是**每帧**可能跑一次的东西，做法稍微随便一点就把省下来的又花回去。两条：

- **按容器走，不翻整棵树。**`MessageList.GetVisualDescendants()` 要遍历整表几千个可视对象，
  而容器只有条目数那么多，容器里那个气泡认准一次就记下来（非文本卡记 `null`，一样不再往里翻，
  它们恰恰是最深的那几棵树）。实测 60 条带代码块的会话（Debug/无头）：
  翻整棵树 **1.86ms**，按容器 **0.17ms**。
- **只有视口真挪过才清扫。**`ScrollChanged` 在**只有 extent 变化**时也会来——流式期间每来一段
  正文都发一次，而那不改变任何气泡与视口的距离。改为只认 `OffsetDelta` / `ViewportDelta`，
  跟底那一路 offset 会跟着动，照样清扫。

## 量到的数（`ConversationViewLayoutTests`，无头真实控件真实模板）

60 条带代码块的回复，全部实化后放清扫过去跑一遍：

| | 正文可视对象 | 整表可视对象 | 滚动区 |
|---|---|---|---|
| 全部实化 | 1860 | 3663 | 15020px |
| 只卸正文（第一版） | 540 | 2343 | 15020px |
| **收整张卡** | **155** | **363** | **15020px** |

整表掉到 **10%**，而**滚动区高度三者一模一样**——这是这条路子唯一的验收口径，
测试里它是第一条断言。

代价在「翻很远再回来」那一下：装回一张卡要重跑模板与样式，比只重建正文贵。
一屏一屏翻（Debug/无头，60 条混排）：

| | 局部来回滚（中位） | 整段翻回来（中位） |
|---|---|---|
| 只卸正文 | ~0ms | 14.9ms |
| 收整张卡 | **0.1ms** | 28.1ms |

**日常那种小幅来回滚一分钱不花**——一屏缓冲整个吸收掉了，只有真的翻过一整屏以外再回头
才会付那一下。为此再分「近处只卸正文、远处收整卡」两段不值得：省下来的是很少发生的那一半，
换来的是两套机制常驻。

## 为什么页面还是常驻，不从树上摘下来

顺着「切走的会话怎么清」往下想，自然会问：换页时干脆把页面从视觉树上摘掉？
（`MainView.RefreshActivePage` 现在**只切可见性**，页面视图首次使用后常驻，
换页不触发 `Loaded`/`Unloaded`——注释里写着理由是避免重挂时重新套样式与布局。）

量了才知道差多少。60 条会话的那一页（此刻只剩 363 个可视对象），Debug/无头：

| | 让出 | 回来 |
|---|---|---|
| 只切可见性 | 0.1ms | **0.3ms** |
| 摘下再挂回 | 9.7ms | **115.9ms** |

而且**挂回来会丢掉阅读位置**：`Loaded` 会重跑一遍落位，视口直接回到底部——
用户翻到一半去看别的页，回来就找不着地方了。

所以维持常驻。这条同时回答了「要不要给隐藏挂个钩子把卡片全收掉」：
收整张卡之后，一页会话常驻的本来就只剩容器占位加视口那几张，
再引一套可见性机制（`IsEffectivelyVisible` 的变更事件是 `internal` 的，
应用层只能逐个祖先盯 `IsVisible`，或者让壳层反过来通知）不值当。

## 还剩什么

清扫之后剩下的 363 个可视对象里，绝大部分是**容器自己**（60 个 `ContentPresenter` 占位）
加视口里那两三张真卡。要再往下省就只能动容器，那就是面板虚拟化——而 Extent 必须是真实测量值，
这条路开头就否掉了。

## 顺手收紧的两处常驻

**TextMate 注册表（31.7MB）**：`TextMateSyntaxService.Install()` 原本每次
`new Registry(...)`。而 `SyncRegistry` 把用到的每份 raw 语法树与编译后的规则表整套挂在
自己身上，一份语法还会连带拉进它 include 的所有 scope——堆里同时活着 4~5 份时，
光 `Raw` 就有 16MB（18.2 万个对象）。改成 `TextMateRegistryPool` 全进程一份。
`RegistryOptions` 也只建一次：构造它要扫一遍全部语法的 package.json，
而它的主题参数只是**默认**主题，换主题走 `LoadTheme` 即可。

（注：`LiveMarkdown.Avalonia` 自己还有一份静态 `Registry`，是库内部的，动不了。）

**窗口缓存**：原本只有「按类型限量 2」，而窗口类型有十几种——实测 10 扇原生窗口活着，
每扇带着自己的完整控件树和一块 GPU 表面，96MB 图形内存基本就是它。
补上全局上限（4）与空闲淘汰（10 分钟）。空闲淘汰是其中唯一对「放着不动」有效的那条：
前两道闸只在「又关了一扇」时才触发，应用放着不动就永远不收。

## 还留着什么

- `ConversationViewLayoutTests.ScrollingFarAway_UnloadsCards_WithoutMovingTheExtent`：
  Extent 恒定是第一条断言。哪天它红了，说明等高占位的前提破了，别去调阈值。
  同一条里还钉着「容器一个不少」——那是「不做面板虚拟化」的另一半。
- 开发脚本（`--dev-script`）驱动真实应用只能验「没变坏」，**验不了这次的收益**——
  它没有滚动这一步，而收益只在滚过之后才出现。真实进程里的前后对比得靠手动跑，
  或者给脚本补一个 `ui.scroll`。

## 已知的边角

- 占位态的卡片丢掉**只存在于控件上**的那几样，滚回去都是重建的：文本选区、
  卡片内嵌 `ScrollViewer` 的滚动位置（旁白正文、工具卡的参数/diff/结果、审批卡的 diff）、
  以及键盘焦点。展开收起状态不受影响——`IsExpanded` 在条目 ViewModel 上。
- 卡片重建会重跑 `DiffTextBlock.Rebuild()` 与 `HoverDeferredContent` 的惰性实例化。
  两者的订阅都是成对的（`OnAttachedToVisualTree` / `OnDetachedFromVisualTree`），不漏；
  重建的只是计算。
- 窗口宽度变化会让占位高度过时（文本重新断行）。占位不会立刻跟上，
  而是等它重新进视口实化时自然取回真实高度——期间 Extent 略有偏差，
  代价落在「改窗口大小」这个本来就在重排整棵树的操作上。
- 流式中的那条消息永远在底部视口内，不会被卸载；只有用户上滚很远时它才会，
  那时跟底本来就已经关了。
