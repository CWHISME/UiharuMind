# 思考回填按助手消息顺序匹配，请求侧键名与响应观测解耦

> **状态**：accepted（2026-10-28）。
>
> **起因**：CommandCode 网关报
> `Missing required parameter: 'messages[8].reasoning_content'. This model needs the reasoning of
> every earlier assistant message`。日志里的请求体（`Bodies.txt`）显示：带 tool_calls 的三条助手消息
> 回填了 `reasoning`，而第 8 条纯文本回复**一个字段都没有**——同一份历史每轮重发都死在同一处，
> 6 次报错全是 `messages[8]`。

## 背景

思考回传的既有机制（见 [ADR 0093](0093-思考回传字段名动态探测与roundtrip三态化.md)）：

- `LazyChatClient` 按 **tool_call id** 收集思考正文，`OpenAICompatibleRequestRewriter` 在字节层按 id
  匹配回填；
- 补空串只对带 tool_calls 的助手消息生效；
- 回填键名取 `EffectiveThinkingField`：**运行时观测值** → 预设表 → `reasoning_content`。

三个前提实际都不成立：

1. **有些服务端要的是每一条助手消息**。纯文本回复身上没有 tool_call id 可挂，
   按 id 索引的数据结构根本表达不了它——**匹配方式是硬伤，与「要不要全量回填」是两件事**。
2. **要求是按模型的，不是按供应商/网关**。同一个 CommandCode：
   `deepseek/deepseek-v4.1-flash` 跑了 88 次请求、105 条无思考的纯文本回复全部通过；
   `reflection/beam:free` 连纯文本回复都要求。按网关整类开启是过度修正。
3. **响应字段名 ≠ 请求字段名**。该网关的响应给 `reasoning`，请求体里只认 `reasoning_content`。

## 决定

1. **数据源改成按助手消息出现顺序索引**：`CollectReasoningByCallId` → `CollectAssistantReasoning`，
   返回「第 N 条助手消息 → 思考正文（可为 null）」的列表。`PendingReasoningSource` 挂的就是即将发给
   SDK 的那份 `messageList`，顺序天然一一对应；`ScanMessage` 补上 `role` 判断，按序取。
2. **有正文就发，不挑消息**：工具调用之外的纯文本回复也把当时的思考带回去。
   各家的校验口径不同（DeepSeek 只查带 tool_calls 的、网关连纯文本都查），
   **全都带回去就同时满足所有口径，不用去猜这一家要哪一种**。
3. **只有一个布尔管「没正文时字段能不能缺」**（`RequestRewrite.FillEmptyReasoning`）：
   为真时每一条助手消息都带字段，没正文补空串；为假时只发历史里真有的。
   判定 `BaseRemoteModelConfig.RequireReasoningOnEveryAssistantMessage` 三个来源：
   预设表声明、从服务端 400 里学到（`ReasoningEveryAssistantModelIds`，按 ModelId 分开记）、
   模型 ID 含 `deepseek` 的兜底。与思考档位无关。
4. **「学到」的路径**：`ReasoningRequirementErrorHandler` 认出这条 400 →
   把当前 `ModelId` 记进配置并落盘 → 整段重发一次。重发是全新的 SDK 调用，请求体按新配置重新改写。
   与 `MaxTokensErrorHandler` 的自愈同口径；换端点时随观测值一起清空。
5. **请求侧键名与响应侧观测解耦**：`EffectiveThinkingField`（观测 → 预设 → 默认）
   换成 `RequestThinkingField`（预设 → `reasoning_content`）。`ObservedThinkingFields` 保留，
   但只作为**响应侧记录**（诊断、编辑窗口改端点时清理），不再决定发出去的键名。

## 与 opencode / pi 的对照

两家参考实现的写法（`F:\Studys\AI\opencode`、`F:\Studys\AI\pi`）：

| | 有正文时的范围 | 没正文时 | 键名 |
|---|---|---|---|
| opencode | 每条助手消息 | `requireReasoning`（布尔，默认：配了 reasoningField、或 provider/端点/模型 ID 是 deepseek）→ 补空串 | `compatibility.reasoningField` → 消息自带 observedField → `reasoning_content` |
| pi | 每条助手消息（`nonEmptyThinkingBlocks` 非空才回放） | **完全不补** | 思考块自带的字段名 + `opencode-go` 特判 |
| 本文 | 每条助手消息 | 布尔，默认 deepseek 系 / 预设 / 学到 → 补空串 | 预设 → `reasoning_content` |

对齐的点：**范围统一成「每条助手消息」**（两家都这么做，也印证了按 tool_call id 索引是错的）；
**空串补全收敛成一个布尔**（opencode 就是 `requireReasoning: boolean`，本文第 3 条与之同构）。

有意不跟的两点：

- **pi 完全不补空串**：它只在有思考时回放，所以碰到「字段必须在」的服务端会直接 400。
  本文保留补空串，因为已经实测到这条 400（ADR 0093 也记过 DeepSeek 的同类）。
- **键名不用响应观测值**：两家都优先回放观测到的字段名。本文固定 `reasoning_content`——
  我们的实测是网关报错点名 `reasoning_content`，而观测名 `reasoning` 在 tool_calls 消息上没被拒
  （两种假设下固定 `reasoning_content` 都成立，回放观测名只在第二种下成立）。
  请求侧确实收别的名字的服务商，在预设表里写 `ThinkingField`。

## 取舍

- **按序匹配 vs 按 tool_call id**：id 免疫顺序漂移，但表达不了纯文本回复；按序能覆盖全部助手消息，
  代价是依赖「一个 ChatMessage ↔ 一条 wire 消息、顺序不变」。实测成立（请求体与历史逐条对得上），
  且挂进 `PendingReasoningSource` 的就是同一份列表，中间没有重排的环节。
- **有正文就发 vs 按需才发**：按需要先知道服务端属于哪一类，而这条要求按模型、还可能是网关私有的校验；
  猜错的代价是 400（整轮失败），多发的代价是 1–6% 输入 token（见下）。选前者。
- **学 vs 写表**：目录里几十个模型补不出表，且同一网关下不一致；服务端亲口说过一次比猜准。
  代价是新模型第一次会失败一轮，之后不再失败。

## 已知代价

- 观测值不再影响请求：万一某个服务商<b>请求侧</b>确实只收 `reasoning`（响应也是 `reasoning`），
  得在预设表里显式写 `ThinkingField`。目前没有已知实例（商汤自研 6.8 是 `reasoning`，但它
  `ReplayExistingReasoning=false`，本来就不回传）。
- **纯文本回复的思考现在也发**：实测 deepseek-v4-flash 的 55 条会话上这部分约占请求体 1.0%，
  277 条的 agent 会话上约 5.8%（思考整体占 18–49%，那部分是工具调用链上原本就在发的）。
- **DeepSeek 系在 None 档也会补空串**（原先按思考档位跳过）：这是合并成一个布尔的直接后果，
  与 opencode 一致；代价是关思考时每条助手消息多一个 `"reasoning_content": ""`。
- 改口径会让该会话的服务端前缀缓存**失效一次**（请求体字节变了，缓存按 token 序列匹配），
  下一轮按新前缀重建。实测：改后首轮 61022 输入只命中 5120，次轮 61407 命中 60416（98%）。
- `EveryAssistant` 学到之前，该模型会先失败一次（一次请求，无输出）；学到之后所有请求都带字段。
- 顺序匹配依赖 SDK 不丢/不重排助手消息；真出现漂移，表现是「思考配错消息」而不是 400，
  排查靠 `Bodies.txt` 里逐条对。

## 本期不做

- 按「思考是不是目标模型产的」过滤历史思考（ADR 0093 已否决，理由不变）。
- `reasoning_details` 结构化思考的回传。
- 把「每条都带」做成界面开关：靠模型家族 + 自愈即可，用户不需要判断。
