# 工具卡内联预览上语法高亮，一次性同步tokenize

工具卡**就地展开的预览段**（参数区、结果区）上 TextMate 语法高亮；全文窗（`FullTextWindow`）
的高亮早已存在，本轮不动。卡片预览上色规则：

- **参数区**：**不上色**。参数原文是 `key: value` 扁平文本（`ConversationTranscript` 把调用参数
  拼成 `$"{x.Key}: {x.Value}"` 一行一个，`ArgumentsJson` 是历史遗留名）。参数值形态多样——
  路径、命令、甚至整段代码（Write 的 content），没有可靠语法能判断值是什么，上色只会添乱。
  整块 muted 灰字最稳。曾试过两条路都否掉：YAML 花哨、把键切成两段（`command` → `c`+`ommand`）；
  自研「第一个 `: ` 分键值」的专用着色，键灰/值黑对比突兀，值含代码时照样乱。
- **结果区**：只有「结果=文件正文」的工具（<c>FileToolNames</c> 白名单，目前仅 <c>Read</c>）
  按 FilePath 扩展名上色；回执类（Write）与非正文类一律纯文本。失败的 Read 结果（错误消息）也不上色。
  **判定用工具语义，不靠文案前缀猜**——回执文案将来随便改（本地化/换词）都不影响；白名单方向安全，
  新工具忘了声明就是纯文本，不会重现「同一回执随扩展名忽有忽无像 bug」。Edit 走独立 diff 面板
  （<c>ResultDiffLines</c>），其识别 <c>DiffLineView.ParseToolResult</c> 同样按工具名判（只收 Edit），
  不复用 "Applied " 文案前缀——两处都不留文本契约。卡片结果区与结果全文窗共用
  <c>ToolCallItem.ResultHighlightSource</c>。
- **diff 区**：不动——它已有增删配色，再叠语法色会打架。
- **渲染**：轻量**一次性同步 tokenize**，预览超限自动降级纯文本，配色跟随 TextMate 主题
  （DarkPlus / LightPlus），与全文窗、markdown 代码块同一套。
- 术语对口：预览（卡片）上色，全文（窗）上色，两处是同一支笔的两种落地。

## 为什么

1. **全文窗的高亮管线是现成的，内联段只需要另一半。** `TextMateSyntaxService` +
   `TextMatePreTokenizer` + `TextMateColorMapTransformer` 已经解决了「语言解析（扩展名 → scope）、
   主题生命周期、按扩展名认语言」。内联段短，不需要分帧，只要把「同步 tokenize 一次 + 查表上色」
   接到卡片上。高亮本身不是新造轮子，是复用。

2. **工具结果不是流式的，所以上色只需要做一次。** 结果唯一入口是
   `ConversationTranscript.CompleteCall` 的一次性赋值（`IsRunning=false` 与 `ResultText=…`
   同处），全文没有 `AppendResult` 路径；正文气泡有 `AppendContent` 而工具结果没有。
   这意味着**没有流式重绘、没有节流、没有增量失效**——Q7 那类「跑着的时候逐帧上色」
   的场景不存在，设计少了一整层复杂度。

3. **grep/glob 的结果天然不上色，不需要「工具名豁免」这条规则。** `GetFilePath` 只认参数里
   明写的路径键，而 Grep 的 `path` 是**搜索范围**（多为目录），`ResolveScope` 认不出目录扩展名，
   自然退化纯文本。豁免规则反而是过度设计：它引入「按工具名分支」的先例，会腐蚀
   「语言只由 FilePath 决定、不猜内容」这条既有原则。唯一例外是单文件搜索
   `Grep(path: "Foo.cs")` 会按 `.cs` 上色——内容确实是那个文件的行，利大于弊，行号前缀
   被染个假色，接受。

## 取舍

- **一次性同步 tokenize，而不是复用 `TextMatePreTokenizer` 的分帧泵。**
  预览已经被 `ToolResultTruncation` 封在 40 行 / 2KB，tokenize 成本有界；会话流没有虚拟化，
  为十几行文本起一个每帧时间片的调度器是杀鸡用牛刀。分帧泵的用武之地是全文窗那种
  几十万字。

- **不把预览段换成 `LongTextView`（AvaloniaEdit 内核）。** 每张展开的卡片 = 一个编辑器实例，
  一条长会话里几十张展开卡的内存与布局成本要拿真金白银换；
  预览段定位是「扫一眼」，块级选中复制交给 `SelectableTextBlock` 的 `Inlines` 保留即可。
  历史教训摆在那里：就地展开**全文**冻过 UI（ADR 0012），预览段要的是同一个警惕心，
  但不需要同一个内核。

- **不做结构性着色。** grep 命中那种「路径 / 行号 / 命中词分色」是另一回事（术语见
  CONTEXT.md「结构性着色」）：卡片现在只拿截断后的扁平字符串，没有结构化 `GrepToolResult`
  管道，为它建管道跟本轮不是一个量级。留作独立议题，将来做的时候再说。

## 代价（明说）

- 卡片上色是**纯 UI 侧**变更，没有 Core 改动，但观感无测试兜底（与 ADR 0012 同款风险），
  深浅两套主题要手测。
- 单文件 grep 例外（见上）会带一点行号前缀的假色，接受。
- **参数区不上色的取舍**：试过 YAML（键红值蓝、键被切成两段）、试过专用键值着色（键灰值黑
  对比突兀，且值含代码时照样乱），都不如纯文本。参数区定位是「扫一眼」，它不值得为装饰引入
  「值可能是代码」这层不确定性。参数全文窗（`ShowFullArguments`）仍按 `FilePath` 选语法——
  那也是一处历史遗留的不精确（参数文本不是文件内容），本轮不动，与现状一致。
- 结构性着色仍欠着，会在 grep 结果场景继续「纯文本 + 全文窗」的现状。
