# 磁盘布局按性质分树，旧布局就地废弃

应用数据目录从「一个 `SaveData/` 装所有东西」改成**四棵按性质分的树**，路径定义从
`SettingConfig` 搬进新的 `AppPaths`，并把制造杂物间的那几个 API 一并删掉。
旧的 `SaveData/`、`SaveLog/` **不迁移、不删除**，就地变成孤儿。

## 布局

```
~/Library/Application Support/UiharuMind/      (Windows: %AppData%\UiharuMind\)
│
├── Config/                              配置：丢了重配即可
│   ├── SettingConfig.json               15 个 TConfigBase，按类名自动落盘
│   ├── ChatSettingConfig.json           （AppPaths 不逐个登记，见下）
│   ├── …
│   └── Mcp/
│       ├── McpServers.json              服务器定义，对齐 .mcp.json 格式
│       ├── McpTrust.json                逐条授权指纹
│       └── McpServerStates.json         本地启停状态
│
├── Data/                                用户数据：删了就没了
│   ├── Characters/
│   │   ├── Overrides/                   内置角色的用户覆盖（本体在程序集资源里）
│   │   └── PromptSnippets.json
│   ├── Sessions/                        角色对话与 agent 对话共用
│   ├── Memory/
```

## 三条规则

1. **第一级按性质，第二级按功能。** 性质轴回答用户和运维的问题（备份哪个、磁盘满了删哪个），
   功能轴回答代码的问题（一个模块的文件在一处）。单用性质轴，第二级会重新变平；单用功能轴，
   `Agent/` 里会同时躺着不能丢的 `FileMemory` 和随时可清的 `Scratch`。

2. **性质轴只切到「用户真会对它采取行动」的粒度。** 没人会为腾磁盘去删一个 2KB 的状态文件，
   所以 `McpServerStates.json` 跟着 MCP 走而不是流放到 `Cache/`。`Cache/` 留给**大的或高频重写的**。

3. **文件名自带功能前缀，目录名不带。** 文件会脱离目录树出现在编辑器 tab、全局搜索结果、
   用户发来的截图里，那时 `Trust.json` 认不出来；目录永远在树里被看到，`Mcp/McpData/` 纯属重复。

## 为什么

1. **杂物间的成因是一个 API，不是命名。** 旧的 `SettingData/` 里混着 MCP 状态、定时任务、
   搜索历史、剪贴板历史——七个根本不是配置的文件。它们全都来自这一对签名：

   ```csharp
   public static void SaveRootFile(string fileName, object target)  // fileName 任意
   public static string GetSaveDataPath(string fileName)            // 名字还是错的，返回 SettingData/
   ```

   任何人拿一个字面量就能往配置目录落文件，**全仓没有一处记录这件事发生过**。反倒是那 15 个
   `TConfigBase` 文件一直是干净的——它们按类名自动落盘，不需要任何人手写路径。所以本轮删掉
   `SaveRootFile` / `LoadRootFile` / `GetSaveDataPath` / `GetSaveClipboardHistoryImagePath`，
   调用方必须显式选一棵树。**被逼着回答「这是配置、数据还是缓存」，正是防复发的机制本身。**

2. **`SettingConfig` 同时是配置 DTO 和路径注册表，两个职责都做不好。** 它有 13 个静态路径字段，
   其中 `SaveChatDataPath` 已经只剩注释里的引用。而真正的叶子目录名（`FileMemory`、`Scratch`、
   `Attachments`、`Skills`、`ApplicationUpdates`）散在五个文件的字面量里——**布局乱只能看磁盘
   才发现，看代码看不出来**。`AppPaths` 用嵌套静态类镜像磁盘层级，代码里挪一个属性等于磁盘上
   挪一个目录，两者不会各说各话。

3. **知识库向量库判定为 Data 而非 Cache，尽管它可再生。** 它的可再生是**有条件的**——依赖当初
   那个 embedding 模型还在、还是同一个；换了模型重建出来的向量和原来不在一个空间里，那不是
   「重建」是「结果变了」。而 `Cache/` 这个名字对用户的承诺是「随便删」，这里兑现不了。
   要给用户腾空间应该是设置里一个知道怎么重建的按钮，不是让用户自己去 `rm`。

4. **剪贴板的记录与图片合并到一棵子树。** 旧布局里 json 在 `SettingData/`、图片在 `SaveData/`，
   隔着两层。用户清剪贴板历史时是连图带记录一起清的，不存在只清一半的场景。

5. **`Config/` 下那 15 个文件不进 `AppPaths`。** 列进去的话每加一个配置类要改两个文件，
   而那 15 个属性永远没人读（读它们的是反射）。按类名落盘这套机制这些年一直好用，
   把它拆掉是在修一个没坏的东西。规则写在 `TConfigBase` 的注释里。

## 取舍

- **旧数据不迁移也不删除。** 老用户升上来等于全新安装：角色、会话、知识库、MCP 授权全部要重来。
  这是明知代价后的选择——本轮同时改了目录、文件名和扩展名，写一套只用一次的迁移表，
  收益低于它自己的出错面。**不删除**则是另一半：递归删用户数据目录的代码一旦进仓就会永久留在
  那里，任何一次路径常量写错都会变成事故，而它换来的只是省用户手动删一个文件夹。

- **模型与引擎收进 `External/`，但文件由用户手动搬。** 这一刀切的维度和上面三棵不同：
  上面按「丢了多贵」分，这一刀按「**谁在管这些字节**」——`Config`/`Data`/`Cache` 是应用生成、
  应用清理的，`External/` 里的是用户手放、应用只读的。代价明说：`LocalModelPath` /
  `ExternalEmbeddedModelPath` 是**存在配置里的用户可改路径**，配置一清就回落到新默认值，
  **升级后模型列表会是空的**，要把三个旧目录搬进 `External/` 才回来；引擎还要重新识别版本。
  这是明知代价的选择——写自动搬迁要处理数 GB 的跨卷移动与中断续传，风险高于让用户拖一次文件夹。

- **`EmbeddedModels/` 必须与 `Models/` 平级，不能收成 `Models/Embedding/`。** 后者读起来更整齐，
  但对话模型的扫描是 `SearchOption.AllDirectories`（`LLamaCppRuntimeService.cs:190`），
  嵌进去会让 embedding 模型混进对话模型列表；embedding 侧则是 `TopDirectoryOnly`，两边不对称。
  这条同时写进了 `AppPaths.External.EmbeddedModels` 的注释——踩坑的人不一定在读 ADR。

- **`AppPaths` 认识每一个功能，是一个刻意接受的耦合。** 只集中根（`AppPaths` 只出四个根，
  各模块声明自己的叶子）能避免这个耦合，代价是「磁盘布局长什么样」重新变成没有任何一个文件能
  回答的问题——而那正是本轮要修的病。七八十行的镜像类不至于变成上帝类，这笔交换值得。

- **动态文件名不进 `AppPaths`。** `{sessionId}.meta`、角色的 `{guid}.json`、剪贴板图片的时间戳名
  留在各自模块：它们是**命名方案**不是布局，而且是函数不是常量，列进来也做不到「一眼看全」。

- **`TConfigBase` 落盘补上了 `.json` 后缀。** 旧文件没有扩展名，用户双击打不开、编辑器不高亮。
  这个改动会让旧配置读不到——因为旧配置本来就全部作废，副作用为零。

- **三个死文件不进新布局**：`AgentProfiles.json`、`ModelCatalogConfig`、`RuntimeEngineSettingConfig`
  在代码里已无写入方，是历史版本的残留。
