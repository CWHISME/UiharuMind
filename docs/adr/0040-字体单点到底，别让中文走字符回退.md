# 字体单点到底，别让中文走字符回退

决定：`MainFont` 的族名按字体文件里的**真实族名**写，并把 markdown 渲染也拉回 `MainFont`。
两处都不是「统一观感」的洁癖，各自修掉一个可见缺陷。

## 先记一条方法论：字体结论只能在真实进程里下

无头测试默认用 `UseHeadlessDrawing = true`，它带的字体管理器是**假的**——系统字体一律解析成
`BareMinimum`，字形度量也不真实。本 ADR 起草过程中在那一层得出过两个**错误**结论
（「族名写错是全应用没粗体的根因」「MiSans 的 630 字面命中不了」），
前者在真实进程里被推翻，后者碰巧对。

**判字体的事用 `--dev-script` 的 `diag.font`**，它在真实进程里报每段字形实际解析到的
字体、字重与是否合成。下面所有数据都出自那里。

## 缺陷一：粗体是「合成」的，中文几乎看不出来

`Assets/Fonts` 里只有 `HarmonyOS_Sans_SC_Regular.ttf` 一个字面，所以 `FontWeight="Bold"`
拿到的是 Avalonia 合成的假粗体（`FontSimulations.Bold` → Skia 侧 `SkiaTypeface.CreateFont`
里的 `Embolden`）：

```
HarmonyOS Sans SC   normal 宽度=167 字重=400 模拟=None
                    bold   宽度=167 字重=700 模拟=Bold   ← 宽度一点没变
```

**宽度不变是关键**：`Embolden` 只把字形描粗一丝、不改字宽，对本来就细的中文黑体几乎看不出来。
用户的原话是「整个字体渲染还是一个样式，没有加粗」。

真 Bold 字面长这样（把 MiSans 的 `usWeightClass` 改成标准 400/700 之后实测）：

```
MiSans              normal 宽度=164 字重=400 模拟=None
                    bold   宽度=174 字重=700 模拟=None   ← 另一套字形，字宽不同
```

**解法只有一个：打包一份真 Bold 字面**，条件是「与 Regular 同族名」且
「`usWeightClass` 为标准 700」。放进 `Assets/Fonts/` 即可，代码一行都不用改。

> 顺带：`MainFont` 的族名从 `#HarmonyOS Sans` 改成了文件里真正的 `#HarmonyOS Sans SC`。
> 真实进程实测**两种写法表现完全一样**，所以这不是修复、只是把名字写对。
>
> 试过 MiSans 但没采用：它十个字重里只有 Regular 与 Bold 共享族名 `MiSans`，
> 其余各自成族；而且 `usWeightClass` 是非标准值（Regular 330 / Bold 630），
> Avalonia 配不上 `FontWeight="Bold"`（=700），真实进程实测直接打包**无效**，
> 仍然退回合成。要用就得改字体文件的 OS/2 表，涉及授权，没做。
> 可变字体版本也别考虑：Avalonia 源码里没有任何 `fvar` / 命名实例处理。

## 缺陷二：同一个 `**XXX**` 一半粗一半不粗

`LiveMarkdown/Styles.axaml` 给它那几个控件硬写了 `Arial, 'Segoe UI', sans-serif`
（代码块是 `Consolas, 'Courier New', monospace`），**两组都不含中文字形**。

于是同一段文字里走了两条路：

| | 路径 | 结果 |
|---|---|---|
| 英文 | 族内匹配（Arial 有真 Bold 字面） | 粗 |
| 中文 | **字符回退** | 不粗 |

差别出在 Avalonia 的 Skia 后端（`FontManagerImpl.cs`）——两条路径不对称：

```csharp
// 族内匹配:会算模拟
if ((int)weight >= 600 && !skTypeface.IsBold) fontSimulations |= FontSimulations.Bold;

// 字符回退 TryMatchCharacter:硬编码
platformTypeface = new SkiaTypeface(skTypeface, FontSimulations.None);
```

**凡是走字符回退拿到的字体，合成粗体被写死关掉了。** 这是上游缺陷，本仓改不了。

同一条回退路还带来另一个症状：回退是**逐字符**解析的，不同汉字可能落到不同字体、
度量不一，同一行里看起来就是有的大有的小（实测 `MarkdownTextBlock` 解析到
`compositefont:Arial, 'Segoe UI', sans-serif`，而普通 `SelectableTextBlock` 解析到
`HarmonyOS Sans SC`）。

**解法是别让中文走回退**：用一个本身含中文字形的族，两种字符都走族内匹配，两个症状一起消失。
`Assets/Themes/CustomMarkdownStyle.axaml` 覆盖 `MarkdownTextBlock` / `CodeBlock` /
`CodeInline` / 列表序号 / 列表项目符号五处。

## 一个必须记住的顺序

`CustomMarkdownStyle.axaml` 的 `StyleInclude` **必须排在 LiveMarkdown 的之后**。
Avalonia 的样式按**挂载顺序**决优先级，不按选择器特异性——本仓原有的
`:is(SelectableTextBlock)` 规则挂在前面，所以一直是 LiveMarkdown 赢。
挂错位置不生效，而且没有任何报错。无头测试应用（`HeadlessTestApp`）的顺序也跟着对齐。

`MainFontTests` 两条同时守着族名、粗体与挂载顺序。
