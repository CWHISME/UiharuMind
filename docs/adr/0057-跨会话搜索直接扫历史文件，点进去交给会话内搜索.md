# 跨会话搜索直接扫历史文件，点进去交给会话内搜索

> **状态**：accepted，**已实现**（2026-10-02）。接 [ADR 0056](0056-会话内搜索搜历史数据，跳旧消息截断重载.md)。

决定：会话列表的搜索框打字仍只按标题滤；用户**点一下**搜索框下面那一行「在消息里搜索「词」」（或回车），
才拿同一个词在**这一侧全部会话的消息**里搜，结果列在列表下方「消息里提到的」那一段；**不建索引**，每次直接扫历史文件。
点一条摘要就切过去，交给会话内搜索跳到那条。

## 为什么要点一下才搜

第一版是跟着打字自动扫的。多数时候打字只是想按标题找会话，每停一下就扫几百个文件（并行时还占着半数核）是白花，
侧栏下方也总挂着一段用户没要的结果。所以默认不扫：开扫之后跟着改词重扫，清空搜索框就收起、下次再要点。

## 为什么不建索引

真实档案实测（513 份历史、206MB，10 核）：

| 做法 | 一遍耗时 |
|---|---|
| 逐个会话整份解析再搜 | 0.9～2.2s |
| 先按行预筛、只解析含关键词的行 | 0.24～0.9s |
| 预筛 + 按文件并行（半数核） | **80～390ms** |
| 只读文件不解析（单线程下限） | 约 210ms |

并行预筛之后，常见词（命中四百多个会话）也在 0.4s 内，罕见词不到 0.1s。索引能省的只剩解析那一截，
换来的是每次落盘都要多维护一份数据、删改历史时还得保持一致——不值。档案再大一个量级再说。

## 口径

- **与会话内搜索同一个匹配**：`SessionSearch.FindIn` 逐条判，显示口径走 `ChatMessageDisplay`；
  跨会话这一路默认只搜正文，思考与工具不开（侧栏没地方放开关，进了会话再在搜索栏里勾）。
- **范围是这一侧的全部会话**（智能体或普通对话，与列表一致），不只是标题匹配的那几个；
  子会话与群成员会话不在列表里，不搜。
- **读的是磁盘那份**（`SessionManager.ReadHistoryLines`），不装载、不驻留——装载会把几百份历史留在内存里。
  正在跑的那一轮还没落盘的部分搜不到，落盘就有。读的时候**不挡写入与删除**（共享读写删）：
  `File.ReadLines` 只共享读，Windows 上读着那一刻那一轮的追加会撞共享冲突、记条日志就丢了（追加不重试）。
- 每个会话只列最近三次提及，其余进会话按回车翻。**扫的时候就只留这三条**（`SessionContentHit`：下标、部分、谁说的、摘要），
  不挂消息本体——常见词能在几百个会话里各中几十条，挂着就是扫一遍把它们全解析进内存。
- 单个会话读不了（读到一半被删、被占、没权限、内容意外）就当没搜到，不拖垮整次；整次出了意外，标题行报错，不停在「正在搜索」。

## 实现时定下的

1. **行级预筛按编码后的词找**。历史行与 `HistoryJsonl` 同一个编码器（`UnsafeRelaxedJsonEscaping`），中文是原文；
   关键词里有它会转义的字符（引号、反斜杠、控制符、emoji 这类代理对）就**不预筛**、整行解析——
   工具结果里嵌着的 JSON 还会再转义一层，按编码后的样子也未必找得到，宁可慢也别漏。预筛只是放行，
   放行的行仍按显示口径判（每行都有 `role` 键，搜 role 不该全中）。
2. **下标是历史文件的非空行序**，与装载后的历史下标大体一致，但不保证：损坏行装载时跳过、这里照数；
   装载还会收掉重复与悬空的工具结果。所以点进去不直接信它：会话内搜索按**扫出那一行的词**（行上记着，
   改词后旧结果还挂着的那一会儿点下去也对）重搜一次，取下标最近的那条（`ConversationSearchViewData.OpenAtAsync`），
   并把焦点给搜索框，接着按回车就是在那个会话里往前翻。会话内重搜用的是它自己的范围开关，开着思考也不碍事：
   正文那条还在，按下标最近照样落到它。
   目标记下、由**下一次采纳的结果**兑现，而不是等这一次搜完就去读列表：这一次可能被追加消息、切范围触发的重搜取代，
   那时列表里还是上一个词的结果；用户自己改了词，目标作废。
3. **跳转等视图接手**。点结果那一刻多半刚换实例，视图还没换绑、会话可能还在装载，当场发跳转没人接。
   视图模型只记下（`RequestSearchReveal`），视图在落位时取走——装载完成、切回缓存实例都经 `SettleNow`；
   已在看那个会话就排到绑定落地之后当场取（两个入口共用一个取法，谁先到谁取）。先照常落位再跳，会话里搜不到也已经落好了位。
   实例被切走（装载中途放下）时这条作废，否则下回从列表正常点开也会弹搜索栏跳过去。
   没切过去（会话刚被删）就不交：交给当前那个会话，它会在自己里面按这个词乱跳。
4. **点开的会话钉在列表里**——标题过滤唯一的例外。标题未必匹配搜索词，不在显示集合里的话列表框认不出选中、会把它写回空，
   页面随之切到空态。所以它在换搜索词之前一直留在列表里（`SessionListModel.SelectFromContentSearch`）；再点开别的就换成钉那个。
   换钉那一下上一个被摘出显示集合、列表框照样写回空，这一下压住选中通知（与 `Sync` 同一套），不然页面先闪一下空态。
   会话被删就把它那一组结果摘掉，不为此重扫；改名跟着条目走。
5. 开扫之后改词，停手 300ms 再扫（比会话内的 200ms 长：一次要扫几百个文件），只采纳最新一次。
   两个搜索的「停手再跑、只认最新」共用 `LatestOnlyRunner`：被取代 ⇔ 令牌已取消，不另记版本号；
   到点经 post 回 UI 线程，测试传同步执行、await 它的 `Pending`，不必真的睡过防抖。
   开发脚本 `sessions.search` 走同一套公开入口（填词、点开扫、等扫完、点第几个会话的第几条），报告落点；
   `start: false` 只填词不开扫。

## 已知的边

- 预筛找的是原始行里的字面子串。命中若横跨两段正文、或跨过被剥掉的 `<think>` 标签，会话内搜得到、这里漏掉——
  罕见，不为它放弃预筛。
