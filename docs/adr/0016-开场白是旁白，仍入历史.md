# 开场白是旁白，仍入历史

开场白在数据层的身份**不变**：它是一条 assistant 消息，落盘、也供给模型。
变的是两件事——旁白这个事实怎么存，以及它长什么样。

- 新增标记 `ChatMessageAnnotations.Narration`（走 `AdditionalProperties`，与 `Attribution`、
  点名调用同一套机制），由 `ChatSession.AddNarration` 在写下开场白那一处**显式**打上。
- 删除 `ChatSession.NarratorName` 哨兵与 `AddMessage` 里 `History.Count == 0 && role == Assistant`
  的隐式判定。
- 渲染：`ConversationItemFactory.CreateNarration` 造一条 `IsNarration` 的文本条目，
  居中、无头像、无发送者名、限宽 560、正文淡一档。操作行只留复制/编辑/删除
  （重试本来就只挂用户消息；分叉在这里等于新建会话，去掉）。

## 为什么

1. **旁白渲染早就丢了，只是数据层还留着残骸。** `AuthorName = "Narrator"` 一直在写，
   而 UI 侧从来没有读过它——`ConversationItemBase.Alignment` 只看 `IsSystem` / `IsUser`。
   于是开场白被画成了一条普通的角色气泡：有头像、有名字、靠左。
2. **仍入历史，是因为模型得知道自己已经开过场。** 不入历史的话首轮很容易再自我介绍一遍；
   而且重试、分叉、裁剪都得为它开特例。这也是酒馆把 `first_mes` 当 assistant 轮次的口径。
3. **不改成 `System` 角色。** 那样 `Alignment` 现成就居中了，但角色的台词进了 system 轨道会被
   模型当指令读；而且 system 段由 `CharacterPromptBuilder` 独家拼（ADR 0005 管着顺序），
   多一个来源会把那个口径撞坏。
4. **标记而不是哨兵字符串。** `AuthorName` 是「显示名」字段，兼职类型标记两头都不牢
   （万一哪天有个角色就叫 Narrator）。隐式判定则更脆：位置是会变的（删条目、分叉、裁剪），
   而「这句是开场白」是写下它的那一刻就定死的事实。

## 取舍

- **旧会话里的开场白不会居中。** 它们身上只有 `AuthorName = "Narrator"`，没有新标记；
  兼容判据（`IsNarration(m) || AuthorName == "Narrator"`）能救回来，但那要长期背一条
  「什么时候能删」说不清楚的分支。代价明说：**升级前建的会话，第一条仍显示为普通角色气泡。**
  新建会话即正常。
- **旁白仍可编辑与删除。** 它是历史里的一条真消息，不给这两个操作反而是回退——
  比如开场白里有错字，或者不想要它。
