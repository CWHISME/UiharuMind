# 文件记忆按角色分目录，而不是按会话

框架的 `FileMemoryProvider` 提供 `file_memory_*` 一组工具，让模型自己写笔记、自己回头读。
我们决定**目录归属改为"一个角色一个目录"**（`FileMemory/{角色名}_{角色id}/`），
由 `FileMemoryLayout` 决定目录名，并在每次挂接时覆写会话状态里的 `WorkingFolder`。

## 为什么（框架事实，1.16.0 实测）

1. **框架默认给每个新会话开一个新目录。** `HarnessAgentOptions.DisableFileMemory` 的文档写明默认
   store 落在 `{cwd}/agent-file-memory/{timestamp}_{guid}`；即便像我们这样传入固定的
   `FileMemoryStore`，那个 `{timestamp}_{guid}` 仍会作为**子目录**出现——因为工作目录名存在
   `FileMemoryState.WorkingFolder` 里，由 provider 的 state initializer 为每个新会话生成。
   磁盘实证：`AgentData/FileMemory/20260805_081538_d60d3dbe-…/memories.md`。
   于是"记忆"实际是每会话一张草稿纸，新会话一律从零开始——名不副实。
2. **`WorkingFolder` 随会话持久化。** 它在会话状态包里，而我们按会话 ID 存了框架 blob
   （`SessionManager.SaveAgentStateAsync`）。因此**光改目录名不够**：恢复回来的老会话里躺着旧值，
   框架会照旧值重建一个空目录，笔记在用户眼里又"丢"一次。覆写与搬迁必须成对做。
3. **`stateInitializer` 只对新会话生效。** `FileMemoryProvider` 的构造函数虽然收
   `Func<AgentSession, FileMemoryState>`，但状态包里已有值时它不跑。所以自建 provider 也**替代不了**
   覆写，只会多一层自建；因此保留框架自己组装 provider，我们只夺走"目录叫什么"这一件事。
4. **状态包可以从外面写。** `AgentSession.StateBag.SetValue<T>` 与 `FileMemoryProvider.StateKeys`
   都是公开 API，键为 `"FileMemoryProvider"`。装配侧拿不到 provider 实例（`StateKeys` 是实例属性），
   故 `FileMemoryLayout.StateKey` 复制了一份，并由测试与框架实例比对钉住。

## 取舍

- **为什么按角色，不按工作区**：这份笔记的语义是"agent 自己学到的东西"，而 agent 的人格与职责
  由角色卡定义。同一角色换会话应当仍记得；角色 A 的笔记漏进角色 B 会污染人格。
- **为什么目录名里带角色名**：纯 GUID 目录用户在文件管理器里没法认。代价是改名要搬目录。
- **为什么 id 一位不截**：内置角色的 `CharacterId` 不是 GUID 而是枚举名
  （`DefaultCharacterManager`），且大量共享前缀——`Assistant` / `AssistantExplain` /
  `AssistantExpert` / `AssistantExpertQuote` / `AssistantSyntacticAnalysis` 的前 8 位全是
  `Assistan`，`Roleplay_*` 与 `Translator*` 同理。截短后这些角色会互相被认作"改名前的自己"，
  对账可能把别人的笔记搬到自己名下。目录名因此长一点，但这是唯一不用引入哈希的正确解。
  （曾经真的截过 8 位，实机上留下了一个 `Uiharu1_Workspac` 目录。）
- **为什么搬迁靠对账而不是"改名事件"**：`CharacterData.CharacterName` 只是
  `Config.PromptConfig.Name` 的透传 setter，没有变更通知；唯一落盘入口也不知道旧名。
  对账（glob `*_{id8}`，前缀不同即搬）不需要知道改名发生过，因此外部导入角色卡、手改 json、
  旧会话恢复全都能自愈。id 后缀正是让"改名可被检测"的东西——纯 GUID 方案给不了这个。
- **搬不动就不搬**：命中多个旧目录、或目标目录已存在时只告警。宁可这个角色从空目录重新记，
  也不覆盖任何一份已有笔记。
- **已知代价：同一角色的多个会话同时写同一目录，没有跨会话写锁。** 笔记本体是各自命名的独立文件，
  真正会互踩的只有 `memories.md` 索引，而它是每次写入后重建的派生物，丢一次下次就补回来。
  要上锁的话拦截点是现成的（`FileMemoryStore` 由我们传入，可包一层装饰器），但不值得。
- **残留缺口**：会话正开着时改的名，要到下一次挂接才生效——对账只发生在 `AttachAsync`。
- **旧的 `{timestamp}_{guid}` 目录不迁不删**，就地留着。反查归属得遍历所有会话状态里的
  `WorkingFolder`，为一次性历史数据不值得写这段代码。

## 提示词与错误信息

- **不给文件记忆写纪律段。** 框架的 `FileMemoryProvider` 自己就注入一整段
  `## File Based Memory`（先 `file_memory_ls`/`file_memory_grep` 查已有记忆、用描述性文件名、
  写入时附描述、大块数据落盘以免被压缩截断）。我们再写一段等于让同样的话在系统提示里出现两遍。
  要改那段措辞只能自建 provider——`HarnessAgentOptions` 不暴露 `FileMemoryProviderOptions`。
- **`FunctionInvokingChatClient.IncludeDetailedErrors` 打开。** 框架自带的 `file_memory_*` 工具
  直接抛异常，而默认策略只回给模型一句 `Error: Function failed.`——失败原因多半是
  "要替换的原文没匹配上"这类它自己能改的事，不告诉它就只会原样重试。
  实测打开后是 `Error: Function failed. Exception: {e.Message}`，只有 Message，不含堆栈。
  选项不在 `HarnessAgentOptions` 上，靠 `agent.GetService<FunctionInvokingChatClient>()` 取到实例设置。
- **框架的 error 级日志降为 Warning。** `App.Error` 会把任何 `Log.Error` 弹成模态错误框，
  而 `MfaLogger` 原先把框架内部 error 日志转发成 `Log.Error`——一次工具执行失败
  （模型下一轮就会换路）因此会打断用户。异常全文照旧进日志。

## 顺带改掉的名字

模型这一侧原先同时看得见 `file_memory_grep`（自己的笔记）和 `memory_search`（用户的知识库），
两个名字都像"搜记忆"，而选错的表现是检索不到却不报错——最难归因的那类。
因此知识库检索工具改名 `KnowledgeSearch`，并在两者都挂载时补一句固定的辨析（`MemoryDisambiguation`）。
用户可见的「记忆库」文案统一为「知识库」是另一次独立的机械重命名，尚未做。
