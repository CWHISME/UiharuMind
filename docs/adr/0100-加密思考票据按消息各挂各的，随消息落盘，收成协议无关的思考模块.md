# 加密思考票据按消息各挂各的，随消息落盘，收成协议无关的思考模块

> **状态**：accepted（2026-10-30）。
>
> **前置**：本文是 [ADR 0099](0099-OpenAI兼容层分层，并把每请求上下文收成快照.md) 的后续，
> 但**不是**它的延续——0099 分的是「传输/改写/清洗」三类职责，本文分的是
> 「思考语义」与「wire 格式」两个正交维度。两者切口不同，可以并存。
>
> **本文记录一次失败**。上一版实现（提交 `3f51fca1` + `e71469da`，已由 `90a31c6e` 还原）
> 在真实档案上每轮都破坏前缀缓存，命中率从 88.2% 掉到 35.3%。那次的教训写在
> [「上次为什么错」](#上次为什么错)，比决定本身更重要——它解释了为什么四条不变量
> 写成那样，而不是更严的写法。
>
> **本文合并了原 ADR 0100 与 0101**：0100 定模块边界与四条不变量，0101 定落盘方式。
> 两者是同一件事的两半——0100 的第 4 条不变量（跨重启不丢）在 0101 里才真正落地。
> 拆成两份会让「不变量」与「实现」分居两个文件，读的人得自己对起来。

## 背景

### 一、闭源模型的思考正文不下发

闭源模型（如 Meta 的 Muse 系列）只回两种东西：加密的思考块，和一个思考 token 计数。
**思考正文一个字都没有**。现在的处理是开一张不带正文的「加密思考」卡
（`ConversationTranscript.ThinkingNotReturned`），注释写得很直白：

> 那两样本来就没有，编不出来；只把标题换成「加密思考」，让人知道它想过。

服务端要的是「把上次那张票原样带回来」，客户端唯一该做的就是保管它、原样出示——
这就是**票据**。

### 二、票据的三种形态

OpenRouter 把 `reasoning_details` 分成三种类型（[官方文档](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)）：

| type | 内容 | 可见 | 要回填吗 |
|---|---|---|---|
| `reasoning.summary` | 推理过程的**高层概括** | 明文 | 否（服务端不认摘要回传） |
| `reasoning.text` | 原始思维链 | 明文 | **要**（`signature` 必须原样带回） |
| `reasoning.encrypted` | 加密的完整思考 | 只有密文 | 要（整块原样带回） |

Anthropic 那边是同一套设计：`thinking.display: "summarized"` 给一段摘要，
完整的加密在 `signature` 里。**给你看概括，密文留作续接凭据。**

实测（Muse 系列）：`reasoning_details` 条目类型只有 `reasoning.encrypted` 一种，
实测结构是**一条**，键为 `type` / `data` / `id` / `format` / `index`。
**没有 summary 条目**——不管请求带不带 `summary: "auto"` 都没有。

`data` 长度**随思考量变化**，实测见过 2791 与 5522 两档（同一个问题、不同轮次）。
所以存储代价要按「最坏一档」估：约 1.5 KB（2791 字符）到 5.4 KB（5522 字符）每条。

对照实测：同一网关上不同模型给的形态并不一样

| 模型类型 | `reasoning_details` 条目类型 | 性质 |
|---|---|---|
| 部分闭源模型 | `['reasoning.encrypted']` | 只有密文 |
| 部分闭源模型 | `['reasoning.summary']` | 给明文摘要 |
| 明文思考模型 | 无（走 `reasoning_content`） | 明文全文 |

所以「摘要」是**模型之间有差异**的，不是网关统一给或不给：
闭源模型里既有只给密文的，也有给明文摘要的。
摘要条目形如 `{type, summary, id, format, index}`，
`summary` 是**一句可读的概括**（「正在计算 17×23，先理清思路，再给出最终结论。」）。

**这一条比「某个模型没有摘要」有价值得多**：它证明摘要是**能拿到**的，
只要模型给。界面上闭源模型的思考卡显示真内容，不是空卡——
只要那个模型属于会给摘要的那一类。

（`Text` 为空 + 只有密文，本身是完全正常的形态：模型默认只给密文。
M.E.AI 的 `TextReasoningContent.ProtectedData` 官方文档明说这种形态合法——
「It's possible for a `TextReasoningContent` to contain only `ProtectedData`
and have an empty `Text` property」。本文的实现正是按这个形态做的。）

### 二之二、整块原样回放实测通过（2026-10-30）

用真实网关验的，不是推断：

```
第一轮  reasoning_details 类型: ['reasoning.encrypted']
        reasoning_tokens: 159
第二轮  （把整块 reasoning_details 原样塞回）
        → 收下了（200），回复 "392"
        reasoning_tokens: 656   ← 推理链真的续上了
```

两条结论：

1. **整块原样回放被网关接受**（200）——不解析、不重排，直接原样贴回去。
2. **`reasoning_tokens` 从 159 涨到 656**，说明回放后模型**接着上一轮的思路继续想**，
   不是把票当字符串忽略了。**推理链确实续上了**，这是票据机制的价值所在。

另外两条实测细节：

- **流式与非流式的密文形状一致**：流式也是**整块一帧**（`data` 长度与非流式相同），
  不是分片——所以「只切不解析」在流式侧成立，一帧就是完整一张票。
- **`id` 每轮都变**（形如 `rs_<响应id>:rs_<条目id>`，实测三轮三个不同值）。
  证实了「id 不跨轮稳定」，所以回放**不能靠 id 定位**，得靠消息本身
  （这正是本文把票据挂到消息上的原因之一）。

### 三、上一版实现在真实档案上打掉了缓存

还原前的实测（本地请求体日志，同一会话连续三发）：

```
#12　4 条消息　票挂下标 2　　命中 71.1%
#13　6 条消息　票移到下标 4　 命中  1.5%　← 下标 2 的票被消费掉了
#14　10 条消息　票移到下标 6　　　　　　 ← 下标 4 的票又被消费掉了
```

跨模型统计（同亲和值内，排除换副本干扰）：

| 前缀形态 | 样本 | 平均命中 |
|---|---|---|
| 纯追加 | 249（真命中 221） | **88.2%** |
| 真实分叉 | 3 | **35.3%** |

分叉点**恰好**是上一轮挂过票的那条消息。原因见「上次为什么错」。

## 上次为什么错

上一版的生命周期是「**用一次即消费**」：票据存在 `LazyChatClient` 的单个 `_pendingTicket`
槽位里，`TakeReasoningTickets` 取走它时顺手 `= null`，并且只挂在**最后一条**助手消息上。

于是每轮发生三件事：

1. 上一轮挂在第 k 条消息上的票，这一轮**不在那了**（挪到了新的最后一条）
2. 第 k 条消息的字节因此变了（`reasoning_details` 字段消失）
3. 前缀在第 k 条处分叉 → **从那条起全部冷启动**

真实数据完全对上：分叉点逐轮落在 2 → 4 → 6，就是上一轮挂票的位置。

**这个错误与协议无关。** 换成 responses 协议，如果还用「只挂最后一条 + 用一次即消费」，
票据照样逐轮漂移，只是漂移的载体从「助手消息下标」变成「item 下标」。

第二个错误是**门禁只比 model id**。实测网关**不校验模型归属**——把 Meta 的票发给
deepseek 照样 200。也就是发错了不会报错，只会安静地错。门禁必须按
provider + model 双等（对齐 opencode `packages/core/src/session/runner/to-llm-message.ts:156-161`）。

第三个错误是**不落盘**。票据只在内存里，重启即丢；丢的那次，历史里原本挂票的消息
全部变成「无票」形态，与重启前缓存的字节不一致——**从第一条助手消息起全冷**。
实测那条会话首条助手消息之后占 72.1% 的正文。

## 决定

### 1. 目录按语义切，不按协议切

`wire 格式`与`思考语义`是两个正交维度：

| | 内容 | 随协议变吗 |
|---|---|---|
| **wire 格式** | chat 的 `reasoning_details` 挂在 `messages` 的消息上；responses 的 `encrypted_content` 挂在 `input` 的 item 上 | **会** |
| **思考语义** | 票据从哪来、怎么存、什么门禁、挂回哪条消息、摘要摘给界面 | **不会** |

新建 `AI/Reasoning/`，**只放协议无关的那一半**：

| 文件 | 职责 |
|---|---|
| `ReasoningDetailExtractor.cs` | 从响应字节里**只切不解析**地取出 `reasoning_details` 数组 |
| `ReasoningTicketCarrier.cs` | 票据挂在消息上：存取与产出方身份（原 `TicketStore` 已退场） |
| `ReasoningGate.cs` | provider + model 双等门禁 |
| `ReasoningSummary.cs` | 摘 `reasoning.summary` 明文给界面（不进回填） |

协议差异**留在 Net 层**，各协议各写各的拼票代码：

```
AI/Net/Request/OpenAICompatibleRequestRewriter.cs   ← chat 的拼票
AI/Net/Request/ResponsesRequestRewriter.cs           ← responses 的拼票（另立一项）
AI/Net/Response/SseSanitizingStream.cs                ← chat 的切票
AI/Net/Response/ResponsesEventParser.cs               ← responses 的切票（另立一项）
```

**放不进 `AI/Reasoning/` 的判据：这段逻辑在 chat 与 responses 下行为是否相同？**
相同的进 `Reasoning/`，不同的留在各自协议的改写器里。

这样加 Anthropic Messages 时 `AI/Reasoning/` 一行都不用改——它压根不知道有协议这回事。

**为什么不按协议切目录**（即不建 `AI/Responses/` 装所有 responses 相关代码）：
协议不是主轴。`OpenAICompatibleRequestRewriter` 361 行里，`ScanMessage`/`ScanToolCalls`/
`FixArguments`/`Build`/`Copy` 全是**字节级通用机制**，真正 chat 特有的只有几个字符串判断
（`"role"`、`"assistant"`、`"tool_calls"`）。按协议切会变成两份 `Utf8JsonSplice` 调用逻辑，
抄着改、越改越歪。

### 2. 四条不变量

每条都要有测试钉死。这是本文最要紧的部分——上次翻车就是因为没有这几条。

1. **每条助手消息永久挂自己那张票。**
   产出时挂在哪条消息上，以后每轮都挂在那条。**不挂最后一条**，票不会被挪走。
2. **逐轮原样重发。**
   一条消息的票据字节从产生那刻起不再变；每轮只往历史末尾追加新消息。
   这样前缀才是纯追加。
3. **换模型时整条丢弃。**
   provider + model 双等，不一致 → 该消息不带票据，思考降级为纯文本。
   （网关不校验，这道门禁是唯一的。）
4. **跨重启不丢。**
   票据随消息落盘，重启后读历史即得。**不变量 1 由此从「靠 store 保证」变成
   「结构上就成立」**——票在消息里，消息不会被挪走。

### 3. 票据长在消息上，随消息落盘（上游做法）

**这是第 4 条不变量的实现方式，也是第 1 条从「约定」变成「结构」的地方。**

上游 agent-framework（`Microsoft.Agents.AI` / `Microsoft.Extensions.AI` 的上游仓库，
`F:\Studys\AI\agent-framework`）的做法可直接照搬：

**密文挂在 content 的一等字段上，随消息序列化。**
Python 侧是 `Content.protected_data`（`_types.py:674`）；
.NET 侧对应 `Microsoft.Extensions.AI.TextReasoningContent.ProtectedData`，官方文档写得很直白：

> This property is used to store data from a provider that should be roundtripped back to
> the provider but that is not intended for human consumption. It is often encrypted or
> otherwise redacted information that is only intended to be sent back to the provider
> and not displayed to the user.
>
> Note that whereas `Text` can be provider agnostic, `ProtectedData` is provider-specific,
> and is likely to only be understood by the provider that created it.

**这两句话正好是我们要的两条语义**：只回给 provider、不给人看；provider 专属，
所以门禁必须比。

Chat Completions 侧上游把整块 `reasoning_details` JSON 塞进 `protected_data`
（`_chat_completion_client.py:913`），回放时解出来挂回 assistant 消息（`:1244`）。

**三条可直接照搬的原则：**

1. **回放数据只放可序列化字段**，不能放 `raw_representation`（provider 原始对象引用，
   重启后就没了）。上游把它写进了 spec
   （`docs/specs/005-python-content-identity-and-protocol-metadata.md:210`）：
   > Replay must not depend on `raw_representation`; it is absent after persisted history reload.

2. **密文变化 == 消息内容变化**。上游 .NET 侧的内容相等性检查把 `ProtectedData` 计入
   （`ChatMessageContentEquality.cs:100`）。这本身就是「密文属于消息字节」的立场。

3. **密文缺失时不静默降级**。上游检测到「有 reasoning 的工具调用组但密文缺失」时
   **直接抛异常**（`_chat_client.py:1847` `_validate_reasoning_groups_for_stateless_replay`），
   而不是悄悄发一个不带 reasoning 的请求——理由写得很清楚：
   那会产生一个语义不同的 transcript，且前缀缓存会分叉。

**落到本仓：**

| 承载什么 | 放哪 | 为什么 |
|---|---|---|
| 密文 | `TextReasoningContent.ProtectedData` | 上游为此场景设计的字段，语义完全吻合 |
| 产出方身份（provider + model） | 同一条思考内容的 `AdditionalProperties` | 与密文同生共死——**票据和它的归属必须一起持久化**，否则重启后无从判断该发给谁 |

**回填侧改成从历史消息读票据，替掉序号映射。**
原设计（`TicketStore`）按「第几条助手消息 → 票据」存，带来两个问题：
序号会漂移（历史被裁剪、消息被替换，对应关系就错位了），且跨重启必须重建映射。
改成随消息走后两个问题一起消失——序号只用于**当轮拼回时的定位**，
这个对应关系由消息列表本身保证，**不需要任何外部状态**。

**连带要修两处：**

1. `ChatContentNormalizer.IsEmptyTextLike` 判「空思考」只看 `Text.Length == 0`，
   而我们的票据恰好是「空文本 + 有密文」——会被当空思考丢掉。
   改成：**空文本且无 `ProtectedData`** 才算空。
   同理，合并思考碎片时不能把带密文的那条并进去（并进去等于丢掉密文）。
2. `LazyChatClient` 里 4 处 `IsEmptyTextLike` 判定要分开处理：
   带密文的思考**不能**被当空内容丢掉，但它的 `Text` 是空的，
   不能因此在请求体里生成一个空的 `reasoning_content`。

**门禁保持 provider + model 双等（比上游严）。**
上游原样回发密文、不检查来源模型，**由 provider 拒**（400）。
但我们实测过本网关**不校验归属**：把 Meta 的票发给 deepseek 照样 200。
在本网关上，「不校验」的后果不是报错，而是**安静地错**——模型拿到读不懂的密文，
轻则忽略（白花钱），重则误解上下文。所以门禁只能在我们这一侧。
产出方身份随票据一起落盘，门禁在重启后依然有效。

**为什么不自己造一个存储层**（比如单独的 `.tickets.json`）：上游证明「挂在消息上」
就能解决，且能一并解决序号漂移。自造存储层要额外维护消息与票据的对应关系，
正是已经踩过的坑。

**为什么不把整个 `reasoning_details` 数组塞进 `ProtectedData`**：上游就是整个塞的
（`json.dumps(reasoning_details)`）。但我们的数组里可能同时有 `reasoning.summary`
（明文摘要）与 `reasoning.encrypted`（密文）两类条目，整个塞进去意味着摘要也跟着回传——
而服务端不认摘要回传。分开放更精确：**密文进 `ProtectedData`，摘要单独走明文路径给界面**。

### 4. `DetailExtractor` 只切不解析

`reasoning_details` 里是密文/签名，**任何再编码（解析后重排、解码再编）都会让它作废**。
客户端唯一该做的是保管它、原样出示。

实现：字节级扫 `"reasoning_details":`，然后括号配平取数组原文。
配平时要**跳过字符串内部**的引号与方括号（密文里有 base64 与 `+/=`）。
**半截数组当没找到**——帧被切断时残缺的票发回去比不发更糟。

只认紧凑写法：SSE 帧里的 JSON 必然紧凑（换行会截断帧），不存在 `"reasoning_details": [`。

### 5. 摘要走明文，不进回填

`reasoning.summary` 是明文，摘出来直接给界面显示（现在只能开空卡）。
**它不参与回填**——服务端不认摘要回传，带回去是白改请求体。

`reasoning.text` 要**拆开处理**：`text` 部分明文可显示，`signature` 部分必须原样回填。

**摘要能不能拿到是模型之间有差异的**（实测，见背景一节）：
有的闭源模型给 `reasoning.summary`（一句可读概括），有的只给密文。
所以摘要是**跟着模型走的**，不是网关统一给或不给——
同一个网关上，有的闭源模型有摘要可显示，有的只能开空卡。

**接口侧已经接住**（`ReasoningSummary` 摘明文、`ReasoningDetailExtractor` 只切不解析），
所以哪个模型给了摘要就显示哪个，不给就照旧开空卡——**不需要额外的开关**。

要注意的是**摘要与密文可能同时出现在同一个 `reasoning_details` 数组里**
（OpenRouter 的三种 type 是并列的）。摘要把 summary 条目摘走，
密文那条整块原样回填——两条路各走各的，不互相干扰。

### 6. 对外只留一个接口

在 `LlmRequestScope` 上挂字段，其余一律内部消化。外部改动点从四处收到两处：
SSE 流切票、请求改写拼票。

`LlmRequestScope` 的读点只有 7 处、分布在 5 个文件，Execution 层碰 Net 层只经
3 个文件（`LazyChatClient`、`TurnDriver`、`HistoryHandoff`）——**耦合面本来就小**，
不需要为了模块化再动架构。

（另有 4 个 WebTools 文件 `using UiharuMind.Core.AI.Net`，但里面**没有引用任何 Net 类型**
——真正需要的是 `System.Net.Http.Headers`。是未使用的 using，与耦合无关。）

## 取舍

- **为什么不顺便重构架构**：ADR 0099 刚做完一次分层（18 个平铺文件分六处、
  三个裸 `AsyncLocal` 收成带作用域的快照），主要耦合点已经收掉。
  `Net/` 各子层的对外引用面是 1~5 个文件。再动架构收益小、风险叠加。
  真要动，该动的是 `Execution` 层内部（`Assembly/`/`Harness/`/`Delivery/`），
  那是独立的一项，与本文无关。
- **落盘为什么放在第二版**：第一版先做内存版跑通，用真实档案量出
  「思考质量有没有变好」。落盘的存储代价是线性增长（实测 `data` 2791~5522 字符/条，
  随思考量变），**不要在收益未验证前先付存储代价**。
  验证之后确认「不落盘就没有跨重启的缓存」——长会话恰是最需要缓存的场景——
  才补上落盘（决定 3）。
- **模块化是副产品，不是任务**：模块边界由测试逼出来，不凭感觉划。
  先写不变量测试，再实现，最后收目录——这样边界是对的，而不是我猜的。
- **summary 要不要做**：接住它的成本很低（切票时顺手多摘一个字段），
  且是唯一能让闭源模型的思考卡显示内容的路径。

## 已知代价

- **存储线性增长**：`data` 实测 2791~5522 字符/条（随思考量变），
  按每条助手消息一张票估，长会话线性增长。**只影响加密思考模型**——
  明文思考模型（deepseek 这类）压根不产生票据，`ProtectedData` 恒为空，存储零增长。
- **票据进分词占 prompt**：约 400 token/条。待落地后从 `prompt_tokens` 增量直接量。
  若占比过高，落盘与回填都要重新权衡。
- **换模型后旧票据全丢**：不变量 3 的直接后果。切模型后思考链断一次，
  换回来又要重新积累。
- **门禁只挡显式换模型**：会话中途改 `ModelId` 会丢票，但历史里其他模型的思考正文
  照旧回传（沿用 ADR 0093 决定 5 的口径：不按产出模型过滤历史思考）。
- **摘要因模型而异**：有的闭源模型给 `reasoning.summary`（可显示真内容），
  有的只给密文（只能开空卡）。接口已接住，给了就显示、不给就开空卡。

## responses 线的接入（2026-10-30 补）

本文定的模块边界（决定 1：思考语义与 wire 格式是两个正交维度）在 responses 线上
被实测验证了一次——**`AI/Reasoning/` 一行没改，只在协议侧接线**。

### 两条线的对照

| | chat 线 | responses 线 |
|---|---|---|
| 请求体 | `messages` 数组 | `input` item 数组 |
| 密文载体 | 消息上的 `reasoning_details` | item 上的 `encrypted_content` |
| **落盘载体** | `TextReasoningContent.ProtectedData` | **同一个字段** |
| **门禁输入** | `AdditionalProperties` 里的产出方身份 | **同一处** |
| 谁做往返 | 我们自己切字节 | SDK 解与拼（`ResponsesClient`） |

**落盘载体与门禁输入两条线完全相同**——所以 ADR 定的落盘路径与门禁
**不需要为 responses 另做一套**。这是「按语义切目录」这个决定的直接兑现：
`AI/Reasoning/` 里的东西一行没改。

### 一处必须补的缺口

chat 线的密文是**我们自己从字节里切出来的**，切的时候就知道是谁产出的，
顺手把产出方身份挂上。responses 线的密文是 **SDK 解出来的**——它只还原
`ProtectedData` 与 item id，**不知道也不该知道「这台机器上是谁签的票」**。

而身份是门禁的输入：缺了它，落盘的票读回来就无从判断该不该发给当前模型，
只能一律不发——**票白存**。

所以在拿到响应后补一步：给带密文的思考内容挂上产出方身份
（`LazyChatClient.StampTicketProducer`）。已有身份的不覆盖——
落盘往返后身份已经在了，再补一次会把「原来是谁产的」改成「现在是谁在发的」。

补的位置能放 `AdditionalProperties` 里，与 SDK 自己放的 `reasoningItemId` 共存
（实测互不覆盖）——那个字段是 responses 线往返回送时对位用的。

### 位置稳定性

chat 侧靠「数第几条助手消息」定位，responses 侧靠 **item 本身的顺序**——
reasoning 是**独立的一条 item**，插在原位，不占助手消息的位置。

**注意**：responses 侧的 reasoning item 带 `id`（形如 `rs_<响应id>:rs_<条目id>`），
但**不能靠它定位**——实测每轮都变。位置稳定性的真正来源仍是 ADR 0100 那条
不变量：「每条挂自己那张，不动别人的」。

### 两个坑

1. **`store` 必须 false**：开了它服务端就存我们的响应，密文在服务端而不在客户端
   手里——那就不是「客户端保管、原样带回」了。有状态续接（`previous_response_id`）
   正依赖它，所以这条路用不了。
2. **`RawRepresentationFactory` 要先抓住原来的工厂**再换掉自己：在配置动作里读
   `x.RawRepresentationFactory` 拿到的是刚赋上去的那个，会自己调自己（无限递归）。
   上游框架的同名实现也是这么写的。

## 实施结果（2026-10-30）

模块按决定 1 的边界收拢：

```
AI/Reasoning/ReasoningDetailExtractor.cs   只切不解析地取出 reasoning_details
AI/Reasoning/ReasoningTicketCarrier.cs      票据挂在消息上：存取与产出方身份
AI/Reasoning/ReasoningGate.cs                provider + model 双等门禁
AI/Reasoning/ReasoningSummary.cs             摘明文给界面（不进回填）
```

接线点：`LlmRequestContext`（挂票据清单）、`SseSanitizingStream` 与 `ResponseSanitizer`
（切票）、`OpenAICompatibleRequestRewriter`（按序号拼回）、`LazyChatClient`（产出票据）、
`SessionChatHistoryProvider.AppendOwned`（落盘时把信号内容转成持久票据）。
`ILlmModel` 加了 `ProviderId`（取配置类型名），供门禁比对。

### 票据怎么落到消息上

流里那条 `EncryptedReasoningContent`（原本只用来开界面那张卡）现在**带着票据**，
框架会把它并进这一发的助手消息；`AppendOwned` 落盘时把它转成一条带 `ProtectedData`
的思考内容，而不是像以前那样摘掉。

非流式路径的回复消息现成，直接挂上。

### 前缀稳定性的验证

`src/scripts/perf/verify-ticket-prefix.py` 拿**真实日志的请求体**重放两种拼法：

```
=== 旧做法：只挂最后一条、用一次即消费（已还原的那版） ===
  第1轮 -> 第2轮：首差下标 2  <== 分叉
  第2轮 -> 第3轮：首差下标 4  <== 分叉
  分叉数：2

=== 新做法：每条挂自己那张、逐轮原样重发 ===
  第1轮 -> 第2轮：纯追加（无首差）
  第2轮 -> 第3轮：纯追加（无首差）
  分叉数：0
```

旧做法的分叉位置（2、4）恰好是上一轮挂票的下标——与还原前的实测完全对上。
新做法分叉数为 0。

### 测试

- `ReasoningTicketInvariantTests`：四条不变量 + 落盘往返 + 规整器不丢票据 + 门禁
- `ReasoningTicketStabilityTests`：端到端连续三轮历史逐字节相同，
  外加**跨重启**（消息序列化再读回来）后依然相同——这条只有落盘版才成立
- `ProtectedDataProbeTests`：三个落盘约束的探针（`ProtectedData` 往返、
  `AdditionalProperties` 带产出方、规整器不丢密文）
- Core 全量 3362 条 0 失败；App 全量 1256 条 0 失败

### 实施中改掉的两处设计

1. **门禁要比对"产出方"与"请求方"，产出身份得跟着票走。**
   原设计是 `ReasoningGate` 只记请求方、票不带身份——那样无法判断票是谁签的。
   改成票据带产出方身份：换模型后旧票仍能留着，换回来还能用。
2. **门禁不过时不能删票**，只是这一轮不带。删了的话换回原模型就接不上了。

## 本期不做

- **Anthropic Messages 协议**：那边要整份翻译（`system` 提到顶层、`content` 变 block 数组、
  `tool_result` 换角色、SSE 事件逐类翻译），思考票据是 `thinking.signature` 而不是一个字符串字段。
- **缓存 TTL 参数**：实测网关的前缀缓存 TTL 明显长于 OpenAI 官方默认
  （真日志：2–10 分钟 30 样本平均 86.1%、27 分钟 98.5%、65 分钟 0%），
  **TTL 不是当前瓶颈，前缀分叉才是**。`prompt_cache_retention` 这类参数不进产品。
- **摘要的显式请求**：实测 chat 端点**自发**给摘要（部分闭源模型的 `reasoning.summary`
  无需任何参数），所以不需要显式请求机制。Responses API 侧的
  `summary: "auto"` / `ReasoningSummaryVerbosity` 属于 responses 协议那一档，
  随那一项一起做。
- **摘要与密文分家**：`reasoning_details` 数组里可能同时有两种条目，
  摘要把 summary 条目摘走、密文整块原样回填——两条路各走各的。
  这条已在本轮实现里分开处理（`ReasoningSummary` 只读不摘、
  `ReasoningDetailExtractor` 只切不解析）。
