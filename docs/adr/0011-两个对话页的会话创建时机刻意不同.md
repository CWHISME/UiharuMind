# 两个对话页的会话创建时机刻意不同（急建 / 懒建）

聊天工作台**急建**会话，智能体页**懒建**，两者不统一：

| | 聊天工作台 | 智能体页 |
|---|---|---|
| 时机 | 点新建按钮就 `StartNewSession` → 入索引 | 只切空态，首轮发送时 `EnsureSessionAsync` 才入索引 |
| 走哪个构造 | `ChatSession(title, character)` | 无参构造 + 手填字段 |
| 因此 | 角色的**开场白当场写进历史**，`Description` 取开场白 | 没有开场白，`Description` 取用户第一句 |
| 新会话进列表时 | **自动选中** | **不自动选中** |

这两条差异收在 `SessionListModel` 的构造参数 `selectNewSessions` 上，**刻意不从
`ESessionListScope` 推导**——它取决于会话何时创建，与「哪一页」无关。

## 为什么

1. **聊天页不能改懒建。** 角色扮演「点完新建立刻看到角色打招呼」是核心体验，而开场白是在
   带角色的那个构造里写进历史的。懒建绕过那个构造，开场白就没了。
2. **智能体页不能改急建。** 懒建下 `OnSessionAdded` 那条通知落在**正在跑的那一轮中间**，
   自动选中会触发重载、把正在流的回复拦腰截断。
3. **这两条约束方向相反**，所以不存在一个能同时满足的统一方案。差异不是历史遗留，
   是两页的产品语义本来就不同：一个是「先有角色，再有对话」，一个是「先有任务，才有会话」。

## 取舍

- **差异显式化为一个构造参数，而不是在类内按 scope 分叉。** 从 scope 推导会读成
  「智能体页就该这样」，而真正的判据是创建时机——将来若加第三页，它得自己回答这个问题，
  不该从「我是哪一页」被猜出来。
- **接受两条不同的构造路径。** 智能体页走无参构造 + 手填字段，字段漏填的风险是真的
  （`Title`/`Description` 默认值是字面量 `"Empty"`）。代价换的是不为一个没有角色的会话
  伪造一个角色。

## 代价（明说）

- **`ChatSession` 有两个构造，语义不等价**，而只有带角色那个会写开场白。新代码走哪个要想一下。
- **智能体会话首轮发送前不存在**，于是任何「发送前就想知道」的功能（能力占用统计、附件登记）
  都得处理「此刻还没有会话」这一态。附件的 `_pendingOwnedFiles` 延迟缓冲就是为它存在的。
- **懒建会话的 `Description` 取用户第一句**，与标题同源，因此早期建的会话带着冗余描述。
