# 长轮次允许从中间裁，硬顶优先于不切开一轮

**修订 `ConversationItemWindowTrimmer` 原先那条「边界一律对齐到用户消息」的口径。**

> ⚠️ 第 4 条（前台仍旧只在轮末裁）已由 [ADR 0038](0038-前台也按消息边界裁，跟底闸收口.md)
> 修订：前台也按消息边界裁，跟底闸收口。

决定：

1. 锚点**首选仍是用户消息**——一轮不被切开依旧是默认口径。
2. 但用户锚点保下来的条目超过上限的 2 倍时，改按**消息起点**切，哪怕这会把一轮切开。
3. 从中间切的那条路必须自己认两条边界：**待决审批卡不许摘走**，
   还没回填来源消息的流式条目天然选不中（它们给不出锚点）。
4. 轮内的**消息边界**成为新的裁剪时机：不在界面上的实例在每次服务调用落盘后回填并裁一次。
   前台不变，仍旧只在轮末裁。

## 原先那条口径为什么会整轮失效

「往头部找最近的一条用户消息」在聊天页是对的：一轮就是一问一答，退到本轮开头
至多多留两三条。但 agent 的一轮可以跑几十次工具调用、堆出几百个条目，
而**整轮之内一条用户消息都没有**——往头部退到的永远是本轮开头那一条，
「保留量」等于整整一轮。裁是裁了（前面几轮被摘掉了），条目数一点没降。

叠加另一半就成了用户报的那个 bug：落盘通知一整轮才来一次，
而后台裁剪只挂在落盘通知上。于是一个跑着长轮次的会话，在它跑完之前
**根本没有裁剪发生**；切回去看到的就是几百条条目一次性重新实体化。
两处都修才有效果——只修锚点，长轮次中途仍然不裁；只加时机，裁了也等于没裁。

## 为什么切点是「消息起点」而不是任意条目

一条助手消息可以摊成思考段 + 正文 + 若干工具卡，它们共用同一个来源消息。
从中间切会让窗口起点指向一条**已经渲染出一半**的消息，「加载更早」把它整条取回来时
就会重复渲染。按来源消息换人处切，切出来的两段各自完整。

## 待决审批卡

摘走一张待决审批卡，卡片没了、回应口还挂在运行循环上：用户按不到，
轮次也不结束，只能等超时按拒绝收口，那次委派白跑。
原先这条边界是**用户锚点顺带保住的**（审批总在本轮之内），
现在允许从轮内切，就必须把它写成显式规则。
