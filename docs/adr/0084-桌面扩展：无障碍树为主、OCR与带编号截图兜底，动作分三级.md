# 桌面扩展：无障碍树为主、OCR 与带编号截图兜底，动作分三级

> **状态**：accepted（2026-10-11），macOS 的第 1、2 段已实现，Windows 第 3 段已写待实测（见文末「实现进度」）。挂在 [ADR 0079](0079-扩展：不常用的能力与MCP收进一对元工具，先查后调、逐条审批.md) 的扩展下，
> 快照、编号、对账、审批卡沿用浏览器那一套（[ADR 0074](0074-浏览器工具：PuppeteerSharp驱动本机Chrome，快照带编号.md)、
> [ADR 0078](0078-浏览器：接管交给用户，审批卡说人话，读正文与截图.md)）。

浏览器只管得到网页。用户要的是「通用的桌面操作」：别的应用里的内容能读进来，系统对话框、访达/资源管理器、记事本这类能替他点。
macOS 与 Windows 都要；Linux（Wayland 与 X11 分裂）只在接口上留位，不写实现。

选型参考了 `computer-use-mcp`、`munim-computer-use`、`open-codex-computer-use`、`cua`、`Agent-S`、`UI-TARS-desktop` 等开源实现
（调研在仓库外）。结论：没有能直接嵌进 .NET 的现成件；外挂 MCP 会和扩展审批两套打架、功能大半重复，所以自己写平台层，其余复用。

## 决定

新增内置扩展 **`desktop`**，与 `browser` 并列：

| 命令 | 做什么 |
|---|---|
| `windows` | 列窗口：所属应用、标题、是否前台 |
| `snapshot` | 给指定窗口拍快照，带 eN 编号；`view` 可选截图 |
| `act` | 点击、输入、设值、按键、滚动、聚焦、选择；目标是编号或坐标；`input: "real"` 才动真实键鼠 |
| `open` | 启动应用，或用默认应用打开工作区、草稿目录里的文件 |
| `handoff` | 这一步交给用户手动做，做完交回 |

- **只拍模型指定的窗口**，不拍整个桌面：一个应用的树动辄上万节点。格式与编号沿用浏览器（`AxNode` / 快照写出器 / `AxRefReconciler`），
  按深度与数量截断。各平台的角色映射到同一套 `Role` 名。
- **`open` 不收任意命令行**，只认应用名与工作区、草稿目录里的文件，免得成了绕过 Shell 审批的口子。
- **目标是浏览器工具自己开的那个 Chrome 时拒绝**，引导改用 `browser`；用户自己的浏览器照常能看、能动。

## 怎么看：三层，逐层兜底

1. **无障碍树**：macOS 用 AX（`AXUIElement*`，C 接口，照现有 `DllImport` 写法放 Core）；Windows 用 UI Automation
   （`Interop.UIAutomationClient`，配缓存请求遍历）。
2. **OCR 文字层**：树为空或太薄（自绘界面、游戏、Canvas、部分 Electron）时，快照追加识别出的文字行作伪节点，同样带编号，
   标明「来自屏幕文字识别」；点它就是点它方框的中心，走第 2 或第 3 级。macOS 用现有 Vision OCR，Windows 见下文。
   这层对纯文本模型是唯一的眼睛；对视觉模型也比「让模型报像素坐标」准得多，有字的界面基本省掉一个定位模型。
3. **带编号框的截图**（Set-of-Marks）：已知的节点与文字行在图上画框标号，看图的回答落在编号上（「e12」「e7 旁边的齿轮」），
   后续动作照常走编号；实在没框可指才用坐标。截图只截这个窗口（macOS `screencapture -l`，Windows WGC 或 PrintWindow），
   交付沿用 `EReadImageMode`：主模型能看图就 `Read`，否则交给识图工具里配置的模型；都没有就不提供这层。

**这次不接本地定位模型**（UI-TARS 一类）：要多载一个几 GB 的视觉模型、权重的商用许可要另确认，而 OCR 加编号截图已覆盖大半。
动作参数保留坐标，确有需要再加。

## 怎么动：三级

| 级 | macOS | Windows | 代价 |
|---|---|---|---|
| 1 无障碍动作 | `AXPress` / `AXSetValue` 等 | UIA 的 Invoke / Value / Toggle / SelectionItem 等模式 | 不动光标、不抢前台；有的控件不支持 |
| 2 向进程投递事件 | 公开的 `CGEventPostToPid` | UIA 加少量窗口消息 | 不动光标；个别应用不认 |
| 3 真实键鼠 | SharpHook | SharpHook | 抢用户的输入 |

- **默认走 1，不行退 2**。Chromium / Electron 里 `AXPress` 会谎报成功（munim 实测），这类目标直接走 2。
  Windows 不以 `PostMessage` 为主：WPF、UWP、Chromium 基本不认。
- **第 3 级只能由模型显式要**（`input: "real"`），要审批，可按应用放行本会话（见「安全与审批」）；执行前把目标窗口提到前台，执行中监听到用户动键鼠立刻中止并如实告诉模型。
- **SkyLight 私有接口先不用**：两个开源实现的后台点击都靠它，但它随 macOS 大版本会坏。先用冒烟实测公开接口的成功率，再决定要不要加。
- **动作后等界面稳定**：先用「快照不再变」轮询加上限，与浏览器同一个思路；系统通知（AXObserver、WinEvent）以后再优化。
- **动作时在目标上闪约 1 秒的高亮框**：第 1、2 级不动光标，用户看不出点了哪。复用自动点击指示器那类置顶、鼠标穿透的窗口
  （`WindowUtils.SetNonInteractiveOverlayWindow`），不画会移动的代理光标。

## 安全与审批

| 风险 | 哪些 | 怎么问 |
|---|---|---|
| 只读 | `windows`、`snapshot` | 三档都不问 |
| 一般 | `act`（第 1、2 级）、`open` | 三档都问；本会话放行**只对放行时那个应用**有效，换应用重问 |
| 逐项 | `act` 带 `input: "real"` | 三档都问；本会话放行按应用**单独记一格**，一般动作的放行与「扩展不再询问」都不算 |
| 硬问 | `handoff` | 永远问；离席化身一律拒，子代理不自动批 |

- 一般级的「本会话放行」比 0079 的按扩展记再窄一层：放行记事本不该连带放行微信。离席化身不批任何「动」。
- **密码只经用户的手**，与浏览器同一口径、做成工具拒而不是审批：macOS `AXSecureTextField`、Windows `IsPassword` 的值在快照里只给圆点，
  往里设值或打字当场拒，让模型改用 `handoff`。
- **默认拒绝名单**：钥匙串 / 凭据管理器、系统设置、终端、本应用自身；用户可在设置里改。名单内的窗口能列出来，但拍不了、动不了。
- Windows 上以更高权限运行的窗口（UIPI 挡着）不提权，直接说明并建议交给用户。
- 审批卡说人话：「在 记事本 点击按钮『保存』」，照 `BrowserCallText` 按发起会话最近一份快照翻编号。
- **并发**：第 3 级全局串行，同一时刻只有一个会话占着，其余排队并告诉模型；第 1、2 级按应用串行，不同应用可并行。
  子代理与群成员能不能用，沿用扩展的现有配置。
- 桌面内容与网页一样不可信。污染标记（另议）做的时候一并纳入。

## 权限

- **macOS**：无障碍权限在设置里启用扩展时引导授权；没授权时扩展显示不可用并写明原因，模型从 `ExtensionHelp` 看得到。
  屏幕录制权限到第一次要 OCR 或截图时才申请，与截图功能现有流程合并。两项授权落在应用自己的签名上，
  [ADR 0029](0029-打包与发版，macOS签名必须用自签名证书.md) 的自签名证书保证升级后不丢。
- **Windows**：读树与动作不需要额外授权。

## 工程

- **Windows 专用代码另起项目** `UiharuMind.Platform.Windows`（`net10.0-windows10.0.19041.0`，`EnableWindowsTargeting` 让 mac 上也能编）。
  Core 与 App 项目只定义接口；Desktop 在 Windows 发布（`win-x64`）或在 Windows 上开发时才引用它，在组装入口接上实现。
  不改现有三个项目的 `net10.0`：`Windows.Media.Ocr` 必须走 `-windows` 目标框架，FlaUI 也只发 `-windows` 包。
- **UI Automation 用 `Interop.UIAutomationClient`，不用 FlaUI**：我们只要缓存遍历加几个模式，FlaUI 的测试自动化那一层用不上，
  还带进 System.Drawing.Common 等依赖。
- 平台层是一个接口（列窗口、读树、动作、截图），macOS / Windows 各一份实现，扩展本身与平台无关。

## Windows OCR

现有截图 OCR 在 Windows 上是空实现（`NullOcrRecognizer`），桌面扩展的 OCR 层又要用，所以先补上，对外仍是 `IOcrTextRecognizer`：

1. **OneOCR 优先**：Windows 11 截图工具 / 照片应用内置的引擎，中文好、有词级坐标。经系统 `PackageManager` 找到本机安装位置，
   首次使用时把 `oneocr.dll`、`oneocr.onemodel`、`onnxruntime.dll` 复制进数据目录，**绝不从网上下载**。
   它是逆向得来的接口（社区 `b1tg/win11-oneocr`，密钥已在多个 MIT 项目里公开），截图工具更新后可能失效；设置里可关。
2. **失败就静默退回 `Windows.Media.Ocr`**：公开、稳定，中文系统自带中文识别。未打包的桌面应用能否直接用（Zaya.OCR 的注释说通常要包身份），
   以 Windows 上实测为准。

不引用 Zaya.OCR 包：同样要 `-windows` 目标框架，带一串用不上的依赖，默认还会从第三方地址下载 OneOCR。参照它与 Starshot（均 MIT）自己写。

## 顺序与验证

先 Windows OCR（独立、对截图 OCR 有直接收益，也是 Windows 兜底的前置）与 macOS 实现，Windows 实现随后，同一套接口、同一套场景。
冒烟用 `src/scripts/smoke/`，两边各 3 到 5 个场景、只用系统自带应用（文本编辑 / 记事本里写字存进草稿目录、访达 / 资源管理器里找文件、计算器）。
OSWorld、Cua Bench 跑在虚拟机里，不搬。

## 不做

- 决策层另起「大脑」（Agent-S 的反思、best-of-N、双模型分层）：工作区代理的循环够用，best-of-N 每步费用翻 N 倍。
- 外挂 MCP 形态的 computer use 服务。
- Linux 实现、代理光标动画、本地定位模型——都留了位，等真需要。

## 已知代价

- 平台层得从零写：仓库里此前没有任何 AX / UIA 代码与权限引导。
- 公开接口的后台点击成功率未知，可能频繁退到第 3 级、频繁打扰用户；这是要不要加 SkyLight 的依据。
- OneOCR 随系统组件更新可能失效，靠退回 `Windows.Media.Ocr` 兜住，但中文效果会降一档。

## 实现进度

**已做（macOS）**：`desktop` 扩展五条命令、宿主（窗口编号、按会话的快照与对账、三级动作、拒绝名单、并发）、
AX 读树与动作、审批（按应用的「本会话允许」、真实键鼠按应用另记、接管硬问、离席化身不批）、审批卡人话、接管卡、动手时的高亮框。
快照、对账、结果写法从浏览器抽到 `Tools/Accessibility/` 两边共用。

实测（这台 Mac）后对上文的修正：

- **打字也走第 1 级**：后台应用没有键盘窗口，投递给进程的按键事件被系统丢掉（文本编辑实测）。
  打字改为经无障碍在光标处插入（`AXSelectedText`），不经键盘；只有快捷键这类真按键才要事件。
  菜单命令可直接按菜单项（`AXPress` 对关着的菜单项也生效），保存之类不必按 Cmd+S。
- **发事件另有一道授权**：「辅助功能（事件）」与读树的无障碍授权是两道。没有时系统静默丢弃，
  所以发事件前先查（`CGPreflightPostEventAccess`），没有就如实报错；第一次用到时请系统弹一次授权框。
  事件源用到才建，免得只是看一眼也弹框。
- **Chromium / Electron 要先开 `AXManualAccessibility`**，网页那半棵树过一两秒才建好：头一次开时等一下。
  网页元素会把自己报成「收起」、标题把层级报成值、链接名下挂着拼出名字的碎字，读树时都滤掉。
- **焦点以应用的 `AXFocusedUIElement` 为准**：列表里的格子个个自报有焦点。
- 应用默认在后台打开（`open -g`），不抢前台。
- 拒绝名单补上：更多终端（Ghostty、kitty…）、系统授权与密码弹窗（`universalAccessAuthWarn`、`SecurityAgent`）、本应用的其他实例。
- 速度：列 18 个窗口约 0.7 秒；访达、日历、Edge 网页一份快照 0.1–0.4 秒，活动监视器约 0.9 秒。

**第 2 段（macOS）已做**：看图的两样本事（认字、画编号框）在界面层实现（`DesktopVision`：截图 OCR 那一套 + SkiaSharp），
经 `IDesktopVision` 挂到宿主上。树里有内容的节点不到 4 个就截窗口认字，认出的行成 `ocr-text` 节点、带编号，
点它直接按框的中心发事件（没有无障碍元素可调）；`view: "ocr"` 强制认字；`view: "screenshot"` 附一张长边 1600 的 JPEG，
图上框出这份快照的每个编号，交付与浏览器截图同一口径（`Read` 或 `AnalyzeImage`）。
截窗口用 `screencapture -l`，要屏幕录制授权：自动认字时没授权只在结果里说明，模型明说要看图时才报错；第一次用到时请系统弹一次授权框。
动作后的等待只比对树，稳了再认字（认字慢，只认一次）。

**应用内实测后的修正（2026-10-11）**：

- **真实键鼠从「硬问」改为「逐项」**。Epic 启动器这类自绘界面不认后台点击，模型改用真实键鼠后每一下都弹卡，用不下去。
  现在卡上给「本会话允许 桌面 · 应用（真实键鼠）」，记成 `desktop:real <应用>`，只放行这个应用的真实键鼠；
  输入框里「扩展不再询问」不覆盖它——一次勾选让所有应用都能抢鼠标、拉前台，范围太大。
- **等用户停手最多 10 秒**（原 3 秒）：真实键鼠总是紧跟着用户在审批卡上点「允许」，手还在鼠标上，3 秒常常等不到。
- **认字丢掉单个字符的噪音行**（图标认成「•」「¢」「贝」），字母数字与箭头、加号、关闭这类留着。
- **认出的行带中心在窗口里的位置**（`at x,y`）：只给字，模型分不出侧栏与正文，把侧栏的「Fab」当成了正文里没有。
  快照说明补一句事实：看不到图片、分不出哪行属于哪张卡片——模型据此自己判断何时截图。
- **扩展目录只列命令说明的第一行（160 字）**：`snapshot` 的 `view: "screenshot"` 写在后面被截掉，模型以为不能截图，
  改用 Shell 截了整个屏幕。要紧的（三种 view）挪到第一行。
  但模型往往只看扩展工具描述里的命令速查（`CallUsage`）就直接调，不查帮助：速查里也写上 view 与 action 的取值。
- **画出来的界面，动作后比截图等稳定**：这类窗口的无障碍树动作前后一样，比树会立刻判「稳了」，
  页面还没换就认了字、报「没变化」，模型只好反复截图核对。现在树太空时改比截图：画面变了又连着两次一样就收；
  一直没变，截满 5 次（约 1.5 秒）认了；一直在动（轮播、加载圈）最多 13 次。
  主模型看不了图时，快照说明补一句事实：截图要另交看图模型，一次十几到几十秒。
- **真实滚轮先把指针挪到目标上**：系统把滚轮发给指针下的窗口、不看事件里的位置，原先真实滚动落在了指针所在的别的窗口上。
  投递给进程的滚轮也带上窗口号，与点击同一做法。

**第 3 段（Windows）已写、未实测**：`UiharuMind.Platform.Windows`（`net10.0-windows10.0.19041.0`），Desktop 在 Windows 上构建
或发布 `win-*` 时换成同一目标框架并引用它，入口里 `WindowsPlatform.Install()` 经 `DesktopHost.UsePlatform` 与
`OcrRecognizerFactory.Use` 挂上；mac 上 `-r win-x64` 交叉编译通过。

- **读树**：UI Automation 控件视图，缓存请求一次读齐元素与子元素的属性，有子元素的节点一次往返；控件类型映射到同一套角色名。
  标题栏整个不读（最小化、关闭几个按钮只是噪音，关窗按 Alt+F4）；Chromium / Electron 窗口每个进程头一次读前等 1.5 秒建网页树。
  商店应用的窗口框属于 `ApplicationFrameHost.exe`，按里面内容窗口的进程认应用——设置（`SystemSettings.exe`）才拦得住。
- **第 1 级**：列表项、标签页、树节点的「点」是选中（列表项的 Invoke 在资源管理器里是打开）；其余 Invoke → Toggle → 选中 → 展开收起 →
  MSAA 默认动作。Invoke 等模态框关掉才回，等 2 秒就当成功。UIA 没有「在光标处插入」，打字退给第 2 级。
- **第 2 级**：投递窗口消息给点到的最里层子窗口 / 线程焦点窗口。投递的按键带不上修饰键（应用查的是真实键盘），组合键直接让模型改用真实键鼠。
- **第 3 级用应用现有的输入模拟**（`InputSimulateManager`，自动点击同一套 SharpHook 后端），给后端补了「按 Unicode 打字」
  （原有 `SendText` 按键位逐个按，中文打不出）。macOS 仍用自己的 CGEvent 私有事件源：那样发出的事件不算进「用户最近一次输入」。
- **截窗口**：`PrintWindow`（`PW_RENDERFULLCONTENT`）画进内存，裁到看得见的外框，与报给宿主的窗口位置一一对应；最小化的报错。没上 WGC。
- **OCR**：OneOCR 经 `PackageManager` 在截图工具、照片应用的安装目录里找三个文件，复制到 `Cache/OneOcr/<包全名>/` 再用；
  先把同目录的 `onnxruntime.dll` 载进来，免得引擎按名字找到别的版本。起不来或这次失败就退回 `Windows.Media.Ocr`（中文逐字给词，两个汉字之间不加空格）。

**未做**：Windows 上实测（读树速度、各级动作、截图与认字，Windows.Media.Ocr 在未打包应用里能否用）；OneOCR 的设置开关；拒绝名单的设置界面；冒烟场景；
在应用自己的授权下实测：第 2 级后台点击的成功率、截窗口与认字的整条路。
