# 内置技能由代码现生成正文，不落盘：uiharu-guide 与开发者模式下的 uiharu-dev

> **状态**：accepted，**已实现**（2026-10-03）。

应用此前不带任何技能，技能目录只扫用户的 `Data/Skills`。段 26 长跑让应用里的一个会话经命令行驱动应用自己（ADR 0059），
命令行在哪、有哪些步骤、哪几步会打断自己，全靠一份手写的长交代——这份知识该随应用走，模型要用时自己取。

## 决策

1. **两个内置技能**：`uiharu-guide` 一直在，讲这个应用怎么用；`uiharu-dev` 只在开发者模式开着时出现，讲经开发控制通道驱动应用。
   分成两个而不是一个技能里加开发者段：普通用户的技能目录里根本看不到开发者内容，开关只是目录里一个过滤。
2. **正文由代码在每次读取时生成，不写文件**（`BuiltInSkill : AgentSkill`，`GetContentAsync` 现拼、同步完成）。
   写死的文件会和应用脱节而没人察觉：开发者模式运行中会开关，命令行路径开发与打包时不同，步骤会增删。
   - `uiharu-guide` 的正文是帮助页那份 `Help.md`（按当前语言），前面补此刻的事实（档案与技能目录、开发者模式开没开）。
   - `uiharu-dev` 的正文：此刻的事实（命令行路径、档案、通道开没开、这是真实档案）、用法与退出码、注意事项、全部步骤。
     **步骤清单从各步骤自己的 `IDevCommand.Usage` 生成**，`app.ops` 也回同一份，不另写一份。
   - 命令行路径按序找：环境变量 `UIHARU_CLI` → 与应用同目录（macOS 打包时多看 `.app` 旁边一眼）→ 开发构建里 Desktop 产物旁的 CLI 产物；都没有就照实说没找到，不猜。
3. **叠在文件技能之上**（`BuiltInSkillsSource`，套在扫盘缓存外面）：先文件、后内置，同名的内置让位——用户放一个同名技能就能顶掉它。
   内置技能可用与否随时会变，不能跟扫盘结果一起缓存。
4. **没有技能目录**：点名调用与 `load_skill` 都只拿正文，不提目录与附件（ADR 0001 那条注入路径对空目录本就不写目录行）。
   设置页的技能列表里单独成「内置技能」一组，排在本地技能之后。
5. **基座层点明运行宿主**（`AgentBasePrompts.HostFact`：「你运行在桌面应用 UiharuMind 里，用户正通过它和你说话。」）。
   此前主代理的提示词里从没说过宿主是谁，技能描述写的「UiharuMind 这个应用」它对不上。只给事实不指路：
   技能开没开因角色而异，指向一个可能不存在的技能就是在指挥不存在的工具。
6. **技能清单关着时，Skill 工具的描述点出内置技能的名字与描述**。总闸关掉后模型看不到清单，只有按名加载的 `Skill` 工具：
   用户技能的名字它能从点名注入的正文里得知，内置技能的名字无处可知。只列内置的（就两个），用户技能照旧不列，省 token 的初衷不破。
   可用的内置技能名入装配快照（仅在清单关着时）：开发者模式运行中开关，下一轮重建，描述跟上。
7. Core 只提供 `BuiltInSkill` 与登记口（`SkillCatalog.RegisterBuiltIn`）；两份正文在 App 里写、启动时登记——
   步骤注册表在 App，Core 不能反向依赖。

## 考虑过并否掉的方案

- **启动时把技能文件写到数据目录**：复用文件技能那条路最省事，但开发者模式运行中开关跟不上，写出去的文件也会被当成用户可改的东西。
- **一个技能、开发者段按开关增删**：普通用户也会看到这个技能的开发者描述，描述又是模型自选的依据，分不干净。
