# 文本编码探测收成一份，文件工具按原编码读写

> **状态**：accepted，已实现（2026-10-08）。

读磁盘文本的地方原先各按各的规则解码：`Read` 用 `StreamReader(UTF8)`，只认 BOM；`Edit`/`Write` 的信封（`TextFileEnvelope`）只认 UTF-8；
Grep 引擎按 UTF-8 字节匹配；只有知识库与文本编辑窗走 `TextFileCodec` 的探测链。同一个 GBK 文件于是在 `Read` 里是乱码、
在 Grep 里搜不到中文，经 `Edit` 只改一行 ASCII 再写回，全文中文就成了「锟斤拷」。

决定：**探测只有一份**（`TextEncodingDetector`），上面几处都经它；文件工具读进来是什么编码，写回去就是什么编码。

`TextFileCodec` 原有的探测链不能直接拿来用。拿 10 个样本实测，它错了 4 个，最要命的是只夹一个中文字的 UTF-8 源码
被判成希腊文（ISO-8859-7，置信 0.52，刚过 0.5 的门槛）。照搬给 `Read` 会把本来正常的文件读成乱码，
而本机历史里 9351 次 `Read` 只有 4 次结果出现过 U+FFFD，读的几乎全是 UTF-8。
新的判定顺序见 `TextEncodingDetector` 的注释：BOM → 开头有 NUL 判二进制 → 严格 UTF-8 → 大体是 UTF-8
→ 探测器的多字节结果 → 东亚编码打分（ASCII 不进分母）→ 探测器的单字节结果。

## 后果

- `Edit` 先做往返校验：解码再编码对不上原字节（编码认不出、或混着坏字节）就拒绝落盘，因为写回会连没碰到的部分一起改。
  新文本里有原编码写不下的字符也拒绝（只有 Big5、Shift-JIS 与单字节编码会这样）：改一小段不该顺带换掉整个文件的编码。
- `Write` 沿用原编码，理由与它沿用 BOM、行尾相同；原编码写不下新内容时改存 UTF-8，并在结果里说出来——整份替换的意图是明确的。
- GBK 一律按 GB18030 处理：它是 GBK 的超集，还能编码全部 Unicode。CP936 独有的 0x80（€）在 GB18030 下不合法，这种文件会被往返校验拦下。
- 纯 ASCII 文件记成 UTF-8。原先记成 us-ascii，在文本编辑窗里打中文再保存会变成 `??`。
- Grep 引擎（自有 fork 的 Glacier.Grep）加了转码钩子：8MB 以内、不是合法 UTF-8 或带 UTF-16/32 BOM 的文件交给 Core 转成 UTF-8 再搜，
  行号不变。转码也是为了正确：Big5、Shift-JIS 的第二个字节会落在 ASCII 区，按原字节搜 ASCII 关键词会命中半个汉字。
  UTF-16 文件从前被当成二进制整个跳过。
- `Read` 只在不是 UTF-8 时在正文后注明编码：模型若改用 Shell 或脚本动这个文件，得知道它是什么编码。
- 已知边界：超过 8MB 的文件只拿开头 64KB 探测，开头全是 ASCII、后面才出现 GBK 的大文件会按 UTF-8 读，Grep 也按原字节搜；
  无 BOM 的 UTF-16 判为二进制。
