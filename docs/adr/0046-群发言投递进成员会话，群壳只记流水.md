# 群发言投递进成员会话，群壳只记流水

群里每个成员仍各有一个真 `ChatSession`。**群发言投递进每个成员自己的会话**——轮到谁，
就把他上次之后的新发言合成一条消息交给他跑一轮。群本身是一个**群壳会话**，
它的历史是一份**只给人看的流水**，永远不喂给模型。

本 ADR 取代 [0045](0045-黑板是与会话历史并列的第二个历史源.md)。0045 的决策 1（成员是真会话）
与决策 7（排序键单调、用提交顺序）保留，其余改写。

> **骨架已落地**：`UiharuMind.Core/AI/Chat/Group/`（调度 `GroupChatCoordinator`、换算 `GroupTranscript`、
> 建群 `GroupChatSessions`），界面在 `Features/Conversation/Group/`。范围见文末「骨架做了什么」。

## 背景

0045 为了「群发言只存一份」，让供给模型的那一份在构建请求时由「黑板视图 + 私有」现拼。
对照代码重看，它否掉副本方案的理由一条是事实错误、其余在一条语义下都不成立（见取舍）；
而现拼方案要和现有机制对着干：

- 成员跑一轮，`TurnDriver` 本来就把输出写进**他自己的会话**。现拼方案还得把这段正文从他的会话里挪走。
- 现拼出来的那一份没有现成的裁剪。0045 最大的未决就是「黑板按谁的上限裁」。

## 决策

1. **群壳会话。** 群是一个 `ChatSession`，带群标记、群类型、成员名单；智能体群的工作区挂在它的
   `WorkspacePath` 上（[0042](0042-对话页合并为单页，类型由左栏切换器唯一决定.md)「已定」）。
   它的历史是**群流水**：用户发言与成员的群发言，按提交顺序只追加。群壳**永不跑轮**。
2. **成员会话用 `GroupId` 挂到群壳，不复用 `ParentSessionId`。** 后者会让成员按子代理装配
   （能力与群壳取交集——群壳是空角色，交完什么都不剩；也不能再开子代理），
   打破「群成员是 peer、在第 0 层」（[0044](0044-委派门面统一为SendMessage，子会话骨架不动.md) 决策 6）。
   左栏排除成员会话；删群级联删成员会话。
3. **投递靠游标。** 每个成员记一个「群流水读到哪儿」。轮到他时，把游标之后的新发言
   **合成一条 user 消息**（逐条标发言人）交给他跑一轮；他正在跑时，走现有注入队列在安全点插入。
   形状与子会话的「【派活方】一条 + 自己一轮」一致。
   合成一条是为了守住 user / assistant 严格交替——部分本地对话模板遇到连续 user 消息会直接报错。
4. **什么算群发言。** 助手消息**有正文、且不带工具调用**——每一次「说完」都是一条（插话会让一轮说好几次话，
   见 [0049](0049-并行群聊调度（唤醒边界@路由主持人），与串行并存.md) 决策 11）。带工具调用的是边做边说的旁白，
   这一步还没说完，只留在他自己的会话；调过 `SendMessage` 发群的那几条以工具发的为准——它所在那条消息带工具调用，
   按定义就不算「说完」，结构上自然不贴。普通角色没有工具，只走前者；弱模型忘了调工具也有正文兜底。
   发言不回投给发送者本人——那条本来就在他的会话里。
5. **调度先串行。** 用户发言后按成员顺序一人一轮，一圈即停，另有「继续一圈」。
   成员之间互相插话要并行，而并行要先定唤醒边界与停止条件（方案 §3.2），放在 Hello World 通过之后。
   决策 3 的两种投递从一开始都做，换并行只改调度、不改投递。
6. **群发言送达即不可改。** 群视图不提供编辑、删除、重试；在成员会话里删一条只改他自己的记忆。
   重试在群里本来就说不清——B 重答时，C 已经是看着 B 的旧回答说的话。
7. **裁剪各管各的。** 每个成员用自己会话现成的压缩与交接文档
   （[0037](0037-长轮次允许从中间裁，硬顶优先于不切开一轮.md)、[0038](0038-前台也按消息边界裁，跟底闸收口.md)），
   按自己模型的上限。

## 取舍：0045 否掉副本方案的四条理由

- **「扇出会让各人前缀长得不一样，破坏前缀缓存」——事实错误。** 成员之间本来就不共享前缀
  （系统提示各不相同），这与推翻方案 §6.8 用的是同一个事实。落到每个成员自己的会话里，
  副本方案是纯追加，恰是缓存最喜欢的形状。
- **「中途入群在副本方案下是三套补全逻辑」——群流水就是来源。** `full` = 把流水重放进新成员的会话，
  `summary` = 一条摘要，`none` = 不补。
- **「撤回或编辑要同步 N 份」——决策 6 之下不存在。**
- **「成员退群后副本留还是删」——留。** 他听过的话就是听过。

存储多 N 份是纯文本，不是成本；发给模型的 token 两案一样多，0045 自己算过。

## 代价（明说）

- **群壳是一个不跑轮的会话。** 所有遍历会话的代码（搜索、导出、统计、装载时压缩）都会看见它，
  要一个明确的群标记，并在跑轮入口拦住。
- **渲染要按发言人显示。** 现在渲染一律取会话级角色（`ConversationItemFactory.CreateAssistant`），
  `ChatMessage.AuthorName` 虽然落盘、却没有任何界面读它。群流水与成员会话里的合成消息都要改。
- **群发言在盘上存 N+1 份，彼此不校验一致。** 一致性靠「送达即不可改」这条语义，不靠同步。
- **0044 决策 1 收窄。** 「群聊广播走 `SendMessage`」只对智能体成立，普通角色用正文说话。

## 骨架做了什么（落地时定下的细节）

- ~~**场景说明随第一次投递给出**~~（已由 ADR 0048 取代：场景与群协议进系统提示的 `# 场景` 段），不进系统提示：成员会话建好就定下的事，放在历史开头同样一次定好，
  而系统提示与工具定义一字不变（前缀稳定、不为群改装配）。代价是压缩把开头裁掉之后场景就没了，
  骨架的对话长度碰不到这一点。
- **成员会话建时不写开场白**：在群里那是他对着空气自我介绍。
- **智能体群的工作区以群壳为准**，~~每轮开跑前让成员对齐~~（已由「修订：成员设置现取」取代：成员不存副本）——右栏改的是群的工作区，成员各存一份会对不上。
- **成员的审批一律拒绝**（与定时任务同一口径）：群视图还接不住成员的审批卡。工作区内读写在自动编辑档本来不问，
  被拒的是 shell 与越界写入；拒绝理由告诉模型「换一个不需要审批的做法，或在群里说明你需要什么」。
- **群的类型跟着切换器那一侧**：在智能体一侧建的就是智能体群，工作区取右栏卡片上选着的那个。
  建时定下、之后不变（[0042](0042-对话页合并为单页，类型由左栏切换器唯一决定.md)「已定」）。
- **插话**：成员正在跑时用户发言，插进他这一轮；游标只在投递时前进，投递时跳过他自己的话与已插给他的话，
  于是插不进去的下一轮照样收到，插进去的不会再投一遍。已插记录与游标一起落在成员会话上（`GroupConsumedPosts`）：
  起初只放内存、接受重启后重投一次，实测成员会认真回一轮「重贴不算新论据」，白花一次调用还带偏讨论，改为落盘。
- **成员发言落盘前剥掉模型自加的前缀**：场景说明要求「直接说，不要加 [名字]: 前缀」，弱模型常照投递格式仿写。
  不剥的话单行发言被 markdown 当链接引用定义整段吞掉（气泡空白、复制有字），投递给别人再包一层变双前缀。
  只在落盘与投递时按「发言人自己的名字」剥（不认别人的名字，避免误伤正文）；剥空说明只剩前缀、实质没说，不记这条。
- **群里的附件**：路径引用拼进发言正文（人人都有，看不了图的成员靠它用识图工具），图片再内联一份在群发言里
  （群气泡靠它显示）；投递与插话时只把图片转交给当前模型看得了图的成员。粘贴图落的盘归群壳，删群时一并删。
- 发群的收件人写 `group`（或「群」「全群」「群里」），在 `SendMessage` 认人名之前认。（已由「群成员不委派」修订取代：发群改走 `PostToGroup`。）

## 修订：成员审批（2026-09-27）

骨架里成员的审批一律拒绝，成员一要跑 shell 就卡住；而会话窗口里若画出卡片，用户点了也没人听。

- **登记等待**：成员那一轮的审批走 `SessionApprovalRegistry`（原 `SubSessionApprovalRegistry`，改名因为不再只服务子会话），
  经 `NestedApprovalResolver` 等人点选。只有他那一轮停着等，其余成员照常说话。
- **在哪批**：群输入框上方的待审批条（`GroupApprovalsViewData`），一条一行：谁 · 工具 · 参数摘要 +
  允许 / 本会话允许（shell 为「放行同类命令」）/ 拒绝 / 查看。不进群流水——流水记的是大家说了什么，审批不是一句发言。
  「查看」打开他的会话窗口，那里画出完整的卡（含 diff），同一次审批两边都能认领，先点的算数。
  其余几张跟着那次审批的最终结果收起按钮、显示决定（`SessionApprovalRegistry.DecisionOf`）；
  窗口在批完之后才打开、从实时流里补画出来的卡也查得到结果（已决出的按请求对象弱引用留着），
  不然它一直挂着，轮末还会被按拒绝收视觉，把批准过的显示成拒绝。
- **没人应**：十分钟按拒绝收口；用户点停止同样按拒绝收尾；连续三轮一条都没批准就收掉他这一轮。
  开始等时弹一条提醒（人不在群视图里就看不到那条待审批条）。
- **看得见谁在等**：成员等审批期间，群本身在运行登记处也挂「等审批」（`BeginApprovalWait(群id)`），
  左栏那一行、导航角标、托盘跟着亮——成员会话不进左栏，用户能看见的只有群那一行。
  右栏成员列表按成员自己的登记（`TurnDriver` 登记的那份）把他标成「等审批」，替掉「发言中」。
- 成员的轮次按「有人看着」跑：他派出的子代理照有人值守的口径处理嵌套审批。

## 修订：成员权限档跟群走（2026-09-27）

实测：群视图里权限档是「自动编辑」，某位成员却在完全自动档下跑 shell、`git stash`——成员各存一份权限档，
只能在各自的会话窗口里改，群那一档对成员不起作用；而中途在成员窗口改档，要到下一轮重新装配才生效，
界面上看着已经调严，这一轮照旧按旧档放行。

- 成员的有效权限档一律取群的（`GroupChatSessions.PermissionOf`），与工作区同一口径。
  ~~每轮开跑前对齐；群视图改档时当场推给各成员~~（已由「修订：成员设置现取」取代）。
- 成员窗口的权限按钮照常显示当前档位，列表只读，提示写明「跟随群聊（在群视图里改）」；
  挂接成员会话时不认界面上那一份。
- 审批规则现取档位（ADR 0010 修订），所以推过去的新档对正在跑的那一轮下一条调用就生效。

## 修订：成员私聊的可见性，关窗不掐断（2026-09-27）

实测：成员在群里被停下后，用户在她自己的窗口里发「继续」，接着关掉窗口——那一轮被关窗掐断，重开时既没在跑也没有结果；
其间群里的成员列表也看不出她在跑。

- **关窗不掐断**：成员 / 子会话窗口（`QuickChatViewWindow`）关闭时，若视图模型自己发起的活还在跑（`IsRunningOwnWork`：装配、一轮、整理交接），
  留到跑完再弃，其间重开同一会话接回它——气泡、审批卡、流式状态都在它身上。与主界面切走会话时保留在跑实例同一口径。
  只是旁观别处跑的（群轮、子代理）照旧当场弃，那边不受影响。
- **成员列表标「私聊中」**：她的会话在跑、却不在群的发言人里，就是在她自己的窗口里私聊（`GroupMemberItem.ShowsPrivateChat`，
  判据取运行态登记处）。私聊的回复只有用户看得到、不进群；要她接着在群里做，用群里的「继续」（ADR 0049 第 14 条）。
- **占用跟着每次服务调用刷**：成员列表此前只在发言人变化时读一次 `LastInputTokens`，成员窗口旁观群轮时只在打开那刻恢复一次，
  两边都要等这一轮结束才对上。现在 TurnDriver 记下用量时发 `SessionManager.SessionUsageReported`，成员列表那一行与旁观中的窗口
  都从会话本体取数；自己跑的那一轮仍走逐块通知。

## 修订：本群产物区（2026-09-27）

方案 v6 §8 的 P0 余项之一（§1.4「产出锚点」）：群右栏成员列表下面一块，列这个群落了哪些盘，每条带路径。

- **两个来源**：草稿目录（全群共用那一间，直接列盘；点开头的隐藏文件不列）；工作区（成员会话里成功的 `Write` / `Edit`）。
  成功与否认工具结果的开头（`Saved '` / `Applied `，提成 `FileToolNames.WriteSucceededPrefix` / `EditSucceededPrefix`，
  工具实现与这里共用），失败、被拒、被取消的不算；相对路径按群的工作区解析；盘上已不在的不列。
  草稿目录里的文件若是成员写的，也标出是谁。最近改过的在前。
- **不看 git**：那会把用户自己的改动也算进来。已知盲区是命令行改的工作区文件认不出来。
- **刷新**：草稿目录用文件监听（目录还没建时先不盯，建出来后下一次刷新挂上）；成员每次服务调用报用量时
  （上一次的写入结果随这一次调用落盘）与一轮跑完时各刷一次；几路合进一次 400ms 防抖，收集在后台线程。
- 收集是 Core 纯函数 `GroupArtifacts.Collect`（测试 `GroupArtifactsTests`），界面在 `GroupArtifactsViewData` / `GroupArtifactsPanel`。
- 「聊了 N 轮盘上还是空的」给主持人的软提示（§1.4 末条）先不做，产物区用一阵再定。

## 修订：成本可见（2026-09-27）

方案 v6 §3.4「可见性优先，不做自动干预」的面板消耗一项：成员行在占用右侧挂「累计 N」（会话本体的

成员列表标题旁挂全群合计。与占用同一处取数、同一时机刷新（`SessionUsageReported` 与发言人变化），只是仪表，不设阈值。
步数 / 耗时（§7 执行期换单位）属 P1，未做。

## 修订：从单聊开群，不做就地升级（2026-09-27）

方案 v6 §6.6b 规则 5（用户拉人 = 升级为群、成为参与者）以**另开一个群**落地：单聊头部「从这里建群」打开建群弹窗，
预选原单聊的角色（屏蔽卡也照样列出——用户正在跟他聊）、群名预填原单聊标题，群的类型跟原单聊那一侧（与空态建群同口径）。
原单聊原样不动。

- **背景**：确认后先让原单聊的模型写一份给新成员看的摘要（`GroupBackground`：复用交接文档那条线，附言改成「写给没看过这段对话的新成员、
  1500 字以内」，同一客户端与装配好的选项，前缀缓存照吃），**填进新群的输入框**由用户过目、删改后再发——新成员看到什么由用户定（§6.6b 规则 2 的隐私顾虑）。
  普通群成员没有工具读不了文件，所以背景是正文不是文件路径。写失败就照常建群并提示用户自己补。
- **先写后建**：草稿只在装载会话时读一次，先建群再回填会跟用户在新群里打字抢，所以摘要写好才建群、打开。代价是要等几秒到几十秒，期间有提示、原单聊照常可用。
- **为什么不就地升级**：它比另开群只多「同一个窗口接着聊」，却要把存量单聊原地改写成群的一部分（`GroupId`、左栏归属、装配、记忆绑定），
  并逼出三条普通建群不需要的特例（Hello World 二跑 G1：群类型看屋里有没有智能体、历史按摘要喂、唤醒规则覆盖小群与无主持人两个默认）。
  那三条归档在 `docs/proposals/代理人格化/HelloWorld二跑/`，真出现就地升级的需求时再用。
- 角色拉人 = 子代理（规则 1–4）早由 `SendMessage` 委派覆盖，不另做。单聊里打 `@某人` 时提示「要拉他进来吗」暂不做。

## 修订：「本轮发过群就不再贴正文」是粒度错了（2026-09-28）

实测（智能体群「优化方案设计」）：成员一轮里用 `SendMessage` 发了两次群，中间跑完四分钟压测（十几轮带工具调用的过程话），
末尾那条纯正文的判决书——数据、结论、点名对手——群里一个字见不到，群流水停在他前两次发言那两分钟。
用户看到的就是「他对着空气自言自语了两分钟然后没了」。

- 原来的判据是「从上一次说完（首轮即本轮起点）起，他自己有没有往群里发过话」，**跨消息**去查。
  而一条正文不带工具调用的消息按定义不可能自己带 `SendMessage` 调用——所以这个检查永远验不到
  「同一句话重复贴」，只验得到「这一轮前面发过群」。一轮里只要中途发过一次群，本轮第一个
  （常常也是唯一一个）说完必被吞，而那通常正是结论。
- 改为**按消息**判：每一次说完都进群。防重复贴由结构本身保证——带 `SendMessage` 的那条永远不算「说完」。
- 代价与判据：模型确实可能在用 `SendMessage` 说完一句之后又用正文把同一句重说一遍（自己复读）。
  那种重复由场景段「说过的点不复述」那条约束兜着，不值得为它牺牲结论。
- **对模型的承诺同步改口径**：场景段与 `SendMessage` 回执原话都是「用过它，这一轮最后的正文就只留在你这里，
  不再贴到群里」。成员是照着做的（他确实按规矩用了两次工具），是这条承诺本身要吞结论。两处都改成
  「发出去的那几条就是你在群里说的话，同一条回复里的其余正文不会重复贴，之后每次说完照常贴到群里」。

## 修订：时间线只用本地落盘时刻（2026-09-28）

实测（智能体群「社会层讨论」）：成员窗口里一方通行的回复标 14:58，群里同一句排在光子 15:01 之后。
查档案：投递 14:58:46，回复的 `CreatedAt` 是远端模型的 `created`（UTC 整秒）14:58:52——那是**开口时刻**，
这条回复思考了四万多字，15:01:51 才说完进群。直播中的气泡盖的也是首块到达那一刻。
成员窗口显示开口时刻，群里记说完时刻，长回复两边就排成两种顺序。
（起初以为是远端时钟差一分钟，那是误读：「回复比投递还早」的那两条投递丢了时间戳，被补成了更晚的落盘时刻。）

- 回复落盘时**一律按本地落盘时刻重盖**（`SessionChatHistoryProvider.AppendOwned` 的 `restamp`），不再沿用远端 `created`；
  直播气泡在配对到落盘消息时按它校准（`ConversationItemActions.CalibrateTimestamp`）。
  群发言沿用成员消息时间（上一条修订），同一句话两边是同一时刻。
- 投递消息盖创建时刻（`GroupTranscript.DeliveryMessage`），不再靠落盘回落值。
- 落盘时把时间**夹到不早于历史里上一条**：中途插话带着注入时刻，却排在它之前那次调用的回复后面落盘，
  不夹就倒流。单调由这一处保证，不靠各处盖章碰巧对齐。
- 代价：回复显示的是说完时刻而非开口时刻；被夹过的插话显示的是它实际被读到的那一刻附近。
  存量历史里的远端标时不动，老消息的旧错位还在，新发言起正常。
- 并发下的诚实说明：成员窗口按**收到顺序**排，群流水按**进群顺序**排——并行时两人同时开口，
  两边相对顺序本来就会不一样，那是两个投影，不算错位。串行群没有这一条。

## 修订：群成员不委派，中途发群换成专用工具（2026-09-28）

实测（智能体群「社会层讨论」，白露）：她先用 `SendMessage` 把汇报发给 `to: "黑猫"`，报错回执说「留空就找默认助手」；
之后两次就照着留空，每次都派出一个后台子代理。子代理把「请求提交」当成任务，**真的做了 git 提交**；
它在群视图里看不见、群的停止按钮也停不了它；报告回来是一条 user 消息，标题恰好以「黑猫，」开头，
她把它当成用户点头，在群外的唤醒轮里接着改文件，最后那句也没进群。

- **群成员装配时去掉委派**（`AgentBuildProfile.EffectiveTools`，装配快照同一口径），角色卡本身不改，出了群照旧。
- **中途发群走 `PostToGroup`**，只收正文，没有收件人可填错。`SendMessage` 的 `group` 收件人分支删除。
  （ADR 0060 再修订：智能体形态只经 `PostToGroup` 说话，回复正文不进群；对话形态只经回复。）
- 代价：群成员不能派子代理。实测 36 个群成员会话里 `SendMessage` 一共 5 次，没有一次是正经委派，3 次填错收件人。
  要读大量材料就用自己的工具，或写进草稿目录。
- 随之消失的问题：后续报告被当成用户的话、唤醒轮在群外跑且说完不进群——这两条都以「群成员有子会话」为前提。

## 修订：建群之后增删成员、更换工作区（2026-09-30）

ADR 0048 决策 2 留的口子（名单变化走一次显式装配重建）落地。三件事与换主持人同一个代价——全员系统提示改写，
各自下一轮整个上下文按全价重算——所以沿用同一个确认口径：**群跑过（有累计花费）才弹确认**，没跑过直接改。

- **只在空闲时改**：群没在跑一波、涉及的成员也没在私聊。否则要处理轮次中途被撤、投递与审批被他占着，不值得。
  **加人与加回例外**（2026-10-04）：只往名单末尾追加，不碰任何人正在跑的那一轮，群在跑也能加（`GroupChatCoordinator.AddToRoster`，
  与取投递同一把锁）。串行这一圈的顺序开头定死，新人下一圈才轮到；并行这一波里 @ 他、或用户发言就能叫醒他。
  正在说的人这一轮还不知道新人（场景段下一轮才重建），确认框里明说；各自下一轮立刻按全价重算，代价与空闲时加人相同、只是来得早。
  摘要由闲着的成员优先来写：主持人与刚发言的多半正在说，持着闸写不成，只能按不补处理。
  成员窗口里拆投递的发言人表随名单变化重建，新人的发言不并进上一位的气泡。
- **移除 = 退群，会话留着**（上文「成员退群后副本留还是删——留」）。从名单摘掉、标 `HasLeftGroup`，`GroupId` 不动：
  右栏「已退出」区能点开看历史，删群照样级联删掉，他写在群草稿目录里的文件链接也不断。
  场景段只认名单里的人，所以他之后私聊就是一个普通角色（不再挂 `PostToGroup`、也不再去掉委派）。
  移掉的是主持人，主持人改成无。群最少留一人。
- **加回**：同一个会话放回名单末尾，历史、游标原样接上。同一个角色在一个群里只有一份成员会话——
  「添加成员」挑中已退出的角色，一律恢复那一份，不另建。
- **补历史**（新成员与加回共用，决策里的 `full / summary / none`）：
  - **不补**（默认）：游标定到流水末尾。
  - **摘要**：由一位成员用自己的模型写（复用 `GroupBackground`，附言按「新加入 / 离开后回来」两种写法），
    **默认主持人，没有就取最近发过言的成员，都没有退回不补**。用成员自己的客户端与装配好的选项，前缀缓存照吃；
    拿全局模型把群流水重读一遍一分缓存都吃不到。写的人群里未必听全（游标没到末尾），所以新人的游标定到写的人的游标，
    之后那几条原文随下一次投递照常给；加回的取两者较大。摘要落在成员会话的 `GroupBriefing` 上，
    **随他下一次投递放在最前**，不进群流水、不单独叫醒他（没有新话时白跑一轮不值），用户在他的会话里看得到。
    不过目：写得不好在群里补一句即可；要过目得多一块可编辑预览，先不做。
  - **全部**：新人游标从 0 起，加回的游标不动，下一轮一次交完。弹窗里写明条数——一次投递压缩裁不了，太长就会顶满上下文。
- **调整发言顺序**：成员行右键上移 / 下移，一次挪一位（`GroupMembership.Move`，同一把锁、整份替换名单）。
  场景段的在场名单改按入群先后列（成员会话 `CreatedAt`，同刻按会话标识），不跟发言顺序：模型用不着知道谁先说，
  串行轮次由调度器排。于是挪顺序不改写系统提示、不失效缓存，也就不弹确认。代价是有过加回的群升级后场景段变一次
  （加回的人在名单末尾、入群先后却在原位）。
- **改群名**：沿用左栏的重命名，群多两道关（`GroupChangePrompts.ConfirmRenameAsync`）：空闲才许改，跑过的群先确认。
  群名写在场景段里，与换主持人同一种代价；此前改名不问、一波中途也能改，后面轮到的人拿到的是新名。
- **更换工作区**（仅智能体群）：写回群壳，成员装配时现取（见下「修订：成员设置现取」）。旧草稿目录留着——历史里写的是它的绝对路径——
  产物区只列当前工作区那一间，删群时各工作区下的旧房间照样清掉（`AgentOutputLayout.DeleteAll` 按 id 扫全部工作区）。
  确认提示讲清三件事：旧草稿不再显示、成员历史里的旧路径不跟着改、项目级 MCP 与记忆跟着换。

## 修订：成员设置现取，名单改动与开波同锁（2026-09-30）

上一节落地后回头看，有两处是「靠同步凑对」而不是由结构保证：

- **成员的工作区与权限档不再存副本。** 原来成员各存一份，靠「每轮开跑前从群拉」与「群改了再推给成员」两套同步凑对，
  还有第三种「取值时查群」的 `PermissionOf`。现在一律现取：`GroupChatSessions.WorkspaceOf` / `PermissionOf`
  （智能体群里 agent 形态的成员取群的工作区，其余成员不绑），装配入口 `AgentBuildProfile.FromSession`、
  MCP 租约、成员窗口与右栏预演都经这两个函数；审批规则每条调用都经 `PermissionModeSource` 现取，群改档对正在跑的那一轮
  下一条调用就生效。群改权限档只发 `PermissionChanged` 让打开着的成员窗口刷新显示，没有要推的。
  成员会话上存量的那两个字段不再被读，也不再被写。
- **改名单与开波同一把锁**（`GroupChatCoordinator.TryEditRoster`）。调度与成员发群在后台线程边跑边读名单，
  「界面先查空闲、再改」两步之间可能恰好被一句发言开出一波。现在判断「有没有在跑的一波」与修改在一把锁里做完，
  撞上就返回忙；名单改成只读类型，一律整份替换，读的一方拿到的永远是完整的一份。`CanEdit` 仍在，只是给界面先问一声用。

## 修订：名单查询收口到 GroupRoster，改了就地换新（2026-09-30）

- **「谁在群里」只从 `GroupRoster` 问**：在场（名单，发言顺序）、已退出、全部三种视图。此前至少六处各写各的解引用
  （`SessionManager.MemberMetasOf`、调度器的 `RosterOf`、场景段、投递渲染、产物区、左栏拼图），数据源与口径各不相同，
  加「退群」时要逐处补「只认名单 / 连退群的一起算」。调度器与它的测试走注入取会话的那个工厂（临时会话不在索引里）。
- **群壳元数据带有序名单**（`ChatSessionMeta.GroupMemberSessionIds`）：左栏拼图按真实发言顺序拼、按名单是否变化判断要不要重拼，
  不再拿「群描述变没变」当信号。旧索引没有这一项时退回按入群先后，群壳下次落盘补上。群描述仍是成员名的展示串。
- **名单变了发 `GroupMembership.RosterChanged`**：群视图就地换一份成员列表、刷新群卡描述与人数、重列产物；换工作区同样就地重建产物区与成员列表。
  不再为此整页重装会话（那会把群流水重渲一遍）。打开着的成员窗口不跟：它们只看自己的会话，名单只影响下一轮的场景段，装配时现取。
