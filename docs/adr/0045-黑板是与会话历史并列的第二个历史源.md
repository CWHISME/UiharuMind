# 黑板是与会话历史并列的第二个历史源，群发言只存一份

> ⛔ **已被 [0046](0046-群发言投递进成员会话，群壳只记流水.md) 取代（未实现即推翻）。**
> 本文否掉副本方案的四条理由，一条是事实错误（成员之间本来就不共享前缀），其余在「送达即不可改」
> 之下不成立；现拼方案还得和 `TurnDriver` 对着干。决策 1、7 由 0046 继承，其余作废。原文保留供追溯。

群聊里每个成员**各自有一个真的 `ChatSession`**（能点进去看、能单独发消息、走同一套 `TurnDriver`），
但**群发言不复制进成员会话的历史**——它只存在**黑板**里一份。
成员会话只存**私聊**那部分。供给模型的那一份在构建请求时现拼：
`系统提示 + 黑板视图 + 私有`，按时间交织。

这**不推翻** [0036](0036-会话历史按上限驻留，本体实例永不换.md)：每个成员会话仍然有自己的
历史本体、仍然按上限驻留。新增的是**第二个历史源**。

> **决策先行，实现未落地。** 群聊尚未实现，见
> [0042](0042-对话页合并为单页，类型由左栏切换器唯一决定.md) 的未决项。

## 背景

群聊方案
（[`docs/proposals/代理人格化/群聊多角色代理设计方案_v5.md`](../proposals/代理人格化/群聊多角色代理设计方案_v5.md) §6.4）
把群成员定为 **peer**，把成员自己派出去的才叫 **subordinate**。这和 0042 拟定的实现路径不同：
0042 设想「群成员 = 复用子会话那套底层」，那条路上群成员在第 1 层，`ParentSessionId` 就够用，
不需要新实体。**成员是 peer 之后，群没有对应物了**——现状里：

- `ChatSession.CharacterId` 是**单个字符串**，没有参与者列表；
- 会话之间**只有一种关系**：`ParentSessionId`。

同时方案 §3.2 的主循环有一行伪码，对存储形态提了硬要求：

```
out = m.step( blackboard_view(m) + private(m) )
```

**每个成员有自己的黑板视图，外加自己的私有上下文。** 这一行排除了「所有人共享一份相同历史」
的做法——[§6.6](../proposals/代理人格化/群聊多角色代理设计方案_v5.md) 的私聊（铁律：成员之间互不可见）
没地方放。

## 决策

1. **成员是真会话。** 每个群成员对应一个 `ChatSession`，能在界面上点进去、能单独发消息、
   由 `TurnDriver` 驱动、在 `SessionRunRegistry` 里登记。唤醒一个成员 = 在他的会话上跑一轮。
   **用户↔成员私聊因此零新机制**：就是往那个会话发消息。
2. **黑板是独立实体，群发言只存一份。** 成员会话的历史里**不放**群发言的副本。
3. **私聊必须存在成员会话里。** 它不能进黑板（成员之间互不可见）。
4. **供给模型的那一份现拼**：`系统提示 + 黑板视图 + private(m)`，按时间交织。
5. **入群上下文策略 `full / summary / none`**（方案 §6.9）落地为**视图往回看多远**，
   一个参数，不是三套补全逻辑。
6. **会话页渲染合并两个来源**，按时间交织显示，群发言与私聊在视觉上可区分。
7. **排序键必须单调，用提交顺序不用墙钟时间。** 归并出来的序列必须是**只追加**的——
   一条带着更早时间戳晚到的消息若插进序列中间，**那一刻起前缀缓存全废**，每轮从头重算。
   仓库已有先例：剪贴板域的 `SortKey`（「列表顺序的唯一依据」，与 `CreatedAt` 刻意分开）。
8. **拼接是增量的。** 序列既然只追加，每个成员缓存上次拼好的那一份，下一轮只追加增量——
   归并成本从 O(历史长度) 降到 O(本轮新增)。

## 取舍

- **为什么不是「每个成员各存一份副本」。** 决定性的是**中途入群**：方案已经写进文档的
  `full / summary / none` 在副本方案下是三套补全逻辑，还要处理补进来的副本与别人的副本时间戳
  对不对得上；在引用方案下就是视图回看多远。**一个已经写进文档的功能，引用方案几乎白送。**

  其余三处也都朝同一个方向：一句群发言在 4 人群里存 4 份，撤回或编辑要同步 4 份、迟早会漂；
  成员退群后副本留还是删要另立规矩；而扇出写入的顺序差异会让各人的对话区前缀长得不一样，
  **恰好破坏前缀缓存最喜欢的那个形状**（同一份黑板顺序追加）。

- **为什么成员必须是真会话，而不是黑板里的一个名字。** 这是复用率的全部来源：
  `TurnDriver`、`SessionRunRegistry`、插话（注入队列）、子会话与唤醒轮、右栏面板、浮窗，
  全都以「会话」为单位。成员不是会话，这些都要重写一遍。
  而 `BackgroundSubAgentDispatcher` 现在就支持 N 个并发子会话——方案 §3.2 那句「并行跑」
  在这条路上是现成的。

- **拼接成本不在归并上，别为它选错存储。** 两个有序列表归并是 O(n+m) 的内存操作，
  万条量级也是微秒级，而它后面跟着一次几秒到几十秒的模型调用——**占一轮的万分之一都不到**。
  真正随成员数线性增长的是 **token**：N 个成员被唤醒 = N 份完整黑板发给模型。
  而这一项**在副本方案里一模一样**——存副本只是提前把同样的内容复制一份，发出去的 token 一个字没少。
  「成员越多越贵」是群聊本身的性质，治它的是方案 §3.2 的唤醒划线（大群只唤醒被 @ 者 + 主持人），
  不是存储方式。**副本方案在成本上没有任何优势，在一致性上全是劣势。**

- **为什么这不推翻 0036。** 0036 说的是「会话本体一经加载就常驻、不换实例，按长度增长的只有历史」。
  引用方案下每个成员会话**仍然**有自己的本体与自己的历史（私聊那部分），0036 原样成立。
  黑板是**并列的第二个源**，不是取代——它需要自己的驻留策略，那是新的，不是改旧的。

## 代价（明说）

- **黑板是一个新实体，要自己的落盘、驻留、裁剪、删除规则。** 「群发言只存一份」的代价是
  这一份的生命周期不再搭会话的便车。
- **裁剪规则要重新想一遍。** [0037](0037-长轮次允许从中间裁，硬顶优先于不切开一轮.md)
  与 [0038](0038-前台也按消息边界裁，跟底闸收口.md) 是按**一个会话的历史**定的。
  黑板视图被几个成员同时看着、每人的上限还不一样（模型不同），
  「裁掉一条」对谁生效是个新问题——见未决。
- **会话页渲染变复杂。** 从「读自己的历史」变成「两个来源按时间交织」。
  这是显示层的事，但它是每次打开成员会话都要做的事，性能要看住。
- **「点进成员会话」看到的东西需要设计。** 用户的预期多半是「他在群里经历了什么」，
  那就得把黑板视图渲染出来；但那些消息**不在这个会话的历史里**，
  删除、编辑、重发这些会话级操作对它们意味着什么，要逐一定清楚。

## 未决

- **黑板的裁剪与压缩口径。** 每个成员的上下文上限不同，黑板视图按谁的上限裁？
  裁剪是视图层（每人各裁各的、黑板不动）还是源层（黑板真的丢历史）？倾向前者，未定。
- **黑板的驻留策略**（对应会话侧的 `SessionResidencyPolicy`）。
  注意与决策 8 的增量缓存区分：**那份拼好的视图是缓存，随时可丢后重建**，不是第三份存储。
  N 个成员各缓存一份**在内存里**确实是 N 份，但它可以被驻留策略赶走，盘上仍然只有一份。

  [0042](0042-对话页合并为单页，类型由左栏切换器唯一决定.md)「已定」。
