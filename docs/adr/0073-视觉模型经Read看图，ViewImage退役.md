# 视觉模型经 Read 看图，ViewImage 退役

> **状态**：accepted，已实现（2026-10-08）。修订 [ADR 0053](0053-ViewImage发送时投影，历史只存路径.md) 的「挂载」一节，投影本身不变。

视觉模型原先要用单独的 `ViewImage` 看图。文件本该一把 `Read` 读完，模型也普遍习惯拿 `Read` 打开图片；
多一把工具，只是多一份每轮重发的定义、多一次选择。

决定：**视觉模型经 `Read` 看图，`ViewImage` 退役**，非视觉模型仍走 `AnalyzeImage`。`Read` 读到图片时怎么办随装配定（`EReadImageMode`）：

- 视觉模型且识图开关开着：缩成预览副本，结果给路径，图由投影带上（ADR 0053 原样）。
- 非视觉模型且 `AnalyzeImage` 挂着：说清是张什么图（格式、尺寸、大小），指向 `AnalyzeImage`。
- 都不成立：如实说这次会话看不了图，不指名任何工具。

`Read` 的描述只在第一种装配里提图片。

**哪次 `Read` 算看图只看调用参数里的路径**（`ImagePreview.IsImageRead`，按扩展名），投影、压缩估算、工具卡缩略图都用它。
`Read` 自己也只按扩展名分流：图片扩展名一律走看图，内容不是图片就报错，永远不当文本读出来，两边因此不会对不上。
若按结果文本里的 `Preview:` 行来判，读一份恰好写着这种行的文档，就会把本地任意文件当成图发出去；
那个文件不是图片的话，此后每次请求都会被服务端拒绝。

## 后果

- 不兼容旧数据：历史里的 `ViewImage` 调用不再投影，工具卡也不再显示缩略图，只剩结果里的路径文本。
- 多张图对比改成同一条回复里并行发几次 `Read`，投影本就把同一串工具结果的图合成一条 user 消息。
  原先「一次最多 4 张」的上限没有了，它从来也限不住总量。
- 探索档子代理也能看图：看图只是读，投影本来就随子会话的模型挂着。`AnalyzeImage` 仍只在可变更的档位挂（它要另调一个模型）。
- 类名随之改为 `ImagePreview`（预览副本与结果格式）与 `ImagePreviewProjection`（投影）。

## 用户已经附上的那张图，不再读第二遍

agent 形态组装用户消息时，内联给视觉模型的图片旁边**还写着一条** `[Attached file: 路径]`
（路径要留给 `Edit` 一类工具，见 `AttachmentTrayViewData.BuildUserMessage`）。模型于是常沿着这个路径再
`Read` 一次：同一张图被烘成第二份预览、投影成第二条带图 user 消息——一次白付一张图的 token
（上限 `InlineImageLimits.MaxTokensPerImage`，此后每轮重发）。
（首次那次 Read 的往返谁也省不掉，它已经发出去了；这里省的是回读循环与那份重发的图。）

决定：`Read` 读到**已经随本轮用户消息附在眼前**的图，只回一句提示（带上尺寸），不烘副本、不投影。

判据（`TurnAttachedImages`）刻意窄成四条，同时成立才拦：

- **只看供给区间（`HistorySupply.From`）里的最后一条用户消息**。不能按「历史上附加过」判：
  老消息会被压缩折叠、被交接文档截断，那之后图已经不在请求里，按历史拒绝等于让模型永远看不到它——
  一次多余的读是浪费，这个是信息缺失。扫描范围因此取与供给同一份区间：无输入轮（助手锚点重试、
  唤醒轮）里最后一条用户消息可能落在交接文档之前，那一条的图已经不在请求里。
- **发这一发的模型真的看得见图**（`ServingModelFacts.SeesImages`，与投影的附图开关、内联图降级同源）。
  看不了图时那些字节先被 `InlineImageDegrading` 换成占位，此时说「已经在你眼前」就是撒谎。
- **字节逐一致**：组装内联与 `Read` 预览用的是同一个缩图器（App 启动时注入），比的是「要发给模型的那一份」。
- **只在本轮第一次工具调用里拦**：折叠与截断都只保留最近两组（`HistoryCompaction.PreservedGroups`），
  而分组规则是「用户消息自成一组、带工具调用的助手消息连同它的结果算一组」——所以本轮开头那条消息
  迟早会跑到保留窗之外。实测（记录型叶子探针）：**第二次服务调用时它还是倒数第二组、受保护**，
  第三次起才可能被删（每轮 3 万字工具结果时第 3 发开始消失；每轮 8 千字 6 轮、6 百字 12 轮都没消失）。
  判据取更严的一侧：多付一次读是浪费，骗模型看图是损失。
  **取舍**：实测第二轮起它仍受保护，所以守门开到第二轮也安全；不放宽的理由只是
  「多省的仅一次读，而这一格需要单独评估插话（`MessageInjectingChatClient` 是每次服务调用都可能
  追加 user 消息的那个东西）对保留窗的净影响」——没量过，所以取保守那侧。

已知代价：隔了几轮再回读一张老图仍重复付一次（判据不跨轮，也不跨本轮的工具轮次）；
判据是在缩图**之后**才问的（`ImagePreview.AttachAsync`），所以为假时白跑一次缩图（解码 + 重编码）
加一次字节比较；缩图器若哪天分叉成两套，判据会静默失效——退回今天的重复读，不会错拦。
子代理与主代理走同一条 `AgentToolsetBuilder`，但资源是**两处各自造**的：
`AgentAssembler.BuildTools`（主代理）与 `SubAgentAssembly.BuildSubAgentOptions`（子代理、脑）。
两边现在都交这个判据，子代理那份用的是**子会话自己**的模型源（子代理可被指定另一个模型）；
派活前的探活输入不交——那只数工具、不跑工具。为什么必须接：子会话是可打开的会话（ADR 0021），
用户能在里面附图，也可以 SendMessage 续聊，那条路同样会产生内联图。

## 三条隐性前提，各自钉在哪

**一、工具执行时本轮用户消息已经落盘。** 判据读的是会话历史，而历史由
`SessionChatHistoryProvider` 在每次服务调用之后追加。这条不能靠注释推断：
`ToolSeesPersistedTurnInputTests` 用真历史提供器 + 脚本化客户端跑一轮，
让探针工具在被执行的那一刻去看历史里有没有本轮提问。次序若不成立，判据只是永远不命中
（退回从前的重复读），不会错拦——但是白做，所以留在测试里。

**二、`AgentToolResources.Session` 指向的就是正在跑这一轮的会话。** 它是按装配时的会话标识取会话的，
而 `HarnessCharacterRunner` 的注释写着「同一 handle 会跨会话复用」。今天找不到这样的路径
（`CharacterRunnerFactory.CreateRunner` 每次新建，`AttachAsync` 的调用方传的都是 runner 自己的宿主会话），
所以暴露为零。若将来真引入 handle 共享：旧会话恰好也贴了同一张图时，判据会在新会话里误命中——
那时要把它改成跟随当前挂接会话的来源（与 `SessionModelSource` 同一套写法）。

**三、注入的上下文消息不会把本轮提问挤出保留窗——这条只在小注入下成立。** 世界设定与知识库都以
User 消息追加在末位（`WorldSettingContextProvider`、`MemoryContextProvider`），实测每条自成一组，
**正好占满 `PreservedGroups = 2` 的保留窗**：本轮的带图提问本来就站在保护圈外，只是截断从最老一头删、
删够就停，所以通常删不到它。注入合计**超过触发线（≈6.3k token，约 2.5 万字）时它连同图必定被整条删掉**；
落在停止线与触发线之间（≈4.9k–6.3k，约 2 万–2.5 万字）时看台阶对齐——两种都可能，
实测只夹了两端：8 千字×2 还在、3 万字×2 已消失。此时判据仍会说「已经在你眼前」。**这条只压第一发**：注入是按轮跑的，第 2 发起请求里就不再带它们，
实测就算第一发被整条删掉，第二发提问与图都回来了——所以代价是「一句不实的话 + 一次额外往返」，
不是永久看不到图。改这条要么让判据看得见请求本身（那就该做在投影层），
要么在工具里重算一份压缩额度——后者正是本仓最忌讳的第二条估算路径。
