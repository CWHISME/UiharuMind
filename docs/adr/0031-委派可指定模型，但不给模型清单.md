# 委派可指定模型，但不给模型清单

派活工具（`RunAgent` / `RunReadOnlyAgent`）多一个 `model` 参数：这一趟用哪个模型。它复用既有的
**会话模型覆写**机制——子会话本来就是个会话，模型名钉在它的 `SessionModelName` 上。

**不给主代理模型清单**：不拼进工具描述，也不另开 `ListModels` 工具。名字由用户投喂，
会话页模型下拉的每一行加了复制按钮。

## 为什么要这个参数

设置页已有 `GeneralSubAgentModelName` / `ExplorerSubAgentModelName` 两档默认，解决的是**常规路由**。
缺的是「这一趟特殊」：某次调研值得上一个更强的模型，或者反过来，一次通读材料不该烧贵的那个。
从前只能改设置页——那是全局的，改完还得记着改回来。

优先级因此是 **`model` 参数 > 档位默认 > 派活者模型**：那两项设置的语义是「默认用哪个」，
而派活时点名是「这一趟用哪个」，更具体的覆盖更笼统的。

## 为什么不给清单

最直接的做法是把可用模型拼进 `## 委派` 段，或者开一个 `ListModels` 工具让主代理自己查。都不做：

1. **判断依据不在清单里。** 「这一趟该换哪个模型」取决于哪个更强、哪个便宜、哪个上下文更长——
   一串名字回答不了任何一条。给了清单，主代理选出来的是瞎猜，而瞎猜比不选更糟：
   它会自信地报告「我用 X 跑的」。
2. **清单会过期，而且不便宜。** 模型列表随用户配置变（远程接口一挂就是几十上百个），
   拼进系统提示是每轮重发的固定开销；开成工具则是每轮重发一份工具定义，
   而这个工具可能几十轮才用一次。
3. **常规路由已经有人管了。** 设置页那两档默认覆盖了绝大多数情况，剩下的「这一趟特殊」
   本来就是用户的判断。

于是链路是：**用户在模型下拉点复制 → 粘进对话 → 主代理原样传给 `model`**。
`## 委派` 段里那句话因此明确写着「不清楚有哪些模型就别猜，问用户——你看不到模型列表」。

复制的是 `ModelName` 而不是 `ModelId`：前者是全局唯一 key（本地与远程同一命名空间，
`LlmManager.CacheModelDictionary` 按它查），后者是发给接口的标识，本地模型恒为空串。

## 名字不可用时：当场不钉，并且说出来

模型名解析在这个仓库里**从不抛异常**——`ChatSession.ChatModelRunningData` 查不到就
`?? LlmManager.Instance.CurrentRunningModel`，静默回落全局（`ChatSession.cs:380`）。
这对用户手工钉的会话模型是对的（名字保留，模型回来自动恢复），但对子会话不成立：
它是 AI 派出去的、生命以分钟计的东西，「等模型回来」这个好处根本轮不到它。

所以这里沿用 `ResolveSubAgentModelName` 原本那条更严的语义：**查得到、跑得起来、客户端就绪
才钉上去**，否则退回档位默认。`PinnableModelName` 是这条判据的唯一出处。

**并且必须告诉派活方。** 回退是静默的，主代理没有任何别的渠道能知道它指定的模型没生效——
不说的话它会一直以为跑的是它点的那个，甚至据此解读报告质量。告知句放在**回执**里
（`BackgroundSubAgentDispatcher.Dispatch` 的 `notice`），理由与 ADR 0025 里那条
「这一次尚无结果」一样：回执紧挨着误读发生的那一刻。

两条硬约束，都有测试钉住：

- **只在真的回退时才加**。回执是每次委派都付的钱，没发生的事不该占位。
- **排在 `[sub-session: …]` 之前**。那一行是跨模块契约（`ToolCallItem.ParseSubSessionId` 认末行），
  告知句缀在它后面，「查看过程」入口会连同这次委派一起消失——而这条支路只在名字写错时触发，
  实机上极难复现。

## 本地模型基本用不上这个参数

这是产品上要认清的一条：**本地模型一次只能跑一个**（`llama-server` 端口写死，
`LlmManager.SetCurrentRunningModel` 切换时先 `StopRunning` 前一个），而且
`EnsureModelStarted` 对本地模型**直接 return 不自动加载**（要走顶栏的风险确认流程）。

于是指定一个没在跑的本地模型必然回退；而如果它在跑，它就已经是全局当前模型了，指定与否没区别。
**这个参数实质上只对远程模型有意义。**

不为此做特殊处理（比如指定本地模型时触发切换）：那会**停掉派活者自己正在用的模型**——
委派到一半把自己的脑子换了。复制按钮也不按远程/本地过滤：清单不进 AI 的上下文，
不存在「诱导无效委派」，而用户复制本地模型名可能是为了别的用途。真指定错了，回执会说。

## 顺带：模型切换器搬进会话头部

`SessionModelPanel` 从前只挂在 `ChatPage` / `AgentPage` 的右栏。子会话窗口
（`QuickChatViewWindow`，只嵌 `ConversationView`、没有右栏）因此**换不了模型**——
而那恰好是最该能换的地方：委派已经派出去了，用户想换个模型让它重跑一遍，只能去改全局设置。

现在头部那行只读的模型名变成可点，点开是同一份 `SessionModelPanel`（控件一行未改，
只是换了宿主），右栏那两份撤掉。「显示当前模型」与「换模型」合成一个控件，
一个值也不再有两处能改。

这条同时让「用户自己进子会话换模型」成为 `model` 参数的人工兜底路径。

## 已知代价

- **`model` 参数是每轮重发的工具定义的一部分**（约 50 词）。它只在用户投喂名字时才用得上，
  但定义每轮都发。这是选了「参数」而非「工具」的直接后果——反过来开一个 `ListModels`
  工具的固定开销更大。
- **主代理不能自主选模型。** 这是有意的（见上），但如果将来模型元数据（能力、价格、
  上下文长度）进了应用，「给清单」这个决定值得重新审视——那时清单才真的能支撑判断。
- **右栏各空出一格**，没有重排。
