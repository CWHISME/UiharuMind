# 本地生图接入 stable-diffusion.cpp：引擎共用分发与进程两层，本地条目进生图回退

> **状态**：accepted（2026-10-08）。

接 stable-diffusion.cpp（下称 sd.cpp）之前已有两种本地引擎：llama.cpp 与 audio.cpp。三者在「怎么下、怎么装、
挑哪个版本、怎么起进程、闲了停掉」上几乎一样，在「怎么问模型」上毫无共同点：chat-completions、音频接口、
异步任务（提交 → 轮询进度与预览 → 取图）。第三种来了，正好把前一半收成共用的，后一半各管各的。

## 共用靠组合，不靠基类

三种本地引擎共用**分发**（`EngineDistribution<T>`：版本扫描、远端发布、下载安装、选中在用）；
设置页的引擎卡、「获取模型」里「没装引擎先装」、启动时的更新检查都只认 `IEngineDistribution`，加一种引擎不动它们。
语音与生图两家还共用**进程**（`LocalServerHost`：用到才起、健康探测、连续失败冷却、闲置停），再加各自的模型解析与任务接口。
文本引擎的进程不走这一层：它由用户加载 / 卸载模型驱动、带加载进度，归模型运行时管。

不用抽象基类：三家问模型的方式没有公共形状，基类只能塞进一串「只有某一家实现」的模板钩子；
而 sd.cpp 的「一个进程只装一个模型、换模型就换进程」这类规矩，放在它自己的类里才看得见。

## 本地生图模型进同一张生图回退列表

不另起一张「本地生图模型」表：`GenerateImage` 已经按 [ADR 0052](0052-生图模型单独登记，回退只认这一家用不了.md)
的列表顺序回退，本地模型就是又一家「可能用不了」的。生图模型多了一种接口格式「本地」，组件与采样参数记在条目上。

失败分类沿用三类：引擎没装、缺组件、起不来、进程崩了、内存不够、超时，都算**这一家用不了**，换下一个；
参数不合法算**请求本身不行**，停下。本地不花钱，没有「可能已扣费」一类——所以本地超时也换家。

## 可下载列表照 sd.cpp 文档转写，档位定死每个槽位

不像对话模型那样搜 HF 仓库让用户挑：sd.cpp 的一个模型是几个文件的组合（扩散模型、VAE、一到两个文本编码器），
配错了要到加载时才炸，而且炸的信息用户看不懂。决定：应用内置一份清单，照**固定的那版** sd.cpp 文档转写，
每个文件都用 HF API 核对过大小与 sha256；每个家族给两三档（省内存 / 均衡 / 高质量），一档把所有槽位定死。
文档列了的图像家族都收（视频不收），合适的标「推荐」，没在这里实际出过图的标「未测试」。
只有 gated 仓库有的文件优先换不 gated 的镜像（如 FLUX 的 VAE 用 Comfy-Org 的）。

组件按仓库落进**同一个模型目录**、记进同一份模型清单，标「只作组件」：同一个文件只存一份、几个生图模型共用，
删时按引用删，用户当对话模型下的不删。为此模型分类也改了：文件头没写架构的 GGUF 归「认不出」，
带扩散架构的归「生图扩散模型」，都不再默认当对话模型——否则一个文本编码器会混进对话模型列表，删掉它生图就坏了。

## 引擎版本钉住验证过的那版

sd.cpp 没有正式版本号，发布就是 master 的构建号，启动参数与接口改得勤。可下载清单与参数拼法都对着某一版验证，
于是钉住它：没装时一键装的是这一版，钉住的版本随应用发版往前挪，更新点只在本机比它旧时亮；更新的构建列着可以手动装，不提示。

## 进程与取消

一个 sd-server 只装一个模型、一次只出一张：出图在我们这边排队，换模型就换进程，闲置十分钟自动停，还回内存。
sd-server 只能撤还在排队的任务，所以在算的那张取消就停进程，下次重新加载。启动 / 加载与出图各有各的超时。

后续（2026-10-09）：进程宿主统一按**启动指纹**换进程——调用方带上这次要的指纹（程序、模型、启动设置），与在跑的不同就在下次用时换，
换之前先等旧进程退干净，免得两份权重同时占内存；语音改启动设置也照此办，不再当场停掉。
拉起前按**此刻可用内存**查一次（各引擎给占用粗估，生图按组件大小加工作区，开了内存映射时权重只算四分之一），
判为危险就不起：智能体出图按「这一家用不了」换下一家，但不熔断——内存是此刻的事；画图窗口有人看着，问过可以照样起。
语音引擎启动时不装模型（按需加载、自带剩余内存下限），不做这一查。llama 的对话进程仍不走宿主（见上「共用靠组合」），
它的加载风险确认照旧。
参考 ollama 与 jan 之后又定了三条：加载超时按**停滞**算（启动日志还在动就接着等），大模型冷启动慢不再被固定秒数误杀；
状态条显示引擎进程的**实际占用与 CPU**（macOS 取活动监视器那一列的物理占用，不像 ollama 那样逐家解析日志）；
画图窗口内存不够时，若本地对话模型或语音引擎在跑，多给一个「先释放它们再加载」——只在有人看着的入口，
不学 ollama 自动卸别的模型。macOS 的可用内存取 vm_stat 与内核 memorystatus_level 中大的：只看 free+inactive
（或 ollama 那种连 inactive 都算占用的口径）在 16G 机器上常只剩两三 G，会把跑得动的模型拦下。

后续（2026-10-09，第三轮）：本机资源读数。模型页页签行右侧显示整机可用内存与 CPU，对话页模型栏显示当前本地模型的实际占用，
点开是同一张明细（对话、知识库嵌入、生图、语音各一行，可逐个停）；只在看得见时每 3 秒刷，读进程与系统在后台线程。
读数旁的圆点在 macOS 上跟内核的内存压力档走（活动监视器那条线），因为可用余量看不出已经在压缩、换页；Windows、Linux 系统不给档，
按可用占总量分档。可用的数字仍与拉起前检查同一口径，不另算一个。
同时修了对话模型的 KV 缓存估算：原先按嵌入维度算，等于假设每个注意力头都存 K/V，GQA 模型会多估数倍
（mythos-nano 16 头只有 2 个 KV 头，32K 上下文估 9.7G、实际约 1.1G，整体从 11.3G 降到 2.9G，实测 2.7G）。
改为 KV 头数 ×（K 维 + V 维）× 元素字节，与 ollama 的 PredictServerVRAM 同式；元素字节按设置里的 KV 缓存类型（额外参数里的 -ctk/-ctv 优先），
量化类型按 ggml 块大小算。还没做的是独立显卡：显存里的权重与 KV 不在进程占用里，拉起前检查也只比系统内存，留到与上下文减半重试同一轮。

后续（2026-10-09，第四轮）：显卡与内存不够重试。显存改问 `llama-server --list-devices`（与 ollama 同法，ggml 各后端自报，
N 卡、A 卡、Intel、Vulkan 都认），不再靠 nvidia-smi；结果缓存 30 秒，加载前当场重取。独立显卡上判风险只拿放不进显存
（留 1 GB 余量，与 --fit 默认一致）的那份比内存，手动指定层数超出空闲显存直接判危险；macOS 统一内存照旧只看内存。
对话 llama-server 默认带 `-lv 4`（加载细节与各设备缓冲要到这一档才打，推理时每轮多二三十行），额外参数自带日志档位的不加；
加载日志里按设备累计缓冲，独立显卡上状态读数多一段「显存 x GB」。加载时分配失败（日志尾巴里有各后端的内存不足说法）且还没就绪，
上下文减半再试一次，最小 2048，实际上下文随之回报给历史预算。实测 macOS 上上下文超大时 llama-server 并不失败，而是挤进交换区、
推理时才报 Metal 内存不足，所以这条重试主要护住独立显卡，macOS 仍靠加载前的确认。
KV 缓存类型可按模型单独设（K、V 同用）：额外参数里的 -ctk/-ctv 优先，其次模型自己的，最后引擎设置；估算走同一顺序。

## 代价

- 内置清单随应用发版，sd.cpp 文档出了新家族要等下个版本；用户可以手动改条目上的组件与参数兜底。
- 一个家族多档共用组件，删一档时只删它独有的文件，磁盘上可能留着另一档还在用的大文件，这是有意的。
- 「未测试」的家族只核对了文件，参数照文档转写，跑不起来时会按「这一家用不了」回退，用户看到的是跳过原因。
