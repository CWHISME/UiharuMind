# 日志存储选纯文本而非 SQLite，正文外置

日志的**唯一真相源从内存改为磁盘**。内存只保留索引项（文件 id / 偏移量 / 长度 / 级别 /
分类 / 时间 / 首行预览），正文按需从磁盘读。

磁盘格式是**纯文本**，两个文件：

- `Log.txt` —— 时间线主流。每条写成 `[时间][级别][分类] (N chars)` 一行头 + 原样正文，
  条目间空一行。
- `Bodies.txt` —— 超过 4KB 的正文外置到这里，主流里那条只留摘要与引用。

定位**不靠解析、不靠长度前缀、不靠分隔符扫描**：写之前记下 `StreamWriter` 的当前 offset，
直接存进索引项。滚动时旧文件只改名，offset 依然有效。

## 为什么

1. **内存曲线原先正比于日志字节数，而不是条数。** `LogManager` 全量驻留内存（5000 条），
   `LogItem` 每条还额外存一份 200 字的短串，`LogViewModel` 再独立持有 2000 条。一条大上下文
   LLM 请求正文就是几百 KB，几十条就是几百 MB。改成索引后，内存占用变成**只跟条数有关**——
   10 万条约 8MB。

2. **原先只有退出时才落盘，崩溃即全丢。** 而崩溃前那几条恰恰是最需要的。改成缓冲追加后，
   崩溃最多丢掉正在写的那一条。

3. **原先真正丢内容的是 `LogSafetyLimit = 256KB`。** 它存在的理由是"不该让一条日志吃掉整个
   面板"——面板现在只吃索引，这个理由消失了，闸随之取消。用户"看不清参数"的症状到此为止。

4. **选纯文本而不是 SQLite，是因为第三方可读性压倒实现便利性。** SQLite 本可一次性替掉分帧、
   索引、滚动、崩溃恢复四样自研代码（`Microsoft.Data.Sqlite` 已随
   `CommunityToolkit.VectorData.SqliteVec` 在依赖图里，`MemoryStore` 也已在用），代价只有一个：
   **不能 `less log.txt`**。但日志的主要消费场景是「用户在 issue 里贴一段」「远程看别人机器上的
   日志」，两者都要求纯文本。这一条否掉了其余所有便利。

5. **手写分帧的脆弱性被"不回读历史"消掉了大半。** 曾经把"崩溃后重新扫描恢复索引"算进成本，
   因而觉得长度前缀方案脆弱。但索引只覆盖当前进程写入的内容，从不重扫——偏移量是**写的时候就
   记下的**，根本不解析文件。唯一的失败模式是"最后一条写了一半就崩"，而那条本来也没写完。

6. **正文外置同时满足了时序与体量两个诉求。** 曾经打算把 LLM 请求正文单开一个文件，被否——
   发送前后的模型选择、工具审批、错误跟正文同属一条因果链，拆文件等于砍断时序。外置的是**正文**
   而不是**条目**：条目仍在主流原位，`Log.txt` 因此既保持完整时间线，又只有几百 KB、一眼能扫完。

## 取舍

- **分类不分文件，保留策略靠按分类删。** 合流的代价本来是"保留策略没法差异化"——请求正文会把
  通用日志挤走。正文外置之后这条不成立了：`Bodies.txt` 与 `Log.txt` 各自滚动，前者按容量留最近
  几百次请求，后者按天留。

- **接受死链。** `Bodies.txt` 滚动会让旧条目的正文引用失效，面板显示「该条正文已因日志滚动被
  清理」。另一条路是让 `Bodies` 的保留跟 `Log` 对齐，但正文比条目大三个数量级，硬要对齐等于
  没有滚动策略。

- **刷盘策略按流分化，64KB 那道阈值从主流上撤掉。** `Flush()` 只推给操作系统页缓存，不是
  `fsync`，代价是一次系统调用。主流条目都是几百字节，阈值实际永不触发，留着只会让人误以为它在
  起作用；改为 2 秒定时器 + `Error` 立即刷。`Bodies.txt` 每条写完即刷——一条本身就是 KB~MB 级，
  攒着没意义。

- **没有内存热区。** 曾打算留最近 500 条完整正文做读取缓存，与"内存只留索引"直接打架：500 条
  里只要有几条大请求就又是几百 MB。改为读取时若 offset 落在未刷盘区间就**先 Flush 再读**——
  用户点开某条是"每分钟几次"级别的频率。

- **写入改为后台单写线程 + `Channel`，`SpinLock` 删除。** 顺带修掉一个隐患：`OnLogChange` 的
  订阅方一抛异常，打日志的那个业务线程就跟着炸。

- **面板倒序靠反转只读视图，不是 `Insert(0)`。** 底层索引仍只 `Add` 到尾部（不搬数据），反转
  视图对外发的 `Insert(0)` 只是通知语义上"旧条目可见序号 +1"，虚拟化面板据此整体下移一格。
  `Insert(0, item)` 则是真搬 10 万个引用。

- **`SaveLog` 里那句 `SaveUtility.Save()` 拆出去。** 保存配置搭日志的车，加上
  `Log.CloseAndFlush()` 被挂在**会吞掉异常、不退出进程**的 UI 线程异常处理器上，导致
  **一次被吞掉的 UI 异常就把日志轮换一代、覆盖掉上一次运行的 `LastLog.txt`**。
  `CloseAndFlush` 语义改为只 Flush 不轮换。

- **旧的 `Log.txt`/`LastLog.txt` 是 JSON 数组格式，不写迁移，启动时识别到就删。** 它们只对
  上次运行有意义。

## 代价（明说）

- **滚动、缓冲刷盘、索引、反转视图四样都是自研代码，正确性全压在自己身上。** 换来的是一份
  任何人用任何编辑器都能打开的日志。

- **`Log.txt` 与 `Bodies.txt` 必须成套给。** 用户只发主流的话，大正文全是死链。面板的
  「打开日志目录」按钮因此指向目录而不是单个文件。

- **日志目录的体量上限明显变大**（主流 8MB×3 + 正文 64MB×2）。原先是"内存里 5000 条、
  磁盘上两份快照"，现在是真正的滚动日志。
