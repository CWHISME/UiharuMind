# 思考回填改为消息对象绑定，序号对齐退场

> **状态**：accepted（2026-10-30）。
>
> **前置**：[ADR 0100](0100-加密思考票据按消息各挂各的，随消息落盘，收成协议无关的思考模块.md)
> 解决了「票挂在哪条消息上」（挂在消息里，随消息落盘），本文解决
> 「发请求时怎么把票找回到那条消息上」。上一版的答案是「数第几条助手消息」，
> 本文把这个约定整个删掉。

## 背景

### 一、序号对齐能防住什么，防不住什么

`ReplayPlan` 按助手消息出现顺序收两张平行清单（明文思考、加密票据），
改写器在 wire 上再数一遍助手消息，第 N 条配第 N 项。当时配了一道数量闸门：

```
wire 上 3 条助手消息，收集到 2 条 → 整段回填不发
```

这道闸门能挡住**增删**（条数变了），挡不住**改**：

- 用户编辑或重新生成一条助手消息 → 条数不变、内容换了 → 闸门放行，思考绑到新内容上。
- 消息对象在收集之后、序列化之前被就地改（历史是可变集合，界面线程随时能改）→ 同上。
- SDK 把两条消息合并、拆开、调序而条数不变 → 同上。

而错配**不会换来 400**：服务端照收，只是那条思考配到了别的消息上，语义安静地脏掉，
事后只能翻 `Bodies.txt` 逐条对。ADR 0095 记的就是这个代价。

`ReplayPlan` 里的「冻结」（`[.. messages]`）只冻住了列表，没冻住消息对象——
它挡的是「列表被换掉」，不是「某条消息被改」。

### 二、前提被证伪：MEAI 其实留了注入点

上一版的注释写着「`Microsoft.Extensions.AI.OpenAI` 不提供 ChatMessage→wire 的转换器注入点，
它会把 `TextReasoningContent` 直接丢掉，所以只能等 SDK 序列化完在字节层补回去」。

前半句对，后半句的推论错了。`OpenAI.Chat.ChatMessage` 确实没有公开的
`SerializedAdditionalRawData`，但它有 **`Patch`**（`System.ClientModel.Primitives.JsonPatch`，
带 `Set` 重载）；而 MEAI 的 `ToOpenAIChatMessages` 第一件事就是：

```csharp
if (input.RawRepresentation is OpenAI.Chat.ChatMessage raw)
{
    yield return raw;
    continue;
}
```

两件事合起来就是注入点：**自己造一条 `OpenAI.Chat.ChatMessage`，把思考用 `Patch.Set`
写进它，挂到 `ChatMessage.RawRepresentation` 上，MEAI 原样发出去。**

实测（真实 SDK 10.10.0 + OpenAI 2.13.0，假 HTTP handler 抓请求体）：

```
输入  ChatMessage(RawRepresentation = AssistantChatMessage{ Patch.Set("$.reasoning_content", "先想一下") })
输出  {"role":"assistant","content":"查一下","tool_calls":[...],"reasoning_content":"先想一下","reasoning_details":[...]}
```

同一批里没挂 `RawRepresentation` 的那条助手消息，思考照旧被丢掉——正是要解决的问题。

`Patch` 的值按插入顺序追加在已知字段之后，与旧做法在字节层 splice 的落点**完全一致**，
所以前缀形态不变。

## 决定

### 1. 思考跟着消息对象走，不再数序号

一条助手消息要发出去的思考，在**建消息对象的那一刻**就写进那个对象。
wire 上不存在「第几条」这个概念，错配在结构上不可能发生：

| 旧 | 新 |
|---|---|
| 收集 `List<string?> reasoning` + `List<string?> tickets` | 无 |
| wire 上数 `assistantIndex` 逐条对位 | 无 |
| 数量闸门 | 无 |

历史怎么增删改都不影响：思考只可能出现在它自己那条消息上，或者干脆不出现。

### 2. 谁接管、谁兜底

绑定发生在 `ChatCompletionMessageBinder`：把一条 `ChatMessage` 复刻成 MEAI 会造出的
`OpenAI.Chat.ChatMessage`，再 `Patch.Set` 两个字段。**只接管能复刻准的消息**：

- 角色必须是 assistant；
- contents 只允许 `TextContent` / `FunctionCallContent` / `TextReasoningContent`。

任何一条不满足 → 返回 null，这条消息**原样交回 MEAI**、这一轮不回填思考（fail closed）。
与旧做法在数量闸门触发时的行为一致：宁缺毋滥。

> **作者名是这里最容易踩空的一处**：`ChatSession.CreateMessage` 给**每条**消息都填了
> `AuthorName`（按角色取人名）。所以「作者名非空就不接管」等于「assistant 消息一律不接管」，
> 回填整个失效。正确做法是连 `SanitizeAuthorName` 一起复刻——它只留 `[a-zA-Z0-9_]`、
> 超 64 截断；中文角色名清洗后是空串、落成 `null`，wire 上不出现 `name`。

复刻的三种 wire 形状（实测，与 MEAI 逐字节相同）：

```
只有正文      {"role":"assistant","content":"你好"}
有正文+工具   {"role":"assistant","content":"查一下","tool_calls":[...]}
只有工具调用  {"role":"assistant","tool_calls":[...]}
```

### 3. 门禁位置不变，仍然只在 `LazyChatClient`

票据的 provider + model 双等门禁留在 `ReasoningGateFilter`（ADR 0100 补记定的），
三条协议线共用。绑定器只读「过滤之后还剩什么票」，自己不再判门禁——
门禁在哪只有一个说法。

### 4. 数量闸门退场，`FillEmptyReasoning` 留下

「每条助手消息都必须带思考字段」那类服务端校验（DeepSeek 系、网关）要的是
**字段存在**，不是字段有值。这条改写不需要知道是哪条消息——给缺字段的助手消息补空串即可，
天然不会错配，留在 `ChatCompletionsRequestRewriter` 里。

已经由绑定器写进去的字段它不覆盖（原有 `hasReasoning` 判断照旧生效）。

### 5. 不碰历史里的原消息

绑定器不原地改 `ChatMessage`，而是用 `ChatMessageCopies.WithContents` 克隆一条再挂
`RawRepresentation`。理由有两条：持久对象里不该出现 SDK 的运行时引用；
`ChatMessage.Clone()` 会把这个引用一起带走，下一轮容易读到上一轮的快照。

（`RawRepresentation` 在 M.E.AI 上是 `[JsonIgnore]`，实测不落盘，但「不落盘」不等于「可以随便挂」。）

### 6. 不为老会话留兼容（2026-10-30 追加）

老档案不再使用，所以上一版攒下的三处兼容一次性删掉：

| 删掉的 | 原来防的是 |
|---|---|
| `ReasoningGate.UnknownProvider` 与「provider 读不出就只比 model」 | 旧版 `ProviderId` 取的是容器类名，所有远程供应商同名 |
| 拼接多段思考碎片 | 老会话的思考是逐 chunk 落下的碎片（落盘往返时 `ChatContentNormalizer` 已并回一段） |
| 回填前的 `ContainsEncrypted` 假票闸 | 旧版提取器把工具参数当票据存了下来 |

代价写清楚：**老会话里那些 provider 没有区分力的加密票据一次性失效**，那几条的推理链断一次。
它们本来也没被门禁保护过（provider 那时恒等，双等形同虚设），所以不算倒退。

## 落地

```
AI/Reasoning/ReasoningReplayPolicy.cs     该不该回填、回填键名（模型声明驱动，两条线共用）
AI/Net/Request/ChatCompletionMessageBinder.cs   一条消息 → 带思考的 wire 消息（chat 线专属）
AI/Net/Request/ReasoningReplayChatClient.cs     管道位置：chat 客户端之外包一层
```

接线点：`ChatClientFactory` 的 chat 分支包一层；`LazyChatClient` 只留门禁过滤。

**删掉的**：`ReplayPlan` 整个类、`LlmRequestContext.PendingReasoningSource`、
`LlmRequestContext.ReasoningTickets`、`RequestRewrite` 的两个清单参数、
改写器的 `ScanMessages` 对位计数与 `Commit` 数量闸门。

**协议归属**：只改 chat 线。responses 线与 messages 线的密文由 SDK 自己从
`TextReasoningContent.ProtectedData` 读出来往返，本来就没有序号这回事。

### 测试

- `ChatCompletionMessageBinderTests`：一条消息只带自己的思考、增删之后不串台、
  票据与正文互不干扰、假票不发、不原地改源消息、三种 wire 形状与 MEAI 逐字节相同、
  作者名清洗口径与 MEAI 一致。
  其中两条是端到端（真客户端 + 假服务端）：思考确实进了请求体且落在自己那条上；
  **同一批消息带思考（我们接管）与不带思考（MEAI 自己转）的请求体，除思考字段外完全相同**——
  这条是复刻转换的防漂移测试。
- `ReasoningReplayTests`：取法本身（碎片拼齐、非助手消息不取、只有票没有正文）。
- `ReasoningTicketStabilityTests`：三轮与跨重启的历史字节稳定性，走的是生产路径那两步
  （门禁过滤 → 按消息绑定 → SDK 序列化）。
- Core 全量 3449 条 0 失败；App 全量 1262 条 0 失败（2026-10-30）。

### 真实模型验证（2026-10-30）

隔离档案 + `--dev-script` 跑两轮/三轮真对话（`src/Build/Tmp/WinDebug` 的 Debug 发布件，
不碰运行中的那份档案）：

| 模型 | 发数 | 结果 |
|---|---|---|
| `Agnes-3.0-Flash` | 2 | 第 2 发的助手消息带 `reasoning_content`，system/user 不带 |
| `(CCG)Beam 1.0` | 3 | 每发都带，且**前缀纯追加**（前一发 N 条与当前前 N 条逐条相同） |

Beam 这一列是关键：它是「每条助手消息都必须带思考字段」的那类模型
（`ReasoningRequirementErrorHandler` 就是为它写的），三发全部 200、没有一次 400。
字段落点是 `role, content, reasoning_content`——与旧的字节级 splice 一致。
Agnes 只给明文、不给 `reasoning_details`，票据那条路这次没被覆盖到
（它需要闭源模型，见 ADR 0100 的实测记录）。

## 取舍

- **为什么不保留序号 + 加内容指纹校验**：指纹只是**检测**错配，不是**消除**错配；
  而且指纹要复刻 SDK 的文本投影，投影一变就静默失去回填——比现在更脆。
  `Patch` 这条路已验证可行，没有理由选检测方案。
- **为什么复刻转换而不是只接管「纯文本回复」**：工具调用消息恰恰是最需要回填的一类
  （DeepSeek 只查带 `tool_calls` 的），漏掉等于主要场景不生效。
- **为什么不顺手把 responses/messages 线也改成 `Patch`**：那两条线的 SDK 本来就不丢密文，
  没有要补的东西。`Patch` 是 OpenAI chat 线的缺口补丁，不是通用机制。

## 已知代价

- **升级后第一次请求会让该会话的前缀缓存冷一次**：字段落点虽然一样，但拼接路径换了，
  字节可能有微小差异（例如 `reasoning_content` 与 `reasoning_details` 的先后）。
  只影响一次。
- **复刻的转换与 MEAI 版本耦合**：MEAI 改了 `ToOpenAIChatMessages` 的映射，
  我们那份就可能与之分叉。缓解：只接管三种内容类型，其余一律退回；
  并用「同一批消息分别走 MEAI 与本绑定器，请求体逐字节相同」的测试钉住。
- **`JsonPatch` 是实验 API**（`SCME0001`）：需要 `#pragma`。MEAI 自己也在用它读响应，
  短期内不会消失；真消失了，编译期就会报错，不是运行时静默失效。
- **转义后的思考正文会常驻一份**：`EscapedLiterals` 按正文的字符串实例弱引用缓存，
  消息活着它就活着（3000 字/轮的会话约 0.9 MB）。换来的是每请求不再重新转义 1.5 MB——
  这笔账在 `docs/perf/` 的补测里有读数（1.67 MB → 165 KB）。
