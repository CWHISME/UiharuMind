# 会话流不做面板虚拟化，改为视口外卸载正文

决定：**会话流继续用非虚拟化的 `ItemsControl`，容器一个不少**；但给气泡正文补上
「滚远了就把视觉树整棵拆掉、只留一个**等高**空占位」的那一半。滚动区高度因此分毫不动，
跟底、滚到顶续窗、前插补偿三条路径一行都不用改。

同时收紧两处常驻：TextMate 注册表全进程共用一份，窗口缓存补上全局上限与空闲淘汰。

## 现场

一个跑了约五小时、然后一直放着不动的 Debug 进程，`phys_footprint` **921MB**（峰值 1039MB）：

| | |
|---|---|
| 托管堆已提交 | 475 MB（gen2 存活 410MB、LOH 47MB，碎片只有 4MB） |
| MALLOC_SMALL / LARGE | 236 MB |
| graphics + IOSurface | 96 MB |

已提交 475MB 对存活 410MB——**GC 没浪费，是真的有 410MB 活对象**。

把 gcdump 的 485 万个对象按归属分桶：

```
200.8 MB (48.9%)  System.*      52万 string / 18万 字典桶数组 / 24万 int[] / 21.8万 byte[]
129.1 MB (31.4%)  Avalonia      UI 树、样式、渲染
 31.7 MB ( 7.7%)  TextMateSharp
 13.5 MB ( 3.3%)  Svg/Skia
 10.9 MB ( 2.6%)  ML.Tokenizers
  1.7 MB ( 0.4%)  UiharuMind    ← 自有数据几乎不占
```

**吃内存的不是数据，是渲染数据的控件树**，而那 200MB 的 `System.*` 绝大部分也是
Avalonia 的属性存储（`StyleInstance` 9.5 万、`StyleClassActivator` 9.9 万、
`DynamicResourceExpression` 9.6 万、`WeakReference<AvaloniaObject>` 16 万）。

关键计数：**3 个 `ConversationView` / 17 个 `ConversationViewModel`**（14 个是后台会话，
已被 `TrimToBackgroundBudget` 裁到 10 条），实化出的卡片 205 张，
对应 **16,018 个 `CompositionDrawListVisual`**——**每张卡约 78 个可视对象**。

空闲本身没问题：40 秒 idle 采样只有 1 次 `AllocationTick`、9 个 GC 事件。
**不是放着不动涨上去的，是用过之后没降下来。**

## 为什么仍然不用虚拟化面板

`ConversationView.axaml` 的注释早就写着「已实测不可用」，这里补上源码依据：
虚拟化面板的 `Extent` 是按**已实化项**估算的，不定高气泡下估值一直在变，
于是进度条跳变、滚动回跳、与跟底互搏。而本仓的滚动语义全部建立在
「Extent 是真实测量值」之上——`AnchorToBottom` 迭代贴底、`PrependKeepingViewport`
按前插高度补偿 Offset、`OnViewerScrollChanged` 判 `Offset.Y` 续窗，三条都要求 Extent 可信。

**换个说法：真正要省的从来不是「容器」，是容器里那棵树。**
205 张卡对应 16,018 个可视对象，容器本身只占 205 个。把容器虚拟化掉是为了省那 205 个，
却要赔上整套滚动语义——不划算。

## 等高占位：省了树，留住高度

`SimpleMarkdownViewer` 原本只有「进视口才建」（`RealizeNow` / 视口通知驱动的排队），
建出来之后就一直留着——一窗 80 条全滚过一遍，80 份完整视觉树就全挂在列表上。
现在补上反向的 `UnloadForViewport()`：

- `Height` 钉成**刚刚量到的那个高度**；
- `MarkdownBuilder = null` 断掉增量源，`DocumentUpdate = null` 让库走
  `documentNode.Clear()`，视觉树整棵拆掉；
- 两个子块都收起来，高度由 `Height` 顶着。

滚回视口时由原有的视口通知触发 `ReloadIntoViewport()`：markdown 档当场转
（占位是空的，排队就是一块白板），纯文本档让占位让位即可。

## 判距离为什么在宿主，不在气泡自己

查了 Avalonia 源码（`LayoutManager.CalculateEffectiveViewport`）：

```csharp
if (control != target && control.ClipToBounds)
    viewport = control.Bounds.Intersect(viewport);
```

视口矩形被**每一个 `ClipToBounds` 祖先**求交，而 `Rect.Intersect` 无交集时返回 `default`。
所以气泡一滚出去，它拿到的矩形就是空的——**只看得出「看不见了」，看不出「离多远」**。
更要命的是同一处的抛事件条件：

```csharp
if (viewport != l.Viewport) l.Listener.RaiseEffectiveViewportChanged(...);
```

矩形不变就不抛。远处那些一直是 `default`，再怎么滚也收不到通知。

因此：`SimpleMarkdownViewer` 只提供 `UnloadForViewport()` 这个**动作**，
「离多远算远」由持有 `ScrollViewer` 的 `ConversationView` 判——
`SweepBubbleViewport()` 用 `TranslatePoint(default, Viewer)` 换算，
与既有的 `RealizeVisibleBubbles()` 同一套几何。上下各留**一整屏**缓冲：
贴着视口边缘卸载，轻微滚动就会来回拆建，而重建是要钱的。

## 量到的数（`ConversationViewLayoutTests`，无头真实控件真实模板）

60 条带代码块的回复，全部实化后放清扫过去跑一遍：

| | 正文可视对象 | 整表可视对象 | 滚动区 |
|---|---|---|---|
| 全部实化 | 1860 | 3663 | 15020px |
| 清扫之后 | **540** | 2343 | **15020px** |

正文那棵树掉到 **29%**，而**滚动区高度两边一模一样**——这是这条路子唯一的验收口径，
测试里它是第一条断言。

## 只解决了一半

清扫之后剩下的 2343 个可视对象是**卡片外壳**（头像、时间戳、气泡边框、操作行），
60 张卡摊下来每张约 39 个，本机制够不着。测试里专门留了一条断言把「还剩多少」钉住，
省得日后误以为卸载已经把列表清空了。

真实进程里那 78 个/张 里，另一半同样没接上：工具卡的 `SyntaxHighlightTextBlock`、
`DiffTextBlock`，思考卡的正文。它们各有各的实化入口，要一个个接。

## 顺手收紧的两处常驻

**TextMate 注册表（31.7MB）**：`TextMateSyntaxService.Install()` 原本每次
`new Registry(...)`。而 `SyncRegistry` 把用到的每份 raw 语法树与编译后的规则表整套挂在
自己身上，一份语法还会连带拉进它 include 的所有 scope——堆里同时活着 4~5 份时，
光 `Raw` 就有 16MB（18.2 万个对象）。改成 `TextMateRegistryPool` 全进程一份。
`RegistryOptions` 也只建一次：构造它要扫一遍全部语法的 package.json，
而它的主题参数只是**默认**主题，换主题走 `LoadTheme` 即可。

（注：`LiveMarkdown.Avalonia` 自己还有一份静态 `Registry`，是库内部的，动不了。）

**窗口缓存**：原本只有「按类型限量 2」，而窗口类型有十几种——实测 10 扇原生窗口活着，
每扇带着自己的完整控件树和一块 GPU 表面，96MB 图形内存基本就是它。
补上全局上限（4）与空闲淘汰（10 分钟）。空闲淘汰是其中唯一对「放着不动」有效的那条：
前两道闸只在「又关了一扇」时才触发，应用放着不动就永远不收。

## 还留着什么

- `ConversationViewLayoutTests.ScrollingFarAway_UnloadsBubbles_WithoutMovingTheExtent`：
  Extent 恒定是第一条断言。哪天它红了，说明等高占位的前提破了，别去调阈值。
- 开发脚本（`--dev-script`）驱动真实应用只能验「没变坏」，**验不了这次的收益**——
  它没有滚动这一步，而收益只在滚过之后才出现。真实进程里的前后对比得靠手动跑，
  或者给脚本补一个 `ui.scroll`。

## 已知的边角

- 卸载态的气泡丢掉文本选区与已渲染状态，滚回去是重建的。
- 窗口宽度变化会让占位高度过时（文本重新断行）。占位不会立刻跟上，
  而是等它重新进视口实化时自然取回真实高度——期间 Extent 略有偏差，
  代价落在「改窗口大小」这个本来就在重排整棵树的操作上。
- 流式中的那条消息永远在底部视口内，不会被卸载；只有用户上滚很远时它才会，
  那时跟底本来就已经关了。
