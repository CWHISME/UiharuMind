# 图片：发多大与按多少 token 计分开，总量按字节回差裁剪

> **状态**：accepted（2026-11-17）。定「内联图片」这一路的三个数：发出去多大、按多少 token 计、
> 一次请求最多带多少。取代 `InlineImageLimits` 里「一个长边管两头」的旧口径。

## 起因

三件看起来无关的事，查下来是同一个：

1. 两个子会话的请求涨到 12.3MB / 14.3MB 后，每一发都只回一帧 `Error processing stream start`，
   从此再没成功过——请求不会自己变小，重试多少次都是同一个 400。
2. 模型偶尔说「看不清」。
3. 图多的会话里，压缩比预期更早触发，每次都断一段前缀缓存。

## 事实（实测）

**缩图的落点（`Logs/Log.2.txt`，344 次「Image downscaled」）**

- 342 次落成 JPEG，只有 2 次落成 PNG。PNG 是编码时**第一个**被尝试的，所以这说明
  真实素材（游戏画面、带渐变的 UI）在长边上限下 PNG 编完普遍超过 `MaxInlineBytes`，
  「截图压缩率高、天然走无损」这条设计假设在真实素材上几乎不成立。
- 43 次在 q55（最低档）之下**仍超预算并照发**，最大 328KB。也就是说 150KB 这条线
  既没保住画质（一路降到 q55），也没守住体积（照发时超出一倍多）。
- 输出平均 114KB，≥150KB 的 59 张。

**上游的口径（DeepSeek 图像理解文档，2026-11 抓取）**

- 请求体 48 MiB；单图 32 MiB（base64 / URL）、64 MiB（Files API）；单请求最多 600 张；
  单边最长 8192px，**≥15 张图时降为 4096px**。
- 每张图 token **上限 1024**；进入模型前归一化到总像素约 **1300×1300（1.69M）**，
  小于 544×544 会放大。2000×2000 与 5000×5000 同价。

对照下来两件事：**12MB 那次 400 与官方限制无关**（是四分之一不到），只可能是中转网关；
而我们的 1568 长边在 16:9 下只有 1.38M 像素，**比模型自己会用的 1.69M 少 18%**，
缩下去的那一截再也放不回来——「看不清」里有一半是它，另一半是 q55。

**估算偏差（`Usage calibration`，21 次）**

系数全部落在 1.08~1.27，说明文本一直被低估 1~3 成；而图片按 `1568²/750 = 3278` 计、
DeepSeek 实际 1024，是 **3.2 倍高估**。两者挤在同一个标量里互相抵账，而且
`Calibrate` 的下界是 1（只向上调，见 [ADR 0009](0009-上下文压缩按历史水位分档，水位随模型现读.md)），
**高估永远不会被纠正**，只会让压缩提前、缓存提前断。

## 决定

1. **两个边分开**：`InlineImageLimits.MaxEdge = 1568` 是 Anthropic 的计价边（超过它服务端自己缩），
   `SendEdge = 1792` 是发送边（16:9 得 1.81M 像素，正好越过 DeepSeek 的归一化目标，它会自己缩到 1.69M）。
   多出来的像素**不多花 token**，只多花一点上传。
2. **单张字节 150KB → 400KB**。150KB 那条的原始理由（压住框架「字节数/4」的估算）已经由
   `CorrectedTokenCount` 从源头修掉，剩下的理由只是上传带宽——而带宽现在有总量预算兜底，
   于是这一档该按画质定：400KB 让多数截图回到 PNG 或至少 q85。
3. **按模型计价**（`ImageTokenPricing`），三档：
   - `DeepSeek` 固定 1024（与尺寸无关）；
   - `Anthropic` 按 1568 推（3278 封顶）——它收下后自己缩，按发送边算会凭空多三成；
   - `Default`（认不出）按**发送边** 1792 推（4281 封顶）——认不出时只有偏高这一侧安全。
   **多算的部分不能指望校准纠**（系数下界是 1）。
4. **总量按编码后字节裁**（`ImageBudget`，挂在改写链最里层：投影之后、传输之前）：
   默认 8MiB 触发、4MiB 停、48 张兜底，阈值进 `ChatSettingConfig` 由组装端注入、每发现读。
   计数口径是**请求体里的 base64 长度**（≈原始字节 ×4/3）——撞网关的是请求体，
   按原始字节算会让 8MiB 实际对应 10.7MB。
5. **占位文案分因**：预算裁掉的图要说「请求超了体积预算」，不能沿用「这个模型读不了图」——
   后者会让模型以为自己没有视觉能力，于是不再看图、也不再去读。

## 代价与边界

- **每裁一次 = 从那一条往后整段前缀缓存作废**。回差（trigger − target）就是为此存在：
  一次裁到触发线之下（通常落在停止线附近），之后要再攒够差额才动下一刀。60 张图的会话因此断 1~2 次，
  而不是像已停用的 `HistoryImageWindow` 那样每来一张新图就断一次（ADR 0006 之后停用的正是它）。
  张数那条同样带台阶（一次腾到上限的四分之三），否则「多来一张就多裁一张」是同一个毛病。
- **一张都不留是不允许的**：单张就超过停止线时（CLI 没注入缩图器、或 target 配得比一张图还小），
  宁可变大超标也要留下最新那张——模型看到「这一轮没有图」比请求大一圈更难查。
- 8MiB / 4MiB 是**保守值**：撞的是中转网关，限比官方紧得多，官方 48MiB 不能拿来用。
  确认网关真实上限之后可以放宽（届时 60 张 400KB 的图一次都不用裁）。
- **压缩估算仍按「所有图都在」计**，而实际发出去已被裁掉一部分。偏差方向偏高（早压、早交接），
  裁掉的又正好是最老那一段，可接受；真要抹平得让预算层把裁掉的量回写给 `TurnInputEstimate`，
  并且在校准里先扣掉——否则图多的会话里，`reported / ours` 会被幻影 token 拉低，
  反而把文本侧的校准系数冲回 1（那也是晚压，方向不对）。这一条留待下一步。
- **图片的清晰度问题没有全靠这条解决**：4K 截图缩到 1792 也只有 6px 的字。
  真要读细节还得靠局部放大（裁剪 / 缩放区域送过去），那是产品级改动，另开。
