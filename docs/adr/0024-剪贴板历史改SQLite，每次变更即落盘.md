# 剪贴板历史改 SQLite，每次变更即落盘

剪贴板历史从「一份全量重写的 JSON」改为 `Data/Clipboard/ClipboardHistory.db`，一张表
`history(id, created_at, text, preview, image_path, is_favorite, sort_key)`。

- **每次变更立即写**，一次变更就是一条 SQL。没有防抖、没有定时器。
- **历史不设上限**，列表**分页**加载（每页 200，游标是 `sort_key`），筛选与搜索下沉到 SQL。
- 内存里只有**预览**与主键；正文在悬停（防抖 300ms，最多 2000 字）与复制时按主键现取。
- 存储层拆成 `ClipboardHistoryStore`（`UiharuMind.Core`，无 UI 依赖），`ClipboardService`
  只留剪贴板本身的读写与监听。

## 为什么

1. **原实现每小时才存一次，退出调试模式就丢一大截。** 落盘只有两个时机：`Dispose()`，
   和一个 `TimeSpan.FromHours(1)` 的 `Timer`。调试停止是直接终止进程，`Dispose` 不跑——
   丢的就是上次整点之后的全部记录。这是本次改造的起因。

2. **「攒够再存」在这里治不了病，因为 n 无界。** 曾打算把 1 小时改成 2 秒防抖，被否：
   历史只有手动删，没有任何东西约束它的大小，而剪贴板里常常是整段代码、整篇文章。
   全量重写 JSON 是 **O(n)/次**，防抖只是把「一小时丢一次」换成「每 2 秒重写几 MB」。

3. **「加条数上限」与「能搜到很久以前那条」直接冲突。** 也曾打算加 500 条上限把 n 钉死，
   同样被否：用户要搜的恰恰是久远的那条，砍掉就等于砍掉搜索的意义。

4. **于是需求收敛成三条同时成立**：无上限、可搜索、改动是增量的（删除 / 置顶 / 收藏都是
   原地修改而非追加）。JSON 全量重写满足不了；JSONL + 墓碑能满足增量，但搜索仍要全扫、
   启动仍要全量进内存。剩下的就是数据库。

5. **这里选 SQLite、日志选纯文本，不是自相矛盾。** 否掉日志用 SQLite 的唯一理由是
   「第三方要能直接打开」——用户在 issue 里贴日志、远程看别人机器上的日志（见
   [ADR 0023](0023-日志存储选纯文本而非SQLite，正文外置.md)）。剪贴板历史是**纯私有数据**，
   没有任何人需要拿文本编辑器看它，那条约束不存在。

6. **依赖零新增。** `Microsoft.Data.Sqlite` 已随 `CommunityToolkit.VectorData.SqliteVec`
   在依赖图里，`MemoryStore` 已在直接用（本次补了显式 `PackageReference`，不靠传递依赖）。

## 取舍

- **置顶只改 `sort_key`，不碰 `created_at`。** 另一条路是复制时把 `created_at` 刷成当前时间，
  但那会篡改用户看到的日期——列表上那个时间本该是内容**第一次**进剪贴板的时刻。
  `sort_key` 是 SQLite 的 64 位 `INTEGER`，按每秒复制 1000 次算要 2.9 亿年才用完。

- **删除时存储层不删图片文件**，只把路径交回调用方，由它在记录落盘之后再删。反过来（先删文件）
  一旦崩在中间，历史里会留下一条指向不存在文件的记录，而那个没人能修；现在最坏结果是
  一个孤儿图片文件，而那正好是 `CheckAndRecordImagesInClipboardHistory` 本来就能自动回收的情况。

- **不迁移旧的 `ClipboardHistory.json`，但也不删它。** 当前用户只有作者本人，写迁移不划算；
  文件原样留在同目录下，需要时再补十行导入即可。这跟日志那次刚好相反——日志旧文件只对上次
  运行有意义，直接删。

- **自动清理默认关闭。** 无上限之后磁盘会一直涨（尤其图片）。给了一项「清理 N 天前的非收藏记录」，
  但默认 0 = 不清理：什么时候该清只有用户自己知道，给旋钮而不替他决定。
  只清图片、文本永久保留的方案没有采纳——同样是历史记录，图片会自己消失很难解释。

- **搜索用 `LIKE` 而不是 FTS5。** 关键字里的 `%` `_` `\` 会转义（不转义的话搜 "100%" 变成匹配
  任意内容）。FTS5 要额外的虚拟表与同步，等真的慢到不能用了再说。

- **列表在用户已经往下翻页之后不再自动刷新。** 复制一次就整页重建的话，正在看的位置会被顶掉。
  判据是「已加载条数是否超过一页」。

- **顺手删掉了设置页里两个空壳选项**（`Max Record Count` / `Save to Disk`）：它们从未接到任何
  东西上。历史现在每次变更即落盘，「要不要存盘」这个选项本身也不再成立。

- **孤儿图片回收不再解码图片。** 原实现把每个 PNG `new Bitmap(file)` 再原样存回去，
  那一趟解码 + 编码纯属白做，启动时有几十张图就卡几十次；现在只写一条记录。

## 代价（明说）

- **历史文件不再是人类可读的。** 要看只能用 SQLite 工具。这是为前面那三条需求付的钱。

- **`ClipboardItem` 不再持有正文**，凡是要正文的地方都变成一次按主键的查询。
  悬停预览因此多了一次异步加载与 300ms 防抖，手感上会比「早就在内存里」慢一点点。

- **多了一个 `.db` 及其 WAL 伴生文件**。`MemoryStore` 已经踩过伴生文件必须成套搬删的坑，
  剪贴板这边目前没有搬移需求，但删库时要记得同样成套处理。
