# 思考档位改为模型声明驱动，固定枚举退场

> **状态**：accepted（2026-10-29）。补 [ADR 0097](0097-模型能力表扩项：价格与思考档位进表，视觉改推导加覆盖.md)
> 的"思考档位进表"——表里有了取值，但请求侧还在发写死的四档。

## 起因

`EThinkingMode` 是固定枚举（`Default/None/Light/Medium/High/Max`），基类 `GetExtraParams`
把后四档硬翻成 `reasoning_effort: low/medium/high/max`。而 models.dev 的 `reasoning_options`
给的是每个模型真实支持的取值集合（实测 `commandcode/Qwen/Qwen3.8-27B` 是 `low,medium,xhigh`）。

两个后果：

1. 只认 `low/medium/high` 的模型收到 `max` → 服务端 400 或静默降级。
2. 声明了 `xhigh` 的模型点不到——枚举里没有这一档。

而 `ModelCapabilityResolver.ResolveEfforts` 早就把声明的取值查出来了，只用于编辑窗里显示一行摘要，
**没有任何约束力**。数据在，消费没接上。

## 决定

1. **档位是字符串，不是枚举。** `BaseRemoteModelConfig.ThinkingMode`（`EThinkingMode`）换成
   `ThinkingEffort`（`string`）：空串 = 不干预，`none` = 关闭，其余原样下发给 `reasoning_effort`。
   `EThinkingMode` 删除。
2. **候选由模型声明决定。** `SupportedThinkingEfforts` = 模型声明的取值；
   没声明回退到 `low/medium/high/max`——「没声明」不等于「不支持思考」，给空列表会让下拉消失。
3. **已知词汇翻译，其余原样。** 表里实际出现的取值只有七个：
   `minimal/low/medium/high/xhigh/max/none`（出现次数 14/167/131/177/91/98/23）。
   这七个有本地化名（`xhigh` = 超高、`minimal` = 极低），表外的值原样显示。
   声明里带 `none` 的模型（如 `opencode/gpt-5.2`）与「关闭」是同一语义，候选里只留一条，不重复。
4. **已选值不在新集合里就退回「不干预」。** 留着会让下次请求发出模型不认的档位。
   但这条只对**声明了**取值集合的模型生效：没声明的模型给的是兜底阶梯，那只是猜测，
   此时保留用户已选的值，并在候选里补上这一项。
5. **JSON 键沿用 `ThinkingMode`。** 旧存档里的枚举名（`Light`/`Max`/…）由
   `ThinkingEfforts.Normalize` 在读入时翻成 wire 值（`Light→low`），不写迁移脚本、不动存档格式。

## 取舍

- **改字段类型 vs 新增覆盖字段**：选了改类型。同款"留一档未覆盖"的结构（`IsVisionOverride`、
  `ReplayExistingReasoningOverride`）解决的是「用户手动值 vs 表推导值」的二选一；
  这里不是二选一，是「档位值本身换了表示」，多留一个字段只会让两个来源打架。
- **枚举换字符串的代价**：`ILLMModel.ThinkingMode` 一并改成 `ThinkingEffort`。
  请求改写侧本来就没读它（`OpenAICompatibleRequestRewriter.For` 只用
  `ReplayExistingReasoning` / `RequireReasoningOnEveryAssistantMessage`），改动面只在配置与编辑窗。
- **不接 `uses_token_budget`**：Claude 风格用 `budget_tokens` 表达思考强度，是第二条轴
  （数值而非档位名）。表里已有这一列，但当前六家都不用它，留到接 Anthropic 线时一起做。

## 补记（同日）：档位有了，字段名还没有

第一版只解决了「发哪个值」，没解决「用哪个字段发」——基类对任何非「不干预」的档位都同时发
`thinking: {type: enabled}` 和 `reasoning_effort`，是赌服务端认其中一个。Agnes 就是因为这个组合
经它的 litellm 网关直接 400，才被迫整份覆写 `GetExtraParams`。

### 事实（参考 pi / opencode 的实现与录制）

- **models.dev 不带字段名。** 模型字段全集里只有 `reasoning`（bool）与 `reasoning_options`
  （`type` + `values`），没有一处写 `reasoning_effort` 或 `thinking`。字段名只能按供应商族硬编码。
- `reasoning_effort` 是 OpenAI o 系引入、被 OpenAI 兼容层抄开的写法，**不是统一名**。
- opencode 的真实 HTTP 录制显示：智谱 `glm-5.2`、Moonshot `k3`、Qwen `qwen-3-8-max` 发高档位时
  **只发 `reasoning_effort`**；智谱另有 `thinking: {type, clear_thinking}` 开关，两者同发也能通；
  Groq 这类纯 OpenAI 兼容端点关闭思考时发 `reasoning_effort: "none"`。
- 七家 270 个模型的思考控制形态：`effort` 187、`toggle` 41、`budget_tokens` 5、没声明 37。
  **41 个只有开关的模型此前会收到一个它们不认的档位名。**

### 追加决定

1. **`EThinkingFormat` 三档**：`Effort`（只发 `reasoning_effort`，关闭写 `none`）、
   `ThinkingType`（`thinking.type` 开关，有档位再附 `reasoning_effort`）、
   `ChatTemplate`（`chat_template_kwargs.enable_thinking`）。
   智谱与 DeepSeek 同形（`thinking.type` + `reasoning_effort`），合成一档。
2. **预设显式声明、自定义按地址推断**：六家各自覆写 `ThinkingFormat`；自定义配置走
   `ThinkingFormats.Detect(ModelPath)`（`bigmodel.cn`/`api.z.ai`/`deepseek.com`/`agnes-ai`），认不出给 `Effort`。
3. **`reasoning_options.type` 进表**：`ThinkingControl`（`Unknown`/`Effort`/`Toggle`/`Budget`）
   取代此前生成但无人消费的 `UsesTokenBudget`。`Toggle`/`Budget` 的模型不再给档位候选，
   请求侧也不发档位名——只拨开关。
4. **Agnes 的覆写收编成格式**：`GetExtraParams` 的整份覆写删掉，改成一个
   `ThinkingFormat => ChatTemplate`。

### 已知代价

- 模型声明了取值集合、而用户的旧存档是集合外的档位时，打开编辑窗会落到「不干预」并在此后保存时生效。
  这是刻意的：那个值本来就会被服务端拒。没声明的模型不受这条影响，用户已选的值会保留。
- 声明值只来自构建期快照（models.dev），快照落后时仍可能发出服务端不认的值——与价格同源同限。
- `CommandCode` / `OpenCode` 这类网关暂时保留改动前的写法（`ThinkingType`）。
  这套参数在它们上面是否被接受仍未验证（ADR 0097 已记），换格式前得先录一次真实请求。
- 自定义服务商的默认格式从「两者同发」变成「只发 `reasoning_effort`」。少发一个非标准字段，
  对标准 OpenAI 兼容端点是净改善，但对只认 `thinking` 的端点会失效——没有声明机制可依。

## 本期不做

- `budget_tokens` 形态的档位（`Budget` 现在只表示「没有档位可选」，还不会发预算数值）。
- 按 `IsReasoning` 收窄候选（非推理模型现在也会看到四档兜底阶梯）。
- 运行时刷新 models.dev 后重建候选（缓存层还没接）。
- 录制回放：把每家一条真实请求体固化成测试夹具，补上「是否被接受」的验证（下一步）。
