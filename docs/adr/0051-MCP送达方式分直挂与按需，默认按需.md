# MCP 的「送达方式」分直挂与按需，默认按需

每个 MCP server 多一个属性 `MountMode`：**直挂**（工具定义放进请求的 `tools`，即原有方式）或
**按需**（工具定义不进 `tools`，模型经两个固定元工具 `McpHelp` / `McpCall` 先查后调）。默认**按需**。

这是继「托管」（连不连，ADR 0008）、「可用」（能不能用，同上）之后第三个与之正交的问题：
工具**怎么送到模型手里**。它是每个 server 一份的**本机偏好**，不入库、不属于角色：
全局 server 存 `McpServerStates.json`，项目级 server 存 `McpWorkspaceMounts.json`（`.mcp.json`
是入库共享的标准形状，不该替仓库里的其他人做决定）。

## 元工具

- `McpHelp(server, tool?)`：只给 server → 返回它的自述与工具名单（每个一行说明）；再给 tool → 该工具的完整描述与参数 schema。
- `McpCall(server, tool, arguments?)`：调用。失败一律是返回值，不是异常。

**定义恒定**——名字、描述、schema 都不随 server 变。**挂不挂只看配置**（该角色有没有未被禁用的按需
server），**不看连接状态**。系统提示里只写配置里就有的东西：server 名与全局 server 的一句话说明，
**不写工具数、不写工具名**。

## 为什么

1. **缓存前缀。** 工具定义排在请求最前面。直挂时，server 连上、断开、退避重连都会让 `McpManager`
   的修订号自增、装配重建、`tools` 数组变化，整段缓存前缀随之失效。中途挂一个 server、或一个 server
   中途掉线再回来，都是一次全量重付。按需下这些全变成一条只追加的工具结果。
2. **token。** 工具定义每轮完整重发。工具多而少用的 server 直挂是纯开销（ADR 0008 已记过这笔账）。
3. **连接时机。** 按需 server 装配期不需要工具定义，因此不预连、不等待；第一次 `McpHelp` /
   `McpCall` 命中它时才连（等最多 10 秒，超时返回结构化错误，后台继续连）。

## 取舍

- **为什么不做成 shell 命令行（`mcp call …`）。** 评估过。它的独占好处是管道与重定向、外部工具可复用；
  代价是审批只能解析命令行字符串（脆）、`ReadOnly` 档拦 Shell 时 MCP 一起不能用、还要做本机 IPC 与
  可执行文件分发（ADR 0029 的 macOS 签名已经够麻烦）。用户要的（缓存稳定、按需发现）元工具全有。
  核心逻辑（`McpBridge`：查、调、结果整形、离线缓存）与载体无关，以后要 shell 壳只需再加一层薄壳。
  因此术语上**不叫「CLI 化」**：载体是元工具，不经 Shell。
- **为什么默认按需，且老配置不迁移。** 用户以云端强模型为主，「先查再调」可靠。旧配置读出来没有该字段，
  取默认值，升级后现有 server 全部变成按需——延续 ADR 0008「个人项目、不做迁移」的口径。
  本地小模型是主要风险（可能不会主动调 `McpHelp`），缓解办法：系统提示里给名单，全局 server 可写一句说明；
  工具少而天天用的 server 手动切回直挂。**不做任何自动判断**。
- **为什么工具数不进系统提示。** 它是运行时信息：没连过的 server 没有这个数，连上后系统提示就变一次，
  缓存白白失效。要知道有哪些工具，调 `McpHelp`。这也是项目级 server 只写名字、不加说明字段的原因。
- **为什么项目级 server 的说明不做。** 说明若写进 `.mcp.json` 就要往标准形状里加字段，其他客户端是否
  容忍未验证；写进本机状态则要再补一套按（工作区, 名字）的存储。名字通常已够说明问题（`unity`、`github`）。
  需要时再加，不影响已有数据。
- **为什么 `McpCall` 不审批。** 与现状一致：现在**任何权限档下 MCP 工具调用都不弹审批**
  （没有 `ApprovalRequiredAIFunction` 包装，`ApprovalModeMapper` 里也没有 MCP 规则）。这次换的是载体，
  不该顺手改权限语义。`McpCall` 现在是单一咽喉，将来要加审批（按权限档或按 server 开关）只改这一处，
  但那会牵动 ADR 0010 的放行矩阵，应另出 ADR。
- **为什么大结果落进会话的产出房间，不落 Cache。** 复用 `WebFetchTruncation` 的「头 + 尾 + 落盘路径」
  形态（提成通用的 `ToolOutputTruncation` / `ToolResultSpill`）。WebFetch 落 Cache 是因为网页可再生；
  MCP 结果往往不可重现（有副作用、数据会变），而历史里写着「全文在 X 路径」，清缓存就留下坏链。
  只溢出**文本块**，图片等非文本块原样透传。
  **预算比网页紧得多**：MCP 结果 8KB（头 4KB + 尾 4KB，对称：关键信息在哪头取决于工具），网页 64KB。MCP 结果又大又频繁，每条都进历史、
  之后每轮重发；实机一条 61KB 的日志结果在网页预算下根本没触发截断。
  超限的 JSON 会先缩进成多行再截断与落盘（`ToolResultSpill.IndentIfJson`）：MCP 结果常是一整行紧凑 JSON，
  按行截断时单行头尾重叠、尾部整个丢掉，落盘文件也没法按行号续读。
  数值在 `ToolOutputBudget.Compact` 一处。**`McpHelp` 的清单单独一档**（`Catalog`，32KB）：它是模型发现工具的
  唯一入口，被截断时丢掉的是中间那批，它们从此无从发现；Unity MCP 全开的 73 个工具约 12.8KB，按 8KB 会消失近三十个。
  另外，结果里 server 自己编码器留下的 `\uXXXX` 转义与 `content`/`structuredContent` 的重复一并整理掉（`McpCallResult`）。
- **为什么离线时 `McpHelp` 读磁盘缓存。** 每次成功取回工具时把清单（含自述）写到
  `Cache/McpToolCatalogs/`，键含配置指纹——命令改过的旧缓存不用。server 不在时模型至少看得见
  「有什么」，再决定等还是换路；`McpCall` 照常失败。

## 后果

- `McpManager.Revision` 的含义收窄为「**装配相关**的修订号」：配置变化，加上**直挂** server 的工具集变化。
  按需 server 的连接事件（取回、回收、命令被改）**不再**自增它。
- 按需名单的变化由 `AgentAssemblyFacts.McpOnDemand`（`McpManager.DescribeOnDemand`）单独入账——
  只含配置信息，所以连接起落不会让它变，而外部改了项目的 `.mcp.json`、授权变了、送达方式切了都会。
  这与 `WorkspaceInstructions` 同理：磁盘内容没有修订号可依，只能把内容本身入账。
- 按需 server 不进 `WarmupAsync`，也就不会再出现「正在连接 MCP」的忙碌标签。
- 右栏能力面板仍是只读的：按需的分组标「按需」、没有工具明细，固定开销（两个元工具的定义 + 名单）
  计入 MCP 一档。送达方式的编辑处：全局 server 在设置页的表单里；项目级 server 在设置页
  「已授权项目」下按工作区列出。
- 角色编辑页的 MCP 勾选项对按需 server 不报工具数，占用只算名单里那一行（与技能广告行同口径）。
- 桥接逻辑经 `IMcpServerHost` 抽象，单测用假宿主；另有一个用手写 stdio 桩 server 的端到端测试，
  钉住「按需连接不改修订号、直挂会」这条核心承诺。
