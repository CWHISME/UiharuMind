# 模型可建群、往群里说话，在跑的群把流水写进群流水.md

> **状态**：accepted（2026-10-25）。扩展命令见 [ADR 0079](0079-扩展：不常用的能力与MCP收进一对元工具，先查后调、逐条审批.md)，
> 群本体见 [ADR 0046](0046-群发言投递进成员会话，群壳只记流水.md)。

## 背景

群一直只能由用户在弹窗里建。模型这一侧看得到群（`chatsession.list-groups` 列最近几个），
但没法自己建一个，也没法往群里说一句话——群发言工具只属于群成员与化身。
于是「派几个人去商量，我盯着、随时插一句」这条路，模型走不通。

## 决定

1. **`chatsession.create-group`**：`name` + `members`（角色名或标识，顺序即发言顺序，至少两位）。
   建的是智能体群、绑当前会话的工作区；`mode` / `stop` / `host` / 逐成员模型仍只在开发脚本那侧暴露——
   模型的参数面越小越不容易填错，这些也能在群右栏改。风险按一般级（`Standard`）问一次：它写的是会话数据。
   建群那条路抽成 `GroupCreation`（Core），开发脚本 `group.create` 与这个工具共用：成员的解析口径、
   模型与成员的下标对齐、主持人校验只有一份。
2. **`SendMessage` 的 `to` 认群**（群名或群壳短号，全库匹配，子会话优先）：那一下以**用户的名义**往群里说一句，
   与化身同语义——会话是替用户在场的。工具**不等这一波跑完**：一整波可能跑十几分钟，主代理这一轮不该被它堵住，
   进度与流水去 `list-groups` 看。提示写在 `create-group` / `list-groups` 的结果里，不改 `SendMessage` 的参数说明——
   子代理场合也看得到那段说明，而它们没有群。
3. **`list-groups` 列最近的群**，且**正在跑的群当场把流水写进标准的 `群流水.md` 并返回路径**：
   跑着的时候「他们说到哪了」只能从流水看，而查询方未必等得起波末。

## 取舍

- **不给群加「发起会话」字段**：早期版本加过 `CreatorSessionId` 让列表只显示「本会话建的群」，
  但那是为过滤引入的存储，换来的是会话之间多一种关系、索引与落盘都要动。
  群名与成员本来就说明得了「这是谁的群」，最近的列表足够用——复杂度不值得。
- **流水复用 `群流水.md`，不另立快照文件**：离席的化身流水（`GroupLogFile`）正在按用户计划还原，
  那份文件的锚点维护随之消失，这里直接复用最简——写进标准路径，人翻开就能看。
- **`to` 认全库的群，不认「我建的」**：没有归属字段之后这是唯一口径；
  `SendMessage` 本就是通用通道（子代理、群、以及其他会话），收件人由调用方点名。
- **群成员与化身不建群**：建群是会话这一层的事，与「群里的人再开一个群」不是一回事；
  成员的 `SendMessage` 只收正文，那条路留在原地。
- **「在跑」只认群壳登记的那一波**，不含成员私聊与离席化身那一轮：与 `group.wait`、界面运行指示器同一口径。
- **共用建群路径允许单人成群**：开发脚本的「群路径」对照场景就这么建（一个人也能把群装配跑一遍）；
  「至少两位」是工具自己的产品规则（一位就是单聊），不下沉到共用路径。
