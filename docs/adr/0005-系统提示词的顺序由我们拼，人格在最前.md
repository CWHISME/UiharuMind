# 系统提示词的顺序由我们拼，人格在最前

智能体档的整段系统提示改由 `CharacterRunnerFactory.ComposeAgentInstructions` 按固定顺序拼：

```
1 角色人格 / 任务（含 # Work loop）
2 用户卡
3 对话模板（扮演档才有）
4 工作目录 + 工具使用纪律
5 工作区 AGENTS.md
```

`HarnessInstructions` 因此**一律为空串**。角色段自身的顺序也随之改成
「角色 `Template` → 用户卡 → 对话模板」（原先用户卡在最前）。

## 为什么（1.16.0 实测）

1. **框架对 `HarnessInstructions` 只做一件事：拼在角色段之前。** 探针（桩 `IChatClient` 抓取
   实际发出的 `ChatOptions.Instructions`）显示结果就是 `harness + "\n\n" + 角色段` 落进同一个
   instructions 字符串，没有第二个用途、没有单独的 system 消息。
   也就是说**顺序完全可以由我们接管**，代价只是不再用这一层。
2. **只要用这一层，人格就不可能排在最前。** 而人格排在一大段英文工具纪律之后，对本地小模型是实际
   损失：它得先读完「怎么用 Glob/Grep」才知道自己是谁、要用什么语言回话。
3. **provider 段落排在我们全部内容之后。** 同一支探针开启 provider 后测得次序为
   `harness → 角色段 → ## Todo Items → ## Agent Mode（45 行）→ ## File Based Memory`。
   因此代码里那句「工作区规矩放在整个系统提示的最尾，遵循权重最高」是**错的**，已改。
   「靠后权重高」这个理由既然不成立，就更没有把人格压后的必要。

## 取舍

- **弃用 harness 那一层。** 若框架未来给 `HarnessInstructions` 加上别的语义（压缩时保留、
  给 provider 读之类），我们会错过。目前 1.16 是纯拼接，且改回来只是一行——用现在确定的收益
  换一个假设中的将来功能，划算。
- **角色扮演档早就是这么走的。** 它的 `HarnessInstructions` 一直是空串，所以这条路是走过的，
  不是新赌注。改动后两档口径一致：**谁的提示词，谁自己排**。
- **用户卡从最前移到人格之后。** 系统提示的开头该回答「你是谁」，然后才是「用户是谁」。
  这一条同时影响扮演档与技能路径（都走 `CharacterPromptBuilder`），是有意统一。
- **对话模板留在角色段里（人格块之后、工具纪律之前），没按讨论时的草图排在工具纪律之后。**
  它是扮演档的东西，智能体档几乎恒为空；为一个恒空的段落在 `CharacterPromptBuilder` 上开一个
  插入点，不值当。
- **子代理不受影响。** 它的指令本来就是自己生成的、`# Role` 开头，人格已在最前；
  `HarnessInstructions` 也已在 ADR 0004 中设为空串。

## 代价（明说）

- **一批测试断言从 `HarnessInstructions` 迁到 `ChatOptions.Instructions`。** 已迁完，
  并新增两条不变量：人格必须排在工具纪律之前、工作区规矩必须排在工具纪律之后。
- **`BuildAgentOptions` 现在会改写传入的 `ChatOptions.Instructions`。** 它本来就是"装配出选项"
  的那一步，但调用方若指望自己填的 instructions 原样保留会踩空——签名里多了
  `workspaceInstructions`，正是为了让整段拼装收在一处，而不是调用方拼一半、这里拼一半。
- **提示词顺序变了，模型行为会有可观察差异。** 内容一字未改、只换次序，但对小模型来说次序本身
  就是变量，需要实机确认没有变差。

## 后续

- **对话模板那一段已退役**（[ADR 0015](0015-对话模板退役，旧值不迁移.md)）。角色段现在是
  「角色 `Template` → 用户卡」两段，整段顺序相应少一节；本文正文保留当时的记录不改。
