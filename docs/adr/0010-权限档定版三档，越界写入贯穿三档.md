# 权限档定版三档，越界写入贯穿三档

会话权限档定为三档，语义只在 `ApprovalModeMapper.BuildRules` 一处定义，主 agent 与子代理都从
那里取规则：

| 档 | 工作区内的写入 | shell / MCP | 工作区外的写入 |
|---|---|---|---|
| 只读/计划 `ReadOnly` | 问 | 问 | 问 |
| 自动编辑 `AutoEdit` | **放行** | 问 | 问 |
| 完全自动 `FullAuto` | 放行 | 放行 | **问** |

读工具（`Read`/`Glob`/`Grep`）压根没包审批，不在这张表里。

**越界写入是贯穿三档的硬规则**：目标路径不在工作目录之下的写工具调用，**完全自动档也要问一次**。

## 为什么

1. **这个词被引用了六处，却从未被定义过。** 实现里 `AutoEdit` 一条规则都不加，行为与只读档
   完全一致，而枚举注释写着「文件读写自动放行」。定时任务代码写死用这一档、无头执行又一律拒绝
   审批，净效果是**定时任务所有文件写入都被拒**——任务表面跑完、实际一个字没落盘。
   一个被六处引用的概念没有单一定义处，就一定会漂移成六个意思。
2. **「完全自动」不能真的完全自动。** 用户选它的意思是「在我的项目里别再问我」，不是
   「你可以往我磁盘任何地方写」。无人值守（定时任务）时这一档没人盯着，越界写入没人拦就
   真的没人拦。
3. **这条硬规则不需要额外状态。** 用户点一次现成的「本会话允许」之后，框架自己会把该工具
   整会话放行，所以只会被问一次。

## 取舍

- **做成「减法」而非「加一条否决规则」。** 框架的 `AutoApprovalRules` 是**或**语义，任一条返回
  true 即放行；加否决规则拦不住 `AllToolsAutoApprovalRule`，只能把那条全放行规则本身换掉。
- **三档而非四档。** 曾考虑给「shell 放行但文件仍问」单开一档。没做：真实使用里 shell 与写文件
  的危险度不构成两个独立维度（`rm` 就在 shell 里），多一档只是多一个要解释的词。
- **越界判定只比规范化后的路径，不解析符号链接。** 工作区里一个指向外部的软链能绕过它。
  接受这个缺口——能这么干的模型同样能直接用 shell，真正的边界是「用户点了那一下」，
  每次审批都去 realpath 一趟只是把成本花在挡不住的地方。
- **权限档不下沉到子代理。** 它是会话级的；子代理继承父会话那一档，收窄只发生在能力维度
  （`AgentToolConfig.Intersect`）。

## 代价（明说）

- **定时任务仍然写死 `AutoEdit`**（`InProcessSchedulerBackend`），`ScheduledAgentTask` 上没有
  权限档字段。想让定时任务全自动做不到，只能靠逐条 glob 预授权。这是个待补的口子。
- **每一格都要有测试。** `PermissionModeApprovalTests` 逐格盯住三档 × 三列——这类「表格与实现
  不符」的缺陷不会编译报错，只能靠测试。
