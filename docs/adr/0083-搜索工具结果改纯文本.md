# 搜索工具结果改纯文本：Grep 与 Glob 不再跨历史序列化挤掉换行

> **修订 [ADR 0017](0017-提示词散文改中文，搜索失败改结构化.md) §12 与「取舍」关于「带
> Notice 的包装类型走反射序列化没问题」的结论。** 那份结论基于「模型能接受紧凑 JSON 形状」，
> 实测换行被挤掉，故撤销，改回纯文本。

从 [ADR 0017](0017-提示词散文改中文，搜索失败改结构化.md) 起，两个搜索工具回给模型的是带
`Notice` 字段的结构化对象（`GrepToolResult`：Body + Notice + Map；`GlobToolResult`：Entries + Notice），
正文铺成 ripgrep 味文本块、说明独立成字段——「模型分不清命中与说明」那条病由此治好。
本 ADR 又推翻掉结构化的另一半，原因是它带来了新的病：**换行在跨历史序列化时被挤掉**。

## 一、问题：对象跨历史/工具边界序列化，正文换行全变字面量

历史经 `HistoryJsonl`（`JsonSerializer.Serialize`）落盘、读回后，`FunctionResultContent.Result`
（object?）是 `JsonElement`（`ImagePreviewProjection` 早就在注释里记着这句
「刚产出时是字符串，从历史文件读回来是 JsonElement」）。工具实时调用时也一样：
`AIFunction.InvokeAsync` 对对象返回值回的是序列化好的 `JsonElement`（ADR 0017 §12 记过）。

`JsonElement` 再发给模型/界面时会再走一次序列化：

- 模型侧（`Microsoft.Extensions.AI.OpenAI` 的 ToOpenAIChatMessages）：`Result as string` 为 null
  （是 `JsonElement{String}`，不是 CLR string），走 `JsonSerializer.Serialize` 分支——
  产出**带引号 + 字面 `\n`** 的 `"line1\nline2"`，模型读不到任何一行正文；
- 界面侧（`ConversationTranscript` 的 `result.Result?.ToString()`）：`JsonElement.ToString()`
  同样给不出真实换行。

全仓只有 `ImagePreviewProjection.TextOf` 的 `GetString()` 分支真正还原过换行，且只服务图片预览。

**结论：Grep/Glob 结构化返回的「正文会把换行挤成一坨」，从工具边界开始就是事实，跨历史
回放更明显。** 所谓「正文铺成文本块最省、最贴近模型见过的 grep 输出」根本没送到模型面前。

## 二、决策：Grep 与 Glob 都返回纯文本 string

1. **形状**：正文（每行一条命中/条目）在前；说明拼在 `"\n\n---\n"` 分隔行后，
   由公共的 `ToolResultText.AppendNotice` 负责（与 `ToolOutputTruncation` 头尾分隔同款惯例）。
2. **没有正文（0 命中）** 时不加分隔行——没有正文可分隔，直接给说明，免得开头空两行。
3. **命中地图**（正文超 32KB 预算）渲成每文件一行的文本（`路径: N 处命中（第 X–Y 行）`），
   Top 50、按命中数降序；**不给 snippet**——与「不返半截正文」同一理由：按扫描序取的片段
   无相关度排序，给了只会让模型锚定到运气好的文件上。**（格式、预算与 Top 50 已由 §六 修订）**
4. **删除** `GrepToolResult` / `GrepMapEntry` / `GlobToolResult` 公共类型；`Glob` 方法
   `private → internal`（与 Grep 对称，测试直接调）。
5. **重放路径在装载侧修**：`ChatContentNormalizer`（`HistoryJsonl.Parse` 调用）把
   `JsonElement{String}` 的工具结果还原成 string——这不止修搜索工具，Read/Write/WebFetch 等
   所有返回字符串的工具跨历史回放一并受益。
6. **恢复 `caseSensitive` 参数**：工具 schema 重新可传（标准 grep/ripgrep 有区分大小写开关）；
   默认保持不区分大小写（仓库既有行为，不动）。

## 三、说明语言统一中文

ADR 0017 当初把失败措辞刻意写成英文（理由是「与工具 schema 同一层」）。本次按同一批文件
的实况推翻：面向中文语料为主的本地小模型，英文说明最容易被略读，而它解释的恰是
「为什么没搜到/搜得不对」。失败、0 命中、正则降级、归一化、截断说明统一中文；
当次真实路径与工具名（`` `Read` `` / `` `Grep` ``）保留原样。

## 四、取舍

- **路径单独成行 vs grep 的 `file:line:content`**：命中行多时少重复路径 token；代价是行号行
  没有文件前缀，模型要把上方路径行与下方命中行自己关联。实测对中文小模型友好——
  命中行恒带 `N:` / `N-` 前缀、路径行无前缀，弱模型不易混淆，且比 `file:line:content`
  更省 token。
- **Glob 也文本化**：Glob 条目小、原本「挤成一行」的问题轻（条目无换行），但两工具同文件
  同生命周期，分开维护两套返回形状的代价更高；且截断/0 命中说明同样受益于统一文本口径。
- **不是给所有工具输出都去结构化**：返回结构化仍对模型有意义的大块内容（如目录树、结构化
  产出）不动；本次只动「正文本身是文本、对象化只是包壳」的搜索工具。

## 五、测试

- `HistoryJsonl` 往返后工具字符串结果保持真实换行（`SessionJsonOptionsTests` 新增）。
- Grep/Glob 文本输出形状逐一钉住：0 命中无分隔、失败回显解析路径、降级/归一化中文说明、
  命中封顶 200、中文超字节预算换地图、地图 Top50、多文件路径行边界、Glob 300 截断说明。
  （地图与 Glob 过宽部分已由 §六 修订，测试随之更新）

## 六、修订（2026-10-12）：过宽时给分布，不给半截

「不给半截正文」从 Grep 推广到 Glob，地图本身也重做。

1. **Grep 过宽**（命中超 200 处或正文超 16KB）只给命中分布，不再返回半截正文。
   - 文件 ≤ 100 个：每文件一行 `路径: N 处（行 a, b, c, d, e, …）`，按命中数降序。
     给前几个具体行号而不是「第 X–Y 行」区间——区间跨几千行时没有定位价值，具体行号能直接 `Read offset=`。
   - 文件更多：按目录聚合，`目录: N 处 / M 个文件`。只有命中数分不清「一个热点文件」还是「很多文件散落」，
     而这正决定下一步往哪收窄。
2. **Glob 过宽**（超过 150 条）不再罗列前 N 条路径，改给目录分布 `目录: N 条`。分布统计到 5000 条为止，
   触顶时总数写成 `N+`。
3. **分布正文开头先声明**「下面是分布，不是匹配内容/文件列表」。本地小模型容易从第一行就照着做，
   放在末尾说明里的话它未必读到。
4. **目录聚合（`PathGrouping`）自顶向下展开**：先把全部命中归到最高的公共目录，再反复拆最重的组，
   拆完仍 ≤ 50 组才拆。各组互不重叠，总和等于总数。标签三种：`src/A`（整棵子树）、`src/A/*`（直属文件，
   子目录另列时才单列）、`src/A（其余）`（子目录多到放不下时，单列高于平均的子目录后剩下的部分）。
   等重的同级一起拆或一起不拆；只有一个子目录的中间层跳过。
   输出按目录树顺序（直属文件在前、子目录按名、「其余」在后），不按权重：「其余」要挨着被单列的兄弟，
   才看得出它是相对谁而言。
   - 被替换的旧做法是「自底向上、低于平均权重的组整体上收」：父目录的数字只是被收上来的零头，
     却和子目录并列显示（实见 `src: 103、.: 7`，模型会读成整个 src 只有 103 处）；
     阈值取全局平均，Grep 有一个热点文件时阈值被抬高，其余目录几乎全被收进顶层。
5. **Grep 加 `filesOnly`**：只列文件（命中数 + 行号，按路径排），不给匹配内容。
   「哪些文件提到了 X」是最常见的第一步，此前没有便宜的入口。
6. **Glob 行格式**：去掉 `[FILE]`/`[DIR]` 前缀，文件 `路径 (大小)`、目录 `路径/`。
   仍按路径字典序（文件在前）而不按修改时间：同目录的文件挨在一起，模型扫得出结构。
7. **预算**：Grep 正文 32KB → 16KB（约 4–5k token），本地小模型的上下文经不起每次搜索吃掉近万。
   单行截断仍是 500 字符：截的是行尾，历史转写按 400 字符折行，截短了会把命中本身截掉。
   按模型上下文窗口缩放预算未做——`Read` 同为 32KB，要缩放应两者一起，另行处理。
