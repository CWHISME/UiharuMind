# 提案：把压缩态挪进运行登记处（SessionRunRegistry）

> 状态：proposed（未决策）
> 相关提交：`91b376a8`（压缩功能修复，含现方案）

## 背景

「整理交接文档（压缩）」是会话的一个具名忙碌态：不是轮次，但同样表示"这个会话有动静"。它在 `TurnDriver` 里以 `_compactingSessionId` + 静态 `TurnDriver.IsCompacting(sessionId)` 存在，**没有**进 `SessionRunRegistry`（那个记录"谁在跑、谁在等审批"的登记处）。

于是每个想知道"这个会话有没有动静"的消费方，都得自己额外查一次压缩态：

| 消费方 | 现在的做法 |
|---|---|
| 会话列表转圈 | `RefreshRunState` 里手动 `\|\| TurnDriver.IsCompacting(...)` |
| 删除/清空闸门 | `CanMutateFiles` 手动 `&& !TurnDriver.IsCompacting(...)`（漏加就是一次真实 bug） |
| 列表刷新触发 | 靠 `SessionRunRegistry.NotifyStateChanged`——一个"只广播不改状态"的旁路通道 |
| 跨线程读 | `_busy` / `_compactingSessionId` 要 `volatile` |
| 导航角标 / 托盘 | 读 `ActiveSessions()`（登记处），**不含**压缩态，与列表转圈口径不一致 |

## 为什么不能简单塞进 BeginRun

压缩不是轮次，**不能**触发 `IsGenerating`。`IsExternallyDriven = !_driver.IsRunning && Running.IsBusy(...)`，一旦压缩被 `BeginRun` 登记：

- `IsGenerating` 变 true → 停止按钮出现，而压缩用 `CancellationToken.None` 停不了——**骗人的按钮**
- 打字从"发送"变"插话"，进注入队列等下一轮——语义全错

所以重构的关键是：**「轮次忙」与「具名忙碌」分开建模**，`IsExternallyDriven` / `IsGenerating` 这类消费方只认「轮次」档。

## 方案

在 `SessionRunRegistry` 增加一个独立的「具名忙碌」集合（与 `_runs` / `_approvals` 并列，例如 `_busy` 计数）：

- `BeginCompacting(sessionId)` / 作用域式注销：压缩开始/结束时登记，与 `BeginRun` 同款计数语义（`StateChanged` 自动广播）
- `StateOf` 返回 `ESessionRunState.Compacting`（新档位），或保持现有档位 + 新增 `IsCompacting(sessionId)` 查询
- `IsBusy` 默认涵盖压缩（删除/清空闸门、列表"有动静"判据自动正确）
- `ActiveSessions` 是否纳入压缩态 → 决策点

消费方随之简化：

- `TurnDriver`：删掉 `_compactingSessionId` + 静态 `IsCompacting` + 手动 `NotifyStateChanged`，压缩处只调 `BeginCompacting`
- `SessionListItem`：`IsRunning` / `CanMutateFiles` 不再手动查压缩态
- `SessionListModel`：刷新链路天然工作（登记处 `StateChanged` 已广播）
- `volatile` 不需要了（登记处内部有锁）

`IsExternallyDriven` / `IsGenerating` **不改**：它们只认「轮次」档（`_runs` / `_approvals`），压缩态不在其判据里。

## 决策点

1. `ESessionRunState` 新增 `Compacting` 档，还是独立 `IsCompacting` 查询、`StateOf` 不暴露？（影响 `ActiveSessions`、角标、托盘）
2. 导航角标 / 托盘是否纳入压缩态？（现方案已知取舍：列表转圈亮、角标不亮）
3. `NotifyStateChanged` 旁路是否删除？（重构后登记处自身广播，理论上不需要）

## 代价

- 触碰面：`SessionRunRegistry` / `ESessionRunState` / `TurnDriver` / `SessionListItem` / 角标托盘等 `ActiveSessions` 消费方，都要过一遍口径
- 属设计级改动，建议单独一轮实施

## 备选（维持现状）

现方案"压缩态住在外置 + 消费方手动查"在「压缩≠轮次」的约束下正确工作，代价是各消费方分散查询、易漏（`CanMutateFiles` 已经漏过一次）。若重构成本不划算，可维持现状并把「角标不含压缩态」记为已知取舍。
