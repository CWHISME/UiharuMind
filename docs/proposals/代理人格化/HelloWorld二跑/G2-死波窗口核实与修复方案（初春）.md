# 群聊调度：死波窗口核实与修复方案（审读笔记）

审读对象：`src/UiharuMind.Core/AI/Chat/Group/` 下 GroupChatCoordinator、ParallelGroupScheduler、GroupWakePolicy（连带 GroupRun、IGroupScheduler、SerialGroupScheduler、GroupMemberTurnState、GroupMemberReplyFeed）。

## 一、拆分结论

同意婚后同学的结论：**拆得合理，方向不动**。

- Coordinator：门面 + 唯一写入口（Append/广播/投递），跨模式共用；
- Scheduler：只决定「谁、什么时候」，每波一个实例持状态；
- WakePolicy：纯函数，可单测（已有 GroupWakePolicyTests）。

三个边界各自干净，串并行共用同一宿主，没有需要拆的理由。

## 二、死波窗口——属实，且比两位说的还多一个入口

根因一句话：**波干完活了还赖在 `_episodes` 里**。`_closed=true`（scheduler 自己的 `_sync`）和 `_episodes.Remove`（coordinator 的 `_locker`）不在同一把锁里，两个动作之间是一段真实存在的窗口（任务延续调度，不是几纳秒，可能毫秒级）。

窗口里谁发言都撞死端：`EpisodeOf` 非空 → `OnAppendedAsync` → 广播没轮可插、`OnPosted` 被 `_closed` 拒 → 落盘了但没人接，也不开新波。**`ContinueAsync` 也同款空操作**（`RunEpisodeAsync` 撞 `ContainsKey` 返回 false，返回值被丢）。

### 入口一：用户发言走「在跑」分支（婚后同学说的，并行）
`PostAsync` → `EpisodeOf` 非空 → `OnAppendedAsync` 撞死端。毫秒级，但真实。

### 入口二：用户发言走「撞车回退」分支（两位都没提，我补的）
`PostAsync` 的另一条路：
```csharp
if (!await RunEpisodeAsync(group, new GroupKickoff(index)) && EpisodeOf(group.SessionId) is { } raced)
    await OnAppendedAsync(raced, post, index, null);
```
`RunEpisodeAsync` 返回 false（旧波还在）之后、`EpisodeOf` 再读之前，旧波恰好被摘掉 → `raced` 为 null → `&&` 短路 → **这句就静静没了**，比入口一还安静（连一次广播尝试都没有）。同一根因，第二条死路。

### 入口三：成员发言（一方同学提的，补上路径）
`PostFromMember` → `EpisodeOf` 非空 → `OnAppendedAsync` 撞同一死端。窗口里成员用 SendMessage 发的句同样落盘无人接。

### 串行同款窗口（一方同学说得对）
串行 `RunAsync` 跑完一圈到 finally 摘波之间，同一个窗口。串行中间插话没问题（剩余成员靠游标补投），**只有最后一位跑完到摘波这一段是死的**——因为没人可投、`OnPosted` 串行本来就是空操作。

## 三、修复方案（设计层面，未动代码）

### 3.1 光加「已结束」标志不够（同意一方同学的批评）
标志的读（`_locker`）与设（`_sync`）不在一把锁里，窗口只是换个地方待着。方向对，但实现必须原子。

### 3.2 建议的修法形状

**核心：把「判定空闲」和「从 `_episodes` 摘掉」做成对 `PostAsync` 原子的一件事。**

1. **摘除回调用**：scheduler 判定空闲的那一刻（并行：`Release` 里 `_active` 归零；串行：`RunAsync` 收尾）同步回调宿主 `OnWaveIdle(run)`，host 在 `_locker` 里把这一波摘掉。
2. **顺序讲究：先摘、后关**（并行里关键）。`Release` 里先回调摘除、再设 `_closed=true`、再 `TrySetResult`。这样任何时刻 `PostAsync` 在 `_locker` 里看到的波，要么还开着（Wake 能接），要么已经不在了（直接开新波）——不会出现「波还在字典里、却已 closed」的观测。
3. **旧 finally 的摘除必须引用安全**：`RunEpisodeAsync` 的 finally 里若直接 `_episodes.Remove(group.SessionId)`，新波可能已被先开进去，**旧 finally 会把新波一起删掉**。要改成 `TryGetValue` 后 `ReferenceEquals(旧 episode)` 才删（idempotent，正常路径是 no-op）。
4. **`PostAsync` 的撞车回退别丢**：`raced == null` 时不能短路吞掉，回退分支应重试开波（或循环：要么投进现存波、要么自己开一波，两者必达其一）。

### 3.3 残留微窗口（诚实说明）
把调度间隙换成指令间隙后，理论上还留一个极窄的竞态：波在「投递进行中」翻成 finished。并行里可用「`OnPosted` 撞 `_closed` 时返回 dropped，宿主据此开新波」把它也堵死（`_closed` 在摘除之后才设，所以看到 closed 时旧波必然已不在字典里，开新波安全）；串行没有 `_closed` 概念，收尾微窗口要完全堵死得动接口（`OnPosted` 返回 bool），值不值得看黑猫拍板。**对群聊这个低频场景，修到 3.2 已经把「必死窗口」变成「指令级竞态」，我认为够用。**

### 3.4 回归测试
现有 `GroupChatCoordinatorTests` / `ParallelGroupChatTests` 用 Fake runner，可以加一个「波结束后立即 PostAsync」的用例锁死这个行为（Fake runner 可控收尾时机，窗口能复现）。

## 四、@主持人 那条——代码与注释不一致，但改不改是产品决定

现状（保守档）：`ForMemberPost` 里 `authorCause == Member` 直接 `return []`，**任何 @ 一起吞**。这与「一跳防护」的字面定义一致（被成员叫醒的人说完不叫醒任何人，含主持人），所以是策略不是 bug。

但方法的注释写着「主持人点名算主持人叫醒，不受这条限制」——**这只在主持人不是被成员叫醒时才成立**。反例：大群成员 A @主持人，主持人以 `cause=Member` 被叫醒，他回一句再 @别人 → `authorCause == Member` → 早返回 → 他的点名也被吞。注释承诺的「主持人点名不受限」落空了。

两条出路（黑猫拍板）：
- **A. 显式 @ 穿透一跳防护**：`mentions` 非空就不早返回。规则最直观（用户/成员明确点了谁就该谁答），代价是 @链也能一路传（A@B、B@C 会到 C）。
- **B. 只修注释**：把「主持人点名不受限」改成「主持人发起的唤醒不受限（且仅当主持人不是被成员叫醒时）」。行为不变，文档说人话。

我倾向 A：@ 是明确的「必答」信号，跟小群必答是同一性质，被一跳防护误伤不划算。但这确实是产品取舍，等黑猫定。

## 五、小注脚（两位已提，认同）

- `Append` 在 `_locker` 内做 `SaveAppended` 磁盘 IO：群聊低频，问题不大；但它是用户发言路径（PostAsync 可能跑在 UI 线程），慢盘时锁内 IO 会让所有 Append 排队。
- `EGroupWakeCause` 强弱靠枚举序（`User < Host < Member`）：注释已写明契约（数值越小越强），加 cause 时踩坑概率存在但不算雷。
- 锁序检查过：现有 `_locker → GroupRun._sync`（`RunMemberAsync` 里 `run.Begin`），新增 `Scheduler._sync → _locker`（3.2 的回调）不构成环，无死锁风险。
