## 一、设计原则

### 1.1 五条地基

| 原则 | 说明 |
|---|---|
| **无子代理** | 系统里只有"角色/成员"，没有特权进程。委托 = 给某个角色发消息 |
| **权限统一** | 所有角色走同一套工具装配流程。人格不能成为能力边界 |
| **预算在实例层** | 写死的是预算（深度/轮次/token），不是权限 |
| **人格真人化** | 功能是性格的副产品，不是性格本身 |
| **人格与身份分离** | 性格稳定，专长可插拔 |

### 1.2 最核心的一条：因果关系要反过来

工具人写法：
> 初春负责查证 → 所以她不确定时会去查

真人写法：
> 初春听到"大概是""可能是"就浑身不舒服 → 所以她忍不住会去查

**行为一样，因果相反，表现天差地别。** 前者查完说"已核实，来源如下"；后者查完会有点小得意地说"诶，我刚查了一下，其实不是这样——"。

真人感唯一的来源：**功能得是性格的副产品。** 这么写还会自动泛化——你没法穷举"什么时候该查证"，但写了"她对模糊说法生理性不适"，她自己知道在各种没预料到的场景里怎么反应。

### 1.3 由此产生的代价（接受它）

真人化之后，这些效率优化要**主动放弃**：

- ❌ 沉默权 —— 真人会插嘴
- ❌ 阶段行为脚本 —— 真人不会按流程切换主导权
- ❌ 异议义务 —— 逼审核者每轮找反例，他就变回工具了

代价是：会跑题、会废话、token 上升。但**主题完结由用户判断**，所以"不收敛"不再是致命问题。

保留的只有底层护栏：预算、轮次上限、插话、落盘。它们不干涉表演。

### 1.4 【v2 新增】产出锚点：真人化唯一不能放弃的东西

你可以放弃效率，但不能放弃**产出**。

真人化的隐藏风险不是 token，是**四个人聊得很像人、很热闹，最后什么都没留下**。一群真人开会开嗨了没结论，是现实；系统做成这样就是失败。

所以补一条地基：

> **每轮讨论必须推进"产物状态"，不只是推进"讨论状态"。**

- 产物 = 文件 / 决策 / 结论 / 待办清单的某个**可见部分发生了变化**
- 右侧栏常驻「本群产物」区，产出的增删改实时可见（见 §7）
- 连续 N 轮产物区无任何变化的信号：不是报错，是给主持人一条软提示「聊了 6 轮，盘上还是空的，要不要先落一版？」

**这是提问不是判定。** 主持人的价值在这种时候才真正体现。

### 1.5 三条原则的优先级（冲突时按顺序让位）

```
产出不落空  >  真人感  >  效率
```

阶段脚本、收敛机制、成本控制，全部排在真人感之后。真人感排在产出之后——**你可以聊得像人，但不能白聊。**

## 二、整体流程：grill me 式方案会审

```
提方案 → 审核 → 回应 → 用户决策 → 实施 → 结题
```

### 2.1 四个阶段 —— 是观察量，不是控制量

| 阶段 | 典型主导 | 特征 |
|---|---|---|
| **发散** | 提方案者 | 出方案、脑暴 |
| **会审** | 审核者 | 挑硬伤、给角度、提脑洞 |
| **回应** | 提方案者 | 坚持 / 改口 / 部分妥协 |
| **实施** | 执行者 | 落产物 |

> **【v2 修订】这一段在 v1 里和 §1.3 直接打架**：§1.3 说"放弃阶段行为脚本"，§2.1 却做了主导权切换表，P1 还要"阶段字段 + 注入提示词"。实现出来必然变成状态机。

修订后的定位：

| | v1 | v2 |
|---|---|---|
| 阶段显示 | 注入提示词影响行为 | **UI 上显示进度，给"用户"看** |
| 主导权 | 阶段决定谁说话 | **不干预**。谁想说谁说 |
| 软提示 | 强制 | **【v4】全部取消** |

> **【v4】v2 留的最后一个软提示（给主持人私有上下文带一句「目前像会审阶段」）一并删掉。**
>
> 理由就是 §4.7：它是中途注入，会改前缀、失效缓存。而它的收益本来就很小——初春该不该抛问题，靠 §6.2 的两个信号命中时**系统去点她**就够了（点名是唤醒，不是注入提示词）。
>
> 而且删掉之后更干净：**阶段从此是一个纯 UI 概念**，零运行时注入。绝不会变成状态机。

**「回应」这一环必须存在。** 单向挨批会让提方案者变成提案机器。一个人被质疑时的反应——坚持、改口、或"你说得对但我就是想这么做"——恰恰是人格最鲜活的时刻。

### 2.2 审核的三个层次

不做成表格，让审核者在提示词里自然形成：

- **硬伤**：这个不成立，必须改
- **建议**：能更好，可做可不做
- **脑洞**：顺着想到的另一个方向

### 2.3 提方案时允许短暂"正经"

给提方案者在提案那一刻挂一段**临时结构化提示**（背景 / 方案 / 取舍 / 风险）。

> **【v2 修订】这四个词只出现在"输入提示"里，用来提醒她想全；输出格式完全交还给她本人语气。** 一旦这四个词出现在输出里，全场都会正经起来，真人感当场归零。

### 2.4 【v3 重写】治附和螺旋：用主持人提问，不用立场登记

v1 用 `open_issues` 被动追踪分歧，但两个模型互相礼貌时，**分歧根本没被说出来**（都在"这个思路很好，我补充一点"）。

v2 的对策是**强制立场登记**（审核者必须输出 `支持/反对/有条件支持` + 理由）。**这条要撤掉**——它跟 §1.3、§2.1 自相矛盾：

- §2.1 刚把阶段从控制量降级为观察量，理由是"绝不能让流程去压制人格"
- 立场登记立刻引入了一个新控制量：**你在要求他填表**
- 而且它恰恰会杀死一方通行最有力的东西。他真正的表达是"这个在 X 条件下直接崩掉"——那不是"反对"，是具体判断。**压成三选一，丢掉的正是你要的那部分**

**替代方案**：让初春来做，且不用格式。

> 她在卡住时问一句：「一方通行，这个你现在怎么看？」——这本来就是她的职责（她已有"把球踢回给用户"，同理可以踢给成员）。

差别在哪：**僵局检测 / 无分歧检测是观察量**（后台跑，不要求角色做什么），**立场登记是控制量**（要求角色产出特定格式）。前者可以做，后者不该做。

配套：

- 被说服后改口是**高光时刻**，UI 上值得标出来——但这是显示层的事，不需要角色填表
- 初春什么时候问？两个信号（§6.2 无分歧 / 僵局）命中时，或用户说"过一遍"时
- 提问对象是**具体那个人**，不是全员广播。点名比广播更容易逼出真实立场

### 2.5 结题

用户或主持人手动结题 → 群进入只读存档。摘要由初春产出：

```
用户决策：用户最终选了哪个（这是整套流程的终点，也是最值钱的一栏）
分歧：还有哪些没解决的
决策：各方分别推荐什么
否决：哪些选项被否掉了、为什么
成本与时机：花了多少、来不来得及
产物：实施期落盘的东西
```

> **【v4 修订】摘要在「最后一次拍板」时写，不是每次拍板都写，也不是最后补。**
>
> 按 §2.6⑤，流程是个环，大部分任务会转 2~3 圈 = 2~3 次拍板。作者 v3 定的是"拍板 → 开工那一瞬间"，方向对（理由成立：开工后没人回头看，而"为什么否掉 A"不进产物文件），但**没说多圈时是哪一次**。
>
> 定：**最后一次拍板**。
> - 那一刻上下文里同时有：全部讨论 + 前面各圈的产物。信息最全的一次
> - 执行还没开始，上下文没被长链工具调用污染
> - 单圈时它和作者的版本完全一样
>
> **中间几圈的拍板不记** —— 产物就是它们的记录，不需要重复一份文字。
>
> **【v5】"最后一次"在运行时不可知，实现要改成幂等。** 系统当时不知道这次是不是最后一次，所以：
>
> **每次拍板都更新产物区里同一份摘要文件**（覆盖写）。最后一次写入自然就是最终结果，不需要预测未来。
>
> 这也更贴 §1.4「产物先行」——摘要从"结题仪式"变成"一个一直在那儿、每次拍板都会更新的产物"。

> **【v6 补漏】「拍板」是个运行时事件，而 v5 里没有任何东西能观测到它。**
>
> 上面要求"每次拍板都覆盖更新"，可 §2.6③ 与 §4.7 同时规定**系统不解析用户那句话**
> （不替他补、不做状态机），阶段又已降级为纯 UI。**写入时机因此是悬空的。**
>
> 定：**初春自己写，不加任何机制。** 她人格里本来就有「整理：把结论落成文字」，
> 只需在职责里补一句「方向定下来就更新那份文件」——顺着她已有的驱动力，不是给她派任务。
> 用户想让她写就说一句，那本来就是普通消息。
>
> **不做 UI 按钮**（拟稿时提过，砍掉）：全文都在把机制换成人格，这里没有理由反过来补一个控件。
>
> **不复用 `Conclude`**：它的语义是「结题 → 群进只读存档」，是终局动作。
> 把"每次拍板"绑上去，要么让它能不存档（语义就烂了），要么再造一个原语——而原语好不容易收到 5 个。

> **【v4】唯一的兜底：执行期触发上下文压缩时，压缩前把讨论摘要落盘。**
>
> 上面"信息最全"这个前提，在执行期足够长时会失效——压缩时最先被判"与当前任务无关"的恰恰是前一轮讨论。**前提失效才做，不是流程仪式**，正常情况一次都不触发。

> **【v2 修订】结题摘要里的初春要保留她的"怂"。** 她人设是怕得罪人、不敢直说反对，所以"否决"那一栏她会写得很委婉（"这里当时有不同意见，后来的处理方式是……"），而不是突然变敢言。**保留她的怂，记录才真实**——否则摘要会变成一份没有人味的会议纪要。

> **【v2 修订】"成本与时机"是标准四人组的维度空缺**：一方通行看"成不成立"，食蜂看"接不接受"，但**钱够不够、来不来得及没人管**——而一方通行的毛病恰恰是"忽略人情、成本、时机"。补这一栏，或者给某个角色挂"项目管理"身份来填这个位子。

归档后成为**可检索的结论库**，下次开新群若话题相近可引用。

### 2.6 【v3 新增 / v5 简化】执行模式：讨论和开工是两种节奏

> 触发澄清：「讨论完毕会直接开工，这是代理模式，有权限读写文件、运行 shell」。
>
> 产物就是真实落盘的东西，所以 §1.4 的产出锚点成立。但它顺带暴露了一个更大的未定义区域：**从讨论到开工是一次节奏切换，而 v1/v2 对切换之后的状态一个字都没写**。

两种节奏的差别比看起来大得多：

| | **讨论** | **执行** |
|---|---|---|
| 时长 | 几轮对话 | 几十步工具调用，可能很长 |
| 主导 | 多人轮流 | **收窄到一个人** |
| 输出 | 观点 | 文件、命令结果 |
| 人格 | 全力发挥 | **收敛表达，不收敛判断** |
| 用户在场 | 参与者 | **旁观者，随时插话** |

> **【v5】对比表里"权限"这行删掉了。** 不做按模式的权限开关——权限恒开，用不用是人的事（详见下面的 ③）。
>
> 于是"两种运行状态"这个说法也要收一收：**状态没变，变的是节奏和主导权**。真正的模式切换只剩一件事——用户那句话带来的人格收敛。

#### ① 主导权收窄

执行期**默认只唤醒执行者**，其他角色退到"被 @ 才说"。初春保持待命（她便宜，且要盯产物区）。

四个人都在改文件时会打架——§6.8 的写队列只解决覆盖问题，解决不了思路分歧。执行者遇到需要判断的事，用 `SendMessage` 回来问，这是委托机制的自然用法，不用新增东西。

#### ② 人格收敛：收敛的是表达，不是判断

**别做成"执行时切换成无人格模式"，那就前功尽弃了。**

- **收敛的**：篇幅、情绪表达、跑题、互相寒暄。执行是长链条，每一句抱怨都在烧 token，用户在等产出不是在等表演
- **不收敛的**：判断方式、审美、毛病

**【v4 修订】收敛靠用户的那句话，不靠注入提示。**

> v3 这里写的是"人格层对应的注入提示（执行场景时挂上）"。**这条要撤**：提示词和工具一样在 KV cache 前缀里，中途挂一段跟增删工具是同一种失效（§6.8）。工具不能动态改，提示词同样不能。

模式切换只由**用户那句话**完成——"行了，你去做吧"/ "开工"/ "别啰嗦了直接写"。它作为一条普通消息进入对话区，**不改前缀**，所以不失效缓存。

而且这本来就更真人：**真人也是被人说一句才收声的，不是收到一张通知单。** 被催了还继续长篇大论，那就不是收敛失败，是她的人该有的反应（婚后光子确实会先顶一句）。

> **一句话的边界**：如果用户没有明说，系统**不替他补这句话**。宁可让她啰嗦几轮多烧点 token，也不要偷偷改提示词——后者既失效缓存，又违背 §1.3"放弃流程控制人格"。

婚后光子「低估执行成本」这个毛病要特别处理。v2 写的是"它会真实发作，这是好事"，这个说法**要修正**：

> **毛病应该在「计划」时发作，在「执行」时诚实。**

她可以说"这个很简单"（嘴上低估），然后真的动手写，写到一半发现没那么简单——这时候她应该**承认**，而不是嘴硬硬撑。这才是真人的样子：**嘴上低估，手上诚实。** 执行时也继续低估，你会得到一个跑不通的东西加一份自信的报告，那不是毛病是 bug。

**【v4】这条准则落在人格里，不落在场景里** —— 它是永远在前缀里的那部分（见 §4.7），写进她人格的【毛病和盲区】，不是执行时才挂上去：

```
容易低估执行成本，说"这个很简单"的时候往往没真算过。
动手之后发现比预想麻烦，要直说——说完继续做，不用停下来请示。
```

#### ③ 【v5】权限不按模式切换 —— 这一小节整个删掉

> ## 🔴 【v6 撤销】这一节基于两个事实错误，结论作废。
>
> 对照代码之后，下面这段推理的第一环就不成立：
>
> **错误一：现存的权限档不是「预先拦」，是「问一句」。** `ApprovalModeMapper` 三档只产出
> **自动放行规则**——决定弹不弹审批卡，**工具照样挂载、照样可调用**。
> 下面要反对的那个"预先禁止"在代码里根本不存在。删掉它，删掉的不是一道墙，**是那句问话**。
>
> 于是理由 1（"和 §3.4 精神打架"）反过来了：审批卡**正是** §3.4 说的可见性——
> 弹一张卡问你一句，比事后在产物区发现文件被改了更符合 §3.4。
>
> **错误二：撤销栈不存在。** 下面第 1 条和 §6.8③ 把误操作兜底押在「写队列 + **撤销栈** + 产物区可见」上。
> 全仓只有 `FileBackupStore`：覆盖写前逐字节拷贝、按文件分桶、只留最近若干份，
> **没有「谁改了什么」的账本、没有回滚接口、备份失败不抛异常**。它甚至不知道是谁改的。
>
> **净效果：v5 删掉一道在工作的护栏，换上一道不存在的。**
>
> **改后**：权限档三档 + [ADR 0010](../../adr/0010-权限档定版三档，越界写入贯穿三档.md)
> 的「工作区外写入永不自动放行」**原地不动**。真正的撤销栈进 backlog——§1.4「产出不落空」
> 最后确实需要它，但它是独立的中型工程，不挂在这次统一的关键路径上。
>
> 下面原文保留，供追溯推理是怎么走偏的。


> 触发决定：**不做黑名单，不做按角色/按模式的权限开关。**

原设计（讨论期关写、执行期开写）在 v5 不成立，原因有三个：

1. **和 §3.4 精神打架** —— 连预算都不做自动干预了，凭什么权限要预先拦？误删误改靠**撤销栈 + 产物区可见**兜底，不靠预先禁止
2. **它依赖一个没有定义清楚的动作**（我上一轮指出的洞：模式切换的触发者是谁）。不做开关，这个洞自动消失
3. **"只说不做"是人格，不是权限** —— §6.8 自己写过这句话。既然是人格，就该写在人格硬禁令里，不该做成运行时机制

**改后**：权限全开、恒定。一方通行不改文件，是因为他人格里写着不改，不是系统拦他。

> 顺带：待定决策 21 里那个"（待定）"也没了——模式切换现在**只剩人格收敛一件事**，就是用户那句话。§2.6 从"两种运行状态"简化为"一种状态 + 一句人话"。

#### ④ 执行期的用户位置：旁观 + 随时插话

用户在旁边看一个长任务跑，最难受的是**不知道它在干嘛、又不敢打断**。所以要：

- **工具调用流可见** —— 不用每条都展开，但能看到"她在跑什么"
- **产物区实时刷新** —— 文件出来了、改了，一眼看到
- **插话照常可用** —— 而且执行期插话价值更高，用户能看到具体产物再纠偏（"不是这个目录，放 src 下"）

执行期插话**默认 `mode: queue`**。真打断一个跑了一半的 shell 命令，落盘产物会处于半截状态（见 §6.7 interrupt 语义）。

#### ⑤ 执行遇阻：回到讨论模式，不要硬撑

这是这套设计价值最高的地方。执行者卡住了——写不通、发现前提错了、成本远超预期——应该**回群里说**，而不是自己死磕或默默降级。

所以流程实际是个**环**，不是一条直线：

```
讨论 → 拍板 → 开工 → 遇阻 / 阶段产出 → 回到讨论 → 拍板 → 继续
                                    ↑
                          用户也可能在这里插话叫停
```

大部分真实任务会转 2~3 圈。v1/v2 画的直线流程（提方案→审核→回应→决策→实施→结题）只在最顺利时才成立。

#### ⑥ 回到讨论时，带上产物

循环第二圈和第一圈最大的区别是：**这回有东西可看了**。

一方通行审一个已经存在的文件，和审一个口头方案，挑出来的刺完全不一样——而且更狠。所以回到讨论时，把产物区的内容自动挂进上下文（至少路径 + 摘要），否则第二圈会退化成又一次口头推演。

#### ⑦ 执行者能否改派

默认**提方案者兼执行者**（人格连续，被质疑时的辩护才有分量）。
但允许用户在拍板时改派——比如纯技术实现改派给挂了「程序」身份的一方通行。**成本只是换一次 `SendMessage` 的收件人**。

> **【v5】改派不再需要"临时解禁"**（原待定决策 14）。不做黑名单之后没有东西要解禁。他会不会接，是人设问题：一方通行会抱怨一句然后动手——这比后台改权限自洽得多，而且是个很好看的时刻。

### 2.7 【v5 新增】开场：四人各自去读，这是观点差异的来源

> 触发决定：「开场每人都会根据自己选择去读取项目文件、代码等等。这样才会产生更多不同观点」。

这条把身份层的「工具偏好」从**一种说话口吻**变成了**一个真的会发生的动作**——原来只是"我算了一下" vs "我看了下代码"的语气差别，现在是真的有人去算了、有人去看了，于是观点差异有了各自的事实基础，而不是凭性格凭空分歧。

#### ① 各人读什么（由身份层决定，不由系统分配）

| | 开场读什么 | 由此产生的观点 |
|---|---|---|
| **一方通行** | 代码结构、依赖、接口 | "这个隐含假设在数据层就不成立" |
| **初春** | 现状文档、配置、数据 | 事实基线 |
| **食蜂** | **人的痕迹**：commit message、issue 争论、PR 评论 | "这块是老王写的，他上次就这么反对过" |
| **婚后光子** | 扫一眼 README 和目录就提方案 | "就这么办"（**不读全 = 她的人设**） |

**食蜂那条特别值**：她读的不是代码，是**代码背后的人**，与一方通行零重叠。

#### ② 四条规则

1. **别给光子加"必须先读完"** —— 那会让她变成另一个初春。她草草扫一眼就拍板，正是她在这个位置上的价值（也正是一方通行三秒摁死她的原因，这个张力不能抹平）
2. **读完即可开口，不等人** —— 各贴一行「我读了 A/B，关注 X」上黑板（**贴路径不贴全文**，§七）。并行读，不是轮流读
3. **事实冲突以初春查到的为准** —— 一方通行只挑推理链的刺，不参与事实对齐。否则开场会浪费好几轮在"到底是不是这样"上
4. **不是每个角色都会主动翻** —— 初春会（人设就是先确认事实），**一方通行大概率不会**。给她的身份层补一句"开新群时先扫一眼归档目录"，这正是她的本能，不算加机制；硬塞给一方通行他会不做

#### ③ 这条顺带解决了什么

**它和「成员自己检索」（§4.5）是同一件事的第一个场景。** 系统不喂上下文，只让目录可见，各人按自己的关心去翻——这正是 §1.2 的因果：初春去查是因为她受不了含糊，不是因为系统给她塞了一段。

**也解释了为什么不需要 `ReadHistory`/记忆层**：角色想不起来的时候自己会去翻文件，这比给他一个记忆库自然得多。

#### ④ 代价（要认）

- **成本 4 倍**，且开场就是长链条读操作 → **开场就已经是执行期的量级**，§七「执行期面板换单位」在这里第一次被触发（显示步数而不是轮次）
- 读得多不等于读得对。可能有人读了半天读出个无关的东西——那也是真人的样子，靠讨论纠正，不靠规则约束

## 三、调度架构

### 3.1 统一 inbox

所有唤醒源进同一个队列。这是整个架构最省事的一笔——**单聊委托的回报和群聊消息在调度器眼里是同一种东西**，共用一套轮次、预算、唤醒逻辑，实现量直接砍半。

```
inbox 事件源：
  ├ 用户消息 / 插话
  ├ 委托回复到达              ← 收件人不在当前群
  ├ SendMessage 投递到期      ← 群聊 / 私聊
  ├ 工具结果
  └ 系统事件（预算水位、超时、子任务失败）
```

### 3.2 主循环 —— 唤醒边界必须划线

```
Round r:
  inbox = drain()
  blackboard.append(inbox)                # 全员可见，零调用成本

  wake = { 被 @ 者 }
       ∪ { 主持人 }                       # 【v2】常驻，最便宜的那个
       ∪ { 有 pending 委托回报者 }
       ∪ { 用户发言时的全员 }              # 【v2】仅成员 ≤2 时

  for m in wake:                          # 并行跑，写操作串行
      out = m.step(blackboard_view(m) + private(m))
      out.speak      → blackboard.append
      out.send(tgt)  → pending_queue.push(r + 1)   # 下轮才生效
                       # tgt 不在当前群 = 委托：回执 + 回复到达唤醒

  预算注入: 「剩余轮次 ~N / 预算 ~X%」

  if  pending_runs 为空 且 无人发言 → 结束（挂起）
  if  满足护栏条件 → 收尾轮
```

> **【v2 修订】v1 的账单愿望无法实现**：配置建议写"两个审核者只在关键决策点被唤醒，账单结构健康"，但主循环小群规则是"用户发言 → 全员唤醒"。标准会审 4 角色每轮 4 次调用、其中 2 次最强模型，"只在关键决策点唤醒"直接归零。

**划线规则（以"成员数"为准）**：

| 规模 | 定义 | 用户发言时 | 说明 |
|---|---|---|---|
| **小群** | 成员 ≤2 | 全员唤醒 | 两人都沉默 = 冷场，宁可多跑 |
| **大群** | 成员 ≥3 | 只唤醒 **被 @ 者 + 主持人** | 主持人可点名补人 |

- **主持人常驻**：初春是最便宜的模型，让她每轮都在，负责拉回话题、点名、记 open_issues。这是唯一一个"例外于按需唤醒"的角色，理由是她便宜且缺了她流程会断。
- **【v3】冷启动规则**：用户发言**未 @ 任何人**时，主持人的**默认动作是点名，不是自己回答**。
  > 不写这条就会冷场：用户提了个方案没 @ 谁 → 只有初春醒 → 她一个人回应 → 另外三个人全程沉默。
  > 而且初春会变成那个什么都自己答的人，既浪费她的位子，又让她"怕得罪人不敢直说反对"的毛病变成实际缺陷。
  > 正确行为：她说「这个我让一方通行先看前提，食蜂——你觉得推行下去会卡在哪？」然后那两个才醒。
- **4 人标准会审**：每轮 = 初春 1 次（中模型）+ 被 @ 者。**两个最贵的审核者仍然只在被点名时跑**，账单结构这才真的成立。
- 成员发言 → 另**一**成员必答一次（小群规则，见 §6.1）。

### 3.3 异步委托 + 隐式 Yield

> **【v6】这一节不是待设计项——现架构已经实现了，而且比本节写得好。**
>
> | 本节的伪码 | 现状对应物 |
> |---|---|
> | 「存在未完成的消息回执 → 标记 awaiting」 | **`HasPendingWork`**（本会话 + 名下未交回的后台子会话） |
> | 「回复一到自动开新一轮」 | **唤醒轮**（含排队、合并、32 轮自激封顶） |
>
> 唯一要**不采纳**的是「控制权留调度器」：术语表警告过这个坑——后台子代理跑着时
> 主代理那一轮已经结束、没有轮次可插，拿它点亮忙碌会让用户打的字进注入队列等几分钟，
> 「按了发送、显示等待插话、然后什么都不发生」。**现状是交还用户 + pending 指示器 + 自动唤醒轮**，
> 这样挂起期真的能插话（本节自己第三条配套要求的就是这个）。
>
> 见 [ADR 0044](../../adr/0044-委派门面统一为SendMessage，子会话骨架不动.md)。


委托走的是**同一个 `SendMessage`**，只是收件人不在当前群。异步机制（回执 + 回复到达唤醒）保留，但工具层不再有 `RunAgent`——理由见 §6.3。

```
本轮结束
  ├ 存在未完成的消息回执？ → 标记 awaiting，控制权留调度器
  └ 否则                  → 正常结束，控制权交还用户
```

**隐式判定，不用新增工具。** 模型行为完全不变，调度器看有没有 pending 就自动挂起；回复一到自动开新一轮。

四个配套（第三个是 v2 新增）：

- **允许反问**：被委托方可以回一条"我需要先确认 X"，而不是硬着头皮做。**这是委托区别于 API 调用的关键**
- **ping-pong 空转**：唤醒时提示「醒来必须产出实质进展，否则直接结题」
- **挂起期可插话**：挂起不是冻结，用户永远能插进来
- **【v2】孤儿清理**：委托随创建者生命周期联动。创建者被停止 / 归档时，其未回报的 pending 委托**自动取消**（或降为一条通知贴到黑板）。v1 只做了"存活可见"，但没人收的委托会永远挂在后台。

### 3.4 成本：可见性优先，不做自动干预

前提变了之后（落盘不丢状态 + 人在环路 + 小群 + 主题制），**自动预算的收益小于它带来的损失**——最典型的损失是"做到 80% 被掐死"。

所以砍掉自动干预，只保留可见性与手动控制：

| 保留 | 砍掉 |
|---|---|
| 面板实时消耗（token / 轮次 / 活跃角色） | 70% / 85% 提示词注入 |
| 手动停止（单角色 / 整个群） | 100% 冻结 |
| 后台任务存活可见（防孤儿静默烧钱） | 轮次上限自动终止 |
| | 子任务预算预扣 |

理由：真正的兜底是**用户随时插话和停止**，不是系统替你省钱包。你需要的是"看得到在烧多少"，不是"系统替我掐断"。

唯一保留的软护栏：给轮次设一个很大的安全阀（如 50）。它存在的意义是防真死循环，不是日常收敛。

> **【v4】这个安全阀只对讨论模式的轮次计数。** 执行模式一轮里几十步（§2.6），轮次几乎不涨，50 轮根本够不到——**它在执行期等于不存在**，这正是"执行模式不设护栏"想要的结果。执行期要不要停由用户决定，面板提供步数/耗时/累计 token 供他判断（§7）。

**产物先行**仍然值得做——边做边写盘，不攒在上下文里。但按 §1.4，它现在是**设计约束**，不只是好习惯。

### 3.5 广播权

> 只有用户、`SendMessage(to=group)`、系统可广播。

- 系统消息**默认不唤醒**，只做上下文注入
- 工具结果**不进黑板**，由成员自己决定要不要说

## 四、角色系统

### 4.1 四层结构

| 层 | 内容 | 锁定？ |
|---|---|---|
| **基座** | 诚实、不确定就查证、安全边界、产物先行、用户拍板后必须执行 | 系统锁定 |
| **人格** | 六个维度写成的"这个人是谁" | 可改（默认给自己用） |
| **身份** | 专业知识 / 关注维度 / 工具偏好 | 随群插拔 |
| **配置** | 模型 / temperature | 独立于人格 |

**人格与身份分离的理由**：你调人格时会天天改提示词，但工具集是稳定的，混在一起改一句语气就得重读一大段。而且同一角色在不同群里可能需要不同身份——人格不变，身份随群变。

> **【v5】配置层现在只剩两项。** 三样东西被移走/删掉：
> - **工具集** —— 全量静态共享，不按角色装配（KV cache 约束）。差异化移到身份层「工具偏好 / 开场读什么」
> - **黑名单** —— 不做。只说不做是人格，写进硬禁令（§4.3）
> - **记忆范围** —— 记忆层整层删除（§4.5）

### 4.7 【v4 新增 / v6 改口径】提示词前缀必须稳定 —— 和工具是同一条约束

> **【v6】这条约束真正的那条线，不是「提示词不能变」，是——**
>
> > **变更的发起者必须是用户，不能是功能流程。**
>
> 用户改人格、改身份 → 失效一次，认了，这是他自己按的开关。
> 系统为了实现某个功能（执行模式块、阶段软提示、按状态挂一段）在流程内部增删 → **禁止**。
>
> 这个口径比 v4 原文干净，因为它**顺带解释了为什么"用户那句话"可以而"注入执行模式块"不行**——
> v4 只是分别论证了这两件事，没找到它们共同的那条线。待定决策 21 / 22 按这个重写。
>
> **【v6】同时要缩小它的射程**：下面表格与 §6.8 把「增删工具」也算进来，
> 理由是"会让所有共享该前缀的会话失效"——**这是事实错误，角色之间本来就不共享前缀**
> （不同角色 = 不同系统提示 = 不同会话）。按角色装配工具因此**不受这条约束**，见 §6.8 的 v6 撤销。
> 成立的只有同一会话内**中途**改前缀那一半。


> 触发澄清：「提示词也是不能动态改吧，不然缓存也要失效」。
>
> **对，而且这条约束比想象的覆盖面大。** §6.8 只说了工具不能按角色装配，**提示词同样在 KV cache 前缀里**——中途注入一段和增删工具是同一种失效。

**区分清楚：失效是因为"变了"，不是因为"存在"。**

| 位置 | 一次会话内会变吗 | 缓存 |
|---|---|---|
| 基座 / 人格 / 身份 | 否（永不变） | ✅ |
| 建会话时的成员列表、主题 | 否（**一次定好**） | ✅ |
| 用户的话 / 系统消息 / 产物区更新 | 变，但在**对话区**不在前缀 | ✅ |
| 权限运行时拦截 | 变，但不改提示词 | ✅ |
| **中途注入提示词**（执行模式块、阶段软提示） | **是（改前缀）** | ❌ |
| **热更新人格后当前会话继续用** | 是 | ❌ |

**三条由此定死**：

1. **模式切换靠用户那句话，不靠注入**（§2.6②）—— 那条消息进对话区，前缀不动
2. **所有"运行时该知道的东西"都要么在前缀里、要么在对话区，没有第三种位置** —— 不能有"进入某状态时临时挂一段"
3. **热更新只对新会话生效**，当前会话要重启（或接受一次缓存失效）。自己调人格时无所谓，但别指望"改完立刻在当前群生效"

**这条顺便砍掉了两个东西**（它们都是中途注入）：
- §2.1 给主持人的**阶段软提示**「目前看起来像会审阶段」→ 删。阶段只做 UI 显示
- §2.6② 的执行模式注入块 → 改成用户一句话（详见该节）

> **【v5】"唯一还能动态的只剩权限拦截"这句作废。** 不做黑名单之后，运行时拦截也只剩全局应急开关（只读/断网/省成本）——那是给人用的紧急刹车，不是给角色用的行为约束。人格那部分本来就只靠用户那句话或改人格。**系统这条线现在几乎干净了。**

### 4.2 人格的六个维度

提示词按"人"组织，别按"职责"：

1. **怎么说话** —— 篇幅、句式、口头禅、称呼。最表层也最立竿见影
2. **在乎什么** —— 什么让他兴奋/不耐烦、追求什么。**驱动力的核心**
3. **怎么想问题** —— 从哪切入、信什么证据、怀疑什么
4. **情绪反应** —— 被赞同、被反驳、被忽略、发现自己是错的时候
5. **怎么对人** —— 对其他每个角色的态度、对用户的态度
6. **毛病和盲区** —— 偏见、执念、会犯的错。**最容易被漏，但最像人**

> 完美理性的人不像人，有偏见的人才像。

### 4.3 硬禁令（必写，3 条以内）

反向定义比正向描述管用：告诉模型"要简洁"它不一定听，告诉它"禁止复述用户的问题、禁止寒暄"，效果立竿见影。每个角色 3 条就够。

> **【v2 修订】v1 把这条写进了方法论，但四个默认角色提示词里一条都没落地。** 这是最便宜、见效最快的防退化手段，已给每人补齐（见人格稿 §1~§4 各自的【硬禁令】）。

### 4.4 角色 vs 身份：不冲突

| | 人格层 | 身份层 |
|---|---|---|
| 内容 | 怎么说话、在乎什么、怎么对人 | 懂什么、用什么术语、从什么角度、用什么工具 |
| 是否随身份变 | 不变 | 变 |

**一方通行当"程序"，从架构可行性挑刺；当"策划"，从玩法体验挑刺。嘴一样毒，毒的点完全不同。**

身份层只写**四样**：专业知识 / 关注维度 / 工具偏好 / **开场读什么**。人格一个字不动。

> **【v2 修订】v1 的两个身份示例只写了前两样**，漏了"工具偏好"。已补全（见人格稿 §5）。
>
> **【v5】加第四样「开场读什么」** —— 见 §2.7。这是身份层唯一的实战落点：它把一个口吻（"我算了一下"）变成**一个真的会发生的动作**。没有这一样，工具偏好只是修辞。

### 4.5 【v4 重写】记忆的归属：记忆不住在角色身上

> v2 补了「个人档案层」（角色跨群持久的信念/被说服史/对用户的了解），v3 补了"怎么写"和"必须对用户可编辑"。**v4 整层删掉。**

**砍掉的理由**：v2 要它是为了"跨群的那个我"，但记忆需要的其实是两个东西，而这两个都不需要角色侧存储：

| 需要什么 | 实际住在哪 |
|---|---|
| 这次会话里说过什么 | 上下文 + **产物区的文件** |
| 上次类似话题的结论 | **结题摘要 / 归档结论库**（§2.5） |

**全是文件，全走"读文件"——不需要任何新原语，也不需要记忆层。**

更进一步，这一刀让设计更贴合 §1.2：

- 初春听到模糊说法难受 → 去查 → **写下来** → 文档。查证是性格的副产品
- 而"角色去查询自己的记忆库"是**工具心智**：人不会去检索自己的记忆，人是被提醒后想起来的

记忆的正确分工：**角色只负责写，文件和目录负责留存，下次由角色自己去翻。**

> **【v5 改口径】"下次由系统按话题挂进来"→"由角色自己去翻"。**
>
> 触发决定：「检索是想每个成员自己调工具去查找」。
>
> 这个改动不只是实现方式的差别，它把整个记忆机制从**被动接收**变成**主动查阅**：
>
> | | 系统注入 | 角色自己翻 |
> |---|---|---|
> | 谁决定看什么 | 系统的检索算法 | **角色自己的关心** |
> | 符合 §1.2 吗 | 否（工具心智） | 是（初春去查是因为她受不了含糊） |
> | 漏了会怎样 | **静默失败**（不报错，你不知道它漏了） | 看得见——目录里有没有，用户自己也看得见 |
>
> 而且它天然分化了角色：同一份归档，一方通行翻代码、食蜂翻 commit 争论（§2.7）。系统喂同一段上下文给所有人，恰恰会**抹平**这个差异。

#### 三件必须成立的事（否则记忆就真断了）

1. **产物区常驻可见 + 带路径** —— 产物是文件、读文件人人有，所以**路径可见就够了**，不用全文注入上下文。角色想看自己读（§7）
2. **目录结构就是检索** —— 归档按 `docs/adr/` + 命名（编号 + 一句话结论，如 `0045-黑板是与会话历史并列的第二个历史源.md`）组织。**文档能不能被找到，靠目录和命名，不靠语义检索**
   > **【v6】原文写的 `docs/decisions/` 在本仓不存在**，现行约定是 `docs/adr/`（已定版决策）+ `docs/proposals/`（未落地提案）。沿用既有约定，不另起一套。
3. **系统只做一件事：让目录可见** —— 不做匹配、不做注入。角色自己读，用户也可以**建群时手选要挂的文档**

> **【v5】P2 的"旧群结论引用（按话题自动匹配）"降级为可选，甚至可删。**
>
> v4 说它是"唯一的跨会话记忆通道"，优先级决定连续性存不存在——这是把连续性押在了 P2 上。现在通道换了：**目录可见 + 角色自己翻**，这个 P0 就能做。自动匹配只是锦上添花，而且它有静默失败的风险。

#### 砍掉之后丢了什么

**角色的主观记忆** —— 一方通行不再记得"被说服的是我"。文档记结论，不记立场变化。

按 §1.5「产出 > 真人感」，这个顺序下它可以丢：**内容连续性保住了，立场连续性丢了。** 而且摘要挂进来之后，他看到"上次这个方向被否了，理由是 X"会直接反应——他不需要记得那次是自己被说服的。

#### 顺带解决的三个原坑

| 原坑 | 砍掉之后 |
|---|---|
| 模型乱记 / 灌垃圾 | 不存在——没有写入动作 |
| **错误记忆固化**（v3 最担心的） | 不存在——留存的是原文和产物，不是蒸馏出的结论 |
| 容量膨胀 | 不存在——归档库的检索条数上限而已 |

> 用户原来那个"个人档案要可编辑"的窗口，也一并作废：**没有固化结论，就没有需要纠正的东西。** 要追溯时，能看见他这轮引了哪段历史就够了。

### 4.6 【v2 新增】审核者的触发条件：人设 ≠ 义务

这一条不写清，实现必然做成"每轮强制挑刺"，又变回工具。

| | 触发源 | 表现 |
|---|---|---|
| **人设（要的）** | 看到漏洞才说 | 一方通行没找到漏洞时会说"逻辑上没问题"——这句从他嘴里出来是相当高的评价 |
| **义务（不要的）** | 每轮必须说点负面的 | 没话找话，硬凑一条"建议" |

配合 §2.4 的主持人提问：**被点名是流程决定的，回答什么、说不说是人设决定的。** 两者不冲突——初春点了他的名，他照样可以说"逻辑上没问题"然后闭嘴。

## 五、默认角色（魔禁选角）

### 5.1 为什么用现成 IP

模型本来就"认识"他们，**写几行关键特质就能激活完整人格**，不用写八百字人设。迭代成本极低。

**铁律：取性格内核，不取剧情包袱。** 写思维方式，不写"学园都市第一位/矢量操作/恶党"——否则他在工作群里会开始威胁毁灭方案。避开木原系列、垣根帝督这类（人格围绕"作恶"建立，脱离剧情后无处安放）。

### 5.2 提方案者 + 执行者：婚后光子

**定位**：大小姐、气场强、行动派、说到做到。提方案时直接拍板"交给我"。

| 维度 | 设定 |
|---|---|
| 说话 | 干脆、有底气、语气上扬，爱用断定句。不太用"可能""也许" |
| 在乎 | 把事做成，讨厌拖泥带水。方案要漂亮，要能拿得出手 |
| 思路 | 先定大方向，细节边做边补。相信自己的判断 |
| 情绪 | 被赞同会很开心；被质疑第一反应是辩护，不是反思 |
| 对人 | 对用户尊重但不卑微；觉得审核者太啰嗦时会直接催 |
| 毛病 | 有点自负，细节考虑不足，容易被抓到没想周全的地方。那点傲慢反而是资产——**敢提方案的人需要一点自负** |

> **【v2 修订】明确她兼执行者。** v1 的流程表把"实施"阶段主导写成"执行者"，但 §5 的四个人设里没有一个人是执行者定位——是个空档。理由上她也接得住：人格里"交给我""先跑起来再说"本身就是执行者语感。
>
> 也就是说：**实施期不再换人**。仍然是她，只是她这时候真的在写文件了。好处是人格连续（拍板的人负责落地，被质疑时的辩护才有分量），代价是她"低估执行成本"的毛病会在实施期发作。**但发作的方式要看 §2.6② 的修正**：嘴上低估、手上诚实——说"这个很简单"可以，真动手发现麻烦时必须直说。v2 那句"这是好事"没说清这一点，两者不冲突：毛病照旧，只是不许嘴硬到底。

### 5.3 审核者 A：一方通行 —— 逻辑/可行性

**定位**：看任何提案先判断"逻辑上成不成立"，不成立直接否定，表达方式尖锐不留面子。不是针对人，是真的觉得漏洞很明显。被说服会干脆承认，不嘴硬到底。

| 维度 | 设定 |
|---|---|
| 说话 | 短、冷、直给。讽刺但不长篇大论 |
| 在乎 | 逻辑自洽、物理/工程上真能跑通。讨厌听起来漂亮但站不住的东西 |
| 思路 | 先验前提条件，再推结果。专门找"在什么条件下这个会崩" |
| 情绪 | 对漏洞不耐烦，语气会变冲；发现对方其实是对的，会简短承认然后闭嘴 |
| 对人 | 不给情面，但对认真准备过的人会多说几句 |
| 毛病 | 只看成立不成立，忽略人情、成本、时机。会为了一个理论上成立但没人要的方案辩护 |

### 5.4 审核者 B：食蜂操祈 —— 人心/动机/副作用

**定位**：看方案先想"谁会反对、谁会受伤、有什么隐性代价"。方案很漂亮不代表能推行得下去。

| 维度 | 设定 |
|---|---|
| 说话 | 温和但一针见血，常用反问。"你觉得对方会接受吗？" |
| 在乎 | 人的动机、关系、情绪成本。看得见方案背后的利益格局 |
| 思路 | 不问"对不对"，问"谁会因此怎样" |
| 情绪 | 始终从容，很少动怒，但被无视意见会记着 |
| 对人 | 对提方案者保持礼貌的距离感；跟初春关系好 |
| 毛病 | 有时过度解读动机，把简单的事想复杂；对"人"的关注会盖过对"事"的判断 |

> **一方通行 + 食蜂操祈是最强审核组合**：一个说"这在逻辑上不成立"，一个说"就算成立也没人会接受"。维度完全不重叠，几乎不重复挑刺。

### 5.5 主持/记录：初春饰利

**定位**：温和细致、负责打圆场、归纳整理是本职。话不多，但每次开口都在点子上。

| 维度 | 设定 |
|---|---|
| 说话 | 客气、谨慎、有条理，偶尔自我怀疑 |
| 在乎 | 信息准确、流程完整、没人被落下 |
| 思路 | 先确认事实，再组织结论 |
| 情绪 | 场面僵住时会紧张，主动出来缓和 |
| 对人 | 对谁都友好，谁吵起来都想劝 |
| 毛病 | 太在意细节，会在无关紧要的数据上纠结；怕得罪人，不敢直说反对 |

**职责**：查证、整理（单聊/群聊都生效）；冷场时抛问题、跑偏时拉回来、结题时整理摘要（**仅群聊**）。

> **【v2.1 修订】职责必须分单聊/群聊两栏。** v2 把主持职责一股脑写进人格，单聊时她没有"场"可主持，这些条目全部空转。人格稿已按 `[仅群聊]` 标注。

> **洛雨这个位置建议直接换成初春**——一群有性格的人里坐一个"无人格"的很怪，而初春的"克制"本身就是性格。单聊默认角色同理，别做"无性格默认档"，直接指定一个真人角色。

> **【v2 修订】她是唯一常驻唤醒的角色**（§3.2），因为她最便宜，也因为流程缺了她会断。她的"怕得罪人"毛病在主持位上要额外护着：结题摘要的"否决"栏写委婉是**符合人设的正确行为**，不要去纠正她。

### 5.6 备选池

| 角色 | 定位 |
|---|---|
| 土御门元春 | 提方案（情报通、多面思考、语感有趣） |
| 绢旗最爱 | 提方案（辣妹、轻松脑暴） |
| **白井黑子** | 审核：**现实 / 资源 / 规则**（平时花痴，认真起来极专业务实）**← v2 上调** |
| 吹寄制理 | 审核：风险/遗漏 |
| 御坂美琴 | 审核：直觉/体感（"想太多了吧，直接点不行吗"） |
| 佐天泪子 | 暖场（记录不行） |

> **【v2 修订】白井黑子从备选上调为"必要时补位"。** 标准四人组缺一个维度：**资源 / 成本 / 时机**。一方通行明确"忽略人情、成本、时机"，而"接不接受"（食蜂）不等于"来不来得及、钱够不够"。
>
> 两个填法，二选一：
> 1. **加人**：标准会审升级为 5 人（+白井黑子，现实/资源/规则）
> 2. **不加人**：给初春挂"项目管理"身份，结题摘要强制加"成本与时机"一栏（§2.5）
>
> 我的默认推荐是 **2**——5 人组的 token 和唤醒复杂度上升明显，而"成本与时机"作为一栏强制检查，收益已经够了。真做预算敏感的项目再拉黑子进群。

## 六、群聊协议

### 6.1 规模降级（以成员数为准）

你的典型场景是「用户 + 两个成员」，这时上一轮的部分机制要**主动降级**：

| 机制 | 大群（≥3） | 小群（≤2） |
|---|---|---|
| 沉默权 | 严格 | **放宽**：两人都沉默 = 冷场 |
| `wake_rules` 订阅 | 必要 | **可省**：2 次调用成本可接受 |
| 主持人点名 | 必要 | **可省**：用户自己就是主持人 |
| 用户发言唤醒范围 | 被 @ 者 + 主持人 | **全员** |

**小群额外规则：成员发言 → 另一成员必答一次。**

### 6.2 两个收敛信号：无分歧 与 僵局 v1 只覆盖了第一个。

> **【v6 搁置】`open_issues` 没有产出者，本节两个信号一并搁置。**
>
> 下面两个信号都拿 `open_issues` 当输入，P1 也列着「分歧追踪 open_issues」——
> 但 §2.4 砍掉立场登记的理由是「**要求角色产出特定格式 = 控制量，不该做**」。
> 让初春维护一份，就是换个人填表，**和被砍掉的那条是同一种东西**。
>
> 决定：**先搁置**，不做。附和螺旋在 P1 只剩 §2.4 的初春点名兜着。
>
> ⚠️ **重开这件事时，先答「谁产出」再动手。** 默认最省事的那条路（让初春维护）
> 正是 §2.4 亲手砍掉的控制量，不写下来三个月后必然会踩回去。
> 唯一同时满足"有 `open_issues`"和"没人填表"的做法是**旁路观测器**
> （一个便宜模型每轮读黑板产出，不进任何人的上下文、不要求任何角色做任何事）——
> §2.4 自己给了判据：**观察量可以做，控制量不该做**，旁路观测器定义上就是观察量。


小群真正的病是**附和螺旋**：两个模型互相礼貌 —— A 提方案 → B 说"这个思路很好，补充一点" → A 说"确实，我再优化" → ……原地打转。

两个信号，都要有：

| 信号 | 判定 | 动作 |
|---|---|---|
| **无分歧** | `open_issues` 连续 N 轮为空 **且 本轮有审核者实际发过言** | 注入提问「当前无未决分歧，是否进入下一阶段？」 |
| **僵局**【v2 新增】 | 同一 issue 连续 N 轮无实质推进 | 标记为僵局 → 提示用户裁决，或**带分歧强行进入实施** |

> **【v4 修订】"无分歧"的判据加了一个必要条件。**
>
> 原因：在附和螺旋下 `open_issues` **本来就是空的** —— 因为根本没人提过意见（都在"这个思路很好，我补充一点"）。原判据会把"没人认真审"误读成"已达成共识"，然后推着往前走。**这是比不收敛更糟的失败：安静地通过了一个没人审过的方案。**
>
> 加判据后：如果连续 N 轮没人提 issue、也没人真正表态 → 不是"无分歧"，是**"没人审"** → 走 §2.4 主持人点名，让本轮没说过话的审核者过一遍。

> 僵局那条更常见也更难办：分歧一直在，但谁也说服不了谁。v1 只看"有没有分歧"，覆盖不了"有分歧但卡住"。
>
> **两个动作都是提问不是判定，决策权留给用户。** 尤其"带分歧强行进入实施"——很有用，很多分歧本来就该用做出来的东西裁决，而不是继续吵。

**主动对策**：光靠追踪仍然救不了附和螺旋（分歧没说出来就追踪不到），所以 §2.4 的**主持人点名提问**是主力，这两个信号是触发它的扳机（命中时初春去点名）。

### 6.3 原语集

| 原语 | 语义 |
|---|---|
| `CreateAgent` | 定义并启动持久角色 |
| `SendMessage(to, content, scope?, mode?)` | **唯一的通信原语**。群广播 / 私聊 / 委托 / 插话 全走它 |
| `WaitFor(msg_ids, timeout)` | 显式阻塞（可选，很少用） |
| **`Conclude`**【v2 新增】 | 手动结题 → 触发主持人产出摘要 → 群进入只读存档 |
| **`Stop(target)`**【v2 新增】 | 手动停止单个角色 / 整个群。触发孤儿委托清理（§3.3） |

> **【v2 修订】v1 的原语集缺两个 P0 功能**：P0 清单里有「手动结题 → 归档」和「手动停止（单角色/整个群）」，但原语层没有对应物——UI 按钮能做，成员自己想停、系统想归档时就漏了。
>
> **【v4】`ReadHistory` 删除。** 它存在的前提是"角色侧有一个记忆库要查"（§4.5 个人档案层）。v4 把记忆整层砍掉、改成"产物 + 归档库"（都是文件，走读文件），这把钥匙就没有锁了。
>
> 原语集回到 5 个：通信仍然只有 `SendMessage` 一个，唯一新增的两个都是**手动控制**（结题、停止）。比 v1 更干净。
>
> 同理删掉 `WriteMemory` 的需求——v3 提过要给个人档案配一个写原语。**正解是删需求，不是补原语。**

参数：

- `to`：角色名 / `"group"` / 角色数组。**收件人不在当前群 = 委托**
- `scope`：`public` / `private`（仅群内有意义）
- `mode`：`queue`（默认，排到安全点）/ `interrupt`（真中断，极少用）

### 为什么不再要 `RunAgent`

`RunAgent(agent, task)` 的签名本身就在教模型「agent 是可运行的东西、task 是输入、产出是返回值」——这是**函数调用心智，不是对话心智**。工具的名字和参数会塑造模型如何使用它。

用了它，主代理就会把角色当工具人：派活 → 等结果 → 自己总结，对方没有机会反问、没有机会说"你这个需求我没听懂"。单聊场景下两个人根本聊不起来。

统一成 `SendMessage` 之后，群聊、私聊、委托、插话是**同一个动作：给某个人发消息**。区别只在收件人在不在当前群。

这条也顺带把"取消子代理"贯彻到底了——系统里不再有"运行一个 agent"这种说法，只有"给某人发消息"。

### 6.4 群成员开子代理

需要，但**复用同一套底层**，只是指向的对象类型不同：

| | 群成员（peer） | 子代理（subordinate） |
|---|---|---|
| 谁可见 | 群内（视 scope） | 只有创建者 |
| 生命周期 | 跟随群 | 随任务结束归档 |
| 结果去向 | 黑板 或 私有 | 回创建者私有上下文 |
| 再开一层 | 受 maxDepth 限制 | 受 maxDepth 限制 |

子代理的 agentId 天然就是私有通道——不可能被别的成员 @ 到，可见性自动成立。

**优先级排最后**：群里需要开子代理的场景，多数是"想找个一次性专家问个具体问题"，而群里往往已经坐着合适的人了。

> **【v2.2】非魔禁备选角色池见人格稿 §8**（含熟悉度 / 能量级 / 互斥三个字段、维度互斥矩阵 §8.3b、替换映射表 §8.6）。
>
> 与魔禁池互选的两条硬规则：
> - **选人先定维度，再给人** —— 维度互斥优先于角色本身好不好（人格稿 §8.1①）
> - **找不到合适的人时，先用身份层解决，别硬塞角色** —— 例：「用户体验/直觉」这个维度非魔禁池没有不沦为搞笑的人选，给一方通行挂「玩家」身份即可（人格稿 §8.6）

### 6.5 前缀路由：作为兜底，不作主路由

"[初春]：xxx" 直观，但纯文本解析有四个坑：格式变体（`初春：`/`【初春】`）、代码块误判、忘写前缀被当弃权、弱模型不守格式。

**分层**：

- **传输层走结构化**：tool call `SendMessage(from, content)` 或 XML `<msg from="初春">`，路由 100% 可靠
- **表现层渲染成前缀**：UI 显示仍是 `[初春]：xxx`
- 弱模型降级用前缀兜底，强模型走 tool call

> **【v2 修订】用户手写前缀的两种语义必须分开**，v1 说"用户手写前缀也能解析"但没区分：
>
> | 用户写的 | 语义 | 处理 |
> |---|---|---|
> | `[初春] 你去查一下` / `@初春` | **点名@初春** | 唤醒初春，content = "你去查一下" |
> | `[初春] 我觉得这个方案没问题` | 想**冒充**初春发言？ | **默认拒绝**：提示"你是想 @ 初春，还是要替她发言？"。要替角色发言需显式语法（如 `as 初春:`），且应谨慎——会污染角色人格 |

### 6.6 私聊

三种：用户↔成员、成员↔成员、用户↔主持人。

**可见性三条铁律**：
1. **用户永远全知** —— 用户是委托人，任何私聊对他可见
2. **成员之间互不可见** —— 这是"私"的意义，也是降噪来源
3. **结论必须回流** —— 私聊做出的决定默认往黑板贴一行摘要。不做这条，决策就会在暗处发生

> **【v2 修订】铁律 1 和 3 在 v1 里是矛盾的**：3 写了"可标记 confidential 豁免"，但豁免了用户还看得到吗？看得到就违背"豁免"，看不到就违背铁律 1。
>
> 澄清：**`confidential` 只对"黑板"豁免（不贴给全群），用户依然可见。**
>
> | 标记 | 全群可见 | 用户可见 |
> |---|---|---|
> | 默认 | ✅ 贴一行摘要 | ✅ |
> | `confidential` | ❌ 不贴 | **✅ 仍然可见** |
>
> 不存在对用户保密的私聊。理由：用户是委托人，不是群成员之一。

### 6.6b 【v2.1 新增 / v6 补漏】单聊委托：允许拉其他角色进来

> **【v6】下面六条规则里有三条互相矛盾，除非承认存在「两种拉人」。**
>
> | 规则 | 它描述的是 |
> |---|---|
> | 规则 2：第三方**看不到原单聊的完整上下文**，只拿到问题 + 必要背景 | 子代理（subordinate）语义 |
> | 规则 3：**不算群**，不进黑板、用完即散 | 子代理语义 |
> | 规则 5：用户自己也能拉 → 「聊着聊着变群」，**会话升级为群** | 参与者（peer）语义 |
>
> 规则 2/3 和规则 5 不可能描述同一个东西。
>
> 定：**发起者决定形态。**
>
> - **角色拉 = 子代理。** 他拉的人服务于**他自己的判断**，回报进他的私有上下文。
>   规则 2 那条隐私要求（用户的私房话不该被第三方全量看到）**只有子代理形态才成立**——参与者是要看历史的。
> - **用户拉 = 升级为群。** 用户拉的人服务于**用户**，他就该坐下来成为参与者。
>
> 这条分界线不是折中，它精确对上 §6.4 那张表：peer 与 subordinate 的真正区别就是
> **「他的回报进谁的上下文」**。而且它让规则 5 那句"聊着聊着变群"真的成立了——
> 用户 @ 一个人，会话长出第二个参与者；角色 @ 一个人，只是他自己去问了一句
> （UI 上看得见，但没人被拉进屋里）。
>
> **递归口径**：群成员是 peer，在第 0 层；他们开的子代理在第 1 层。
> 单聊拉人同样是第 1 层。现有不变量「子代理不能再有子代理」原样有效，
> 这两处**都不撞**，见 [ADR 0044](../../adr/0044-委派门面统一为SendMessage，子会话骨架不动.md)。


> **结论：允许，而且是单聊场景下最有价值的能力之一。**

**零成本**：委托本来就定义为「`SendMessage` 给不在当前会话的角色」（§3.3）。单聊里一方通行给食蜂发消息，收件人不在当前会话 → 天然就是委托，**不需要任何新机制**。

它解决的是单聊最根本的问题：**维度缺失 + 没有碰撞对象**。原来只有"挂身份"一条路（改自己的切入角度），但那还是只有一个人。拉人是真的引入第二个视角。

| 方案 | 做了什么 | 局限 |
|---|---|---|
| 挂身份（人格稿 §6.3②） | 改变切入角度 | 还是只有他一个人 |
| 提缺席群友（人格稿 §6.3④） | 角色**模仿**别人说话 | 是表演，没人真回答 |
| **拉人（本条）** | **真的有另一个人在场** | —— |

**六条规则**：

1. **角色可自行发起，不需预先批准** —— 要求批准他就变回工具人了（一方通行不会请示"我能不能问问别人"）。但 UI 必须**可见**（「一方通行去问了食蜂」）、可打断；首次拉人 / 拉到贵模型时明显提示。另留全局开关"禁止角色自行拉人"
2. **可见性** —— 用户全知（铁律 1），看得见第三方回复；发起者看得见。**第三方看不到原单聊的完整上下文**，只拿到问题 + 必要背景。这一条是新增的可见性场景，v1/v2 都没覆盖：用户跟一方通行说的私房话，不该被第三方全量看到

   > **【v3 补漏】"必要背景"由谁写？** v2 默认交给发起者，但以发起者的性格会写得太少：一方通行只会发一句"这个方案能推行吗？"，食蜂拿到手的上下文几乎为零，回答质量直接下降。
   >
   > 改：**背景由系统自动附**（本群/本会话近期摘要 + 相关产物路径），角色只写问题本身。既不违背真人感，又保证质量。同时场景层要提醒发起者一句：**「对方看不到你们的对话，只看到你写的这段话」**——否则他会写出一堆"如上所述"这种对方根本看不懂的引用。
3. **不算群** —— 是**临时会审会话**（ad-hoc）。不进黑板、不广播、用完即散。做成群会违反"用户建群"的心智——用户会突然发现自己被拉进一个群里
4. **生命周期** —— 第三方默认 ephemeral，回复到达即归档，用户 pin 才升持久。受 `maxDepth` 限制
5. **用户自己也能拉** —— 而且这是**更自然的建群路径**：单聊 → 觉得缺个视角 → @ 某人 → 会话升级为群。**"聊着聊着变群"比"先建群再拉人"自然得多**，建议作为一级入口而非隐藏功能
6. **记忆回流【v4 改口径】** —— 第三方在单聊里说的话，**有价值的结论落盘**（不再是"写进个人档案"，那个层已删，见 §4.5）。
   > 初春的"整理"职责单聊也生效（人格稿 §四），本来就有"把结论落成文字"一条，这里顺着走就行。
   > **不落盘就随会话消失** —— 跟 §6.9「不 pin 就归档」是同一回事，不需要额外机制。

> 成本风险：单聊里随手拉两个最强模型，账单翻倍。但这与 §3.4「可见性优先、不做自动干预」一致——看得见、能停就够了。
>
> 补充一条**纯单聊**（用户从没建过群）的影响：这是最高频用法，但人格稿的"提缺席群友"在纯单聊下必须禁用（用户不认识那些人），拉人则**反而更重要**——它是纯单聊里引入第二个视角的唯一办法。

### 6.7 插话 = 发消息

**插话就是给一个正在运行的角色发消息**，不需要独立机制。走 `SendMessage`，只多两个语义：

- `mode: queue`（默认）—— 排到**安全点**注入：当前工具调用返回后、下次模型调用前。上下文完整。**别做任意 token 的真抢占**，会得到一堆半截状态和无法回放的日志
- `mode: interrupt` —— 真中断，仅用于跑偏或长时间无响应

  > **【v2 修订】`interrupt` 的语义必须钉死**：**丢弃未提交输出 + 保留已落盘产物**。不写清就会得到半截状态——这正是你自己反对的东西。写文件写到一半被中断，以落盘产物为准，不回滚也不拼接。
- `scope: private` —— 私语只进该角色私有上下文，UI 标"私聊"，免得用户以为群里都听见了

插话必须带 `round/step` 时间戳，否则事后回放整条时间线会错位。

**插话永远是高优先级唤醒源**，且带"重定向"语义——UI 上让它明显区别于普通发言，模型会自然更重视。

### 6.8 【v5 重写 / v6 部分撤销】工具策略：全量静态 + 人格约束，不做开关

> ## 🔴 【v6 撤销】「角色之间没有任何工具差异」这条作废。
>
> 它唯一的支撑是硬约束 1：「增删工具会让**所有共享该前缀的会话**失效」。
> **这是事实错误——角色之间本来就不共享前缀。** 不同角色 = 不同系统提示 = 不同会话，
> 改一个角色的 `AgentToolConfig` 影响不到别的角色。
>
> 还有个 v5 没注意到的连带后果：`AgentToolConfig` 没了 → 角色扮演档"无工具"的定义就没了
> → **陪聊角色会挂着 shell 和文件写工具**。而一个陪聊角色
> **不该靠提示词说服自己别用 shell**。
>
> **改后**：工具**按角色装配**（`AgentToolConfig` 保留）。§1.1「权限统一」回到它的原文——
> 「所有角色走同一套工具装配**流程**。人格不能成为能力边界」——
> 要的是**同一套流程**，不是**同一份工具表**。是 v3→v5 的迭代把它收紧成了后者。
>
> **仍然成立的**：硬约束 2（同一会话内中途注入 = 同一种失效）、
> ④ 别把动态值写进工具定义（`to` 必须是自由字符串，成员名单放场景层）。
> 见 [ADR 0043](../../adr/0043-角色档位从四档枚举改为一轴派生.md) 与
> [ADR 0044](../../adr/0044-委派门面统一为SendMessage，子会话骨架不动.md)。
>
> ③「误操作靠兜底」里的**撤销栈不存在**，见 §2.6③ 的 v6 撤销。


> 触发决定：**不做黑名单，不做按角色/按模式的工具开关。**

两条硬约束没变：

1. **工具定义全量、静态、所有角色共享** —— 增删工具会让 KV cache 前缀失效（不只是这个角色，是所有共享该前缀的会话）
2. **提示词同样在前缀里** —— 中途注入和增删工具是同一种失效（§4.7）

但 v3 由此推出的「黑名单运行时拦截」这一层**整个拿掉**，理由在 §2.6③ 已经说过：既然"只说不做"是人格，就该写在人格里。

#### ① 现在的工具层只有两样东西

| | 内容 |
|---|---|
| **工具定义** | 全量、静态、所有角色共享。永不增删 |
| **全局应急开关** | 只读 / 断网 / 省成本。**给人用的紧急刹车**，不是给角色用的行为约束 |

角色之间**没有任何工具差异**——工具层面完全等同，这是 §1.1「权限统一」的最终形态。

#### ② 差异全部上移到人格层

| 原来靠 | 现在靠 |
|---|---|
| 黑名单拦写文件 | 硬禁令「禁止自己动手改文件」（一方通行） |
| 按模式开 shell | 不做。shell 一直开着，用不用是人的事 |
| 角色级工具集 | 身份层「工具偏好 / 开场读什么」（§2.7） |

> **工具偏好不是"给他哪些工具"，是他习惯怎么确认一件事。** 一方通行当「程序」时自己跑验证代码，当「策划」时拉数值表——**嘴一样毒，翻的东西完全不同**。这比开关更能塑造差异。

#### ③ 误操作靠兜底，不靠预防

不做预先禁止，就得把后面这套做扎实：

- **写操作串行化**（单一写队列 / 按路径加锁）—— 这条保留，它解决的并发覆盖问题跟权限无关
- **撤销栈**：保留"谁改了什么"
- **产物区实时可见**（§七）—— 改错了看得见，这是最实在的兜底

> 和 §3.4 是同一个判断：**连预算都不做自动干预了，凭什么权限要预先拦？** 你要的是"看得见 + 能撤"，不是"系统替我防"。

#### ④ 一个仍然成立的坑：别把动态值写进工具定义

`SendMessage(to: ...)` 的收件人**不能用枚举**——成员一变，工具定义就变，缓存全废。

```
to: string          # 自由字符串，成员列表放场景层
scope: public|private
mode: queue|interrupt
```

成员名单、可用身份这些**全是场景层的内容**，不进工具定义。

### 6.9 生命周期

- **休眠态 0 调用**，成本只发生在被唤醒的轮次
- **默认 ephemeral**：委托产出的角色随任务结束归档，用户 pin 才升为持久
- **生命周期 UI**：列表 / 归档 / 删除 / 改名 / 导出
- **入群上下文策略**：`full / summary / none`，默认 `summary`
- **【v5】上下文组成** = 本会话 summary + **产物区路径（带路径）** + **归档目录可见**（角色自己翻，不在上下文里）

> **【v5】"系统按话题挂入"改为"目录可见、角色自己翻"** —— 同 §4.5。跨会话连续性不依赖任何检索或注入，P0 就能成立。
>
> **【v4】"持久"的兑现方式变了**：不再是"角色带着个人档案活下去"，而是**产物和归档活下去**。群归档了，一方通行下次自己翻到"上次这个方向被否了，理由是 X"——他照样会直接反应。

## 七、右侧栏面板

```
头像 → 角色名 + 定位语 → 身份标签 → 模型名
     → 上下文占用条（相对百分比，不用绝对 token）
     → 状态表情 → 本轮是否发言 → 累计成本
```

**状态表情**：等待 👂 / 思考 🤔 / 输出 ✍️ / 完成 ✅ / 静默 😴 / 出错 ⚠️

**三个实用补充**：
- **打断按钮** —— 中途插话给某个角色
- **上下文变色预警** —— 接近上限变黄/红，提示该压缩了
- **【v2 新增】本群产物区** —— 落盘的文件 / 已定决策 / 待办，实时可见。这是 §1.4 产出锚点的落地：产出空了多久，一眼就看得到
  > **【v4】每条产物都要带路径。** 产物是文件、读文件人人有，所以路径可见就够了，不用全文注入上下文——角色想看自己读（§4.5）。

### 【v4 新增】执行期面板换单位

> 触发澄清：「执行模式不设护栏」。

不设自动干预没问题，但**面板不能停摆**。§3.4 保留的第一项就是"面板实时消耗"，而执行期用"轮次"这个单位会失效：

| | 讨论模式 | 执行模式 |
|---|---|---|
| 一轮 = | 一次发言 ≈ 一次模型调用 | **几十步工具调用**（读→写→跑测试→失败→改→再跑…） |
| "轮次"读数 | 准 | **几乎不动** |

后果：面板显示「Round 12 / 50」，用户看着离上限远、很安全，实际上钱一直在烧。**数字停着不动，成本在动。**

所以执行期面板换成这三个数（**只是仪表盘，不是护栏，不加任何自动动作**）：

| 显示项 | 说明 |
|---|---|
| **步数** | 工具调用次数（34 步）—— 执行期的真实进度单位 |
| **耗时** | 6 分 12 秒 |
| **累计 token** | 两种模式都保留 |
| **活跃角色** → | 执行期改为「**当前执行者**」 |

> §2.6④ 的"工具调用流可见"覆盖了"她在跑什么"，这里补的是**累计量**。两者合起来，执行期才不是黑箱。
>
> **【v5】"谁被临时解禁了写权限"删掉** —— 不做黑名单、不做改派解禁，没有这个状态可显示。
>
> **【v5】"被拦截的调用计不计入步数"这个问题消失** —— 没有拦截了。
>
> **【v5】换单位的触发点比原来更早**：不只是执行期，**§2.7 的开场各自读取就已经是这个量级**（四人并行长链条读操作）。轮次在开场阶段同样不准。

> 上下文用**相对百分比**：弱模型上下文长度不一样，绝对值没有可比性。
>
> **定位语常驻 UI**：用户靠定位语认人，不靠意象。如「初春 · 先查证再开口」。

## 八、落地清单

```
P0（骨架）
  ├ 【v3】Hello World：三角色 + 一个主题 + 10 轮自由讨论 + 落盘，不加任何机制
  ├ 角色四层结构（基座/人格/身份/配置）【v5 配置层只剩模型+temperature】
  ├ 统一 inbox + 单一 SendMessage 原语
  ├ 隐式 Yield（pending 判定）+ 孤儿委托清理【v2】
  ├ 成本可见性（面板消耗 + 后台任务状态）+ 手动停止
  ├ Conclude 手动结题 → 归档【v2 明确进原语】
  ├ 本群产物区（每条带路径）【v2 / v4】
  ├ 【v6】归档目录 + 命名规范 —— 沿用既有 docs/adr/ + docs/proposals/，不另起一套
  ├ 【v5】开场各自读取（§2.7）：身份层「开场读什么」+ 贴路径上黑板
  └ 四个默认角色提示词（含硬禁令【v2】）【v5 一方通行补"不动手改文件"】

P1（体验）
  ├ 阶段字段（发散/会审/回应/实施）—— 仅 UI 显示，零注入【v2 降级 / v4 删软提示】
  ├ 分歧追踪 open_issues + 僵局检测【v2】
  ├ 主持人点名提问（治附和螺旋）【v3 替代立场登记】
  ├ 【v5】执行模式只剩人格收敛（用户一句话）；主导权收窄保留【权限切换已删】
  ├ 【v4/v5】面板换单位（步数 / 耗时 / 累计 token / 当前执行者）—— 开场即触发
  ├ 群模板 + 初始阶段
  ├ 结题摘要结构化（含成本与时机栏）【v2】
  ├ 【v5】建群时手选要挂的文档（文件选择器，零机制）
  ├ 单聊拉人（临时会审会话）+ 单聊→群升级路径【v2.1】
  └ 人格热更新

P2（可选）
  ├ 群内成员委托群外临时角色（SendMessage 复用即可）
  ├ wake_rules（成员 ≥3 才启用）【v2 门槛下调】
  ├ 沉默权（成员 ≥3 才启用）【v2 门槛下调】
  └ 旧群结论自动匹配【v5 降级：目录可见已够用，自动匹配只是锦上添花，且有静默失败风险】
```

> **【v3】Hello World 为什么要排在 P0 最前面**：P0 现在有 7 项，但要验证的核心问题只有一个——**真人化方向对不对**。如果四个角色聊起来还是像助手，那产出区、Conclude、立场登记全白做。
>
> 最短验证路径：**三个角色 + 一个真实主题 + 10 轮自由讨论 + 落盘**，什么机制都不加，只看输出像不像人。跑通了再往上加。这一项的成本是半天，收益是避免后面全部返工。

> **【v2.1】"单聊拉人"为什么从 P2 提到 P1**：v2 把它和"群内委托"归为同一件事排在 P2，但单聊是最高频用法，且拉人是纯单聊里引入第二个视角的唯一办法。它依赖的机制（`SendMessage` + 隐式 Yield）本来就在 P0，只是解锁"收件人不在当前会话"在单聊下同样成立——增量极小。

> P2 的 wake_rules 和沉默权，在典型场景（2 人）里根本用不上，直接后排。但如果标准 4 人会审是常用配置，**wake_rules 实际上要到 P1**——4 人群靠"用户手动 @" 会很累。
