# 群聊调度代码审·逐条核实（初春饰利）

对 `GroupChatCoordinator` / `ParallelGroupScheduler` / `GroupWakePolicy` 三件逐行对了一遍，连带 GroupRun、GroupMemberTurnState、GroupMemberReplyFeed、GroupTranscript、EGroupWakeCause、ADR 0046/0049。结论：婚后同学的两处缝、一方同学补的三点，全部属实，没有虚报。下面按条记核实依据，另补两处小项。

---

## 一、僵尸轮 + rewake 泄漏：属实

`RunMemberAsync` 里 `run.End(member.SessionId)` 只出现在 happy path（`replies.WhenPostedAsync()` 之后、return 前一行）。`run.Begin(turn)` 之后到 `run.End` 之间，能抛的点不止婚后同学列的三处：

- `SpeakerChanged?.Invoke(group.SessionId)`（锁外，订阅方抛）——一方同学补的第 2 点，属实；
- `member.SaveMeta(touchUpdatedAt: false)`（落盘 IO 抛）——同属一方同学第 2 点，属实；
- `ComposeInput`（锁外读 History，竞态 NRE）——婚后同学 #1 所列；
- `GroupMemberReplyFeed` 构造 / `replies.Finish`（内含 `Scan`：迭代成员历史 + `PostedSince(_group.History,…)` 锁外迭代群流水 + 可能 `member.Save()` 落盘抛）——婚后同学 #1 所列，`Finish` 里的 `Save` 抛也归在这个点；
- `turn.CloseAsync`（内部已 catch `WithdrawAsync` 异常，自身抛点只剩 WaitAsync，概率低）。

任一点抛了，`run.End` 不调 → `_turns` 里永远挂着他 → `SpeakersOf` 一直显示在说、`BroadcastAsync` 继续 `InjectAsync` 进这条已死的轮（`_accepting` 仍是 true，照插不误），`_injected` 只增不减。

一方同学 #1 的加重：`InjectAsync` 里的 `TryInjectAsync` 是往成员注入队列**入队**、不是丢弃——僵尸轮期间插进去的每条，成员下一轮真开跑时会跟新投递一起被取走，紧跟新投递成连续两条 user，正是 `GroupMemberTurnState` 类注释（「堵『收尾之后才入队』的缝……成了连续两条 user 消息」）要防的东西。属实。

`LoopAsync` 的 catch：只有 `Log.Error` + `_causes.Remove` + finally `Release`，**没清 `_rewakes`**。下次 Wake 他时 `_causes.TryGetValue` 落空 → 重开 LoopAsync → 第一圈跑完 `_rewakes.Remove` 把旧 pending 取出来 → 旧 postIndex 几乎必然 unmet → 白跑一圈。属实。

改法（婚后同学 #1 + 一方同学 #2 合起来）：`run.Begin` 后整段包 try/finally，finally 里 `run.End`（幂等：`_turns.Remove` 删不到返回 false，安全）；`LoopAsync` catch 里补 `_rewakes.Remove(memberId)`。游标**不回滚**（一方同学第 2 点）：已推的游标里若含他已回过的部分，回滚会重投成重复；try/finally 修的是收尾，游标语义不动。

## 二、锁外读：属实；`History[index]` 那条安全，但理由要换

- `ComposeInput` → `GroupTranscript.HasUnaddressedUserPost(run.Group.History, deliveredFrom, RosterOf(run.Group))`：`for (i = deliveredFrom; i < groupLog.Count; i++)` 整段迭代在 `_locker` 外，跟 `Append`（另一线程的用户发言）赛跑。`List<T>.Add` 先写槽位再 `_size++`，无内存屏障——读方可能看到 size 已涨、槽位未落字，取到 null NRE。属实。
- `GroupMemberReplyFeed.Scan` → `PostedSince(_group.History, _segmentStart, …)` 与 `_segmentStart = _group.History.Count`（Scan 里锁外读 Count）：同上，锁外迭代群流水。属实。
- `ParallelGroupScheduler.RunAsync` → `_run.Group.History[index].Text`：**安全**，但婚后同学给的理由（「Append 返回前槽位已写完，List 扩容会搬走」）不精确。真正原因是：`RunAsync` 只在开波路径被调（`PostAsync` 群闲着 / `ContinueAsync`），与 `Append` 的写入在**同一线程、同一执行路径**上（`PostAsync → Append → RunEpisodeAsync → Scheduler.RunAsync`），程序顺序保证可见性；`ContinueAsync` 在群已跑时会在 `_episodes` 检查处直接返回 false，到不了 `RunAsync`。跨线程场景（群在跑时用户发话）走的是 `OnPosted(post.Text)`——用传入的 post 对象，不读 `History[index]`。所以这条无竞态，一方同学「逻辑上没问题」的判断对。

修法（婚后同学 #2）：两处锁外迭代都在 `_locker` 内做 Count+引用快照再交给纯函数，或在锁内算完。都很短，无碍。

## 三、Wake 来由升级方向矛盾：属实，且修法有个方向陷阱

- `Wake` 里 `if (wake.Cause > current) _causes[…] = wake.Cause;`：`EGroupWakeCause` 数值 User=0 < Host=1 < Member=2（注释「数值越小越强」），`>` 覆盖 = **保留较大值（向弱升）**——Member 盖得掉 Host/User，反过来不升。
- `LoopAsync` 结算 rewake 用 `cause = unmet.Min(x => x.Cause)` = **取最小值（向强升）**。
- `EGroupWakeCause` 类注释「同时有多个来由时取最小的」跟 `Wake` 的 Max 方向直接矛盾。ADR 0049 第 12 条（撤回段）原文确有一句「『跑着时被成员点到，他接下来说的按第二跳算』保留」。三方核对，一方同学第 3 点属实。

窄角后果核实：成员 X 以 Member 来由跑着（保守档），主持人点名 X → `wake.Cause = Host(1) > current = Member(2)` 不成立 → `_causes[X]` 保持 Member → X 消费插话回应后，`WakesForMemberPost` 读 `_causes[X]` = Member → 保守档 `return []` 不叫醒任何人。而 `GroupWakePolicy.ForMemberPost` 注释与 ADR 决策 2 / 会审第 2 条都写「主持人点名算主持人叫醒，不受一跳限制」——打架。差一跳，属实。

**修法方向（我的补充）**：不能简单把 `>` 翻成 `<`。反向副作用：X 以 Host 来由跑着被成员 @ 时，`<` 不覆盖 → 保持 Host → 他的回复按 Host 算、保守档能叫醒别人——这恰恰违反第 12 条「被成员点到按第二跳」。要贴合现有文档，应在 `Wake` 里按 cause 分流：

- `wake.Cause == Member`：被成员点到 → 一律落成 Member（第二跳语义，含 Host/User 跑着被 @ 的情况）；
- `wake.Cause < current`（Host/User）：向更强升级（主持人点名 / 用户发言盖过 Member，符合注释「取最小的」与 ForMemberPost 注释）。

唯一剩角：User 来由跑着被成员 @ 会降成 Member，与「取最小的」注释字面冲突，但保守档防连锁的角度讲得通；rewake 结算的 `Min` 不受影响。也可以反过来：定死一个语义（比如统一成「取最小」），把第 12 条那段描述改掉——文档和代码总得有一个改，具体由拍板的人选。

## 四、婚后同学 #3（波已空转、壳没摘）：属实，记着即可

`Release` 判空闲（`_idle` 完成）到 `RunEpisodeAsync` finally `_episodes.Remove` 之间的窗口，`PostAsync` 的 `EpisodeOf` 还看得到 episode，但 `OnPosted` 里 `_closed` 已 true → 丢弃。下一波必投，不丢话，低危。同意记着。

## 五、我额外扫到的两处低概率项（不急着动，记着）

1. `ParallelGroupScheduler` 构造时 `_active = 1` 占位，`RunAsync` 里 Wake 完靠 `Release()` 归零。若 `WakesForUserPost` / `Wake` 在 Release 前抛（纯文本解析 + 字典操作，概率极低），`_idle` 永不完成，这一波挂死。
2. `RunEpisodeAsync` 里 `_episodes` 登记后、try 块前的 `SessionManager.Instance.Running.BeginRun` 若抛，episode 留在 `_episodes` 里成僵尸。同样概率极低。

两者都不构成现在要动的理由，只在此留痕。

---

## 结论

两份结论逐条核实通过：拆分不用动；僵尸轮（含 rewake 泄漏、额外抛点、游标不回滚）、锁外读（`History[index]` 那条改记理由）、Wake 方向矛盾都真实存在。改法建议以婚后同学的 try/finally + 锁内快照为主线，Wake 那条按上面「按 cause 分流」或定语义改文档，由用户拍板。

# 第二轮：婚后光子改动核对（2026-09-27）

黑猫拍板：僵尸轮 + 锁外读先改；Wake 方向按「被成员点到算第二跳」定语义、改注释。婚后光子落地，逐行核对如下，三处均通过。

## 1. try/finally（僵尸轮）——通过

- 正常路径：`run.End` 返回 true → `ended = true` → `SpeakerChanged` → `WhenPostedAsync`。「先摘在说、再等广播」时序保住（广播排队时界面不一直显示在说）。
- 异常路径：finally 里 `if (!ended && run.End(...)) SpeakerChanged?.Invoke(...)` 兜底。`run.End` 幂等（`_turns.Remove` 删不到返回 false）：`turn == null` 没 Begin 过 → 不误报；正常已 End 过 → 不重复通报。
- `SpeakerChanged` 自身抛（订阅方）也会被 finally 收住：正常路径已置 `ended`，不会二次通报；异常路径 finally 兜底。
- `replies` 的 using Dispose（退订）内层先跑、不抛，先于外层 finally 的 `run.End`，顺序无害。

## 2. 锁外读——通过

- `ComposeInput` 的 `HasUnaddressedUserPost` 改成本类私有方法：名单 `RosterOf` 锁外取（只读成员元数据，不碰流水）、迭代 `GroupTranscript.HasUnaddressedUserPost` 收进 `_locker`，与 Append 对齐。✓
- `GroupMemberReplyFeed.Scan`：`PostedSince` 与 `_group.History.Count` 两处收进注入的 `_historyLock`（就是 coordinator 的 `_locker`）；`_segmentStart` 用锁内快照，比原来锁外读 Count 更一致（顺带修好）。构造新增 `historyLock` 参数，全仓只有 coordinator 一处调用（`new(group, member, turn.Cursor, ..., _locker)`），已确认无遗漏调用方。✓
- 锁序：feed `_sync` → `_locker`（Scan 内层）；`_post` 出了 `_historyLock` 内层锁、仍在 feed `_sync` 锁内调用 → `PostFromMember` → `Append` 拿 `_locker`。全仓无 `_locker` → `_sync` 反向路径，不死锁。✓

## 3. Wake 方向（拍板：改注释）——通过

- 代码未动（`wake.Cause > current` 只往弱升保留）。`EGroupWakeCause` 注释把「结算取最小、Wake 只往弱升」两个方向写死，点明「被成员点到之后说的按第二跳算」（ADR 0049 实现时定下 12）、主持人被成员点到一样降档。
- `GroupWakePolicy.ForMemberPost` 注释补窄角：跑着时来由定格、只被更弱的新点降档；「主持人不受限制」指叫醒通道（没在跑的人以 Host 开跑），不覆盖插话通道。语义自洽，文档与代码一致。

## 残余（双方已共识，记着）

- 异常路径轮摘了，但死轮里已注入的消息没机会 `CloseAsync`/`WithdrawAsync` 撤回，留在 runner 队列，下轮第一次调用被取走——低危、有界，`GroupMemberTurnState` 注释认这个机制，不加码。
- **编译/测试未验证**：婚后光子与一方通行跑测试/构建的命令均被拒；我这轮也没跑。结构、括号、锁嵌套逐行过了一遍没找出毛病，但没人实际编译过——需批一次 `dotnet msbuild src/UiharuMind.Core.Tests/UiharuMind.Core.Tests.csproj -t:Test`（或先 `dotnet build`）才算落地。
