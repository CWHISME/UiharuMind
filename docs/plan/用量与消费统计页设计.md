## 0. 先说一个必须先验证的前提

图表库定的是 `LiveChartsCore.SkiaSharpView.Avalonia`。它有两个版本可选，**都带风险**，必须在动手前用一个 30 分钟的 spike 验证掉：

| 版本 | 对 Avalonia 的依赖 | 判断 |
|---|---|---|
| `2.0.5`（当前稳定） | `Avalonia >= 11.0.0` | 针对 **Avalonia 11** 编译。本仓是 12.1.2，Avalonia 12 有破坏性变更，**二进制兼容无保证**，可能在实例化控件时 `MissingMethodException` |
| `2.1.0-dev-798`（预发布） | `Avalonia >= 12.0.0`、`Avalonia.Skia >= 12.0.0` | 唯一**明确为 Avalonia 12 编译**的版本，且内建 `net10.0` 目标 |

两者都声明 `SkiaSharp >= 2.88.9`，而本仓在 `UiharuMind.csproj` 里**钉死 `SkiaSharp 3.119.4`**，并附了一条不能动的注释：

> 别升 4.x：4.x 的 SKPath 首次读 Handle 时才把构建器定型……Svg.Controls.Skia.Avalonia 也因此停在 3.x 那版

即：LiveCharts 是对着 SkiaSharp **2.88** 编译的，要跑在 **3.119** 上。SkiaSharp 2→3 是破坏性升级（绘图 API 大改），这里存在 `TypeLoadException` / `MissingMethodException` 的真实可能。

**spike 清单（半天内可判生死）**

1. 临时引 `LiveChartsCore.SkiaSharpView.Avalonia 2.1.0-dev-798`，写一个 20 行的 `CartesianChart` 页面，跑起来看能不能出图。
2. 再试 `2.0.5`，同样跑一遍。
3. 两者都能出图 → 用 `2.1.0-dev-798`（为 Avalonia 12 编译的那个）。
4. 都炸 → 走备选：**自绘**。仓库里已有两个可抄的骨架——`Shared/Controls/ArcProgressRing.cs:114` 的 `Render(DrawingContext)` 重写范式，与 `Features/QuickTools/PieSliceHelper.cs:17` 的 `StreamGeometry` 扇形生成。趋势图自绘一个 `Control` 约 300 行，占比环形几乎白拿。这条路的成本可控，且不引入任何版本风险。

**本文其余部分按 LiveCharts 可用来写**，若 spike 失败，只有第 7 章与第 5.4 节需要换成自绘，其余（数据层、接口、入口、表格）完全不变。这也是下面刻意把图表绘制隔离在单个控件里的原因。

## 1. 现状：统计是怎么做的

### 1.1 一句话

**只有「会话级 token 累计」和「一轮快照」，且只在内存里滚动、随会话头落 JSON；没有任何"每次请求一行"的结构化记录，因此按时间、按模型、按供应商聚合这件事目前无米下炊。**

### 1.2 现有的三层

**第一层：`TurnUsageLedger` —— 内存账本**

`Core/AI/Chat/TurnUsageLedger.cs`。它是 `sealed` 类，**不落盘**，只在一次会话的驱动期活着。字段分两组：

- 本轮：`TurnInput` / `TurnOutput` / `TurnCachedInput` / `TurnRequests`（`BeginTurn()` 清空）
- 会话累计：`SessionInput` / `SessionOutput` / `SessionCachedInput` / `SessionReasoningTokens` / `SessionRequests`

另有诊断用的 `LastInput` / `LastCachedInput` / `TotalTokenCount`（最近一次响应的快照，不是累计）。

`Add(UsageDetails)` 是唯一的累加入口；`Record(details, session)` 是「累加 + 写回会话本体」的唯一收口：

```csharp
// TurnUsageLedger.cs:231-241
public void Record(UsageDetails details, ChatSession session)
{
    (long input, long output, long reasoning, long cached) = Add(details);
    session.AccumulateUsage(input, output, reasoning, cached);
    session.LastInputTokens = LastInput;
    ...
}
```

**第二层：`ChatSession` 本体 —— 唯一的持久化落点**

`Core/AI/Chat/Core/ChatSession.cs:246-295` 上挂着一排累计字段（`TotalInputTokens`、`TotalCachedInputTokens`、`TotalOutputTokens`、`TotalReasoningTokens`、`TotalRequests`、`TotalGeneratedImages`），由 `AccumulateUsage(...)` 增量累加（`:1192`）。

落盘形态是 **JSON 文件**：`~/.uiharu/Data/Sessions/{sessionId}.meta.json`，由 `SessionManager.SaveMeta` 在每次服务调用边界与轮末各写一次。**注意：这些数是"这个会话一共花了多少"，没有时间轴，也没有模型轴。**

`ChatSessionMeta`（列表索引）里只冗余了 `LastInputTokens` 一个 token 字段，且 `ToMeta()` 不投影 `Total*`——索引层看不到花费。

**第三层：`ContextUsageViewData` —— 唯一的展示**

`Features/Conversation/SidePanels/ContextUsageViewData.cs:123-253`，渲染在 `ContextUsagePanel.axaml`，挂在输入框左侧的环形指示器与右栏。它展示：占用/上限、已折叠、草稿估算、**会话累计缓存命中率**、思考 token、请求次数、生图张数。

命中率算法（`:271-275`）：

```csharp
cached > 0 && input > 0
    ? $"{Math.Clamp(cached * 100.0 / input, 0, 100):0.#}% · {Format(cached)} / {Format(input)}"
    : string.Empty;
```

群场景另有一套 `SessionUsageStats`（不读账本，直接读会话本体），只出 token 数。

### 1.3 数据来源矩阵

| 需求里的指标 | 现在有没有 | 在哪 | 能否支撑新页面 |
|---|---|---|---|
| 输入 / 输出 token | ✅ | `ChatSession.Total*Tokens` | 只有会话总量，**无时间、无模型** |
| 总 token | ✅ 可算 | 同上相加 | 同上 |
| 请求次数 | ✅ | `TotalRequests` | 只有会话累计 |
| 缓存命中**读取** token | ✅ | `TotalCachedInputTokens` | 有，但只有会话累计 |
| 缓存命中**写入** token | ❌ | 无 | **服务端基本不报**，见 3.5 |
| 缓存命中率 | ✅ | 现算 | 只能在会话维度算 |
| 估算费用 | ⚠️ 半成品 | `ModelPrice.Cost(...)` 已写好，**生产零调用** | 公式现成，缺输入数据 |
| 平均响应延迟 / 首 token 延迟 | ❌ | 无 | 只有**消息级**思考耗时（`ChatMessageAnnotations.ThinkingDurationMs`），不是请求级 |
| 错误率 / 失败请求数 | ❌ | 无 | 失败只写日志文本，不计数 |
| 按时间聚合 | ❌ | 无 | **没有时间戳字段** |
| 按模型 / 供应商聚合 | ❌ | 无 | 记录里根本没有模型字段 |

### 1.4 三条已经存在、但没被接上的资产

1. **`ModelPrice.Cost()`**——`Core/AI/Models/ModelPrice.cs:69`，公式已经写好且注释明确了口径（`inputTokens` 含缓存命中，`cachedInputTokens` 是其中一部分；未单独给缓存价时按输入价算，宁可高估）。`ForContext(long)` 处理阶梯价。**全仓只有测试调用过它。**
2. **两张价格表**——`ProviderPricingTable.g.cs`（官网，权威，94 条）与 `ModelCapabilityTable.g.cs`（models.dev，270 条），由 `ModelCapabilityResolver.TryGetPrice(configType, modelId, out price)` 统一查询，优先级 官网 > models.dev，**禁止跨供应商借价**。
3. **SQLite 先例**——`Core/Core/Clipboard/ClipboardHistoryStore.cs`，WAL + 每次变更一条 SQL + 游标分页，是这个仓库认可的本地库写法（ADR 0024）。

### 1.5 槽点

- `SessionManager.cs:27-35` 的类注释还写着 `SessionData/{sessionId}.json`，实际是 `.meta.json`，注释已过期。
- 群后台的 `GroupBackground.cs:92` 直接调 `session.AccumulateUsage(...)`，**绕过账本**。新增埋点若只挂在 `TurnDriver`，群离席摘要那次请求会漏计——这一点必须在实现时一起处理。
- 日志（`Logs/Log.txt`）里其实有每次请求的 usage（SSE 收尾帧），`src/scripts/perf/cache-audit.py` 已经在解析它。但日志是纯文本、7 天滚动、10 代上限，**只能当一次性审计，不能当账本**。

## 2. 目标与非目标

**要做的**

1. 新增一张「请求级用量明细」表，逐次落盘，带时间、会话、模型、供应商、token、延迟、成败、费用。
2. 在该表上做聚合查询，支撑 今日 / 近 7 天 / 近 30 天 / 自定义区间，粒度按时/日/周。
3. 新增独立页面：KPI 卡 + 双轴趋势图 + 模型/供应商排行与占比 + 明细表（排序/分页/导出 CSV）。
4. 模型列表条目上加入口，直达该模型的统计视图，且**保留已有时间范围筛选**。

**不做的**

- 不改会话存档结构（`.meta.json` 与 `SessionJsonContext` 一行不动），避免撞 `SessionJsonShapeGuardTests` 的逐字节护栏。
- 不做汇率换算。价格表口径是 USD/百万 token，页面就显示 USD（ADR 0097 已定）。
- 不把日志当数据源。
- 不做实时账单对账（供应商 API 的真实扣费另有 `ProviderStatusService`，两套口径不混）。

## 3. 数据层

### 3.1 存储选型：SQLite

理由与 `ClipboardHistoryStore` 一致：数据量随时间单调增长、需要带条件的聚合与分页、需要崩溃一致性。JSON 全量重写在几十万行上不可接受。

依赖已存在（`UiharuMind.Core.csproj` 已引 `Microsoft.Data.Sqlite 10.0.12`），**零新增**。

路径：`AppPaths.Data` 下新增一条，形如 `~/.uiharu/Data/Usage/Usage.db`。落在 `Data` 而非 `Cache` 的依据是 ADR 0013 三条规则——这批数据**不可再生**（重跑一次推理是另一次推理，不是同一次），删了就是真的没了。

> WAL 会带 `-wal` / `-shm` 伴生文件，删除或迁移必须成套处理（`MemoryStore` 踩过）。

### 3.2 表结构

```sql
CREATE TABLE IF NOT EXISTS usage_record (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    ts               INTEGER NOT NULL,   -- 请求完成时刻，Unix 毫秒
    started_ts       INTEGER NOT NULL,   -- 请求发出时刻，算延迟用
    session_id       TEXT    NOT NULL,
    -- 模型身份：三列一起才是唯一，缺一不可
    model_name       TEXT    NOT NULL,   -- 用户可见名，也是配置字典键
    model_id         TEXT    NOT NULL DEFAULT '',  -- 发给服务端的 id
    provider_id      TEXT    NOT NULL DEFAULT '',  -- Config 类型名；本地为 'local'
    provider_key     TEXT    NOT NULL DEFAULT '',  -- 定价表键，查不到为 ''
    api_base         TEXT    NOT NULL DEFAULT '',  -- 归一化 base url，区分同家多实例
    is_local         INTEGER NOT NULL DEFAULT 0,
    -- 用量
    input_tokens     INTEGER NOT NULL DEFAULT 0,   -- 含命中缓存的输入
    cached_read      INTEGER NOT NULL DEFAULT 0,   -- 其中命中前缀缓存的部分
    cached_write     INTEGER,                      -- NULL = 供应商没上报（≠ 0）
    output_tokens    INTEGER NOT NULL DEFAULT 0,
    reasoning_tokens INTEGER NOT NULL DEFAULT 0,
    -- 性能与结果
    latency_ms       INTEGER,                      -- NULL = 未测得
    first_token_ms   INTEGER,
    ok               INTEGER NOT NULL DEFAULT 1,
    error_kind       TEXT,                         -- 'http' / 'timeout' / 'cancel' / 'stream'
    status_code      INTEGER,
    -- 计价快照
    cost_usd         REAL,                         -- NULL = 未定价（≠ 免费）
    price_source     TEXT,                         -- 'official' / 'modelsdev' / NULL
    price_input      REAL,                         -- 计价时用的四价，留证以便回溯
    price_output     REAL,
    price_cache_read REAL,
    price_multiplier REAL NOT NULL DEFAULT 1
);

CREATE INDEX IF NOT EXISTS idx_usage_ts        ON usage_record(ts);
CREATE INDEX IF NOT EXISTS idx_usage_ts_model  ON usage_record(ts, model_name);
CREATE INDEX IF NOT EXISTS idx_usage_ts_prov   ON usage_record(ts, provider_key);
CREATE INDEX IF NOT EXISTS idx_usage_session   ON usage_record(session_id, ts);
```

**几个刻意的决定**

- **模型三维冗余进记录行，不 join 配置表。** 配置会改名、会被删（`RemoteModelManager.DeleteRemoteModel` 直接从字典里 `Remove`）。历史消费记录必须回答"当时用的是哪个模型"，只能靠快照。
- **`cached_write` / `cost_usd` 允许 NULL。** NULL 的语义是「不知道」，不是「零」。UI 必须把两者区分开——这是全仓反复强调的口径（`ModelPrice.IsKnown == false` 表示供应商没公布，不是免费）。
- **`price_*` 四列存下来。** 价格表是生成物，明天重跑脚本价格就变了。不存快照，历史账单会跟着变，用户会以为是 bug。
- **`error_kind` 用字符串不用枚举。** 以后加错误类别不用改表；取值在 Core 层用常量约束。

### 3.3 埋点位置

**主埋点：`TurnDriver.RecordUsage`（`Core/AI/Execution/TurnDriver.cs:674`）**

选它的理由：这是「一次服务调用」的唯一记账收口，且 `StreamUsage.KeepLast` 已经保证**一次服务调用只吐一份 usage**（`Core/AI/Execution/StreamUsage.cs`，注释写明是为了防 SenseNova 重复上报），这里记一次就是一次请求，不会翻倍。

调用点只有两处，都要覆盖：

| 位置 | 场景 |
|---|---|
| `TurnDriver.cs:275` | 常规轮次 |
| `TurnDriver.cs:936` | 交接压缩请求（注释已说明这一发往往是整个会话最大的一次） |

**旁路埋点：`GroupBackground.cs:92`**。群离席摘要直接调 `session.AccumulateUsage`，绕过了账本。**必须单独补一条**，否则群场景漏计。做法是让它改走一个共享的 `record` 方法，而不是各写各的。

**能在这个位置拿到什么（已核实）**

| 字段 | 取法 |
|---|---|
| `session_id` | `session.SessionId` ✅ |
| `model_*` | `LazyChatClient.ServingModel(session.ChatModelRunningData, LlmManager.Instance.EffectiveGlobalModel)`——这正是「本轮真正发请求的模型」的权威判据，`TurnDriver.cs:599` 已有一处同样用法 |
| `provider_id` | `model.ModelInfo.ProviderId`；本地为 `GGufModelInfo`，写入时归一成 `"local"` |
| `provider_key` | `ModelCapabilityTable.ProviderKeyOf(configType)`（internal，通过 `ModelCapabilityResolver` 间接取，或加一个公开的 `ProviderKeyOf`） |
| `api_base` | `ProviderStatusContext.DeriveBaseUrl(config.ModelPath)`，现成实现（`ProviderStatusViewData.cs:637`） |

**延迟**

现在没有任何请求级计时。需要在两处打点：

- 发出前：在 `runner.RunAsync(...)` 调用前 `Stopwatch.GetTimestamp()`
- 首帧：在 `await foreach (AIContent content in runner.RunAsync(...))`（`TurnDriver.cs:271`）的**第一次迭代**记时间差
- 收尾：`await foreach` 结束或异常时记总时长

严格意义上的 TTFT 应该打在 HTTP 层（`SseSanitizingStream` 收到第一条 `data:` 行）。但从 `await foreach` 首迭代回推，误差只在栈内解包，对"体验延迟"这个用途够了，且不用侵入传输层。**先用这个口径，若后续要精确再往下沉。**

**失败**

失败路径在 `TurnDriver.cs:298` 起的 `catch (OperationCanceledException)` 与后续 `catch`。这里能拿到异常类型，但**拿不到 `UsageDetails`**（失败时服务端通常不报用量）。所以失败记录写成 `ok = 0`、token 全 0、`error_kind` 按异常类型归类。失败请求计入「失败请求数」与「错误率」，**不参与 token 与费用的均值**（否则平均延迟会被 0 拉低）。

### 3.4 计价

复用 `ModelPrice`，不新写公式：

```csharp
// 1) 取适用价（含阶梯）
ModelPrice price = ModelCapabilityResolver.TryGetPrice(config, out var p) ? p : ModelPrice.Unknown;
ModelPrice applied = price.ForContext(details.InputTokenCount ?? 0);

// 2) 峰时/促销倍率（仅 CommandCode 一家当前有数据）
decimal scale = notice?.Multiplier ?? 1m;

// 3) 算钱
decimal? cost = applied.IsKnown ? applied.Cost(input, cachedRead, output) * scale : null;
```

**换算逻辑要在页面上写清楚**，一行公式 + 一句出处：

- 单位：**USD / 百万 token**
- `cost = (未命中输入 × 输入价 + 命中输入 × 缓存读价 + 输出 × 输出价) / 1,000,000`
- 缓存读价未公布时按输入价计（**宁可高估，也不让人以为缓存不花钱**——这是 `ModelPrice.Cost` 里的原注释）
- 阶梯价：上下文超过 `TierFromContext` 时整笔换用阶梯价
- 价格来源：官网定价页（`ProviderPricingTable`）优先，其次 models.dev（`ModelCapabilityTable`），**不跨供应商借价**
- 本地模型：不构造 `ModelPrice`，`cost_usd` 记 NULL，UI 显示「本地 · 不计价」
- 未定价：`cost_usd` NULL，UI 显示「未公布」并可一键跳转到「未定价明细」

### 3.5 缓存写 token 的诚实处理

需求要求「写入/读取分别统计」。现状是：**读取（`CachedInputTokenCount`）可靠，写入基本拿不到**——`Microsoft.Extensions.AI` 的 `UsageDetails` 没有 cache-write 字段，OpenAI 兼容协议也不报。只有 Anthropic 系的 `cache_creation_input_tokens` 会出现在 `AdditionalCounts` 里。

方案：

- 字段留好（`cached_write INTEGER NULL`）
- 写入时尽力从 `AdditionalCounts` 里找键名同时含 `cache` 与 `write`/`creation` 的项（照 `TurnUsageLedger.ReadCachedTokens` 的键名兼容思路）
- 找不到 → 记 NULL
- UI：该列在有数据时正常显示，全为 NULL 时**整列降级为「当前供应商未上报」的说明条**，而不是显示一排 0

这是刻意的取舍：一排 0 会被读成"缓存写入是 0"，而事实是"我们不知道"。

### 3.6 聚合查询

全部下沉到 SQL，不把原表拉进内存（这是分页与大数据量不卡的前提）。

**概览 + 排行**（一个查询 + 分组）

```sql
SELECT model_name, provider_key, is_local,
       SUM(input_tokens)          AS input,
       SUM(cached_read)           AS cached_read,
       SUM(output_tokens)         AS output,
       SUM(reasoning_tokens)      AS reasoning,
       COUNT(*)                   AS requests,
       SUM(CASE WHEN ok = 0 THEN 1 ELSE 0 END) AS failures,
       SUM(cost_usd)              AS cost,          -- 全 NULL 时得 NULL，正确
       AVG(CASE WHEN ok = 1 THEN latency_ms END)      AS avg_latency,
       AVG(CASE WHEN ok = 1 THEN first_token_ms END)  AS avg_first_token
FROM usage_record
WHERE ts >= @from AND ts < @to
  AND (@model IS NULL OR model_name = @model)
GROUP BY model_name, provider_key, is_local
ORDER BY input + output DESC;
```

一次查询同时喂：KPI（各列再汇总一次）、模型排行、供应商排行。省掉三次往返。

**趋势分桶**——按时区偏移做整数分桶，不用 `strftime`（避开 SQLite 时区陷阱）：

```sql
SELECT ((ts + @offsetMs) / @bucketMs) * @bucketMs - @offsetMs AS bucket,
       SUM(input_tokens + output_tokens) AS tokens,
       SUM(cost_usd) AS cost
FROM usage_record
WHERE ts >= @from AND ts < @to AND (@model IS NULL OR model_name = @model)
GROUP BY bucket ORDER BY bucket;
```

`@offsetMs` 是运行时算出的本地时区偏移。粒度→`@bucketMs` 映射：时=3600000，日=86400000，周=604800000（周桶需按本地周一零点对齐，先算出起点再整体平移）。

**点数上限**：近 30 天按小时是 720 点，按天 30 点。给一个硬上限（>1500 点时强制降粒度），避免图表卡死。

**明细分页**：`ORDER BY {col} {dir} LIMIT @size OFFSET @offset`。排序列走白名单映射（`ts` / `input_tokens` / `cost_usd` / `latency_ms` …），**绝不拼接用户输入进 SQL**。

### 3.7 体量与保留

单行约 180–220 字节（含索引）。重度使用按每天 500 次请求算：

| 周期 | 行数 | 库体积 |
|---|---|---|
| 1 个月 | 1.5 万 | ~3 MB |
| 1 年 | 18 万 | ~40 MB |
| 3 年 | 55 万 | ~120 MB |

可接受。仍提供「保留天数」设置（默认 0 = 永久），清理走 `DELETE FROM usage_record WHERE ts < ?`，**不做 VACUUM**（避免一次大 IO 卡界面），依赖 SQLite 自身的页复用。

## 4. 接口定义（Core 层契约）

放在 `Core/AI/Usage/`，无 UI 依赖。UI 只认这几个类型，不碰 SQL。

```csharp
/// 一次请求的用量明细（写入侧）
public sealed record UsageRecord(
    long Ts, long StartedTs, string SessionId,
    string ModelName, string ModelId, string ProviderId, string ProviderKey, string ApiBase, bool IsLocal,
    long InputTokens, long CachedRead, long? CachedWrite, long OutputTokens, long ReasoningTokens,
    int? LatencyMs, int? FirstTokenMs,
    bool Ok, string? ErrorKind, int? StatusCode,
    decimal? CostUsd, string? PriceSource, decimal? PriceInput, decimal? PriceOutput,
    decimal? PriceCacheRead, decimal Multiplier);

/// 时间范围
public readonly record struct UsageRange(long FromTs, long ToTs, EUsageGranularity Granularity);

/// 聚合出行（KPI / 排行共用）
public sealed record UsageAggregateRow(
    string ModelName, string ProviderKey, bool IsLocal,
    long InputTokens, long CachedRead, long OutputTokens, long ReasoningTokens,
    int Requests, int Failures,
    decimal? CostUsd, double? AvgLatencyMs, double? AvgFirstTokenMs);

/// 趋势点
public sealed record UsageTrendPoint(long BucketTs, long Tokens, decimal? CostUsd, int Requests);

/// 明细行（分页）
public sealed record UsageDetailRow(long Id, long Ts, string SessionId, string ModelName,
    string ProviderKey, long InputTokens, long CachedRead, long? CachedWrite, long OutputTokens,
    int? LatencyMs, int? FirstTokenMs, bool Ok, decimal? CostUsd);

/// 查询与写入
public interface IUsageStore
{
    void Append(UsageRecord record);
    UsageSnapshot Query(UsageQuery query);        // KPI + 排行 + 趋势，一次查出
    UsageDetailPage QueryDetails(UsageDetailQuery query);
    long ExportCsv(UsageDetailQuery query, string path);  // 流式写，不整表进内存
    IReadOnlyList<string> KnownModelNames(long fromTs, long toTs);
}
```

`UsageQuery` 带 `string? ModelFilter`（来自模型页跳转）、`string? SessionFilter`、`EUsageDimension GroupBy`。

写入必须**非阻塞**：`Append` 走一个后台单写通道（照 `LogManager` 的 Channel + 单写线程范式），**绝不在 UI 线程或请求路径上同步写盘**。丢一条统计可以接受，卡住一次对话不可接受。

### 5.4 趋势图（token 与费用双轴）

隔离在 `UsageTrendChart.axaml` 一个文件里，这样 spike 失败换成自绘时只改这一个文件。

```xml
<lvc:CartesianChart Series="{Binding TrendSeries}"
                    XAxes="{Binding TrendXAxes}"
                    YAxes="{Binding TrendYAxes}"
                    TooltipPosition="Top"
                    LegendPosition="Hidden" />
```

```csharp
// 左轴 token（Column，柱），右轴费用（Line，线），用于区分量级差两个数量级的两组数
TrendSeries =
[
    new ColumnSeries<long?> { Values = tokens, ScalesYAt = 0, Fill = palette.TokenFill, Name = "Token" },
    new LineSeries<decimal?> { Values = costs, ScalesYAt = 1, Stroke = palette.CostStroke,
                               GeometrySize = 0, Fill = null, Name = "费用" }
];
TrendYAxes =
[
    new Axis { Labeler = FormatTokens, TextSize = 11, LabelsPaint = palette.AxisLabel },
    new Axis { Position = AxisPosition.End, Labeler = FormatCost, TextSize = 11, LabelsPaint = palette.AxisLabel }
];
```

**颜色一律从 `UsageChartPalette` 取，不在 XAML 里写字面量。** 这是仓库既有口径——`ArcProgressRing` 的注释明确说"样式指定画刷、不写死颜色，由样式按 StateKey 选"。palette 内部按 `ApplicationThemeManager.IsDarkTheme()` 选两套色，主色用 `SemiBlue5` / `SemiGreen5`，网格线用 `SemiGrey2`，刻度文字用 `SemiGrey5`。

**LiveCharts 自带的 `AddDefaultTheme()` 不要用。** 它按 OS 主题自动切，而本仓的主题是 `ApplicationThemeManager.ApplyTheme` 手动设的 `RequestedThemeVariant`，两者可能不一致。自己给颜色，可控。

主题切换时需重建 series（订阅既有的 `ApplicationThemeManager` / `LanguageChanged` 通知点），否则线色会停在上一个主题。

### 5.5 排行与占比

**模型排行 / 供应商排行**：`RowSeries`（横向条），按 token 或费用排序，各取 Top 8 + 「其他」。指标可切（token / 请求数 / 费用）。

**占比**：`PieSeries` 环形。取 Top 5 + 合并其余，避免饼图碎成一片。

两张图放同一张卡片内左右分栏（`Grid ColumnDefinitions="1.2*,1*"`），与 `ServicesPage.axaml:121` 的两栏比例一致。

> 若 spike 失败改自绘：排行用 `ProviderStatusPanel.axaml:31-32` 那套 `ProgressBar Height=6 CornerRadius=3` 的行式进度条（读起来比横条图更快），占比用 `PieSliceHelper.CreatePieSlice`。这两种退化形态在视觉上都不算降级。

## 7. LiveCharts 接入细节

### 7.1 依赖

```xml
<!-- UiharuMind.csproj -->
<PackageReference Include="LiveChartsCore.SkiaSharpView.Avalonia" Version="2.1.0-dev-798" />
```

**不要**同时引 `SkiaSharp.HarfBuzz`——它会带自己的 SkiaSharp 依赖解析，可能把本仓钉的 3.119.4 顶掉。若编译报版本冲突，用 `Directory.Build.props` 显式钉住。

### 7.2 初始化

在 `App.axaml.cs` 的启动路径里配一次：

```csharp
LiveCharts.Configure(config => config
    .AddSkiaSharp()
    .AddDefaultMappers()
    .HasGlobalSKTypeface(SKFontManager.Default.MatchCharacter('汉')));  // 中文刻度必需
```

**中文 typeface 不能省。** 不注册的话图例与刻度里的中文会渲染成豆腐块。

**不调 `.AddDefaultTheme()`**——理由见 5.4，颜色自己给。

### 7.3 AOT / Trim

`UiharuMind.csproj` 开了 `EnableAotAnalyzer` 与 `EnableTrimAnalyzer`。LiveCharts 内部有反射（mapper 注册、XAML 类型），大概率出 IL2xxx 警告。应对：

1. **不用 XAML 的 `XamlLineSeries` 系列**。它们在 XAML 里实例化，走反射。改为在 `UsagePageData` 里直接构造 `ISeries[]`，XAML 只写 `Series="{Binding TrendSeries}"`。这也顺带满足仓库"页面数据类持有状态、XAML 只绑定"的分工。
2. 保留警告若有增无减地出现在 LiveCharts 程序集内，加 `TrimmerRootAssembly`；出现在自己的调用点时逐个 `[DynamicDependency]` 修掉，**不要整体 `<NoWarn>`**——那会把仓库自己代码里的真问题一起盖掉。

### 7.4 无头测试

`Avalonia.Headless` 下 Skia 通常不可用，图表控件在无头环境里可能抛异常或画不出来。所以：

- **`UsagePageData` 的所有逻辑（筛选、聚合、分页、CSV、空态判定）必须能脱离控件测**——这是把图表隔离成独立 `axaml` 的另一个理由。
- 无头测试只覆盖数据与 ViewData，**不实例化 `CartesianChart`**。若整页实例化就必须造图表，在测试里给它一个 `IsVisible=false` 的替身或直接测子组件。
