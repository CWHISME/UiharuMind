# 会话渲染身份与写入口重构计划

> 状态：**阶段 0 已落地，阶段 1–4 待排期**。
> 本文记录 2026-11-15 那次实机「重复条目」的取证、两份独立评审查出的遗漏，以及把去重从补丁收成结构的分阶段方案。
>
> **前置**：会话历史的落盘口径在
> [ADR 0104](../adr/0104-会话历史收成带锁的集合，跨多条操作的读一律取快照.md)，术语见 [CONTEXT.md](../CONTEXT.md)。
> 本文只谈「界面条目 ↔ 历史消息」的对应关系，不动历史文件格式、提示词、工具定义与请求结构。
>
> 阶段划分是综合评审发现后形成的**设计判断**，不是评审给出的结论——两份评审给的是缺陷清单与验证顺序。

---

## 一、现象与取证

### 1.1 用户看到的东西

同一条助手回复在会话里出现两条一字不差的气泡，时间戳分别是 19:35 与 19:36；思考卡同样会重复。用户反馈「之前改过几版，似乎压根没解决问题」。

### 1.2 实测数据（2026-11-15，真实档案 `~/.uiharu`）

| 证据 | 数值 | 出处 |
|---|---|---|
| 目标会话历史行数 | 817 行，按「角色+正文」统计 **0 组重复** | `Data/Sessions/47ef42e7…history.jsonl` |
| 截图那句话 | 只在第 **797** 行，`CreatedAt=19:36:14.4329442+08:00` | 同上 |
| 全档案历史文件 | **92 个**，有重复消息行的 **0 个** | `Data/Sessions/*.history.jsonl` |
| 19:36:14 的对账警告 | 两条，间隔几毫秒：`missing=1 / service call usage`、`missing=2 / message boundary` | `Logs/Log.txt:35803`、`:35820` |
| 全天补尾次数 | **173** 次：message boundary 157、service call usage 15、session idle 1 | `Logs/Log.txt` |
| 会话形态 | 外驱唤醒轮：`Wake turn started … cause=sub-agent reply … instance=34646073` | `Logs/Log.txt:35678` |
| 会话本体 | 全天 `instance=34646073` 唯一，无 `stale session body` 警告 | 同上 |

**结论：重复不是数据层的。** 盘上一条消息只有一份，是界面把同一条消息画了两遍。ADR 0104 记的「`Append` 无落盘水位线、文件写出 `11,10,11`」这次没发作，序列化、装载、切会话、并发追加均排除。往这些方向改自然没效果。

### 1.3 时间戳的成因（更正过的解释）

三个时间源：

- 流式壳：`ConversationItemFactory.cs:153` `CreateAssistant` 盖 `DateTimeOffset.Now`，唤醒轮 19:35:22 开跑 → **19:35**。
- 历史回放：`ConversationHistoryRenderer.cs:240/356` 用 `message.CreatedAt` → 797 是 **19:36**。
- 配对校准：`ConversationItemActions.cs:188-192` `CalibrateTimestamp` 只在 `WireStreamed` 成功配对时改写。

**不需要假设「配对错到 795」。** 流式气泡只要保持空来源、没被 `WireStreamed` 配对，就一直带着壳上的 19:35；补画那份按 797 的 `CreatedAt` 显示 19:36，两者正文一字不差。曾推测「错配到上一条」，但 795 与 797 正文不同、且 797 在两条警告之前已 `assistant reply ended`，错配反而与数据矛盾。

### 1.4 历次修复为什么没覆盖

| 提交 | 修了哪条路 | 为什么仍漏 |
|---|---|---|
| `8ed2015c` 子代理来信已由流画过就不再从历史补画 | `AppendPersisted` | 只管一类消息 |
| `0f71c1f5` 重发前告知界面上一发作废 | 流内 `StreamRestartContent` / `DiscardSegment` | 与落盘补画无关 |
| `d71c7307` 对账先配对再判定、思考卡按段长配对 | `WireStreamed` 启发式 | 让配对更准，配对失败时补画仍无条件 |
| `bb4fd41e` 唤醒轮跑着时界面不再整轮不刷 | 加 `AppendSkippingRendered`；**同一提交引入 `CatchUpTail`** | 去重只装在 `AppendPersisted` 一侧；新引入的 `AppendTail` 从来是 `_items.Add` 无条件追加 |
| 本次（未提交）`ConversationItemDedup` | 两条补画通道共用一道闸 | 见第四节「已知盲区」 |

`bb4fd41e` 是关键转折：为修「唤醒轮整轮不刷」，把补尾触发拉到每次服务调用/消息边界，等于把**没有去重闸的那条路径**变成了主路径，全天 173 次。

### 1.5 两个独立评审查出的遗漏

- **思考卡口径**（两份评审独立撞到）：`ThinkingItem.Message` 是「前 512 字 + 已截断 N 字」的预览（`ConversationItems.cs:213-216`），N 随流式长度变化；按它全等比对，长思考必然认领失败。
- **判重闸只覆盖两条路**：全仓往 `Items` Add 的路径十几条，知识卡（`ConversationViewModel.cs:1765`）无来源、无 `CallId`，闸在结构上拦不住。
- **放大器**：`FindMissingTail` 用最大下标做减法，工具结果消息只回写工具卡、不产条目，尾部成对时 `missing` 恒不收敛。
- 其余：`StreamRestartContent` 在 `_segmentFirstItem == -1` 时不删旧段、`HandoffWritten` 兜底、`LiveTurnStream` 双通道、`Retry` 重建副本、加密思考占位卡空正文。

## 二、问题的结构

### 2.1 同一个集合有十几个写入口

`ConversationViewModel.Items`（`ObservableCollection<ConversationItemBase>`）被两股来源同时写：实时内容流与历史落盘。已盘点的直接写入：

| 组 | 位置 | 是否过判重闸 |
|---|---|---|
| 实时流 `ConversationTranscript._target` | 工具卡 `:203`、审批卡 `:267`、错误卡 `:274`、用户气泡 `:295`、加密卡 `:502`、正文 `:647`、思考卡 `:674` | 否，各自靠 `CallId` / 引用自判 |
| 历史回放 `ConversationHistoryRenderer` | `Append :111`、`Prepend :125`、`Replace :186`、`EnsureHandoffCard :202`、`AppendSkippingRendered :449` | **仅 `:449`** |
| 对账 `ConversationHistoryReconciler` | `AppendTail :191`、`ReplayPreservingWindow :218` | `AppendTail` 阶段 0 起过闸；`:218` 先 `DiscardAll` |
| 开窗 `ConversationHistoryPager` | `Replay :98`、`LoadEarlier/Later`、`JumpTo/ReturnToLatest` | 否；跳转类先清空，续窗类不清 |
| 视图模型直接 | 乐观用户气泡 `:1581`、角色气泡 `:1636`、知识卡 `:1765`、若干 `ErrorItem`、`HandoffWritten :1780` | 否 |
| 其它 | `ConversationItemActions.Retry :582`、`HandoffWritingPlaceholder :45`、DevAutomation 注入 | 否 |

**判定「有没有第三条通道」目前只能靠人工盘点**，没有机械保证。

### 2.2 判重建立在两个不稳定的东西上

1. **对象引用**：`ConversationItemDedup.cs:32`、`ConversationOrderCheck.cs:34-40`、`WireStreamed :126`、`PairStreamedThinking :342`、`Trimmer :267` 全用 `ReferenceEquals(ChatMessage)`。而 `SessionManager` 的冷历史卸载（`:463-467`、`:477-516`）与跨进程 `DropStaleLoaded`（`CrossProcess.cs:304-312`）会换掉 `ChatMessage` 实例，一换就是**整套判据同时失效**。本次日志证明该会话本体全天未换，所以不是这次的成因，但机制确实存在。
2. **显示形态**：阶段 0 的「空来源条目内容认领」按 `Message` 比对，而 `Message` 对思考卡是截断预览、对知识卡是空的（正文在 `ResultText`）、对图片气泡不含图。显示用的字符串天生不是身份。

### 2.3 放大器

`FindMissingTail` 返回 `history.Count - 1 - lastDrawn`，`lastDrawn` 只认「有 `SourceMessage` 且在历史里」的条目。于是：

- 流式气泡没配对 → 不计入；
- 工具结果消息只回写工具卡（`ConversationTranscript.cs:354-374` 找不到卡就静默返回）→ 永远不产生带来源条目；
- 历史以 `[assistant+call, tool result]` 成对结尾时，`missing` 稳定停在 2。

每个消息边界都跑一次 `CatchUpTail → AppendTail → Build`。**只要判重闸有一处口径不齐，就会反复补出重复条目**——这就是「改了几版都没解决」的往复机制。

### 2.4 一句话

> 导火索是 `AppendTail` 无条件 Add，但根子是「条目没有稳定身份 + 写入口没有收口 + 对账判据靠猜」。补丁只能逐条堵，堵完还得靠人工盘点兜着。

## 三、目标与不变量

重构完成后必须同时成立：

1. **一条历史消息的每个内容块，在界面上至多一个条目**，无论是流式先画、落盘补画还是回放。
2. **判重身份不依赖显示形态**：截断预览、Markdown 渲染结果、图片、统计文案都不参与判重。
3. **身份跨会话本体重载稳定**：`ChatMessage` 换成另一个实例不影响判重。
4. **所有「从历史来」的写入只有一个出口**，新增写入口必须被机械检查拦下。

明确不做的：不改 `history.jsonl` 格式、不改 `ChatMessage` 序列化、不动提示词/工具定义/请求改写、不引入面板虚拟化（见 ADR 0041）。

## 四、分阶段方案

### 阶段 0 · 已落地（本次改动，未提交）

| 改动 | 文件 |
|---|---|
| 抽 `ConversationItemDedup`，`AppendSkippingRendered` 与 `AppendTail` 共用一道闸 | `ConversationItemDedup.cs`（新）、`ConversationHistoryRenderer.cs`、`ConversationHistoryReconciler.cs` |
| 空来源条目按同类同内容认领；思考卡用 `CurrentText` 全文（空缓冲回落 `Message`）、知识卡用 `ResultText`、有 `CallId` 的工具卡仍按 `CallId` | 同上 |
| `FindMissingTail` 在尾部只剩工具结果消息时不触发补画，但真有漏画时仍按整段尾部计数（保住 `from = Count - missing` 的切片语义） | `ConversationOrderCheck.cs` |
| `missing <= 0` 防御越界；`AppendTail` 只在真补上东西时打日志并带实际条数 | `ConversationHistoryReconciler.cs` |
| 回归用例累计 10 例（上一轮 6 例、本轮 4 例）：长思考截断、知识卡、尾部工具结果、连续同正文不合并 | `App.Tests/Conversation/` |

验证：`dotnet build` 0 错误；`--filter-namespace UiharuMind.App.Tests.Conversation` **624/624 全绿**。

### 阶段 1 · 稳定身份改用 `MessageId`

**改动**：`ChatMessage.MessageId` 在历史 JSON 里已有（`messageId` 字段），把它作为判重主键，`ReferenceEquals` 降为快速路径/兜底。

- 新增 `ConversationItemIdentity`：`(MessageId | 临时键, ContentOrdinal, ItemKind)`。
- `ContentOrdinal` = 内容块在 `message.Contents` 中的序号；流式阶段拿不到序号，用 `(轮次 EpochId, 本轮内递增序号)` 作临时键，`WireStreamed` 配对成功时回填正式身份。
- 依次替换：`ConversationOrderCheck.MessageIdentity` → `WireStreamed` 的 `persisted` 集合 → `PairStreamedThinking` 的 `claimedSegments` → `ConversationItemWindowTrimmer.IndexOfSame` → `ConversationItemDedup.rendered`。

**收益**：一次改掉「截断预览」「本体重载」「配对启发式」三类失配；也让 `FindMissingTail` 可以不再猜。
**风险**：老存档可能缺 `MessageId`（历史文件里有些行没写），需要回落策略：缺 id 时按 `(角色, CreatedAt, 正文 hash)` 生成会话内稳定 id，并在装载时缓存到消息对象上，不写回盘。
**验收**：造两份从同一文件反序列化出的 `ChatMessage` 实例，断言判重仍成立；`SessionManager` 冷卸载/重载场景的回归用例。

### 阶段 2 · 统一写入口 + 机械护栏

**改动**：引入 `ConversationItemSink`（构造函数接收，符合 AGENTS.md [规则4-1]），持有 `Items` 与「已渲染身份表」。

- 所有 `Add` 收敛到 `Sink.Add(item, identity)`：按身份判重，重复直接返回。
- 实时流用临时身份，落盘配对后 `Sink.Rebind(temp, formal)`；回放直接带正式身份。
- 白名单：`DiscardAll` 之后的全量重放、定点 `Replace`、纯 UI 占位卡（`HandoffWritingItem`、`ErrorItem`）显式标注 `// sink-exempt: 理由`。
- 新增 `App.Tests/Architecture/ConversationItemWriteBoundaryTests`，仿 `ServiceAccessBoundaryTests` 做源码扫描：凡直接写 `Items` 的位置必须有 `sink-exempt` 标记，新增未标记的写入口让测试红。

**为什么护栏放到这一步**：现在合法的直接写点有二十多处，先加静态护栏只会得到一份又长又脆的白名单；收口之后护栏才有稳定的判据。
**验收**：护栏测试绿；人工盘点表（2.1）里「否」的行数降到白名单可枚举的个位数。

### 阶段 3 · 对账判据改造

`FindMissingTail` 改为按「已渲染身份集合」逐条判尾部哪些消息确实缺条目，跳过由设计就不产条目的种类（`ConversationMessageOrigin` 提供 `ProducesOwnItems`）；返回「补画起始下标」而不是「缺几条」，与 `AppendTail` 的 `from` 语义合并成一个量。

- `WireStreamed` 从「按角色/段长猜」改成「按临时身份回填」，猜不出来就不再猜，交给轮末全量重放。
- `PairStreamedThinking` 的段长配对退役，改按 `ContentOrdinal` 归属。
- `missing <= 0` 的分支取消；`FindDivergence` 补一条「身份超前也算分歧」，避免掩盖漏画。

**验收**：日志中 `2 trailing message(s) not drawn` 收敛；`CatchUpTail` 每次触发的 `added` 与真实漏画条数一致。

### 阶段 4 · 收敛剩余独立重复源

逐条收口并各补一个回归用例：

| 来源 | 位置 | 处置 |
|---|---|---|
| 知识卡实时 + 回放双画 | `ConversationViewModel.cs:1765` / `Renderer.cs:278` | 实时卡带临时身份，落盘时 rebind |
| 交接卡兜底竞态 | `ViewModel.cs:1773-1781`、`Renderer.EnsureHandoffCard` | 统一走 Sink，去掉 `if (_driver.IsRunning)` 的半条判据 |
| 重发不删旧段 | `ConversationTranscript.cs:386-424`，`_segmentFirstItem == -1` | 重发信号自带段范围，不再依赖全局游标 |
| `LiveTurnStream` 双通道补发 | `LiveTurnStream.cs:105/123-125` | observer 只投递身份，不重复建卡 |
| `Retry` 乐观气泡 vs 重建副本 | `ConversationItemActions.cs:582`、`Transcript.cs:299-303` | 按临时身份认领，不按引用 |
| `Replay` 自身不清空 | `ConversationHistoryPager.cs:94-99` | 由 Sink 统一负责清空或判重，调用方不再隐式担保 |

## 七、决策记录

- **不先写 ADR 再改代码**：阶段 0 的两处盲区是确定性 bug、改动局部、有回归用例，先落地止损；完整重构（阶段 1–4）在动工前补一份 ADR，把四条不变量与 `MessageId` 回落策略钉死。
- **不在阶段 0 加静态护栏**：合法直接写点太多，先收口再护栏，否则只得到一份脆白名单。
- **不做「按正文全局去重」**：`ConversationOrderCheck.cs:33` 的口径是「正文相同的两条消息是两条，不能合并」；认领只针对**来源为空**的条目，已配对条目永不参与。
- **不上 UI 虚拟化**：与重复无关，且 ADR 0041 已实测不可用。
